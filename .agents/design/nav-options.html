Four ways through 6,797 pages

The homepage already does its job — 31 cards, filterable, honest about what is written. Everything after the click is where it falls apart. Below: what I measured in the running site, then four navigation architectures with working mockups. They are different in kind, not degrees of the same idea. Pick one.

What I found in the running site

Measured against the corpus and the dev server on :3100, not guessed. Each finding names its evidence.

01

Once you are inside a technology, you cannot reach another one

The navbar is deliberately empty — navbar.items: [] — so the only route from Java to React is back to the homepage and re-pick. For a reference where React, Next.js and TypeScript constantly cite each other, this is the most expensive thing on the list.

02

A technology opens on furniture, not content

/docs/java shows three sidebar entries: Overview, Syllabus, Explanations. The 17 phases are one level further down. Two clicks before you see a single topic.

03

The tier system — the spine of the whole project — is invisible in navigation

6,519 of 6,797 pages carry a tier badge. Java alone: 831 Master, 1,008 Understand, 244 Know, 97 When Needed. None of it reaches the sidebar. You cannot ask "show me the Master-tier pages in phase 4" — the metadata exists and nothing reads it.

04

Collapse all / Expand all is in the DOM but nobody can see it

The swizzled bar renders at top: 0 inside the sidebar viewport — which starts underneath the 60px fixed navbar. The buttons sit at y = 8–31, behind the header. The one sidebar control that exists today is painted under the navbar. That is a live bug, not a design opinion.

05

Every category at every depth is styled identically

.menu__list-item-collapsible .menu__link sets 0.72rem uppercase mono in --db-ink-3, the palest ink in the palette — applied the same to a top-level phase and a fourth-level chapter. All 17 Java phase labels wrap onto two lines, and a wall of identical grey small-caps gives the eye nothing to land on.

06

The tree gives a 585-page phase the same weight as a 1-page phase

Java's Data access is 585 pages; Messaging is 1. Both are one row of the same height with no number on them. Nothing in the sidebar tells you how much is behind a caret before you open it.

07

Nesting reaches six levels, and the indent eats the label

python/pages/phase-1-language-core/12-eafp-vs-lbyl/05j-designing-the-failure-channel/ — by that depth a 300px sidebar has roughly 150px of usable text width for labels like "3 · Composition and checked exceptions".

08

Nothing remembers you were here

No visited marks, no resume point, no scroll restoration, no per-technology collapse memory. On a corpus this size that is the difference between a reference you can work through and one you re-orient yourself in every session.

Four architectures

Every mockup below is live — type in the filters, open the dropdown, hit the palette, move the tier control. They use the real Java tree and the real page counts, in the project's own palette, so what you see is what it would look like.

A

Tuned Classic

Character · an instrument panel

Same three-column room, properly equipped. A filter box over the tree, tier dots on every page, page counts on every category, real typographic hierarchy by depth, and a technology dropdown in the navbar. Nothing about the shape of the site changes.

Effort

~4 components
swizzle-only

What changes

  • Filter box at the top of the sidebar — matches labels across the whole tree and auto-expands to the hits.
  • Tier dot on every page row; solid pine = Master, ring = Understand, amber = Know, grey = When Needed.
  • Page count on every category, so a 585-page phase looks like one.
  • Three real type levels for phase / chapter / page instead of one grey.
  • Technology dropdown in the navbar, grouped by the layers the homepage already defines.
  • Collapse all / Expand all moved where it can actually be seen, and its state persisted.

What it costs

  • Swizzle DocSidebar, DocSidebarItems, NavbarItem. No route changes, no build-step changes.
  • Tier dots need tier in sidebar metadata — a one-off script writing sidebar_custom_props, or read from the badge at build time.
  • The tree is still a tree. Java is still 2,240 items; you can now search it, but you cannot reduce it.
  • Still no answer to "I am in Java and want React". The dropdown helps; it is not a switcher you can see.

B

Workspace Rail

Character · you can see the whole building from any room

Everything in A, plus a permanent left rail listing all 31 technologies grouped by layer. The page tree becomes the second column. You switch from Java to React in one click from anywhere in the site, and you always know how big the thing you are standing in is.

Effort

A + layout work
4 breakpoints

What changes

  • A 170px rail, always visible in /docs, driven by the same LAYERS array the homepage uses — one source of truth for the stack.
  • Live page count next to each technology, straight out of progress.js.
  • Collapses to initials under 1280px, folds into the mobile drawer below 996px.
  • The homepage stops being a toll gate and becomes what it should be: the dashboard you visit on purpose.

What it costs

  • Swizzle DocRoot/Layout — the one piece of real layout surgery here. Breakpoints need testing at 996 / 1280 / 1600.
  • ~170px of horizontal width, permanently. On a 1440px screen that is the TOC's worth of room.
  • 31 items means the rail itself scrolls. Honest, but it is another scrolling column.
  • Same as A on the tree: Java is still 2,240 items.

C

Command First

Character · a terminal

Stop asking the sidebar to hold 2,240 items. It shows only your neighbourhood — the current phase expanded, its siblings as one line each. Everything else is reached by typing: ⌘K over all 6,797 page titles, every technology, and tier filters, in one box.

Effort

palette + index
~6,800 titles

What changes

  • Sidebar becomes short and legible at every depth — siblings collapse to one row, so indent never eats the label.
  • ⌘K fuzzy-matches titles across all technologies, which is the one thing the split search index cannot do today.
  • Modes in the same box: > jump to technology, # filter by tier, plain text searches titles, recents on open.
  • Titles-only index — roughly 400KB for the whole corpus, versus the 94.7MB full-text index that forced the per-technology split.

What it costs

  • A new generated artifact: a titles index built in postBuild, next to the existing search indexes. New build step, new thing to keep current.
  • Genuinely opinionated. Superb once you know the corpus; a stranger gets less to browse.
  • Discoverability rests on a keyboard shortcut. Needs a visible affordance in the navbar, not just ⌘K.
  • Contextual sidebars make "where am I in the whole thing" harder, so breadcrumbs have to carry more weight.

D

Study Mode

Character · a curriculum, not a filing cabinet

The tier system becomes navigation. A control sets your tier floor and the whole sidebar filters to it — Java drops from 2,240 pages to 831 at Master‑only. Add visited marks, per-phase progress rings, and a resume point per technology. This is what the four tiers were always implying.

Effort

needs tier in
frontmatter first

What changes

  • Tier floor control filters the tree live. Counts update; empty categories disappear.
  • Progress ring per phase from pages you have actually opened, stored per technology.
  • Resume card at the top of the sidebar — the page you left, and the next unread one at your tier.
  • "Next unread at this tier" in the pagination footer, so reading a track becomes a straight line.
  • Reuses progress.js, which already computes exactly this shape for the homepage.

What it costs

  • Tier must move out of the page body first. Today it is a <span class="db-tier"> in MDX. It has to become frontmatter or sidebar_custom_props across 6,519 pages — a scripted migration, and a house-style change the authoring skills have to learn.
  • The 289 pages with no badge need a rule: shown always, or hidden at Master-only.
  • Reading state is per-browser localStorage. It does not follow you to another machine.
  • Biggest behavioural change of the four — worth agreeing before it is built, not after.

What I would pick, and why

B, then D. B is the honest floor: it contains all of A, and A alone leaves the single most expensive problem — being stranded in one technology — only half solved. B is one piece of layout surgery and everything else is swizzle work.

Then D, separately, once the tier migration is done. D is the only option that actually shrinks the tree, and the tier data is already written on 6,519 pages — it is sitting in the corpus doing nothing. But it needs tier moved into frontmatter first, which touches the authoring contract, so it should be its own decision rather than a rider on a sidebar change.

C is the interesting outlier. It is the only one that gives back cross-technology search, which the 94.7MB index problem took away by necessity — and a titles-only index is cheap enough to sidestep it entirely. If you navigate more by recall than by browsing, C beats B for you specifically. It is the pick I would make second-guessing myself about.

Finding 04 — the collapse control painted under the navbar — I would fix regardless of which of these you choose. It is a few lines.
