**`up` is not "start my containers". It is "make the running state equal the
file", and the interesting behaviour is all in what it decides to recreate.**

## The recreation rule

The documentation states it directly: when configuration or the image has changed
since a container was created, `up` "picks up the changes by stopping and
recreating the containers (preserving mounted volumes)".

Unpack that into the three cases you actually see:

| Situation | What `up` does |
|---|---|
| Nothing changed | Nothing. The container is left running, untouched |
| A service's config or image changed | **That service's** container is stopped and recreated. Mounted volumes are preserved |
| A service was removed from the file | Its container is removed |

The middle row is what makes the edit-and-`up` loop fast: change one environment
variable and only that one service bounces. The third is why deleting a block from
`compose.yaml` is a destructive edit, not just tidying.

**"Preserving mounted volumes" is the important half of the promise.** Recreating a
container replaces its writable layer, which is where data would be lost — but the
volume is a separate object and survives ([Phase 0, page
04](../../phase-0-what-a-container-is/04-image-vs-container.md)). That is precisely
why a database belongs in a named volume and not in the container.

## Detached, attached, and Ctrl-C

```bash
docker compose up            # attached: streams every service's logs
docker compose up -d         # detached: returns, leaves them running
```

Attached, `up` "aggregates the output of each container (like `docker compose logs
--follow` does)" — one interleaved, prefixed stream.

🔴 **Attached, Ctrl-C stops the stack.** "If the process is interrupted using
`SIGINT` (ctrl + C) or `SIGTERM`, the containers are stopped, and the exit code is
`0`." That is a clean, deliberate shutdown and a zero exit — not a crash. It is
also why you should not leave an attached `up` running in a terminal you might
close.

The habit worth forming: **`up -d` to run, `logs -f` to watch**
([page 14](../14-day-to-day-commands.md)). It decouples "is it running" from "am I
looking at it", which is the same argument as `attach` versus `logs -f` in
[Phase 1, page 16](../../phase-1-running-containers/16-attach-vs-logs.md).

## Building and pulling

Two different questions, two different flags.

```bash
docker compose up -d --build          # rebuild images that have build: before starting
docker compose up -d --no-build       # never build, even if policy says to
docker compose up -d --pull always    # always pull, even if the tag is present locally
```

| Flag | Documented meaning |
|---|---|
| `--build` | "Build images before starting containers" |
| `--no-build` | "Don't build an image, even if it's policy" |
| `--pull` | "Pull image before running (`always` \| `missing` \| `never`)" |
| `--quiet-build` | "Suppress the build output" |
| `--quiet-pull` | "Pull without printing progress information" |

**The trap:** `up` does not rebuild just because your source changed. It rebuilds
when it decides an image needs building — so after editing application code the
command is `up -d --build`, and the commonest wrong answer is
`docker compose restart`, which reuses the existing image and therefore cannot pick
up any change at all.

Note that `--pull always` is the useful one in CI against a moving tag, because a
tag is a subscription rather than a version
([Phase 2, page 02](../../phase-2-images-and-registries/02-tags-vs-digests.md)).

## Forcing and preventing recreation

```bash
docker compose up -d --force-recreate      # recreate everything regardless
docker compose up -d --no-recreate         # leave existing containers alone
docker compose up -d --always-recreate-deps
docker compose up -d -V                    # --renew-anon-volumes
```

| Flag | Documented meaning |
|---|---|
| `--force-recreate` | "Recreate containers even if their configuration and image haven't changed" |
| `--no-recreate` | "If containers already exist, don't recreate them." Incompatible with `--force-recreate` |
| `--always-recreate-deps` | "Recreate dependent containers." Incompatible with `--no-recreate` |
| `-V`, `--renew-anon-volumes` | "Recreate anonymous volumes instead of retrieving data from previous containers" |

`--force-recreate` is the blunt instrument for "I do not believe the reconciler".
It is fine in development and worth being suspicious of as a habit — if you need it
routinely, something is changing that Compose cannot see, and finding that is the
real fix.

`-V` deserves a mention because anonymous volumes are quietly sticky: a recreated
container **reuses** the previous anonymous volume by default, which is how stale
state survives a `up --force-recreate` and confuses everybody. `-V` is the switch
that says "start that empty".

## When does `up` return?

```bash
docker compose up -d --wait
docker compose up -d --wait --wait-timeout 120
```

`--wait` waits "for services to be running|healthy" and "implies detached mode";
`--wait-timeout` caps it. Without `--wait`, `up -d` returns as soon as the
containers are *started*, which is not the same as the application being ready —
the same distinction that makes plain `depends_on` insufficient
([page 05](../05-depends-on.md)).

**`--wait` is the flag that makes a CI script honest.** Without it, the test step
begins the instant containers exist and fails intermittently on a slow database.

## Foreground exit behaviour

For one-shot runs — CI, integration tests — three flags decide the exit code:

| Flag | Documented meaning |
|---|---|
| `--abort-on-container-exit` | "Stops all containers if any container was stopped." Incompatible with `-d` |
| `--abort-on-container-failure` | "Stops all containers if any container exited with failure." Incompatible with `-d` |
| `--exit-code-from` | "Return the exit code of the selected service container. Implies `--abort-on-container-exit`" |

```bash
docker compose up --exit-code-from tests --abort-on-container-exit
```

That is the canonical "run the test service against the stack and give me its exit
code" invocation, and it is why a Compose stack can be a CI job rather than a
development convenience.

## Scoping what `up` touches

```bash
docker compose up -d api            # this service and its dependencies
docker compose up -d --no-deps api  # this service only
docker compose up -d --remove-orphans
```

`--no-deps` — "Don't start linked services" — is how you restart one service
without bouncing the database it depends on.

`--remove-orphans` — "Remove containers for services not defined in the Compose
file" — is the answer to a container that lingers after you rename or delete a
service. Without it, the old container keeps running under the project and Compose
warns about it.

## Podman

`podman compose up` delegates to the installed provider
([page 01](../01-what-compose-is.md)), so the flag surface is whatever that provider
supports. With `docker-compose` as the provider, everything above applies. With
`podman-compose`, expect the common flags (`-d`, `--build`, `--force-recreate`,
`--remove-orphans`) and check the rest rather than assuming — `--wait` and the
`--abort-on-*` family are exactly the kind of newer surface that lags.
[Page 15](../15-podman-compose.md) goes into it.

## Gotchas

**Symptom:** Code changed, `docker compose up -d` reported "up-to-date", and the
old behaviour is still live.
**Cause:** Nothing Compose can see changed — the image tag is the same and the
service config is the same — so there was nothing to reconcile.
**Fix:** `up -d --build`. Do **not** reach for `docker compose restart`: it reuses
the same image and cannot pick up a rebuild.

**Symptom:** A container from a service you renamed is still running and Compose
warns about orphans.
**Cause:** The container belongs to the project but no longer matches any service in
the file.
**Fix:** `docker compose up -d --remove-orphans`, then check `docker compose ps`.

**Symptom:** CI tests fail intermittently right after `up -d`, and pass when re-run.
**Cause:** `up -d` returns when containers are started, not when the application is
ready.
**Fix:** `up -d --wait` (with `--wait-timeout`), backed by real healthchecks
([page 06](../06-healthchecks.md)). Sleeping for a fixed number of seconds is the
wrong fix — it is both slower and still racy.

**Symptom:** Stale data survives even after `--force-recreate`.
**Cause:** Anonymous volumes are reused by the recreated container by default.
**Fix:** Add `-V` / `--renew-anon-volumes`. If the state is meant to persist, give
it a **named** volume so it is deliberate rather than accidental
([page 08](../08-volumes.md)).

**Symptom:** Closing the terminal took the whole stack down.
**Cause:** `up` was running attached, and `SIGINT`/`SIGTERM` stops the containers —
by design, with exit code 0.
**Fix:** `up -d` plus `logs -f`. Reserve attached `up` for the moment you actually
want to watch a boot.

## Interview questions

**★ What does `docker compose up` do when the stack is already running?**
It reconciles. If nothing changed, it does nothing. If a service's configuration or
image changed, it stops and recreates *that* container while preserving mounted
volumes. If a service was deleted from the file, its container is removed. It is
not "start the containers" — it is "make reality match the file".

**★ Your code change is not showing up after `docker compose up -d`. Why, and what
is the fix?**
Because nothing Compose can observe changed: the service config is identical and
the image tag is the same, so there is nothing to recreate. The fix is
`up -d --build` so the image is rebuilt from source first. `docker compose restart`
is the common wrong answer — it reuses the existing image, so it cannot possibly
pick up a code change.

**★ What is the difference between `up -d` and `up -d --wait`?**
`up -d` returns once containers have been started. `--wait` holds until services
are running or healthy, and implies detached mode; `--wait-timeout` bounds it. In CI
that difference is the whole flakiness story — without `--wait` the next step starts
against a stack that exists but is not ready.

**What happens if you press Ctrl-C on an attached `docker compose up`?**
The containers are stopped and the exit code is 0. It is a deliberate shutdown, not
a crash — which is also why an attached `up` is a poor way to leave a stack running.

**When would you use `--no-deps`?**
When you want to recreate exactly one service without bouncing what it depends on —
restarting the API without restarting the database underneath it. `up api` alone
would bring the dependencies along.

**Why might stale state survive `--force-recreate`?**
Because anonymous volumes are reused by the new container rather than recreated.
`-V` / `--renew-anon-volumes` starts them empty. Any state that genuinely matters
should be in a named volume, where its lifetime is explicit.
