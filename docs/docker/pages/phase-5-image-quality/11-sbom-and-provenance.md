**BuildKit has been attaching provenance to your images by default, and almost
nobody has ever read one.** That is the whole subject of this page: the
generation side is close to free and largely already on, and the consumption side
is where all the value and all the work actually is.

## What an attestation is

An attestation is build metadata that travels *with* the image rather than in a
wiki:

> "Build attestations describe how an image was built, and what it contains. The
> attestations are created at build-time by BuildKit, and become attached to the
> final image as metadata."

Mechanically:

> "Attestation records are wrapped in the in-toto JSON format and attached to the
> image index in a manifest for the final image."

Two things follow from "attached to the image index". The attestation is part of
the artefact — push the image and it goes too, pull it anywhere and it is still
there. And it is *addressed alongside* the image rather than inside it, so it
does not become a layer and does not change what runs.

There are two kinds:

> "Software Bill of Material (SBOM): list of software artifacts that an image
> contains, or that were used to build the image. Provenance: how an image was
> built."

**SBOM answers "what is in it". Provenance answers "where did it come from".**
They are complementary, and a policy that wants to act on either usually needs
both.

## Provenance: on by default, at the minimum level

This is the part people are surprised by:

> "Provenance attestations with the `mode=min` level are added to images by
> default."

So your images very likely already carry provenance. What is in it depends on the
mode, and the modes differ substantially.

| | `mode=min` (default) | `mode=max` |
|---|---|---|
| Build timestamps | ✅ | ✅ |
| Frontend used, build platform | ✅ | ✅ |
| Build materials | ✅ | ✅ |
| Source repository and revision | ✅ | ✅ |
| Reproducibility information | ✅ | ✅ |
| The LLB definition — the exact build steps | ❌ | ✅ |
| The Dockerfile, base64-encoded in full | ❌ | ✅ |
| Source maps from build steps to layers | ❌ | ✅ |
| **Build argument values** | ❌ | ⚠️ **exposed** |

`min` "explicitly excludes build argument values, secret identities, and detailed
layer metadata". `max` includes "the LLB definition of the build … the exact
steps taken to produce the image", the Dockerfile itself, and source maps.

:::danger `mode=max` exposes build arguments
> "Note that `mode=max` exposes the values of build arguments."

This is the same failure mode as
[phase 4 · build args vs runtime env](../phase-4-build-strategy/13-build-args-vs-runtime-env.md),
arriving by a new route. A credential passed as `--build-arg` was already
recoverable from the image; with `mode=max` it is also sitting in a structured,
machine-readable document attached to the image index. The docs' own
recommendation is the one this track has given throughout: use
[secret mounts](../phase-4-build-strategy/05-mount-type-secret.md) instead, and if
one has already shipped, **rotate it — rebuilding does not unpublish**.
:::

## SBOM: opt-in, SPDX

SBOM generation is **not** on by default; you ask for it with `--sbom=true`.

> "SBOMs generated by BuildKit follow the SPDX standard and attach to the final
> image as a JSON-encoded SPDX document"

Per package it records the "Name of the artifact, Version, License type, Authors,
Unique package identifier". The licence field is worth noting — SBOMs get
discussed as a security control, and in practice legal and compliance teams are
often the first real consumers.

Two scope controls matter, because the default scope is narrower than people
assume:

- **Only the final stage is scanned** by default. `BUILDKIT_SBOM_SCAN_STAGE`
  widens it — `true` for the current stage, `false` to disable, or a list of
  stage names like `base,bin`.
- **The build context is not scanned** unless you set
  `BUILDKIT_SBOM_SCAN_CONTEXT` to `true`.

For a multi-stage build this is exactly the gap you would expect and exactly the
one that produces a misleadingly clean SBOM: the toolchain, compilers and dev
dependencies that lived in the build stage are not in the final image, so they
are not in the default SBOM either — even though a vulnerability in the build
stage is a real supply-chain question. If you care about *how it was built* as
well as *what shipped*, you have to say so.

A different scanner can be substituted: "You can select a different plugin to use
with the `generator` option, specifying an image that implements the BuildKit
SBOM scanner protocol".

## Where attestations can and cannot go

This is the practical trap, and it is a driver and exporter question rather than
a flag question.

> "The `docker-container`, `kubernetes`, and `remote` drivers support
> attestations. The `docker` driver requires the containerd image store."

> "The `local` and `tar` exporters cannot save attestations to image manifests;
> they write JSON files instead. All other BuildKit exporters provide support."

So a build on the **default `docker` driver without the containerd image store**
is the case where attestations quietly do not land the way you expect — the same
constraint that
[phase 4 · buildx and platforms](../phase-4-build-strategy/11-buildx-and-platforms.md)
and [cache import and export](../phase-4-build-strategy/12-cache-import-export.md)
run into, for the same underlying reason: the classic image store cannot
represent a multi-manifest index. And `--output type=tar` does not lose the
attestation, it *relocates* it to a JSON file, which is a different problem — a
pipeline that tars an image and expects the attestation to travel inside it will
find nothing there.

## Reading them

`docker buildx imagetools inspect` with `--format` is the reader. Provenance data
is available under the `.Provenance` attribute and SBOM data under the
corresponding SBOM attribute, both queryable with Go template expressions.

The habit worth forming is small: **inspect the provenance of an image you did
not build before adopting it.** The source repository and revision, the frontend,
and the build timestamp are in the default `min` attestation, so this works on
most images without anyone having opted into anything.

## Who consumes it — the honest part

Generation is nearly free. Verification is the entire cost, and it is not
automatic. SLSA defines provenance as:

> "Verifiable information about software artifacts describing where, when and how
> something was produced."

and is explicit that acting on it is the consumer's job: verification means
confirming the builder's identity, validating external parameters against known
acceptable values, and checking that resolved dependencies match expected
sources. **An attestation can exist without being verified**; verification
requires deliberate action by whoever consumes the artefact.

That distinction is the one to carry out of this page. An image carrying a
`mode=max` provenance attestation that no pipeline ever reads is not more
trustworthy than one without it. It is better *instrumented* — which is genuinely
useful during an incident, and is not a control.

What consumption actually looks like, in rough order of how commonly it exists:

| Consumer | What it does with it |
|---|---|
| **A human, during an incident** | "Which commit is this image, and when was it built?" — the default `min` provenance answers it |
| **Licence and compliance tooling** | Reads the SPDX document for licence obligations |
| **Vulnerability scanners** | An SBOM lets a scanner report without re-deriving the package list ([page 07](07-vulnerability-scanning.md)) |
| **An admission policy** | Refuses images whose provenance does not name an expected builder and source repository — the strongest consumer, and the rarest |

The first row is not a consolation prize. Being able to map a running image back
to a commit, without guessing from tags, is most of the practical value most
teams ever extract.

## Podman

**This is a genuine divergence, not a flag-name difference.** Podman generates
SBOMs and its surface is scanner-image based:

> "Generate SBOMs (Software Bills Of Materials) for the output image by scanning
> the working container and build contexts using the named combination of scanner
> image, scanner commands, and merge strategy."

with `--sbom-scanner-image` and `--sbom-scanner-command` selecting the scanner,
and two different destinations — `--sbom-output` stores "the generated SBOM in
the named file on the local filesystem", `--sbom-image-output` stores it "in the
specified path in the output image".

Read those last two carefully, because the model differs from BuildKit's. Podman
writes the SBOM to a **file**, or to a **path inside the image** — that is, as
image *content*. BuildKit attaches it as an in-toto attestation on the **image
index**, which is not content and is not a layer.

And on provenance: **`podman-build(1)` documents no `--provenance` flag and no
attestation support beyond SBOM generation.** A pipeline that depends on SLSA
provenance attestations is depending on a BuildKit feature, and a Buildah-based
build will not produce one — consistent with
[phase 4 · docker vs podman vs buildah](../phase-4-build-strategy/14-docker-vs-podman-vs-buildah.md),
where Buildah not fetching BuildKit frontends was the same shape of difference.

## Gotchas

**Symptom:** A build argument holding a token turns up in a readable document
attached to the image.
**Cause:** `--provenance=mode=max` includes build argument values — the docs say
so directly.
**Fix:** Use `--mount=type=secret` rather than build args for anything sensitive.
For anything already pushed, rotate it; rebuilding does not unpublish.

**Symptom:** `--sbom=true` was set, and the SBOM lists far less than the build
touched.
**Cause:** Only the final stage is scanned by default, and the build context is
not scanned at all.
**Fix:** `BUILDKIT_SBOM_SCAN_STAGE` with the stage names you want, and
`BUILDKIT_SBOM_SCAN_CONTEXT=true` for the context.

**Symptom:** Attestations are requested and do not appear on the image.
**Cause:** The default `docker` driver without the containerd image store, or an
exporter — `local`, `tar` — that writes attestations to JSON files instead of the
manifest.
**Fix:** Build with the `docker-container` driver, or enable the containerd image
store, and check which exporter the pipeline uses.

**Symptom:** An audit is satisfied because "our images have provenance", and
nothing in the pipeline reads it.
**Cause:** Confusing existence with verification. SLSA puts verification on the
consumer, deliberately.
**Fix:** Name the consumer. If no policy, scanner or human process reads the
attestation, say that plainly rather than counting it as a control.

## Interview questions

**★ What are build attestations, and which ones do you get without asking?**
Build metadata created by BuildKit and attached to the final image — wrapped in
in-toto JSON and attached to the image index, so they travel with the image
without becoming a layer. There are two kinds: SBOM (what is in it) and
provenance (how it was built). **Provenance at `mode=min` is added by default**;
SBOM is opt-in via `--sbom=true`.

**★ What is the risk of `--provenance=mode=max`?**
It exposes the values of build arguments, along with the full LLB definition, a
base64-encoded copy of the Dockerfile and source maps. A credential passed as a
build arg was already recoverable from the image, and `mode=max` additionally
puts it in a structured document attached to the image index. Use secret mounts
instead, and rotate anything that has already shipped.

**★ An image has an SBOM and a provenance attestation. Is it more trustworthy?**
Not by itself. SLSA is explicit that verification is the consumer's
responsibility — confirming the builder's identity, checking external parameters
against acceptable values, checking resolved dependencies against expected
sources. An attestation that exists but is never read makes the image better
instrumented, not more trustworthy. The question to ask is which consumer reads
it.

**Why might an SBOM look suspiciously clean on a multi-stage build?**
Because only the final stage is scanned by default and the build context is not
scanned at all. Everything that lived in the build stage — compilers, dev
dependencies, the toolchain — is outside the default scope.
`BUILDKIT_SBOM_SCAN_STAGE` and `BUILDKIT_SBOM_SCAN_CONTEXT` widen it.

**You asked for attestations and none appeared. Where do you look first?**
The driver and the exporter. The `docker-container`, `kubernetes` and `remote`
drivers support attestations; the default `docker` driver requires the containerd
image store. And the `local` and `tar` exporters cannot save attestations to
image manifests — they write JSON files instead, so a tarball-based pipeline will
not find them inside the image.

**Does Podman produce the same thing?**
Not the same thing. Podman generates SBOMs through a scanner image
(`--sbom`, `--sbom-scanner-image`, `--sbom-scanner-command`) and writes the result
to a local file or to a path *inside the output image* — image content, not an
attestation on the index. And `podman-build(1)` documents no provenance or
attestation support beyond SBOM generation, so SLSA provenance is a BuildKit
feature a Buildah-based build will not give you.
