Search for "run a Podman container under systemd" and most of what you find will
tell you to use `podman generate systemd`. **That command is deprecated**, and
its own documentation says so:

> "`podman generate systemd` is deprecated. We recommend using Quadlet files
> when running Podman containers or pods under systemd."

It is not being removed, so nothing you already run is about to break. But the
reason it lost is more useful than the notice, because it is a difference in
*direction* rather than in syntax.

## The two work in opposite directions

`podman generate systemd` "creates a systemd unit file that can be used to
control a container or pod" — from a container you already made. You build the
thing, then generate a description of it.

Quadlet is "a systemd **generator**": you write a `.container` file, and systemd
turns it into a service unit at boot and on `systemctl daemon-reload`
([Phase 11 · 04](04-quadlet/README.md)).

| | `podman generate systemd` | Quadlet |
|---|---|---|
| Source of truth | The **container** — the unit is a snapshot of it | The **`.container` file** |
| When it runs | Once, when you type it | At boot and every `daemon-reload` |
| Changing config | Change the container, regenerate, reinstall, reload | Edit the file, `daemon-reload` |
| What you commit | A generated unit full of `podman run` flags | The declaration itself |
| Drift | The unit and the container can disagree | There is only one artefact |

🔴 **That last row is the whole argument.** A generated unit is derived data
checked into a repository. The moment someone changes the container without
regenerating — or regenerates on a different Podman version — the file on disk
stops describing what runs. Quadlet has nothing to drift from, because the file
*is* the input.

## What a generated unit looks like, so you can recognise one

You will meet these in existing systems. The tells:

- A header comment: **"autogenerated by Podman"** with a version and a
  timestamp. (`--no-header` suppresses "the header including meta data such as
  the Podman version and the timestamp" — which is a hint about how often people
  wanted to hide that this was generated.)
- An `ExecStart=` that is an entire `podman run` command line, flags and all.
- `--cidfile %t/%n-cid` and `--conmon-pidfile %t/%n-pid` — plumbing so systemd
  can find the container it started, which is
  [Phase 10 · 14](../phase-10-production/14-under-systemd.md)'s problem being
  solved by hand.
- `Restart=on-failure` and `WantedBy=default.target`.

If you open a unit file and find a hundred-character `podman run` line, you are
looking at generated output, and the container's real configuration lives in that
line rather than anywhere a human chose to put it.

## `--new` is the flag that decides what you actually have

This is the distinction worth knowing, because the same command produces two
fundamentally different things.

**Without `--new`**, the unit controls an **existing** container: start and stop
act on a container that must already be there. Delete or recreate that container
and the unit is broken — it references something that no longer exists. The
container is the state; the unit is a remote control.

**With `--new`**, the command generates "systemd unit files that create and
remove containers at service start and stop commands", built so that "new
containers and pods are created based on their configuration files". The unit
becomes self-contained: nothing needs to pre-exist, and the service can be moved
to another machine.

🔴 **`--new` is almost always what people meant, and it is also Quadlet's design,
done by hand.** Once you have written `--new`, you have accepted that the unit
file should be the source of truth — at which point Quadlet is the same idea with
none of the generated noise.

The default `--restart-policy` is **`on-failure`**, which is a reasonable default
and not the same as Docker's restart-policy semantics
([Phase 10 · 07](../phase-10-production/07-restart-as-supervision.md)) — this one
is systemd's, evaluated by systemd, and `systemd.service(5)`'s own default is
`no`.

## Migrating, without pretending it is automatic

There is no supported converter in Podman itself. The practical route is by hand,
and it is short because a `.container` file is mostly a list of `podman run`
options with different capitalisation:

1. **Read the generated unit's `ExecStart=`.** That command line is your
   inventory — image, ports, volumes, environment, user.
2. **Write the `.container` file** with one key per option: `Image=`,
   `PublishPort=`, `Volume=`, `Environment=`, `User=`
   ([Phase 11 · 04](04-quadlet/README.md) has the key list).
3. **Put it in the right directory** — `~/.config/containers/systemd/` rootless,
   `/etc/containers/systemd/` for root. The path is what makes it a Quadlet unit;
   there is nothing to "install".
4. **`systemctl daemon-reload`**, which is when the generator runs and
   `foo.container` becomes `foo.service`.
5. **Disable and delete the old unit** before starting the new one, or you will
   have two supervisors for one container — the failure
   [Phase 10 · 14](../phase-10-production/14-under-systemd.md) is entirely about.

⚠️ **Step 5 is the one people skip.** The old unit is still enabled, so at the
next boot both try to run, and the symptom is a container that immediately exits
or a name conflict that nobody can explain.

⚠️ **Third-party converters exist**, and this page does not name one as
recommended — Podman's documentation does not endorse any, so treat a converter
as a first draft to read rather than trusted output.

## So when is the old command still the answer?

Rarely, and honestly:

- **You are on a Podman old enough not to ship Quadlet**, which arrived in
  Podman 4.4. On an old LTS host, `generate systemd --new` is the correct tool.
- **You need a one-off unit for something ephemeral** and will not keep it.
- **You are reading an existing system** and need to understand what is there
  before changing it.

For anything new on a current Podman, it is Quadlet. The deprecation notice says
so, and the drift argument above is why it says so.

## Gotchas

**Symptom:** A `systemctl start` fails with the container not found, on a service
that worked for months.
**Cause:** The unit was generated **without** `--new`, so it only starts an
existing container — and something removed or recreated it. `podman system
prune` and a manual `podman rm` both do this.
**Fix:** Regenerate with `--new`, or better, replace it with a `.container` file
that creates the container itself.

**Symptom:** After migrating to Quadlet, the container starts twice at boot or
fails with a name conflict.
**Cause:** The old generated unit is still enabled. Both supervisors run.
**Fix:** `systemctl disable --now <old-unit>` and delete the file, then
`daemon-reload`.

**Symptom:** A `.container` file was written and `systemctl start foo.container`
says no such unit.
**Cause:** Quadlet generates `foo.service` from `foo.container` — the `.container`
file is input to the generator, never a unit name.
**Fix:** `systemctl start foo`. And run `daemon-reload` first: the generator only
runs at boot and on reload.

**Symptom:** The generated unit in version control no longer matches what is
running.
**Cause:** Someone changed the container and did not regenerate, which is the
structural weakness of generating units at all.
**Fix:** Move to Quadlet, where the committed file is the input rather than a
snapshot.

## Interview questions

**★ Why is `podman generate systemd` deprecated in favour of Quadlet?**
Because it generates derived data. The unit is a snapshot of a container that
already exists, so the two can drift apart, and every configuration change means
regenerate-reinstall-reload. Quadlet inverts it: you write a `.container` file
and systemd's generator produces the service at boot and on `daemon-reload`, so
the file you edit is the only artefact. The command is deprecated but not
scheduled for removal.

**★ What does `--new` change, and why does it matter so much?**
Without it, the unit merely starts and stops a container that must already exist
— remove that container and the service is broken. With it, the unit creates and
removes the container itself at start and stop, so it is self-contained and
portable. `--new` is the behaviour almost everyone wanted, and accepting it is
accepting Quadlet's premise.

**★ How do you migrate a generated unit to Quadlet?**
Read the `ExecStart=` line as the inventory of options, rewrite them as
`[Container]` keys in a `.container` file, drop it in
`~/.config/containers/systemd/` or `/etc/containers/systemd/`, and
`daemon-reload`. Then disable and delete the old unit — leaving it enabled gives
you two supervisors for one container, which is the classic double-start failure.

**How do you recognise a generated unit at a glance?**
An "autogenerated by Podman" header with a version and timestamp, an `ExecStart=`
containing a full `podman run` command line, and `--cidfile`/`--conmon-pidfile`
plumbing so systemd can track the container. If the configuration lives inside a
single enormous command line, it was generated.

**Is there ever a reason to still use it?**
On a Podman older than 4.4, which predates Quadlet — there `generate systemd
--new` is correct. Otherwise only for reading or maintaining something that
already exists. New work should be a `.container` file.

**What restart policy does it default to?**
`on-failure`. Worth noting because it is systemd's policy, evaluated by systemd,
not the engine's `--restart` — and `systemd.service(5)`'s own default is `no`, so
the generated unit is making a choice on your behalf.
