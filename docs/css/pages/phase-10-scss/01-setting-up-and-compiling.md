**Sass is a compiler: `.scss` in, `.css` out.** Everything else in this phase is
a language feature that disappears at build time — nothing you write in Sass
reaches the browser.

## `.scss` or `.sass`

Two syntaxes for the same language:

```scss
// .scss — braces and semicolons, a superset of CSS
.card {
  padding: 1rem;
  &__title { font-weight: 600; }
}
```

```sass
// .sass — indentation, no braces or semicolons
.card
  padding: 1rem
  &__title
    font-weight: 600
```

**Use `.scss`.** It is the dominant syntax, every valid CSS file is already valid
SCSS — which makes migration a rename — and examples you find online will match.
The indented syntax has no advantage beyond brevity.

## The compiler

`dart-sass` is the only implementation still maintained. `node-sass` (LibSass) is
deprecated and should be removed from any project still carrying it.

```bash
npm install --save-dev sass          # this IS dart-sass
```

Compile once, or watch:

```bash
npx sass src/styles.scss dist/styles.css
npx sass --watch src/styles.scss:dist/styles.css
npx sass --watch src:dist            # whole directory
```

Useful flags:

| Flag | Effect |
|---|---|
| `--style=compressed` | minified output; default is `expanded` |
| `--no-source-map` | omit the source map (they are on by default) |
| `--load-path=<dir>` | add a directory to the module search path |
| `--quiet-deps` | silence deprecation warnings from dependencies |

`--quiet-deps` is worth knowing early: a project pulling in an older library will
otherwise flood the terminal with warnings about code you cannot change.

## In a bundler

Most projects never call the CLI. Vite has built-in support — install `sass` and
import a `.scss` file:

```js
import './styles.scss';
```

Webpack needs the loader chain `sass-loader` → `css-loader` → `style-loader`,
ordered right-to-left in the config. Either way the compiler is the same
`dart-sass`; only the invocation differs.

## Partials and the `_` convention

A file whose name begins with an underscore is a **partial** — a module meant to
be loaded by another file, not compiled to its own `.css`:

```
styles/
├── styles.scss        ← the entry point, compiles to styles.css
├── _tokens.scss       ← partial
├── _mixins.scss       ← partial
└── _components.scss   ← partial
```

```scss
// styles.scss
@use "tokens";        // note: no underscore, no extension
@use "mixins";
@use "components";
```

**The underscore is omitted when loading.** Without it, `sass --watch src:dist`
would emit a `_tokens.css` nobody wants.

## Source maps

Generated by default, and the reason they matter: without one, DevTools shows the
compiled CSS and every rule appears to come from `styles.css` line 4,000. With
one, it points at the partial and line you actually wrote.

Keep them in development. In production they are optional — they expose your Sass
source, which is usually harmless but is a decision worth making deliberately.

## What Sass does *not* do

Worth stating plainly at the start of the phase:

- **No autoprefixing.** That is PostCSS/Autoprefixer's job.
- **No minification beyond `--style=compressed`.**
- **No bundling of `@import`ed plain CSS.** A `@import "foo.css"` stays a runtime
  CSS import.
- **No knowledge of runtime values.** Sass runs at build time and cannot see a
  custom property's value, the DOM, or the viewport — the point that
  [03 · Variables](./03-variables-sass-vs-custom-properties.md) turns on.

## Trade-off

**A compile step buys you the language and costs you immediacy.** Editing CSS in
DevTools and pasting it back stops being possible — what you paste into a `.scss`
file is fine, but what DevTools shows you is compiled output that does not map
onto your source structure. Source maps mitigate this and do not remove it.

There is a build-time cost too, small for a single stylesheet and noticeable on a
large project with many partials, where a watch rebuild sits between saving and
seeing the change.

The honest question for a new project in 2026 is whether it needs Sass at all:
nesting, custom properties and colour functions are native now, and a project
using only those is better off without a compiler. The remaining reasons —
`@use`/`@forward`, mixins with logic, loops over maps — are real but narrower
than they were, which is what the rest of this phase is about.

## Gotchas

**A partial compiles to its own CSS file.**
*Symptom:* unwanted `_tokens.css` in the output.
*Cause:* the file is being compiled directly, or the underscore is missing.
*Fix:* prefix partials with `_` and compile only the entry point.

**`@use "tokens"` cannot find the file.**
*Symptom:* "Can't find stylesheet to import."
*Cause:* the path is relative to the *current file*, or the directory is not on a
load path.
*Fix:* use a correct relative path, or add `--load-path`.

**Deprecation warnings from a dependency.**
*Symptom:* pages of warnings about code you do not own.
*Cause:* an older library using deprecated syntax.
*Fix:* `--quiet-deps`, and open an issue upstream.

**DevTools points at the wrong line.**
*Symptom:* every rule appears to come from one enormous file.
*Cause:* no source map, or the browser's source-map support is disabled.
*Fix:* keep source maps on in development and enable them in DevTools settings.

**`node-sass` fails to install.**
*Symptom:* native build errors on a new Node version.
*Cause:* LibSass is deprecated and its bindings lag Node releases.
*Fix:* replace it with `sass` (dart-sass).

## Interview questions

**★ What is the difference between `.scss` and `.sass`, and which should you
use?**
Two syntaxes for the same language: `.scss` uses braces and semicolons and is a
strict superset of CSS; `.sass` is indentation-based. Use `.scss` — any valid CSS
file is already valid SCSS, so migration is a rename, and it is what nearly all
documentation and examples use.

**★ What is a partial and why does it start with an underscore?**
A file intended to be loaded by another rather than compiled on its own. The
leading underscore tells the compiler not to emit a separate `.css` for it. The
underscore is omitted when loading — `@use "tokens"` loads `_tokens.scss`.

**★ Which Sass implementation should a project use?**
`dart-sass`, installed as the `sass` npm package. It is the only maintained
implementation; `node-sass`/LibSass is deprecated and its native bindings break
on newer Node versions.

**What does Sass not do that people expect it to?**
Autoprefixing, bundling of plain-CSS imports, and anything involving runtime
values — it compiles before the browser exists, so it cannot read custom
properties, the DOM or the viewport.

**Why do source maps matter here?**
Without one, DevTools attributes every rule to the compiled output, so you cannot
tell which partial a rule came from. With one, it points at the source line you
wrote.
