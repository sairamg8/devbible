**A function returns a value; a mixin emits declarations.** That is the whole
distinction, and it decides which one you want every time.

## The built-in modules

Sass's standard library is namespaced, and each module must be loaded:

```scss
@use "sass:math";
@use "sass:color";
@use "sass:string";
@use "sass:list";
@use "sass:map";
@use "sass:meta";
```

The global forms (`darken()`, `map-get()`, `percentage()`) still work but are
**deprecated**. New code should use the module form, and existing code will emit
deprecation warnings until it does.

## `sass:math` — and the division change

The most consequential change in recent Sass: **`/` is no longer division.**

```scss
@use "sass:math";

$half: math.div(100%, 3);   // ✅
$half: 100% / 3;            // ⚠️ deprecated — ambiguous with the CSS slash
```

The slash was ambiguous because CSS uses it as a separator (`font: 1rem/1.5`,
`grid-area: 1 / 2`), so Sass could not reliably tell division from syntax.
`math.div` is unambiguous.

Other frequently used members:

```scss
math.round($x)    math.ceil($x)    math.floor($x)   math.abs($x)
math.min($a, $b)  math.max($a, $b) math.percentage($x)
math.$pi          math.pow($base, $exp)
```

Note `math.min`/`math.max` are **build-time** — quite different from CSS's
`min()`/`max()`, which compare at runtime
([Phase 3](../phase-3-custom-properties/02-clamp-min-max.md)). If a literal
`min()` in your output is being resolved at build time unexpectedly, quote it or
use `#{}`.

## `sass:color` — and what moved to the browser

```scss
@use "sass:color";

color.adjust($c, $lightness: -10%)
color.scale($c, $lightness: -10%)
color.mix($a, $b, 50%)
color.change($c, $alpha: 0.5)
```

`color.scale` is usually the one you want: it scales *towards* the limit
proportionally, so it cannot overshoot into black or white the way
`color.adjust` can.

**Most of this now exists natively**, and the native versions are better because
they work at runtime:

| Sass, build time | CSS, runtime |
|---|---|
| `color.mix($a, $b, 50%)` | `color-mix(in oklab, $a 50%, $b)` |
| `color.adjust($c, $lightness: -10%)` | `oklch(from var(--c) calc(l - 0.1) c h)` |
| `darken()` / `lighten()` (deprecated) | `color-mix(… , black)` |

The decisive difference: a Sass colour function cannot see a custom property, so
it cannot participate in theming. If `--brand` changes at runtime, only
`color-mix()` follows — see
[Phase 8 · `color-mix()`](../phase-8-color-theming/02-color-mix.md).

**What `sass:color` still does well** is compute a palette **at build time** from
a literal, which is genuinely useful for generating a token set that is then
emitted as custom properties.

## Writing your own with `@function`

```scss
@use "sass:math";

@function rem($px, $base: 16) {
  @return math.div($px, $base) * 1rem;
}

.title { font-size: rem(24); }   // → 1.5rem
```

A function **must** `@return`, and it cannot emit declarations — that is what a
mixin is for. Functions are the right tool for unit conversion, token lookup and
any computed value.

The token-lookup function from
[06 · Loops and maps](./06-loops-and-maps.md) is the pattern worth keeping:

```scss
@function token($path...) {
  $value: map.get($tokens, $path...);
  @if $value == null { @error "Unknown token: #{$path}"; }
  @return $value;
}
```

## `sass:meta` — occasionally essential

```scss
@use "sass:meta";

@if meta.type-of($value) != "number" {
  @error "Expected a number, got #{meta.type-of($value)}";
}
```

`meta.type-of`, `meta.inspect` (for debugging a value's structure) and
`meta.variable-exists` are the useful three. `meta.inspect` is particularly good
for seeing what a map actually contains during a build.

## Trade-off

**Build-time functions are precise and blind.** They can compute anything from
values known at compile time and nothing from values that are not — which,
increasingly, is where the interesting values live. A colour scale generated by
`color.scale` is exact and frozen; the same scale via `color-mix()` follows a
runtime theme but cannot be inspected in the source.

There is also a fragmentation cost: `math.div` and `min()`, `color.mix` and
`color-mix()`, Sass `map.get` and CSS custom properties all coexist, and a reader
must know which layer each belongs to. The similar names actively mislead — Sass
`math.min` and CSS `min()` look identical and behave completely differently.

The rule that keeps it straight: **compute with Sass only what must be known at
build time — units, generated selectors, literal token maths. Everything that
could vary at runtime goes through CSS functions.**

## Gotchas

**`100% / 3` produces a deprecation warning or a string.**
*Symptom:* unexpected output or a build warning.
*Cause:* `/` is no longer division in Sass.
*Fix:* `math.div(100%, 3)`.

**`darken()` is deprecated.**
*Symptom:* warnings on build.
*Cause:* the global colour functions are superseded by `sass:color`, and by
native CSS.
*Fix:* `color.scale`, or `color-mix()` if the value should follow a theme.

**A CSS `min()` is evaluated at build time.**
*Symptom:* the literal `min()` disappears from the output.
*Cause:* Sass resolves it as `math.min` when both arguments are static.
*Fix:* interpolate — `#{"min(10vw, 4rem)"}` — or ensure a custom property is
involved.

**A function does not emit any CSS.**
*Symptom:* nothing appears in the output.
*Cause:* functions return values; they cannot emit declarations.
*Fix:* use a mixin.

**A colour helper ignores the theme.**
*Symptom:* a derived colour stays fixed when the theme changes.
*Cause:* Sass computed it at build time from a literal.
*Fix:* `color-mix()` on custom properties.

## Interview questions

**★ What is the difference between a Sass function and a mixin?**
A function returns a **value** and cannot emit declarations; a mixin injects
declarations at the call site and returns nothing. Use functions for computed
values — unit conversion, token lookup — and mixins for blocks of CSS.

**★ Why is `math.div()` needed instead of `/`?**
Because `/` is ambiguous in CSS syntax, where it is a separator in `font:
1rem/1.5` and `grid-area: 1 / 2`. Sass could not reliably distinguish division
from syntax, so division moved to an explicit function and the slash form is
deprecated.

**★ Which Sass colour functions have been superseded, and why does it matter?**
Most of them. `color.mix` → `color-mix()`, `darken()`/`lighten()` →
`color-mix()` towards black or white. It matters because the CSS versions work at
**runtime** and can therefore operate on custom properties, so they follow a theme
change; a Sass function bakes one value at build time.

**What does `sass:color` still do well?**
Generating a palette at build time from literal values, which is then emitted as
custom properties — build-time computation feeding runtime values.

**Why do `math.min()` and CSS `min()` cause confusion?**
They look identical and behave completely differently: Sass's resolves at build
time from static arguments, CSS's compares at runtime. A CSS `min()` with static
arguments can be silently evaluated away by Sass.

**How do you make a token lookup fail loudly?**
Wrap `map.get` in a `@function` that `@error`s when the result is `null`, since
`map.get` itself returns `null` silently.
