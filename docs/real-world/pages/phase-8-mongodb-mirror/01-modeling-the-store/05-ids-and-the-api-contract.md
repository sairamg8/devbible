**The gate for this phase is that Phase 3's routes and published contract do not
change. Almost nothing presses on that, because Phase 3 was designed well: public
URLs use slugs, ownership lives in query filters, and every response goes through
a mapper function. Two things do press. This chunk takes the first — the
`order_id` field, which is a JSON number on PostgreSQL and a hex string on
MongoDB — and shows that the mirror did not break the contract so much as expose
a latent bug in it. [Chunk 7](05b-the-cursor-and-the-boundary.md) takes the
second.**

## The identity decision

`_id` is an ObjectId, everywhere, generated by the driver.

```js
{_id: ObjectId("66d2f1a4c8b91e0f4c7a2b31"), slug: "walnut-standing-desk", …}
```

The Postgres original argued for `bigint` identity columns over UUIDs because
*"this app generates every key in one database"*. That argument does not
transfer: the driver generates `_id` client-side by default, so keys are already
distributed, and reproducing `bigint` would mean building a sequence generator
the database does not provide. ObjectId is 12 bytes against 8, ordered by its
leading timestamp, and indexed unconditionally — the `_id` index cannot be
dropped or renamed.

The trade the Postgres chapter named still holds and still matters: **keys are
guessable, so nothing authorises by key possession.** Every ownership check goes
in the query filter, never in a comparison after the fetch.

Slugs are unaffected. `products.slug` and `categories.slug` remain the public
identifiers with unique indexes, so `/products/walnut-standing-desk` is
byte-identical across both stacks. That one Phase 3 decision — made for SEO
reasons, not portability ones — is what kept the public URL surface out of this
chapter entirely.

## The collision: `order_id` on the wire

[The checkout endpoint](../../phase-3-express-api/07-the-checkout-endpoint.md)
responds with

```js
res.status(replay ? 200 : 201).json({
  order_id: order.id, status: order.status, total_cents: order.total_cents,
});
```

On PostgreSQL, `orders.id` is `bigint`, and
[Phase 2's pool](../../phase-2-node-services/02-the-data-layer.md) installs
`setTypeParser(INT8, Number)`, so `order_id` reaches the client as a JSON
**number**. On MongoDB, `_id` is an ObjectId, which serialises to a
24-character hex **string**.

That is a type change in a published field, and no amount of mapper discipline
hides it. There are exactly three honest resolutions and it is worth writing all
three down, because which one a real team picks depends on facts this book does
not have.

### Resolution A — pin `order_id` as an opaque string on both stacks

One line changes on the PERN side, in the mapper, not the route:

```js
// Phase 3, checkout route — the amendment the mirror forces
res.status(replay ? 200 : 201).json({
  order_id: String(order.id),          // was: order.id
  status: order.status, total_cents: order.total_cents,
});
```

This is the recommended answer, and the reason is that it was already correct.
`bigint` keys and JSON are a known hazard: JSON has one number type, `JSON.parse`
produces a double, and any key above 2^53 loses precision *silently* — no error,
just a different order id. The PERN implementation was one successful business
away from customers looking up orders that do not exist. **A resource identifier
should be an opaque string in a JSON API regardless of what the database calls
it**, which makes this a one-line correction rather than a concession.

⚠️ It is still a change to a file Phase 8 does not own. It is reported, not made.

### Resolution B — give orders a numeric sequence

If the contract genuinely cannot move, MongoDB can produce monotonic integers
with a counters collection, and the operation is atomic because it is a single
document:

```js
// db/mongo/counters.js — one document per sequence, atomically incremented
export async function nextSeq(db, name, session) {
  const {value} = await db.collection('counters').findOneAndUpdate(
    {_id: name},
    {$inc: {seq: 1}},
    {upsert: true, returnDocument: 'after', session},
  );
  return value.seq;
}

// at checkout: orderNo is the wire identity, _id stays an ObjectId
const orderNo = await nextSeq(db, 'orders', session);
await orders.insertOne({_id: new ObjectId(), orderNo, userId, …}, {session});
await orders.createIndex({orderNo: 1}, {unique: true});   // in the migration
```

The costs, all real and all worth stating before choosing this: one extra round
trip inside the checkout transaction; a single hot document that every checkout
in the system serialises on, which is a throughput ceiling the ObjectId design
does not have; a unique index on `orderNo` so the invariant is enforceable rather
than hoped for; and — because the counter increments inside the transaction — a
sequence that rolls back on abort and therefore leaves gaps. That last one at
least matches a Postgres sequence's behaviour, so the surprise is familiar.

Take this route when the contract is load-bearing for a client you cannot deploy,
and only then.

### Resolution C — accept the type change and version the API

Correct engineering, disqualified by the gate — and worth stating precisely
because the gate is a constraint this book imposed, not a law of nature. A real
project weighs a version bump and a client deploy against a one-line mapper
change, and frequently the version bump wins because the client is a mobile app
on a two-week release train.

## Gotchas

**★ Comparing ObjectIds with `===` is always false.** They are objects;
`order.userId === req.user.id` compares references and quietly denies every
request. Use `.equals()`, or — better — keep the comparison out of JavaScript
entirely by putting it in the query filter. The reason this recommendation is
more than style is that the failure is *silent in the safe direction* during
testing (everything 404s, which looks like a data problem) and can be "fixed" by
someone relaxing the check.

**★ An ObjectId round-tripped through `JSON.stringify` is not an ObjectId.**
`JSON.stringify` yields the bare hex string, so anything that serialises a
document — a cache layer, a job payload, a test fixture — silently converts ids
to strings, and the value then fails to match on the way back in. The
[cache layer](../../phase-2-node-services/08-the-cache-layer.md) stores
serialised values, so it must either re-hydrate ids on read or store only
already-mapped response shapes. Storing response shapes is the simpler rule and
the one to adopt, because it also stops the cache from becoming a second place
that knows the document schema.

**★ ObjectId's timestamp is generated by the client, at second resolution.**
Sorting by `_id` is sorting by creation time only to the extent that the
application servers' clocks agree, and two documents created within the same
second order by counter and random bytes rather than by time. Fine for one user's
order list; not an audit-grade event order. Keep `createdAt` on the document as
the authoritative timestamp — [chunk 4](03-the-order-document.md) does — and let
`_id` be the cursor's tiebreak, which is all it needs to be.

**★ The unique index on `idempotencyKey` is what makes checkout replay-safe, not
`_id`.** Nothing about ObjectId provides replay safety: the key is a
client-supplied string and the index is an explicit `createIndex` that the
collection works perfectly well without. Miss it, and the endpoint's replay path
silently stops working — two orders for one payment, with no error anywhere.
[Chapter 03](../03-checkout-with-transactions/README.md) builds its entire
correctness argument on that index existing.

**★ Resolution B's counter document is the only global serialisation point in
the app.** Every checkout, in every process, updates one document. That is fine
at this app's scale and it is a genuine bottleneck at ten thousand orders a
minute — and worse, it is a bottleneck *inside a transaction*, so it lengthens
the window in which everything else the transaction touches is contended. If B is
chosen, it should be chosen knowing that the ObjectId design had no such point.

**★ Do not use ObjectId's timestamp as `createdAt` "to save a field".** It is
tempting — the data is right there — and it welds the business's notion of "when
was this ordered" to a driver implementation detail that is documented as a
generation strategy, not a guarantee. It also cannot be corrected: a backfill or
an import that assigns fresh ObjectIds rewrites every creation time.

## Interview questions

**★ The gate says "no contract change", and you are recommending a change to
`order_id`. Defend that.** The gate protects clients from a forced redeploy, and
it is worth honouring — but it is not a reason to preserve a mistake. `order_id`
was a JSON number derived from a `bigint`, and JSON has one numeric type, so any
id above 2^53 loses precision on the client with no error at all. The PERN
implementation had a latent correctness bug that arriving at scale would turn
into customers looking up the wrong order. `String(order.id)` fixes that and
makes both stacks emit the same type, for one line in one mapper. If a client
truly cannot absorb number-to-string, resolution B restores numeric identity at
the documented cost of an extra round trip and a globally hot document — a
legitimate trade, not a failure.

**★ Why ObjectId rather than reproducing `bigint` identity columns?** The
Postgres argument for `bigint` rested on every key being generated in one
database, so a small dense ordered integer beat a UUID. In MongoDB the driver
generates `_id` client-side, so keys are already distributed and the premise is
gone; matching `bigint` means building the sequence generator yourself, complete
with the hot document. ObjectId costs four extra bytes per key and per index
entry, sorts by creation time, and is indexed unconditionally. The one property
`bigint` had that ObjectId lacks — density, and therefore smaller indexes — is a
real consideration at very large scale and not at this app's.

**★ Someone proposes making `_id` the slug string, since slugs are already
unique. Good idea?** It removes an index and turns URL lookups into primary-key
fetches, which is genuinely attractive. It fails on mutability: `_id` is
immutable, so a slug change — a rename before launch, a typo fix — requires
inserting a new document and deleting the old one, which breaks every reference
from carts, orders and reviews. `_id` should be the one identifier nothing about
the business can ever want to change, which disqualifies anything human-readable
by construction. A unique index on `slug` costs little and keeps renaming a
one-field update.

**★ How would you detect, in a running PERN system, that the `order_id`
precision bug is about to bite?** Query the current sequence value and compare
it to `Number.MAX_SAFE_INTEGER`; the distance is your remaining runway. The
subtler check is on the client: a JSON number id that round-trips through
`JSON.parse`/`JSON.stringify` unchanged is safe, and one that does not is
already broken. What you cannot do is wait for an error, because there is none —
the failure is a silently different integer, which is exactly why the string
form is the right default rather than a defensive measure.
