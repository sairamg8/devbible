**Most Angular knowledge on the internet was written against the `NgModule` bootstrap, so
the fastest way to stop mistranslating it is to hold both files open at once. This chunk
prints the legacy pair the CLI still generates on request, maps every field of it onto its
standalone replacement, and pins the two facts people get wrong: the legacy template says
`platformBrowser()` and not `platformBrowserDynamic()`, and `bootstrapApplication` installs
`BrowserModule`'s providers but deliberately not its testability providers.**

## Against the call it replaced

The v14-and-earlier form, still generated today by `ng new --standalone=false`
(`application/files/module-files/src/main.ts.template`, 22.1.7):

```ts
// src/main.ts — legacy NgModule bootstrap
import { platformBrowser } from '@angular/platform-browser';
import { AppModule } from './app/app-module';

platformBrowser().bootstrapModule(AppModule, {})
  .catch(err => console.error(err));
```

```ts
// src/app/app-module.ts — legacy root module
import { NgModule, provideBrowserGlobalErrorListeners, provideZoneChangeDetection } from '@angular/core';
import { BrowserModule } from '@angular/platform-browser';
import { AppRoutingModule } from './app-routing-module';
import { App } from './app';

@NgModule({
  declarations: [App],
  imports: [BrowserModule, AppRoutingModule],
  providers: [
    provideBrowserGlobalErrorListeners(),
    provideZoneChangeDetection({ eventCoalescing: true }),
  ],
  bootstrap: [App],
})
export class AppModule {}
```

Read the two side by side and the substitutions are exact:

| The `NgModule` bootstrap | The standalone bootstrap |
|---|---|
| `platformBrowser().bootstrapModule(AppModule)` | `bootstrapApplication(App, appConfig)` |
| `@NgModule.bootstrap: [App]` | first argument of `bootstrapApplication` |
| `@NgModule.providers` | `ApplicationConfig.providers` |
| `imports: [BrowserModule]` | inlined as `BROWSER_MODULE_PROVIDERS` |
| `imports: [AppRoutingModule]` | `provideRouter(routes)` in the same array |
| `declarations: [App]` | `imports` on `App` itself |

⚠️ **The legacy template says `platformBrowser()`, not `platformBrowserDynamic()`.** Angular
v20 deprecated every entry point of `@angular/platform-browser-dynamic` (v20.0.0 CHANGELOG,
Deprecations → platform-browser). If a tutorial you are following writes
`platformBrowserDynamic().bootstrapModule(AppModule)`, it predates v20; the package is still
published at 22.1.5 but it is the JIT-compiling platform and you do not want it in a build.
## The one thing `bootstrapApplication` does not carry over

`BrowserModule`'s own injector definition in 22.1.5 is:

```ts
// @angular/platform-browser 22.1.5 — BrowserModule.ɵinj (shipped source)
providers: [...BROWSER_MODULE_PROVIDERS, ...TESTABILITY_PROVIDERS],
imports: [CommonModule, ApplicationModule],
```

`bootstrapApplication` prepends **only** `BROWSER_MODULE_PROVIDERS`. `TESTABILITY_PROVIDERS`
— `Testability`, `TestabilityRegistry` and the `BrowserGetTestability` hook — are not
installed. That is deliberate: they exist for Protractor-style external drivers and are dead
weight in an app that does not have one. If you do need them, there is an explicit function:

```ts
import { provideProtractorTestingSupport } from '@angular/platform-browser';

export const appConfig: ApplicationConfig = {
  providers: [
    provideProtractorTestingSupport(),
    provideRouter(routes),
  ],
};
```

This is a small case of the general pattern the whole standalone design is built on: what an
`NgModule` bundled implicitly, a `provide*` function now exposes explicitly, and you pay for
only what you name. Topic [03](../03-the-provider-array/README.md) is that pattern in full.

## Gotchas

**★ Symptom: `NG5100: Providers from the BrowserModule have already been loaded.`** The
verbatim v22.1.5 message continues *"If you need access to common directives such as NgIf
and NgFor, import the `CommonModule` instead."* Cause: something in your provider graph
still pulls in `BrowserModule` — usually an old library `NgModule` reached through
`importProvidersFrom()`, or a copy-pasted `imports: [BrowserModule]` on a component.
`bootstrapApplication` already installed those providers, and `BrowserModule`'s constructor
throws in dev mode when it finds its own marker token in a *parent* injector. Fix: delete the
`BrowserModule` reference. If it is inside a third-party module you cannot edit, import that
library's feature module rather than its root module. If you genuinely wanted the directives,
they are standalone in v22 — import `NgClass` or `AsyncPipe` by name:

```ts
import { AsyncPipe, NgClass } from '@angular/common';

@Component({
  selector: 'app-status',
  imports: [AsyncPipe, NgClass],
  template: `<span [ngClass]="cls()">{{ label$ | async }}</span>`,
})
export class StatusComponent {}
```

**★ Symptom: `The App class is a standalone component, which can not be used in the
@NgModule.bootstrap array. Use the bootstrapApplication function for bootstrap instead.`**
That is NG6009, verbatim from `@angular/compiler-cli` 22.1.5, and it is a **compile-time**
error with a related-information marker pointing at the offending `NgModule`. Cause: a
half-finished migration — the component lost its `standalone: false` but the module still
lists it. Fix: delete the `AppModule` and move to `bootstrapApplication`, or put
`standalone: false` back until you are ready. There is no third option; a standalone class
can never appear in `bootstrap`.

**★ Symptom: `ng update` ran clean but `main.ts` still says `platformBrowserDynamic()`.**
Cause: no `ng update` migration rewrites your bootstrap. `platformBrowserDynamic` was
*deprecated* in v20 (v20.0.0 CHANGELOG, Deprecations → platform-browser: *"All entries of the
`@angular/platform-browser-dynamic`"*), not removed, and the package is still published at
22.1.5 — so nothing breaks and nothing tells you. Fix: run the migration mode that does it,
covered in chunk [09](09-the-standalone-migration-schematic.md):

```bash
ng generate @angular/core:standalone --mode=standalone-bootstrap
```

If you are staying on `NgModule` for now, at least swap the platform:
`platformBrowser().bootstrapModule(AppModule)` uses the AOT-compiled path,
`platformBrowserDynamic()` drags the JIT compiler into your bundle. Topic 11 covers why that
matters.

**★ Symptom: during a partial migration, a service you thought was a singleton has two
instances.** Cause: it is listed both in the surviving `AppModule.providers` and in
`appConfig.providers`, and the two are different injectors if any part of the app is still
bootstrapped through the module. Fix: pick one home per token. During migration, move
providers to `appConfig` in the same commit that deletes them from the module, and prefer
`providedIn: 'root'` on the service itself so there is nothing to move.

**Symptom: an e2e driver reports the app never becomes stable after moving to
`bootstrapApplication`.** Cause: `TESTABILITY_PROVIDERS` are not installed by
`bootstrapApplication`; they were only ever part of `BrowserModule`'s own injector. Fix: add
`provideProtractorTestingSupport()` to `appConfig.providers`, as shown above.

**Symptom: `imports: [BrowserModule]` on a standalone component compiles, then fails at
runtime.** Cause: `BrowserModule` is a legal `NgModule` and `imports` accepts NgModules, so
the compiler has no reason to object — the failure is NG5100 from its constructor when the
module injector is created. Fix: never import `BrowserModule` anywhere in a standalone app.
What you wanted was `CommonModule`, and what you probably wanted instead of *that* is the
built-in control flow, which needs no import at all — chunk
[06](06-not-a-known-element.md) has the details.

## Interview questions

**★ What happened to `BrowserModule`?**
Its providers were inlined into `bootstrapApplication`, which prepends
`BROWSER_MODULE_PROVIDERS` — the root injector scope marker, the default `ErrorHandler`, the
`DomEventsPlugin` and `KeyEventsPlugin` event manager plugins, `DomRendererFactory2`,
`SharedStylesHost` and `EventManager` — to your `ApplicationConfig.providers`. The class
still exists for `NgModule` apps and now exists mainly to *detect* misuse: its constructor
throws NG5100 when those providers are already present.

**★ Why does the modern legacy template use `platformBrowser()` rather than
`platformBrowserDynamic()`?**
Because `platformBrowserDynamic()` is the platform that ships the JIT compiler so it can
compile decorators at runtime, and an AOT-built app has nothing left to compile.
`platformBrowser()` is the same platform without the compiler. Angular v20 deprecated the
whole `@angular/platform-browser-dynamic` package for exactly this reason; seeing it in a
tutorial dates that tutorial to v19 or earlier.

**★ Map each `NgModule` bootstrap field to its replacement, from memory.**
`bootstrap: [App]` becomes the first argument of `bootstrapApplication`. `providers` becomes
`ApplicationConfig.providers`. `declarations: [App]` becomes the `imports` array on `App`
itself. `imports: [BrowserModule]` disappears — those providers are built in.
`imports: [AppRoutingModule]` becomes `provideRouter(routes)` in the same provider array.
`exports` has no replacement at all, because nothing needs re-exporting when every component
names its own dependencies. Chunk [07](07-what-replaced-each-ngmodule-responsibility.md) is
the full table.

**What breaks in a hybrid app that keeps an `AppModule` *and* calls `bootstrapApplication`?**
Two independent environment injectors. Anything `providedIn: 'root'` is instantiated once
per injector, so caches, stores and socket connections silently double. There is no error
because both graphs are individually valid. The only safe hybrid is one bootstrap: keep the
`NgModule` bootstrap and reach standalone components through `imports`, or move to
`bootstrapApplication` and reach the legacy module through
[`importProvidersFrom`](08-ngmodule-interop-importprovidersfrom.md).

**Why is "standalone component in `@NgModule.bootstrap`" a compile-time error rather than a
runtime one?**
Because `ngtsc` already knows both facts at build time: the `standalone` flag is in the
component's metadata and the `bootstrap` array must be a statically analysable literal. Every
constraint Angular *can* check in the compiler it does check there — that is the point topic
[01](../01-compiler-with-a-framework-attached/README.md) makes about static analysability,
and this error is a small instance of it.
