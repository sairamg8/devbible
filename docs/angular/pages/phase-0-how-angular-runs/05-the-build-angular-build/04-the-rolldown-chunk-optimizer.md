**Everyone knows the Angular build "uses esbuild". Almost nobody knows that a production build
then throws esbuild's chunk layout away and rebuilds it with a second bundler.** Since v22.1.0 that
second bundler is Rolldown, it is on by default, it runs as a distinct pass *after* esbuild has
finished, and the rest of the builder — budgets, size reporting, the output files you deploy — sees
only its result. The pass is not documented on angular.dev at all; it exists in the package's
dependency list, in one source file, and in one line of a changelog. This chunk is that pass: what
it is, where it sits, what happens when it fails, and why its output has to pretend it came from
esbuild.

## The file says what it is, in its own header

`chunk-optimizer.ts` opens with a `@fileoverview` block, and it is the clearest single statement
of the mechanism anywhere:

> *"@fileoverview This file provides a function to optimize JavaScript chunks using rolldown.*
> *It is designed to be used after an esbuild build to further optimize the output.*
> *The main function, `optimizeChunks`, takes the result of an esbuild build, identifies the main
> browser entry point, and then uses rolldown to rebundle and optimize the chunks. This process can
> result in smaller and more efficient code by combining and restructuring the original chunks. The
> file also includes helper functions to convert rolldown's output into an esbuild-compatible
> metafile, allowing for consistent analysis and reporting of the build output."*
> — [`chunk-optimizer.ts`](https://github.com/angular/angular-cli/blob/v22.1.7/packages/angular/build/src/builders/application/chunk-optimizer.ts) at `v22.1.7`

Read the three verbs. *"after an esbuild build"* — it is a second stage, not a plugin inside the
first. *"rebundle"* — not minify, not tree-shake, not rename: bundle again, from esbuild's output.
*"combining and restructuring the original chunks"* — the chunk graph you ship is not the chunk
graph esbuild produced.

The corroboration is in the package manifest. `@angular/build@22.1.7` declares an exact,
unhedged dependency:

```json
"dependencies": {
  "esbuild": "0.28.2",
  "vite": "8.1.5",
  "rolldown": "1.2.0",
  "oxc-parser": "0.142.0"
}
```

*(Four entries out of the twenty-six in the real manifest; the full list is
[02 · Inside the package](02-inside-the-package.md).)* A bundler does not appear in another bundler's
dependency list by accident.

## Where the pass sits, from the call site

`execute-build.ts` is the function that runs one application build. This is the block that invokes
the optimizer, verbatim:

```ts
// Optimize chunks if enabled and threshold is met.
// This pass uses Rollup/Rolldown to further optimize chunks generated by esbuild.
if (options.optimizationOptions.scripts) {
  // Count lazy chunks (files not needed for initial load).
  // Advanced chunk optimization is most beneficial when there are multiple lazy chunks.
  const { metafile, initialFiles } = bundlingResult;
  const lazyChunksCount = Object.keys(metafile.outputs).filter(
    (path) => path.endsWith('.js') && !initialFiles.has(path),
  ).length;

  // Only run if the number of lazy chunks meets the configured threshold.
  // This avoids overhead for small projects with few chunks.
  if (lazyChunksCount >= optimizeChunksThreshold) {
    const { optimizeChunks } = await import('./chunk-optimizer');
    const optimizationResult = await profileAsync('OPTIMIZE_CHUNKS', () =>
      optimizeChunks(
        bundlingResult,
        options.sourcemapOptions.scripts ? !options.sourcemapOptions.hidden || 'hidden' : false,
      ),
    );

    if (optimizationResult.errors) {
      executionResult.addErrors(optimizationResult.errors);

      return executionResult;
    }

    bundlingResult = optimizationResult;
  }
}
```

Four facts are visible in that block before you know anything else about rolldown:

- **The input is `bundlingResult`** — the finished esbuild result, complete with its `metafile` and
  its `initialFiles` set. esbuild has already run to completion.
- **The module is loaded lazily**: `await import('./chunk-optimizer')`. When the conditions are not
  met, rolldown is never even imported into the process. That is why the pass is invisible in a
  small project — not merely inactive, absent.
- **The pass is instrumented** under the label `OPTIMIZE_CHUNKS` via `profileAsync`. The build's
  profiling switches are [11 · Cache, workers and the environment variables](11-cache-and-workers.md).
- **`bundlingResult = optimizationResult`** — on success the optimized result *replaces* the
  esbuild result for the remainder of the build.

That last line is the one that matters most, and it is worth being blunt about: after it executes,
nothing downstream in the builder is looking at esbuild's output any more.

## Where "the rest of the build" is, and why the replacement matters

`execute-build.ts` reads as an ordered sequence of concerns, each introduced by its own comment:
bundle, dispose the bundler contexts, **optimize chunks**, analyse external imports, check budgets,
calculate estimated transfer sizes, check for CommonJS modules, process assets, extract licenses,
handle i18n, and write the metafile.

⚠️ **That ordering is the comment structure of one file, not a published pipeline diagram.** Angular
does not document a stage list for the `application` builder, and this page does not invent one —
read [`execute-build.ts`](https://github.com/angular/angular-cli/blob/v22.1.7/packages/angular/build/src/builders/application/execute-build.ts)
if you need the exact order at a given tag.

What the ordering does tell you is unambiguous: **budgets, transfer-size estimates and the
CommonJS check all run after the assignment.** Every number the build reports about your bundles is
measured on rolldown's output, not on esbuild's. If you have ever computed a bundle total by hand
from an esbuild metafile and found it disagreed with the build's own figure, this is why.

## Why the optimizer has to fake an esbuild metafile

The fileoverview's last sentence is the design constraint:

> *"The file also includes helper functions to convert rolldown's output into an esbuild-compatible
> metafile, allowing for consistent analysis and reporting of the build output."*

A metafile is esbuild's machine-readable description of what it produced — which outputs exist,
what went into each, how big each is. Everything after the optimizer in `execute-build.ts` consumes
that shape. Rather than teach budgets and reporting to understand two bundler dialects, the
optimizer translates: rolldown bundles, and then its result is rewritten into the structure esbuild
would have produced.

The practical consequence is that **the second bundler is undetectable from the outside.** There is
no separate rolldown report, no extra artifact, no marker in the output directory. A build that ran
the optimizer and one that skipped it produce the same *kind* of result — just not the same chunks.
Bundle analysis in **Phase 14 — Performance and the build** *(not written yet)* is therefore always
analysis of the post-optimizer graph, whether or not the analyst knows it.

## What this chunk stops short of

Whether the pass *runs* for your build is three separate conditions, none of which is a documented
option — they are two environment variables in an internal utility file and one field of
`optimization`. That, the arithmetic of those variables, and what the sources will and will not
claim about the benefit are
**[04b · What the second pass is worth, and when it runs](04b-what-the-second-pass-is-worth.md)**.

## Gotchas

**★ Symptom: a bundler-shaped error naming rollup or rolldown, in a project with no rollup config
and no rolldown config.** Cause: the post-esbuild optimizer. It is dynamically imported, so it does
not appear anywhere in the process until the moment it runs, and its errors surface as build errors
with no obvious owner. Fix: establish which bundler produced the defect by disabling the second
pass and rebuilding — if the error goes away it is the optimizer's, and if it stays it is esbuild's:

```bash
NG_BUILD_OPTIMIZE_CHUNKS=0 ng build --configuration production
```

**★ Symptom: the build fails inside the optimization step and you expect it to carry on with
esbuild's perfectly good output.** Cause: there is no fallback. The call site adds the errors to the
execution result and **returns immediately** — `executionResult.addErrors(optimizationResult.errors); return executionResult;`
— so an optimizer failure is a build failure, not a downgrade. Fix: unblock the build with the
switch while you file or investigate the defect, and put the reason next to it so it is removed
later:

```bash
# CI: temporary — chunk optimizer fails on <dependency>, see <issue link>
NG_BUILD_OPTIMIZE_CHUNKS=0 ng build --configuration production
```

**★ Symptom: your own bundle arithmetic from esbuild's metafile disagrees with the build's reported
sizes and with your budgets.** Cause: `bundlingResult = optimizationResult` replaces the esbuild
result before budgets and transfer-size estimation run, so every reported figure describes
rolldown's chunk graph. Fix: analyse the emitted output directory, which is post-optimizer by
definition, rather than an intermediate esbuild artifact:

```bash
ls -1 dist/my-app/browser/*.js
```

**★ Symptom: after upgrading from 22.0.x to 22.1.x, every output filename changed and the deploy
diff is unreviewable.** Cause: 22.1.0 made Rolldown the default chunk optimizer (`585d08af8`), so
chunk contents changed; with `outputHashing` on, filenames are derived from content and therefore
changed too. Fix: to compare the actual code rather than the hashes, build both sides with hashing
off:

```bash
ng build --configuration production --output-hashing none
```

**Symptom: someone states in a design document that "Angular switched to Rolldown".** Cause:
conflating the bundler with the chunk optimizer. esbuild still bundles the application; rolldown
re-bundles esbuild's chunks, and only when three conditions hold. Fix: say the precise thing —
esbuild builds, Rolldown re-chunks — and check the two conditions people usually forget:

```bash
# is this build even eligible? optimization on, and enough lazy chunks
node -p "require('./angular.json').projects['my-app'].targets.build.configurations.production"
```

**Symptom: `rolldown` appears in a dependency audit, licence report or SBOM and nobody can explain
why an Angular app depends on it.** Cause: `rolldown` is a direct, exactly pinned runtime
dependency of `@angular/build` (`"rolldown": "1.2.0"` at 22.1.7), alongside `esbuild` and `vite`.
Fix: nothing to fix — but record where it came from, because you cannot bump it yourself; it moves
when the CLI moves:

```bash
npm ls rolldown
```

**Symptom: a stack trace or profile mentions `OPTIMIZE_CHUNKS` and it matches nothing in the
documentation.** Cause: that is the label the builder passes to `profileAsync` around this pass; it
is internal instrumentation, not a documented phase name. Fix: read it as "the chunk optimizer ran
here" and go to the source file rather than searching angular.dev, which never mentions the pass.

## Interview questions

**★ Why would an esbuild-based build need a second bundler at all?**
Because bundling and *chunking* are different problems, and esbuild solves the first one extremely
fast without necessarily solving the second one optimally. esbuild's code splitting emits a chunk
wherever a module subgraph is shared, which is correct but can be granular; a second pass over
those finished chunks can merge the ones always loaded together and restructure the rest. Angular's
own words for it are *"combining and restructuring the original chunks"* to produce *"smaller and
more efficient code"*. Two things are worth adding if you want the answer to be honest rather than
merely fluent: nothing in the sources quantifies the benefit, and the builder itself does not
believe the pass always pays — it refuses to run when there are fewer than three lazy chunks,
because *"this avoids overhead for small projects with few chunks"*.

**★ Does Rolldown replace esbuild in Angular 22?**
No, and the distinction is the whole point. esbuild bundles the application — module resolution,
the Angular compiler plugin, the emit. Rolldown then takes esbuild's finished result and rebundles
the chunks, and only under conditions that a development build never satisfies. Both packages are
direct dependencies of `@angular/build` at 22.1.7 (`esbuild` at `0.28.2`, `rolldown` at `1.2.0`).
What changed in 22.1.0 was not "esbuild out, rolldown in" but which library performs the
already-existing chunk optimization pass: the changelog entry is *"default chunk optimization to
use Rolldown"*, and the previous implementation used Rollup.

**★ What happens to the build if the chunk optimizer errors?**
The build fails. The call site checks `optimizationResult.errors`, adds them to the execution
result, and returns before any of the later stages — budgets, transfer sizes, the CommonJS check,
assets, licences — run at all. There is deliberately no fallback to the esbuild output that was
sitting right there and was known good, which means a defect in a second-stage optimization can
take down a build whose actual compilation and bundling both succeeded. In practice that makes
`NG_BUILD_OPTIMIZE_CHUNKS=0` a useful first bisection step for any build error you cannot attribute.

**★ Why does the optimizer convert its output into an esbuild metafile?**
Because everything downstream in the builder speaks esbuild's metafile format — budget checking,
size estimation, the emitted build metadata. The optimizer's own description says its helpers
convert rolldown's output into an esbuild-compatible metafile *"allowing for consistent analysis
and reporting of the build output"*. The design consequence is that the second bundler is invisible
from outside the builder: there is no rolldown-specific artifact or report, so any bundle analysis
you perform is analysis of the post-optimizer graph whether or not you knew a second pass existed.

**Where in the build does the pass sit, and how do you know?**
Between bundling and every form of analysis. It runs after esbuild has produced a complete result
with a metafile and an `initialFiles` set — it needs both to count lazy chunks — and before budget
checking, transfer-size estimation and the CommonJS check, all of which read the result it
overwrites. The evidence is the ordered comment structure of `execute-build.ts` at `v22.1.7`, not a
published pipeline diagram; Angular does not document a stage list for the `application` builder,
which is exactly why reading that one file is the reliable way to answer the question for a given
version.
