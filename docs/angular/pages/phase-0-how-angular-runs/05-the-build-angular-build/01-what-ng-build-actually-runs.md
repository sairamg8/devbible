**Almost everything people believe about "the Angular build" is a belief about a builder, and the
builder is a string in a JSON file.** `ng build` resolves a project, reads its `build` target, and
runs whatever that target names. There is no built-in bundler, no hard-coded pipeline, and no
special case for Angular's own builders — swap the string and a different program runs. Starting
from that fact makes the rest of this topic mechanical rather than mysterious, and it makes the
first debugging question obvious: *which builder is this project actually using, and where did I
look?*

## One sentence, and everything else is downstream

angular.dev states the whole contract in a line:

> *"`ng build` only executes the builder for the `build` target in the default project as specified
> in `angular.json`."*
> — [angular.dev/tools/cli/build](https://angular.dev/tools/cli/build)

Read what that does **not** say. It does not say esbuild. It does not say Angular compiles anything.
Those are properties of the particular builder that happens to be named, and a project can name a
different one — which is exactly what a project still on webpack is doing.

The corollary matters more than the sentence: **`ng build` behaving differently in two projects, or
in two branches of one project, is a `build` target difference until proven otherwise.** Diff the
target before diffing anything else.

## The four builders a `build` target can name

angular.dev lists them, verbatim:

> *"| `@angular/build:application` | Builds an application with a client-side bundle, a Node server,
> and build-time prerendered routes with [esbuild](https://esbuild.github.io/). |"*
>
> *"| `@angular-devkit/build-angular:browser-esbuild` | Bundles a client-side application for use in
> a browser with [esbuild](https://esbuild.github.io/). |"*
>
> *"| `@angular-devkit/build-angular:browser` | Bundles a client-side application for use in a
> browser with [webpack](https://webpack.js.org/). |"*
>
> *"| `@angular/build:ng-packagr` | Builds an Angular library adhering to [Angular Package Format](https://angular.dev/tools/libraries/angular-package-format). |"*

Four rows, and the shape of the whole topic is already visible in them:

| Builder | Bundles with | Status |
|---|---|---|
| `@angular/build:application` | esbuild | The current default for applications |
| `@angular/build:ng-packagr` | ng-packagr | The current default for libraries |
| `@angular-devkit/build-angular:browser-esbuild` | esbuild | ⚠ Deprecated in v22.0.0 |
| `@angular-devkit/build-angular:browser` | webpack | ⚠ Deprecated in v22.0.0 |

⚠️ **The two `@angular-devkit/build-angular` rows are deprecated as of v22.0.0** and the
documentation page above does not say so — the deprecation lives in the changelog. Both still ship
and still work at 22.1.7. Which packages were deprecated, on what day, and why the release notes
name no removal version is **07 · The webpack builders are deprecated** *(not written yet)*.

🔴 **The `application` row is doing more than the other three.** *"a client-side bundle, a Node
server, and build-time prerendered routes"* — one builder covering what used to take `browser`,
`server`, `prerender` and `app-shell` between them. That consolidation is why the migration off
webpack is a single migration rather than four.

## The two defaults, and how to check rather than assume

> *"Applications generated by `ng new` use `@angular/build:application` by default.*
> *Libraries generated by `ng generate library` use `@angular/build:ng-packagr` by default."*
>
> *"You can determine which builder is being used for a particular project by looking up the
> `build` target for that project."*
> — [angular.dev/tools/cli/build](https://angular.dev/tools/cli/build)

Here is what that lookup actually finds in a project generated by `ng new my-app` on 22.1.7,
written out from `addAppToWorkspaceFile()` in the application schematic:

```json
{
  "projects": {
    "my-app": {
      "root": "",
      "sourceRoot": "src",
      "projectType": "application",
      "prefix": "app",
      "targets": {
        "build": {
          "builder": "@angular/build:application",
          "defaultConfiguration": "production",
          "options": {
            "browser": "src/main.ts",
            "polyfills": ["zone.js"],
            "tsConfig": "tsconfig.app.json",
            "assets": [{ "glob": "**/*", "input": "public" }],
            "styles": ["src/styles.css"]
          },
          "configurations": {
            "production": {
              "budgets": [
                { "type": "initial", "maximumWarning": "500kB", "maximumError": "1MB" },
                { "type": "anyComponentStyle", "maximumWarning": "4kB", "maximumError": "8kB" }
              ],
              "outputHashing": "all"
            },
            "development": {
              "optimization": false,
              "extractLicenses": false,
              "sourceMap": true
            }
          }
        }
      }
    }
  }
}
```

**One line in that object is the answer to "what does `ng build` run":**
`"builder": "@angular/build:application"`. Everything else on the target is arguments to it.

Two details worth noticing now, because they surprise people later. `polyfills` carries `zone.js`
only because this project was not generated `--zoneless`; the schematic writes `undefined` when it
was. And `defaultConfiguration` is `production`, which is why a bare `ng build` optimizes and a bare
`ng serve` does not — `serve` defaults to `development`.

The equivalent one-liner, if you would rather not read the file:

```bash
node -p "require('./angular.json').projects['my-app'].targets.build.builder"
```

⚠️ **A workspace may use `architect` instead of `targets`** — the older key name, still accepted and
still what angular.dev's own illustrative fragment shows. If the command above prints `undefined`,
try `architect`. Which key wins when both are present is topic 06's problem, and the short answer
there is: do not have both.

## Where the output goes, and the sentence that is incomplete

> *"The result of this build process is output to a directory (`dist/${PROJECT_NAME}` by default)."*
> — [angular.dev/tools/cli/build](https://angular.dev/tools/cli/build)

🔴 **That is true of the build as a whole and misleading about your `index.html`.** The
`application` builder writes the browser output into a **`browser/` subdirectory** of that path, so
a default `my-app` build puts the deployable files in `dist/my-app/browser/`, not `dist/my-app/`.
The full layout — and why the extra level exists once a build can emit a server bundle beside the
client one — is **09 · What breaks when you switch** *(not written yet)*.

The practical version, worth internalising before you write a deploy script rather than after:

```bash
# what a deploy script usually wants
ls dist/my-app/browser/index.html
```

## Gotchas

**★ Symptom: `ng build` behaves completely differently in two projects on the same Angular
version.** Cause: different `build` targets. The version pins the *available* builders; the target
picks one, and a project can sit on the deprecated webpack builder indefinitely. Fix: compare the
one line that matters before comparing anything else:

```bash
node -p "require('./angular.json').projects['my-app'].targets.build.builder"
```

**★ Symptom: your deploy uploads `dist/my-app/` and the site 404s.** Cause: the `application`
builder writes the browser output to `dist/my-app/browser/`, while the documentation sentence about
output says `dist/${PROJECT_NAME}`. Fix: point the deploy at the `browser/` directory, and check it
in CI so a rename cannot silently break it:

```bash
test -f dist/my-app/browser/index.html || { echo "browser output missing"; exit 1; }
```

**★ Symptom: a tutorial's `angular.json` snippet does not match your file — it uses `architect` and
yours says `targets`.** Cause: both key names exist and the older one is still accepted; even
angular.dev's own illustrative fragment uses `architect`. Fix: read whichever key your file has, and
keep exactly one of them.

**★ Symptom: `ng build` in a multi-project workspace builds the wrong application, or errors
outright.** Cause: no project argument, and the working directory does not sit inside a project
root. Fix: name the project explicitly rather than relying on the cwd:

```bash
ng build my-app
```

**★ Symptom: a bare `ng build` produces optimized output but `ng serve` does not, and you assumed
one of them was configured wrong.** Cause: the schematic writes `defaultConfiguration: "production"`
on `build` and `defaultConfiguration: "development"` on `serve`. Fix: expected. To build the
development configuration deliberately, ask for it:

```bash
ng build --configuration development
```

**★ Symptom: you set an option on the `build` target and `ng serve` ignored it.** Cause: `serve` is
a different target running a different builder; it references `build` through `buildTarget` rather
than inheriting from it. Fix: put build options on the `build` target and check that `serve`'s
`buildTarget` points at the configuration you changed.

**★ Symptom: a project generated `--zoneless` has no `polyfills` entry and a tutorial says it should
have `zone.js`.** Cause: the schematic writes `polyfills` as `undefined` for a zoneless project, so
the key is simply absent. Fix: expected; adding `zone.js` back to a zoneless application is a
decision about change detection, not a build fix.

## Interview questions

**★ What does `ng build` actually do?**
It resolves a project, reads that project's `build` target out of `angular.json`, and executes the
builder named there — nothing more. angular.dev puts it as *"`ng build` only executes the builder
for the `build` target in the default project as specified in `angular.json`."* The reason this is
worth stating precisely is that it relocates every other question: whether esbuild or webpack runs,
whether a server bundle is produced, where the output lands, are all properties of the named
builder, not of `ng build`. In practice it makes the first diagnostic step "print the builder
string" rather than "read the CLI's source".

**★ Which builders can a `build` target name, and which are current?**
Four appear in angular.dev's table. `@angular/build:application` is the default for applications
and covers the client bundle, a Node server and build-time prerendering with esbuild;
`@angular/build:ng-packagr` is the default for libraries. The two `@angular-devkit/build-angular`
entries — `browser` on webpack and `browser-esbuild` on esbuild — still ship and still work, but
were formally deprecated in v22.0.0, which the build documentation page does not mention. The detail
worth adding is that `application` consolidated what used to be several builders, which is why
migrating off webpack is one migration rather than four.

**★ Where does a default `ng build` put `index.html`, and why is that a common deployment bug?**
In `dist/<project>/browser/`, not `dist/<project>/`. The documentation's sentence about output
gives `dist/${PROJECT_NAME}` and is describing the build output directory as a whole; the
`application` builder adds a `browser/` level below it because the same build can also emit a server
bundle. Deploy scripts written against the older layout — or against that sentence — upload the
parent directory, get no `index.html` at the root, and serve 404s with a build that succeeded.

**How would you find out which builder a project uses, without guessing?**
Read the `build` target: `node -p "require('./angular.json').projects['my-app'].targets.build.builder"`.
If that prints `undefined`, the workspace is using the older `architect` key instead of `targets`;
both are accepted. angular.dev gives the same instruction in prose — *"You can determine which
builder is being used for a particular project by looking up the `build` target for that project."*

**What does `defaultConfiguration` on the generated `build` target tell you?**
That a bare `ng build` is not a neutral build. The application schematic writes
`defaultConfiguration: "production"` on `build` and `"development"` on `serve`, so the same project
optimizes when you build and does not when you serve — which is correct, and is also why "it works
in `ng serve` but not in `ng build`" is such a common report. Naming the configuration explicitly
removes the ambiguity.
