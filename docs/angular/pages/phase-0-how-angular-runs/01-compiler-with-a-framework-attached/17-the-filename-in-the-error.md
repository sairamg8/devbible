**[14d](14d-how-a-diagnostic-gets-home.md) explained how a position inside machine-generated code is
mapped back to a position in your template. This page is the last step of that journey: which
*filename* the finished diagnostic carries. There are three possible answers, one branch chooses
between them, and two of the three name a file TypeScript has never compiled — one of which does not
exist on disk in any form. This is the single most disorienting thing about Angular for a newcomer,
and it has a precise, quotable mechanism rather than a folklore explanation.**

## Three source-mapping cases, three filenames

`makeTemplateDiagnostic` branches on the template's source-mapping type. The `direct` case, with the
compiler's own comment, verbatim:

```ts
// For direct mappings, the error is shown inline as ngtsc was able to pinpoint a string
// constant within the `@Component` decorator for the template. This allows us to map the error
// directly into the bytes of the source file.
```

The other two share a branch, verbatim:

```ts
} else if (mapping.type === 'indirect' || mapping.type === 'external') {
  // For indirect mappings (template was declared inline, but ngtsc couldn't map it directly
  // to a string constant in the decorator), the component's file name is given with a suffix
  // indicating it's not the TS file being displayed, but a template.
  // For external temoplates, the HTML filename is used.
  const componentSf = mapping.componentClass.getSourceFile();
  const componentName = mapping.componentClass.name.text;
  const fileName =
    mapping.type === 'indirect'
      ? `${componentSf.fileName} (${componentName} template)`
      : mapping.templateUrl;
```

Which gives exactly three shapes a reader can see in a terminal:

| Mapping | How the template was written | Filename in the error |
|---|---|---|
| `direct` | a string literal in the decorator | `src/app/user-card.ts` — **your file, at the right character** |
| `external` | `templateUrl: './user-card.html'` | `src/app/user-card.html` — a file `tsc` never parsed |
| `indirect` | inline but **computed**, e.g. `template: TEMPLATE_CONST` | `src/app/user-card.ts (UserCard template)` — **not a path that exists** |

🔴 **The third one is a filename with a space and parentheses in it.** Nothing on disk matches it,
your editor cannot open it, and grepping for it finds nothing. It means the compiler had a template
string but could not point at a string literal in the decorator to blame, so it manufactured a name
that at least tells you which class to look at.

⚠️ **angular.dev's AOT page is out of date here.** It gives the synthetic name as
`my.component.ts.MyComponent.html`. At `v22.1.5` the format is `<path> (<ComponentName> template)`.
The page's *explanation*, however, is exactly right and worth keeping: > *"is a synthetic file
generated by the template compiler that holds contents of the `MyComponent` class template. The
compiler never writes this file to disk."*

## The synthetic file is your template parsed as if it were TypeScript

The name is not the only manufactured thing. To place an error inside a template that TypeScript has
no `SourceFile` for, the compiler builds one — verbatim:

```ts
const TemplateSourceFile = Symbol('TemplateSourceFile');
// …
function getParsedTemplateSourceFile(
  fileName: string,
  mapping: TemplateSourceMappingWithSourceFile,
): ts.SourceFile {
  if (mapping[TemplateSourceFile] === undefined) {
    mapping[TemplateSourceFile] = parseTemplateAsSourceFile(fileName, mapping.template);
  }
```

The template text is handed to TypeScript's parser as though it were source code, and cached on the
mapping object under a symbol key. The result is nonsense as TypeScript — HTML does not parse — but
that does not matter: all the diagnostic needs from a `SourceFile` is a name and a text buffer to
compute line and column positions against. **The `.html` file in your error message is a `ts.SourceFile`
that TypeScript was never asked to compile, only to measure.**

This is why the file can appear in an error while being absent from `tsconfig.json`'s `include`, and
why nothing about it shows up in `tsc --listFiles`.

## Every non-direct error carries a breadcrumb back to the `.ts`

The branch does not stop at the filename. It attaches related information, verbatim:

```ts
relatedInformation.push({
  category: ts.DiagnosticCategory.Message,
  code: 0,
  file: componentSf,
  // mapping.node represents either the 'template' or 'templateUrl' expression. getStart()
  // and getEnd() are used because they don't include surrounding whitespace.
  start: mapping.node.getStart(),
  length: mapping.node.getEnd() - mapping.node.getStart(),
  messageText: `${typeForMessage} occurs in the template of component ${componentName}.`,
});
```

`typeForMessage` is `Error`, `Warning`, `Suggestion` or `Message`. So the complete experience of an
external-template error is **two locations**: the error itself, in the `.html`, and a note pointing at
the `templateUrl:` string in the `.ts` that owns it — deliberately spanning the expression without
its surrounding whitespace, so an editor highlights the string and not the padding.

🔴 **Read the related information, always.** It is the only thing in the message that names the
component class, and in a codebase where six components share a partial view name it is the
difference between the right file and a plausible one.

## Two more details worth recognising

**The diagnostics are labelled.** Every template diagnostic carries `source: 'ngtsc'` and a
`typeCheckId`. That is how an IDE or a build tool tells an Angular template diagnostic from an
ordinary TypeScript one — a distinction that matters because they arrive through the same
`ts.Diagnostic` channel ([14c](14c-the-type-check-file-and-how-errors-get-home.md)).

**There is a fallback for the reporting machinery failing**, verbatim:

```ts
const failureChain = makeDiagnosticChain(
  `Failed to report an error in '${fileName}' at ${span.start.line + 1}:${
    span.start.col + 1
  }`,
  [makeDiagnosticChain((e as Error)?.stack ?? `${e}`)],
);
```

If you ever see `Failed to report an error in '…' at 12:4` followed by a stack trace, **that is not
your template failing — that is the diagnostic machinery failing to describe a failure.** There is a
real error underneath it that you are not being shown. The `+ 1`s are worth noticing too: spans are
zero-based internally and one-based in messages, which is why an off-by-one between a compiler
message and a hand-counted line is always the message being right.

## Gotchas

**★ Symptom: an error in `user-card.html`, and that file is not in `tsconfig.json`.** Cause: nothing
is wrong. The template type-checker owns that file, not `tsc` — the `.html` becomes a `ts.SourceFile`
manufactured from the template text purely so positions can be computed. Fix: none. Read the *"Error
occurs in the template of component UserCard"* note to get back to the `.ts`.

**★ Symptom: an error located in `src/app/user-card.ts (UserCard template)`, which does not exist.**
Cause: an `indirect` source mapping — your `template:` is not a string literal the compiler could
point into, typically because it is a constant, a concatenation or an imported value. Fix: make it a
literal, or move it to `templateUrl`, and the filename becomes real:

```ts
// ⛔ indirect: errors land in "user-card.ts (UserCard template)"
const TEMPLATE = `<p>{{ user.nmae }}</p>`;
@Component({selector: 'app-user-card', template: TEMPLATE})
export class UserCard {}

// ✅ direct: errors land in user-card.ts at the exact character
@Component({selector: 'app-user-card', template: `<p>{{ user.nmae }}</p>`})
export class UserCard {}
```

**★ Symptom: `Failed to report an error in '…' at 3:12`, followed by a stack trace.** Cause: the
diagnostic-construction path threw while building the message — the synthetic source file could not
be produced. Fix: this is a compiler-side failure, so treat the stack as a bug report rather than a
lint. The underlying template error is still there and unreported; simplify the template until the
real diagnostic appears.

**★ Symptom: your editor jumps to the wrong file when you click an Angular error.** Cause: the
diagnostic's primary location is the template — `.html` or the synthetic name — and the `.ts` is only
in the *related information*. Tooling that ignores related information has nothing to jump to when
the primary file is synthetic. Fix: use the component name from the note; it is always in the
message text even when the location is unusable.

**★ Symptom: a line number in a template error is one off from what you counted.** Cause: spans are
zero-based internally and the message adds one — `span.start.line + 1`. Fix: trust the message. If it
disagrees with your count by exactly one, you counted from one and it already did.

**Symptom: a build tool shows Angular template errors and TypeScript errors in one undifferentiated
list.** Cause: they arrive as the same `ts.Diagnostic` type. Fix: filter on `source: 'ngtsc'`, which
every template diagnostic carries alongside a `typeCheckId` — the labelling exists precisely so
tooling can separate them.

**Symptom: moving a template from `templateUrl` to an inline literal changed where errors appear.**
Cause: that is the mapping type changing from `external` to `direct`, which is the whole mechanism.
Fix: none — it is an improvement. `direct` is the only case that puts the error at the exact byte in
a file you can open.

## Interview questions

**★ A template error names an `.html` file. Which tool produced it, and why does TypeScript not know
that file exists?**
The Angular template type-checker produced it. TypeScript compiles `.ts` files and knows nothing
about templates, so to report an error *inside* one, `ngtsc` manufactures a `ts.SourceFile` by
parsing the template text as if it were source — the compiler does this in
`getParsedTemplateSourceFile` and caches it on the mapping. The parse is meaningless as TypeScript,
but a `SourceFile` is all a `ts.Diagnostic` needs to compute a line and column against, and the
filename it is given is the real `templateUrl`. That is why the file can appear in an error while
being absent from `tsconfig.json` and from `tsc --listFiles`.

**★ You get an error in a file called `user-card.ts (UserCard template)`. What happened?**
That is the `indirect` source mapping. The template was written inline but not as a string literal
the compiler could point into — a constant, a concatenation, an imported value — so `ngtsc` had the
template text but no byte range in the decorator to blame. Rather than reporting the error at a wrong
location, it synthesises a filename of the form `<path> (<ComponentName> template)`, which exists
nowhere on disk and is a deliberate signal that the location is approximate. The fix is to make the
template a literal or move it to a `templateUrl`, either of which restores a real file. Note that
angular.dev still documents an older format for this name, so the docs and the compiler disagree —
the compiler is the authority.

**★ What are the two locations in an external-template error, and why does the second one matter?**
The primary location is the template file; the related information points at the `template:` or
`templateUrl:` expression in the component's `.ts`, with the message *"Error occurs in the template of
component X"*. The second matters because the first does not name the component. A partial view can be
referenced from more than one place, and a filename alone does not say which class's compilation
scope produced the error — the related information is the only part of the diagnostic carrying the
class name, and the span deliberately excludes surrounding whitespace so an editor highlights the
expression itself.

**How would a build tool distinguish an Angular template error from a TypeScript error?**
By the `source` field, which is `'ngtsc'` on every template diagnostic, alongside a `typeCheckId`.
Both kinds arrive through the same `ts.Diagnostic` channel — that is the design, since it lets
Angular errors flow through any TypeScript-aware pipeline for free — so a tool that wants to treat
them differently has to read the label rather than the shape. It is the same principle as the error
codes being negative TypeScript codes: ride the existing rails and mark your traffic.

**You see `Failed to report an error in 'foo.html' at 4:9` with a stack trace. What is the state of
your build?**
Worse than it looks. That message comes from a `catch` around the diagnostic construction, so what
failed is the machinery that describes an error — the error it was describing is real and you are not
being told what it is. It is not a template error you can act on, and it is not a lint. Treat the
stack as evidence for a compiler bug report, and in the meantime narrow the template until the real
diagnostic gets through.
