# Link map · Next.js · Part 2 (chapters 4–7)

Covers every topic row of chapters 4 to 7 in `docs/nextjs/syllabus/02-data-rendering-resilience.md`: data fetching (T04-01 to T04-05), caching, PPR and Cache Components (T05-01 to T05-05), SSG, ISR and SSR strategy (T06-01 to T06-05), and error handling and resilience (T07-01 to T07-06). That is 21 topic rows. The four "Project Milestone" bullets (T04-06, T05-06, T06-06, T07-07) are not topics and are skipped. Every row has a written page of ours; a chunked topic shows its first chunk file, under `docs/nextjs/pages/<chapter-dir>/`.
*read* = I read the passage that supports the claim. Every link below was fetched at 200 on 2026-10-14 and none is left at headings only. Third-party links carry a date only where the page shows one. No `#anchors` are given. Where no good non-official explanation turned up after searching, the block has no "Beyond the docs" line.

🔴 **Version note.** The syllabus targets **Next.js 16.3** and React 19.2. Every official pick is the unversioned `nextjs.org/docs/app/...` page, which on 2026-10-14 serves 16.x (some pages carry a 16.4.0 version header). Four things differ from what the syllabus bullets say. First, with `cacheComponents` on, the route segment options `dynamic`, `revalidate` and `fetchCache` are removed (since 16.0.0), so T04-03 and T06-03 describe the previous model; the guide "Caching and Revalidating (Previous Model)" is the page that still documents them. The Route Segment Config reference contradicts itself on `dynamicParams`: its option table still lists it, but its version-history row names it as removed too. Second, the Turbopack build cache is not one flag named `turbopackFileSystemCache`: the options are `turbopackFileSystemCacheForDev` (default since 16.1.0) and `turbopackFileSystemCacheForBuild` (default since 16.3.0), both under `experimental`, plus `turbopackMemoryEviction` (experimental since 16.3.0; `false`, `'auto'` by default, or `'full'`; only has an effect in `next dev` with the dev cache on). Third, the `error.js` recovery prop is now `retry` (stable in 16.3.0, `unstable_retry` in 16.2.0); `reset` still exists but only clears the error state without re-fetching, and the docs say to prefer `retry`. Fourth, third-party picks were mostly written for Next.js 13 to 15 and each such block says so.
