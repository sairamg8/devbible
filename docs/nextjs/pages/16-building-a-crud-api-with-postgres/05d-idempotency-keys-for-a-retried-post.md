> ⚠️ The idempotency header is an **Internet-Draft, not an RFC**; draft-07 carried an expiry of 18 April 2026 and no later revision was published as of the verification date. Treat it as the best-documented convention, not a standard.
> Documentation-verified; **no sandbox run, no timings**.
> Target: **Next.js 16.3.4** · **PostgreSQL 18.4** · `drizzle-orm` **0.45.2** · Node **24.20.0**.

**The retried POST is not an exotic failure mode you handle for completeness. It is what happens every time a phone changes cell tower mid-request, every time a serverless function is killed at its timeout after the write committed, and every time a user taps a button twice because the first tap produced no visible change. In all three the client has sent a create and does not know whether it happened — and RFC 9110 has already ruled out every automatic recovery. This page builds the one recovery left: a client-supplied key, a unique index, and a replay that returns the original result rather than a second card. [05da](05da-scoping-expiry-and-the-records-table.md) covers the parts that make it safe to operate — scope, expiry, and the general design the key column cannot reach.**

## The client's dilemma, stated by the specification

RFC 9110 §9.2.2 removes the two obvious options in consecutive paragraphs:

> *"A client SHOULD NOT automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent, regardless of the method, or some means to detect that the original request was never applied."*

> *"A proxy MUST NOT automatically retry non-idempotent requests. A client SHOULD NOT automatically retry a failed automatic retry."*

And it notes what happens in the field regardless:

> *"Some clients take a riskier approach and attempt to guess when an automatic retry is possible. For example, a client might automatically retry a POST request if the underlying transport connection closed before any part of a response is received, particularly if an idle persistent connection was used."*

🔴 **That last paragraph is a description of your production traffic.** HTTP client libraries do this. Service meshes do this. A `fetch` wrapped in a three-attempt retry helper does this, and the person who added the helper was thinking about GETs. You do not get to decide whether your create endpoint receives duplicate POSTs; you only get to decide what happens when it does.

The escape hatch is in the first quote — *"some means to know that the request semantics are actually idempotent, regardless of the method"*. An idempotency key manufactures exactly that means, and once the client has it, the retry becomes legitimate rather than reckless.

⚠️ **This is the mirror image of [ch15 · 04ea](../15-databases-apis-and-full-stack-patterns/04ea-external-effects-and-provider-idempotency.md)**, which argues the *client* side — how to consume somebody else's idempotency key when your job calls a payment provider. This page is the *server* side: what you must build so your own clients can do the same thing to you. 04ea closes with the obligation you owe your consumers; this is that obligation implemented.

## What the draft actually specifies

The Idempotency-Key draft is short and its useful part is the enforcement table. On syntax:

> *"An idempotency key is a unique value generated by the client which the resource uses to recognize subsequent retries of the same request. The Idempotency-Key HTTP request header field carries this value."*

> *"The idempotency key MUST be unique and MUST NOT be reused with another request with a different request payload."*

> *"It is RECOMMENDED that a UUID [RFC4122] or a similar random identifier be used as an idempotency key."*

The five outcomes, which are the whole design:

| Situation | Draft's prescription |
|---|---|
| Key never seen | *"process the request normally and respond with an appropriate response and status code"* |
| Key seen, original **completed** | *"respond with the result of the previously completed operation, success or an error"* |
| Key seen, original **still running** | *"respond with a resource conflict error"* — the draft's example is `409 Conflict` |
| Key reused with a **different payload** | `422 Unprocessable Content` — *"Idempotency Key MUST not be reused across different payloads"* |
| Key **missing** on an operation that requires it | `400 Bad Request` with a link to your documentation |

The draft also names the mechanism for detecting the fourth case:

> *"An idempotency fingerprint MAY be used in conjunction with an idempotency key to determine the uniqueness of a request. Such a fingerprint is generated from request payload data by the resource."*

It lists checksum-of-payload, checksum-of-selected-fields and field-by-field comparison as acceptable approaches. Implementing that rule needs somewhere to store the fingerprint, which is where the cheap design below runs out — see [05da](05da-scoping-expiry-and-the-records-table.md).

## The cheap version: a key column on `cards`

For exactly one operation — create a card — you do not need a second table. Add a nullable key column and a partial unique index:

```sql
-- an addition this topic proposes; not part of the canonical cards table
ALTER TABLE cards ADD COLUMN idempotency_key text;

CREATE UNIQUE INDEX cards_idempotency_key_unique
  ON cards (board_id, idempotency_key)
  WHERE idempotency_key IS NOT NULL;
```

The index is partial for a reason that is easy to miss: `NULL` values are distinct under a plain unique index, so rows with no key would not collide anyway — but the partial predicate makes that intent explicit and keeps the index small, since most rows will never carry a key. It is scoped to `board_id`, and that scoping is a security property argued in [05da](05da-scoping-expiry-and-the-records-table.md).

```ts
// lib/dal/cards.ts
import 'server-only'
import { and, eq } from 'drizzle-orm'
import { db } from '@/db'
import { cards } from '@/db/schema'
import { requireBoardAccess } from '@/lib/dal/access'

export type CreateResult =
  | { outcome: 'created'; card: CardDTO }
  | { outcome: 'replayed'; card: CardDTO }
  | { outcome: 'in_flight' }

const CARD_COLUMNS = {
  id: cards.id,
  boardId: cards.boardId,
  title: cards.title,
  body: cards.body,
  status: cards.status,
  position: cards.position,
  version: cards.version,
  createdAt: cards.createdAt,
  updatedAt: cards.updatedAt,
} as const

export async function createCardIdempotent(
  boardId: string,
  input: CreateCardInput,
  idempotencyKey: string,
): Promise<CreateResult> {
  await requireBoardAccess(boardId)

  const [inserted] = await db
    .insert(cards)
    .values({
      boardId,
      title: input.title,
      body: input.body ?? null,
      status: input.status ?? 'todo',
      position: input.position ?? (await nextPosition(boardId)),
      idempotencyKey,
    })
    // 🔴 The target is REQUIRED here. See the gotcha below.
    .onConflictDoNothing({ target: [cards.boardId, cards.idempotencyKey] })
    .returning(CARD_COLUMNS)

  if (inserted) return { outcome: 'created', card: inserted }

  // Nothing came back, so the key already exists. Read the row it belongs to.
  const [existing] = await db
    .select(CARD_COLUMNS)
    .from(cards)
    .where(and(eq(cards.boardId, boardId), eq(cards.idempotencyKey, idempotencyKey)))
    .limit(1)

  // Still nothing: the original transaction has not committed yet.
  if (!existing) return { outcome: 'in_flight' }

  return { outcome: 'replayed', card: existing }
}
```

### The `RETURNING` trap, which is the whole reason this needs a second query

The PostgreSQL `INSERT` reference states it in one clause, and it is easy to read past:

> *"Only rows that were successfully inserted or updated will be returned."*

`ON CONFLICT DO NOTHING` does not insert and does not update. **So on every replay, `RETURNING` yields an empty result set.** The naive implementation —

```ts
// 🔴 wrong: destructures undefined on every single replay
const [card] = await db.insert(cards).values({ /* ... */ })
  .onConflictDoNothing({ target: [cards.boardId, cards.idempotencyKey] })
  .returning(CARD_COLUMNS)
return card   // undefined on replay -> TypeError, or a 500, or a null body
```

— works perfectly in every test that does not retry, and fails on the first real retry in production. Whatever the handler does with `undefined` becomes the response to a client that is already in a bad state and about to retry again.

`ON CONFLICT DO UPDATE` avoids the empty result, because an updated row *is* returned, and the reference calls that guarantee out explicitly: *"ON CONFLICT DO UPDATE guarantees an atomic INSERT or UPDATE outcome; provided there is no independent error, one of those two outcomes is guaranteed, even under high concurrency."* It is nevertheless the wrong tool here — a replay must not modify the stored row, and a `DO UPDATE` that sets columns back to the request's values would cheerfully overwrite an update someone made in between. Prefer `DO NOTHING` plus a read, and handle the empty read as a real state.

## The `in_flight` case is not a theoretical race

The `existing` lookup can legitimately return nothing: the original request's transaction is still open, so under READ COMMITTED its row is invisible to your snapshot. That is exactly the draft's third row — *"The request was retried before the original request completed. The resource SHOULD respond with a resource conflict error."*

⚠️ **The documentation does not settle what `ON CONFLICT DO NOTHING` does against an uncommitted conflicting row.** The `INSERT` reference guarantees the atomic outcome only for `DO UPDATE`, and says of the general case that *"Tables with unique indexes might block if concurrent sessions perform actions that lock or modify rows matching the unique index values being inserted."* I could not find a sentence specifying the `DO NOTHING` behaviour precisely, so the code above does not depend on one: whether the statement blocks briefly and then finds the row, or returns immediately and finds nothing, both paths are handled and neither produces a duplicate card.

Returning 409 there is correct, and the client's retry policy should treat it as *retryable after a short delay* — unlike the 409 from a duplicate title, which is not retryable at all. That is an argument for a distinct machine-readable `code` in the envelope even where the status matches.

## Wiring it to the handler, and what a replay returns

```ts
// app/api/boards/[boardId]/cards/route.ts
export async function POST(
  request: NextRequest,
  ctx: RouteContext<'/api/boards/[boardId]/cards'>,
) {
  const { boardId } = await ctx.params
  const id = BoardIdParam.safeParse(boardId)
  if (!id.success) return errorResponse(400, 'invalid_board_id', 'boardId must be a UUID')

  const key = request.headers.get('Idempotency-Key')
  if (!key || !isValidKey(key)) {
    return errorResponse(400, 'idempotency_key_required', 'Send an Idempotency-Key header containing a UUID')
  }

  const parsed = CreateCardRequest.safeParse(await request.json())
  if (!parsed.success) return validationResponse(parsed.error)

  const result = await createCardIdempotent(id.data, parsed.data, key)

  switch (result.outcome) {
    case 'created':
      return Response.json(result.card, {
        status: 201,
        headers: { Location: `/api/cards/${result.card.id}` },
      })
    case 'replayed':
      // 200, not 201: nothing was created by THIS request.
      return Response.json(result.card, {
        status: 200,
        headers: {
          Location: `/api/cards/${result.card.id}`,
          'Idempotency-Replayed': 'true',
        },
      })
    case 'in_flight':
      return errorResponse(409, 'idempotency_in_flight', 'A request with this Idempotency-Key is still being processed')
  }
}

function isValidKey(key: string): boolean {
  // The draft RECOMMENDS a UUID; requiring one keeps the key space
  // unguessable and bounds the column width.
  return /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i.test(key)
}
```

**Why 200 and not 201 on a replay.** §15.3.2 says 201 *"indicates that the request has been fulfilled and has resulted in one or more new resources being created."* On a replay, *this* request created nothing. Returning 201 twice tells a client that counts creations that two cards exist. 200 with the same body and the same `Location` is accurate: here is the resource, it already existed. The draft is looser — it says only to *"respond with the result of the previously completed operation"*, which some implementations read as replaying the original 201 verbatim; both are defensible, and the one thing that is not defensible is leaving it undocumented.

**The `Idempotency-Replayed` header is not standard.** It is a convenience for your own clients and your own monitoring, and it must be documented alongside the key policy or it is noise.

## Gotchas

**★ Symptom: every replay returns `undefined`, a null body, or a `TypeError` on destructuring.** Cause: `ON CONFLICT DO NOTHING` combined with `RETURNING` — the reference says *"Only rows that were successfully inserted or updated will be returned"*, and a `DO NOTHING` conflict inserts nothing. Fix: treat an empty result as a real outcome and read the existing row explicitly, as `createCardIdempotent` does. Do not switch to `DO UPDATE` to make the empty case disappear; that overwrites whatever happened to the card since.

**★ Symptom: duplicate titles stopped returning 409 and started silently succeeding with no card created.** Cause: `onConflictDoNothing()` was called with no `target`. The reference: *"For ON CONFLICT DO NOTHING, it is optional to specify a conflict_target; when omitted, conflicts with all usable constraints (and unique indexes) are handled."* So the title index was swallowed along with the key index. Fix: always name the arbiter:

```ts
.onConflictDoNothing({ target: [cards.boardId, cards.idempotencyKey] })
```

**★ Symptom: a client retries and gets a second card anyway.** Cause: the key was generated inside the retry loop, so each attempt sent a different one and the server saw unrelated requests. Fix: the key must be minted once, at the point the *user intent* is formed, and reused for every attempt of that intent — the same argument [ch15 · 04ea](../15-databases-apis-and-full-stack-patterns/04ea-external-effects-and-provider-idempotency.md) makes for job payloads. On a form submission, mint it when the form is rendered, not when the request is sent.

**★ Symptom: `INSERT ... ON CONFLICT` fails with a unique violation during a maintenance window, despite the conflict clause.** Cause: documented behaviour — *"While CREATE INDEX CONCURRENTLY or REINDEX CONCURRENTLY is running on a unique index, INSERT ... ON CONFLICT statements on the same table may unexpectedly fail with a unique violation."* Fix: nothing in the statement helps; the mapping in [05ca](05ca-mapping-sqlstate-to-status-codes.md) turns it into a coherent 409 rather than a 500, and index rebuilds on tables carrying `ON CONFLICT` traffic belong in a window where a brief conflict rate is acceptable.

**★ Symptom: two entry points create cards, and only the Route Handler is idempotent.** Cause: the key was read from an HTTP header inside the handler, and a Server Action has no header to read. Fix: `createCardIdempotent` takes the key as an argument, so the action supplies one too — minted when the form renders and submitted as a hidden field, which is also what makes a double-submitted form safe. Do not give the DAL function an optional key parameter that silently degrades; make it required so a non-idempotent call site is visible at the type level.

**★ Symptom: under load, a burst of retries returns 409 and clients give up permanently.** Cause: correct server behaviour for the `in_flight` case, but the client treated 409 as terminal, because a duplicate-title 409 *is* terminal. Fix: distinguish them in the envelope — `idempotency_in_flight` versus `duplicate_title` — and document that the first is retryable with backoff and the second is not. The status code alone cannot carry that difference, which is a good argument for the machine-readable `code` field in [ch7 · Designing the error envelope](../07-error-handling-loading-states-and-resilience/04b-designing-the-error-envelope.md).

**★ Symptom: a client sends a key, gets a 201, retries, and gets a 500 with no explanation.** Cause: the key column exists but the unique index was never created — a migration generated and not applied, or applied to a branch database. Without the index there is no arbiter, and `onConflictDoNothing({ target })` against a non-existent unique index is an error, not a no-op: the reference says of inference that *"If an attempt at inference is unsuccessful, an error is raised."* Fix: this is the SprintDesk milestone's seam 2 — assert applied migrations at deploy time rather than discovering them from a request.

## Interview questions

**★ Why is "the client should just retry" not an available answer for a failed POST?**
Because RFC 9110 forbids it in two directions. §9.2.2 says a client *"SHOULD NOT automatically retry a request with a non-idempotent method"* unless it has some way to know the semantics are actually idempotent or to detect the original was never applied, and it says a proxy *"MUST NOT"* retry one at all. That is not arbitrary: the intended effect of two identical POSTs to a create endpoint is two cards, so a retry is a semantic change, not a recovery. The spec's own escape clause names the fix — the client needs *"some means to know that the request semantics are actually idempotent, regardless of the method"* — and an idempotency key is that means. Once the server enforces the key, retrying becomes correct rather than reckless, and the client library that was going to retry anyway is now doing something safe.

**★ Walk through what `ON CONFLICT DO NOTHING ... RETURNING` returns on a replay, and why that is the most common bug in idempotent create code.**
It returns an empty result set. The `INSERT` reference is unambiguous — *"Only rows that were successfully inserted or updated will be returned"* — and a `DO NOTHING` conflict does neither, so there is nothing to return. The bug is common because the code reads correctly and passes every test: a suite that creates a card once always takes the insert path, and the replay path is only exercised by an actual retry, which is by definition a production event rather than a CI one. The symptom is then `undefined` flowing into a response builder, producing a `TypeError`, a null body, or a 500 — delivered to a client that was already in an uncertain state and will very likely retry again. The fix is to treat the empty result as a defined outcome and issue a second, explicit read.

**★ Should a replay return 201 or 200, and does it matter?**
200, and it matters to any client that counts. §15.3.2 defines 201 as indicating that the request *"has resulted in one or more new resources being created"*, and on a replay this request created nothing — the resource already existed. A client that increments a counter, appends to a list, or fires an analytics event on 201 will double-count if you replay the 201. 200 with the identical body and the identical `Location` header says the accurate thing: here is your resource, it is already there. The draft is looser and merely says to *"respond with the result of the previously completed operation"*, so replaying the original 201 is a defensible reading — what is not defensible is picking one and not documenting it, because a client cannot write correct handling for a status code it has to discover empirically.

**★ Why does the `in_flight` outcome deserve its own response rather than being folded into the replay path?**
Because the two states are genuinely different and only one of them is stable. A replay means the original completed and there is a definite answer to give. `in_flight` means the original is still running, so there is no answer yet, and any card you return would be a guess. Silently treating it as a replay would require inventing a row; silently treating it as a fresh create would produce a duplicate the moment the original commits. The draft's answer — a conflict response — is the only honest one, because it tells the client to ask again shortly, which is exactly what the situation calls for. It also tells you something operationally: a sustained rate of `in_flight` responses means your create path is slower than your clients' retry timeout, which is a latency problem wearing an idempotency costume.

**★ Why is `ON CONFLICT DO UPDATE` the wrong tool for a replay, given that it solves the empty-result problem?**
Because it changes the row, and a replay must not. The point of a replay is to hand back the result of an operation that already happened; `DO UPDATE` re-applies the request's values, so any change made to that card between the original request and the retry is silently reverted. If a colleague moved the card to `doing` and someone's flaky connection replays the create thirty seconds later, the card goes back to `todo` with no update event, no version bump anyone asked for, and no error. The empty result from `DO NOTHING` is not a problem to route around; it is the database correctly telling you that nothing happened, which is precisely the information a replay needs.
