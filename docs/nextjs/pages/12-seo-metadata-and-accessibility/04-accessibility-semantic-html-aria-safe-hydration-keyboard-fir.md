**Your page is rendered twice. Once visually, and once into the accessibility tree — a parallel structure the browser builds from your markup, in which every element has a name, a role and a state, and from which every screen reader, voice control system and switch device operates. Semantic HTML is not a style preference; it is the only way to produce that second rendering without hand-maintaining it. And the thing that surprises people arriving from a framework mindset is how little the framework does here: Next.js contributes exactly one runtime feature, its documentation page for it has not been reviewed since November 2024, and the one thing that page promises — automatic accessibility linting during a build — stopped being true when `next lint` was removed in 16.0.**

## The accessibility tree, and the criterion that defines it

WCAG's Level A criterion for interactive things is the whole model in one sentence:

> *"For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set; and notification of changes to these items is available to user agents, including assistive technologies."*
> — **4.1.2 Name, Role, Value (Level A)**

And its note, which is the entire argument for semantic HTML:

> *"standard HTML controls already meet this success criterion when used according to specification."*

A `<button>` has a role (button), a name (its text content), a state, keyboard activation on both Enter and Space, and a focus ring — for free, correct, on every platform. A `<div onClick>` has none of those and cannot be given all of them without writing and testing each one. The structural criterion is the same idea for non-interactive content:

> *"Information, structure, and relationships conveyed through presentation can be programmatically determined or are available in text."*
> — **1.3.1 Info and Relationships (Level A)**

"Conveyed through presentation" is the operative phrase. If a sighted user can tell that this is a group of related items because they are in a bordered box with a bold label, then that grouping must exist in the markup too — as a `<fieldset>` with a `<legend>`, a `<section>` with an accessible name, a list, a table with headers. CSS conveys nothing to the accessibility tree.

## What Next.js actually gives you — all of it

The architecture page describes exactly two things, and one of them is no longer true.

**1 · The route announcer.** Real, useful, and worth understanding precisely:

> *"The Next.js route announcer looks for the page name to announce by first inspecting `document.title`, then the `<h1>` element, and finally the URL pathname."*

A full page load is announced by the browser. A client-side transition is not — the URL changes and the DOM is replaced with no navigation event — so Next ships a live region that announces the new page's name. 🔴 **This makes `title` an accessibility API, not just an SEO field.** Everything in [01b](01b-the-title-algebra-and-the-viewport-export.md) about `title.template` and `title.default` is therefore also about what a screen-reader user hears on every in-app navigation, and a route whose title is the site name with no page-specific part announces the same words on every transition.

The documentation's own conclusion: *"For the most accessible user experience, ensure that each page in your application has a unique and descriptive title."* That aligns exactly with WCAG **2.4.2 Page Titled**: *"Web pages have titles that describe topic or purpose."*

⚠️ **The announcer announces; it does not move focus.** The architecture page describes announcement only and says nothing about focus management. This page does not claim it moves focus, and you should not assume it does — focus after navigation is treated as your responsibility in [04e](04e-keyboard-first-interactive-components.md).

**2 · Linting — and this is the stale half.** The architecture page (2024-11-06) states:

> *"By default, Next.js includes `eslint-plugin-jsx-a11y` to help catch accessibility issues early"*

and links the **Pages Router** ESLint page. The current ESLint reference (2026-08-25) describes `eslint-config-next` as `@next/eslint-plugin-next` plus recommended rule sets from `eslint-plugin-react` and `eslint-plugin-react-hooks` — **jsx-a11y is not in that list**, though the same page names it later as a plugin that can conflict if you configure it yourself.

🔴 **The two pages disagree, and this cannot be settled here** — `next` is not installed in this checkout, so there is nothing to inspect. What *is* settled, and matters more: **`next lint` was removed in 16.0 and `next build` no longer lints.** Whatever jsx-a11y coverage may or may not be bundled, nothing runs it during a build any more. The safe action is to wire `eslint-plugin-jsx-a11y` into your own flat config explicitly and run ESLint as its own CI step — the wiring is [13 · Linting after `next lint`](../13-testing-and-developer-experience/13-linting-after-next-lint.md).

Everything else on that page is a list of external resources. **That is the complete framework contribution.** The rest of this and the following four chunks is web platform, React and WCAG.

## Landmarks

Landmarks let a screen-reader user jump directly to a region instead of listening through the page. They come from elements, not from `className`:

```tsx
// app/layout.tsx
export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        <a href="#main" className="skip-link">
          Skip to main content
        </a>
        <header>
          <nav aria-label="Primary">{/* … */}</nav>
        </header>
        <main id="main">{children}</main>
        <footer>{/* … */}</footer>
      </body>
    </html>
  )
}
```

| Element | Landmark role | Rule |
|---|---|---|
| `<header>` (top level) | `banner` | Only when not nested in `<article>`/`<section>` |
| `<nav>` | `navigation` | Several are fine — **name each one** |
| `<main>` | `main` | 🔴 Exactly one per page |
| `<aside>` | `complementary` | Name it if there are several |
| `<footer>` (top level) | `contentinfo` | Same nesting rule as `<header>` |
| `<section>` | `region` — **only with an accessible name** | A `<section>` with no name is not a landmark at all |

That last row catches people constantly. `<section>` is not a semantic `<div>`; it becomes a landmark only when it has an accessible name, via `aria-label` or `aria-labelledby` pointing at its heading. Without one it contributes nothing, and a page built out of a dozen anonymous `<section>` elements has the same accessibility tree as a page of `<div>`s.

Two navigations therefore need distinguishing:

```tsx
<nav aria-label="Primary">…</nav>
<nav aria-label="Breadcrumb">…</nav>
```

## The skip link is a real requirement

> *"A mechanism is available to bypass blocks of content that are repeated on multiple web pages."*
> — **2.4.1 Bypass Blocks (Level A)**

A keyboard user landing on any page tabs through your whole header before reaching content — on every navigation. The skip link is the standard mechanism, and it must be **the first focusable element in the DOM** and **visible when focused**:

```css
.skip-link {
  position: absolute;
  left: -9999px;
  top: 0;
}

.skip-link:focus {
  left: 0;
  z-index: 100;
  padding: 0.75rem 1rem;
  background: var(--sd-surface);
  color: var(--sd-text);
}
```

🔴 **Do not hide it with `display: none` or `visibility: hidden`** — both remove it from the tab order, which removes the entire feature. Off-screen positioning keeps it focusable.

And it must land somewhere focusable. `<main id="main">` is not focusable by default, so in some browsers the focus does not move and the next Tab returns to the header. Add `tabIndex={-1}`:

```tsx
<main id="main" tabIndex={-1}>{children}</main>
```

which makes it programmatically focusable without adding it to the tab sequence — the `tabindex="-1"` semantics from [04e](04e-keyboard-first-interactive-components.md).

## Headings are a cross-component contract, and RSC makes that harder

> *"Headings and labels describe topic or purpose."*
> — **2.4.6 Headings and Labels (Level AA)**

Screen-reader users navigate by heading. The rules are ordinary: one `<h1>` per page describing the page, no skipped levels on the way down, and heading text that means something out of context — *"Details"* three times on one page is three useless landmarks in the heading list.

The composition problem is real and specific to component frameworks. A `<TaskCard>` that renders `<h3>` is correct on the board page and wrong when reused inside a dialog whose title is an `<h2>`, or on a detail page where it sits under an `<h1>`. Hard-coding the level puts a page-level constraint inside a leaf component.

```tsx
// components/task-card.tsx — level is a prop, with a sane default
type HeadingLevel = 2 | 3 | 4 | 5 | 6

export function TaskCard({
  task,
  headingLevel = 3,
}: {
  task: Task
  headingLevel?: HeadingLevel
}) {
  const Heading = `h${headingLevel}` as const

  return (
    <article className="task-card">
      <Heading className="task-card__title">{task.title}</Heading>
      <p>{task.summary}</p>
    </article>
  )
}
```

This works identically in a Server Component — it is a string tag name, not a hook — so it costs nothing at the RSC boundary. The alternative you may have seen, a React context carrying the current level, requires a Client Component and therefore drags the whole subtree across the boundary. **In an RSC codebase the prop is the correct answer** and the context is a trap.

## Gotchas

**★ You assumed `next build` was linting your JSX for accessibility.** `next lint` was removed in 16.0 and `next build` no longer lints; the architecture page that promises bundled `eslint-plugin-jsx-a11y` was last reviewed in 2024-11 and the current ESLint reference does not list it. Fix: add `eslint-plugin-jsx-a11y` to your flat config explicitly and run ESLint as its own CI step.

**★ Every route announces the same thing on navigation.** The route announcer reads `document.title` first, and a `title.default` with no page-specific part is identical everywhere. Fix: a real per-route `title`; this is the same fix as the SEO one and it is worth knowing it buys both.

**★ A page built entirely from `<section>` has no landmarks.** `<section>` is a `region` landmark **only** with an accessible name. Fix: `aria-labelledby` pointing at the section's heading, or use `<div>` and stop pretending.

**★ Two `<nav>` elements and a user cannot tell them apart.** Both announce as "navigation". Fix: `aria-label="Primary"` and `aria-label="Breadcrumb"`.

**★ The skip link does nothing when activated.** `<main>` is not focusable, so focus stays where it was and the next Tab goes back into the header. Fix: `tabIndex={-1}` on the target.

**★ The skip link is `display: none` until focus.** `display: none` and `visibility: hidden` remove it from the tab order, so it can never receive focus to become visible. Fix: position it off-screen and bring it back on `:focus`.

**★ A reusable card hard-codes `<h3>` and breaks the outline wherever it is reused.** Heading level is a page-level fact living in a leaf component. Fix: a `headingLevel` prop with a default; do **not** reach for context, which forces the subtree to become a Client Component.

**★ `<html lang>` is missing or wrong.** WCAG 3.1.1 — *"The default human language of each web page can be programmatically determined"* — and it changes pronunciation, not just metadata. Fix: set it in the root layout, and from the route param in a localised app ([03d](03d-localized-metadata-for-i18n-routes.md)).

## Interview questions

**★ What does Next.js actually do for accessibility, and what does its documentation claim that is no longer true?**
Exactly one runtime feature: a route announcer, because client-side transitions produce no navigation event for a screen reader to announce, and it picks the name from `document.title`, then the `<h1>`, then the pathname. That is it. The stale claim is linting: the architecture page, last reviewed in November 2024, says `eslint-plugin-jsx-a11y` is included by default and links the Pages Router ESLint page, while the current ESLint reference does not list it — and independently of who is right, `next lint` was removed in 16.0 and `next build` no longer lints, so nothing runs those rules during a build regardless. The correct posture is to treat accessibility linting as something you wire up yourself.

**★ Why is `title` an accessibility concern and not just an SEO one?**
Because the route announcer reads `document.title` first when deciding what to announce after a client-side transition. A site where every route resolves to the same title announces the same words on every navigation, which tells a screen-reader user that something changed but not what — arguably worse than silence, because it is noise that carries no information. It also maps directly onto WCAG 2.4.2, which requires titles that describe topic or purpose. So `title.template` and `title.default` are shared infrastructure between the two concerns, and getting them right pays twice.

**★ A designer's mock has a bordered box labelled "Assignees" containing three checkboxes. What must the markup contain that CSS cannot supply?**
The grouping itself. WCAG 1.3.1 requires that structure and relationships conveyed through presentation be programmatically determinable, and the border-plus-label is exactly such a presentation. That means `<fieldset>` with a `<legend>Assignees</legend>`, so a screen reader announces the group name when focus enters and each checkbox is understood as part of it. A `<div>` with a styled heading looks identical and conveys nothing — the visual grouping exists only for people who can see it.

**★ How do you handle heading levels in a component reused at different depths, and why is the obvious React answer wrong here?**
Take the level as a prop with a sensible default and build the tag name — `const Heading = \`h${level}\`` — because a heading level is a fact about the page's outline, not about the component. The obvious React answer is a context provider carrying the current depth, and it is wrong in an RSC codebase for a mechanical reason: consuming context requires a Client Component, so every card that reads the level becomes client code and drags its subtree across the boundary. The prop works identically in a Server Component and costs nothing.
