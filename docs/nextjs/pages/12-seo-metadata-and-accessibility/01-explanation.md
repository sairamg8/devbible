**Almost everything that goes wrong in this chapter goes wrong quietly, and for two different reasons. The metadata API is a small, sharp system with rules people do not expect: two mutually exclusive exports, root-to-leaf evaluation with a merge exactly **one level deep**, six tags it will never emit no matter what you pass, a `metadataBase` whose absence is a build error rather than a bad preview, and — since 15.2 — a dynamic route's metadata appended to the body *after* the UI, with a hard-coded list of HTML-limited bots that still get it blocking. Get one of those wrong and the page looks perfect in a browser while every link unfurl is broken. Accessibility fails for the opposite reason: nothing about it is subtle, and no tool can check the part that matters. An automated audit can tell you an `aria-label` is present; it cannot tell you the label is wrong, that focus went nowhere after the dialog closed, or that the control your keyboard user needs is a `<div>`. The chapter treats both halves the same way — name the mechanism, then name what has no signal.**

## 🔴 What this chapter corrects

Six claims in wide circulation are wrong at 16.3.4, each corrected with a verbatim source on the page that owns it:

| Claim you will meet | What the documentation or source says | Where |
|---|---|---|
| Metadata merges deeply down the route tree | The merge is **one level deep**, which is where almost every wrong social preview comes from | [1](01-static-and-dynamic-metadata-metadata-objects-generatemetadat.md) |
| `viewport` is a metadata field | It stopped being one in Next.js 14 — it is a **separate export**, it cannot stream, and its own reference example carries an accessibility trap | [2](01b-the-title-algebra-and-the-viewport-export.md) |
| Whatever tag you need, `other` will emit it | Six tags are **permanently refused** as design decisions, each with a documented replacement; resource hints go through ReactDOM instead | [3](01c-the-tags-the-metadata-api-will-not-emit.md) |
| Your Slack unfurl works because metadata is in the head | Since 15.2 a dynamic route's metadata is appended to the **body** after the UI; unfurls work because of a hard-coded `htmlLimitedBots` list | [5](01e-streaming-metadata-and-html-limited-bots.md) |
| A Lighthouse run will catch a streaming-metadata problem | 🔴 **It cannot.** `Chrome-Lighthouse` is in the default HTML-limited bot list, so Lighthouse always gets blocking metadata — settled from framework source at tag `v16.3.4` | [5](01e-streaming-metadata-and-html-limited-bots.md) |
| The `generateSitemaps` docs example is correct | 🔴 **It does not typecheck.** It does `id * 50000` after `const id = await props.id`, while the 16.0 version history calls `id` *"a promise that resolves to a `string`"* | [16](03c-splitting-a-sitemap-generatesitemaps-and-the-50000-url-rule.md) |

⚠️ **Also worth knowing, because the production checklist still says otherwise:** it advises *"Use the built-in `eslint-plugin-jsx-a11y` plugin"*, but **`next lint` was removed in 16 and `next build` no longer lints**, so those rules run only if you wired ESLint or Biome up yourself. Whether `eslint-config-next@16.3` still bundles the plugin is **unresolved** — the architecture page says yes, the current ESLint reference does not list it, and `next` is not installed here to probe. Pages [18](04-accessibility-semantic-html-aria-safe-hydration-keyboard-fir.md) and [24](04g-auditing-accessibility-and-what-no-tool-can-reach.md) both say so rather than picking a side.

## Phase gate

You are done with this chapter when you can take a route whose social preview is wrong and name, in order, the four places the failure could be — the one-level merge, a missing or wrong `metadataBase`, a tag the API refuses to emit, or streaming metadata reaching a client that is not on the HTML-limited bot list — and say which tool would show you each one. Then do the accessibility equivalent: given a component that passes an automated audit, name three ways it can still be unusable, and say what you would have to *do* rather than run to find them.

The common stopping point is a page that renders correctly in a browser. Almost every failure in the metadata half is invisible there by construction, and the entire accessibility half is invisible there by definition.
