**Everything the rest of this chapter relies on is absent here.** There is no `error.js` for a
Route Handler, no boundary to bubble to, no fallback UI, no `retry()` button, and no `digest` to
correlate with. A handler is a function that returns a `Response`; if it throws, the framework
produces a generic error response and your caller — which is usually another program, not a
person — receives something it was not designed to parse. That makes error handling in a handler
a matter of *design* rather than of placement: you decide the failure shape, you decide the
status, and nothing in the framework will decide it for you if you forget.

🔴 **One thing to be clear about up front: the `route.js` reference does not define an error
envelope format.** It shows a `try`/`catch` returning a 400 for a webhook and nothing more.
Everything beyond that — a response shape, a status mapping, a correlation id — is a decision the
framework leaves to you, and it is worked through in
[04b · Designing the error envelope](04b-designing-the-error-envelope.md) as **this book's
recommendation** rather than as a documented contract.

## What the reference does guarantee

Seven methods, and one behaviour worth knowing:

`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`.

> *"If `OPTIONS` is not defined, Next.js will automatically implement `OPTIONS` and set the
> appropriate Response `Allow` header depending on the other methods defined in the Route
> Handler."*

An unsupported method is therefore already handled for you at the discovery level — but only for
`OPTIONS`. A `DELETE` to a handler that exports only `GET` is not your code's problem to reject;
it never reaches your code.

The parameters:

- `request` is a `NextRequest`, *"an extension of the Web `Request` API"*, adding `cookies` and
  the parsed `nextUrl`.
- `context.params` is **a promise**, and has been since `v15.0.0-RC`. Awaiting it is not
  optional.
- `RouteContext<'/users/[id]'>` types the context from a route literal and is *"globally
  available"* after types are generated by `next dev`, `next build` or `next typegen` — no import
  needed.

```ts
// app/users/[id]/route.ts
import type { NextRequest } from 'next/server'

export async function GET(_req: NextRequest, ctx: RouteContext<'/users/[id]'>) {
  const { id } = await ctx.params
  return Response.json({ id })
}
```

## Headers are read-only once you are inside

> *"This `headers` instance is read-only. To set headers, you need to return a new `Response`
> with new `headers`."*

This is the handler-shaped version of the constraint that runs through the whole chapter: the
response is the only place a header can be set, so anything that wants to influence the response
must return one rather than mutate ambient state. The same is true for cookies — `cookies()` from
`next/headers` can `set` and `delete`, or you can return a `Set-Cookie` header on a `Response` you
construct.

## The one error shape the reference shows

It appears in the webhook example, and it is worth reading carefully because it is the only
error-handling guidance the page gives:

```ts
// app/api/route.ts
export async function POST(request: Request) {
  try {
    const text = await request.text()
    // Process the webhook payload
  } catch (error) {
    return new Response(`Webhook error: ${error.message}`, {
      status: 400,
    })
  }

  return new Response('Success!', {
    status: 200,
  })
}
```

Three observations, none of which the page states:

1. **It returns 400 for any failure in the `try`.** A malformed body and a database timeout
   produce the same status. For a webhook receiver that is often wrong in an expensive way —
   most webhook senders retry on 5xx and give up on 4xx, so classifying an outage as a client
   error silently discards the event.
2. **It puts `error.message` in the response body.** Fine for a first-party webhook, a leak in a
   public API — messages carry table names, file paths and connection strings.
3. **`error` is untyped in the `catch`.** Under TypeScript's `useUnknownInCatchVariables`
   (implied by `strict`), `error.message` does not compile without narrowing.

## Gotchas

### `error.message` in the `catch` does not compile
**Symptom.** `Property 'message' does not exist on type 'unknown'` on the exact code the
documentation shows.
**Cause.** The example is illustrative and predates, or ignores, `useUnknownInCatchVariables` —
which `strict` turns on. The caught value is `unknown`, and it genuinely can be anything: a
string, `undefined`, a rejected non-`Error`.
**Fix.** Narrow before reading, with a helper you can reuse.

```ts
export function messageOf(cause: unknown): string {
  if (cause instanceof Error) return cause.message
  if (typeof cause === 'string') return cause
  return 'Unknown error'
}

export async function POST(request: Request) {
  try {
    const text = await request.text()
    await processWebhook(text)
  } catch (cause) {
    return new Response(`Webhook error: ${messageOf(cause)}`, { status: 400 })
  }
  return new Response('Success!', { status: 200 })
}
```

### A 400 for an outage, so the sender stops retrying
**Symptom.** Webhook events go missing during a database incident and are never redelivered.
**Cause.** A blanket `catch` returned 400. Most senders treat 4xx as permanent and 5xx as
retriable, so the events were discarded rather than queued.
**Fix.** Classify. Return 400 only for a payload the sender could fix; return 5xx for anything on
your side.

```ts
export async function POST(request: Request) {
  const raw = await request.text()

  let event: WebhookEvent
  try {
    event = parseWebhook(raw) // signature + schema
  } catch {
    return new Response('Invalid payload', { status: 400 }) // sender's problem: permanent
  }

  try {
    await handleWebhook(event)
  } catch (cause) {
    console.error(cause)
    return new Response('Temporarily unavailable', { status: 503 }) // ours: please retry
  }

  return new Response('Success!', { status: 200 })
}
```

### Trying to set a header after work has started
**Symptom.** A `Cache-Control` or `x-request-id` set by mutating the `headers()` instance never
appears on the response.
**Cause.** *"This `headers` instance is read-only."* It describes the request, not the response.
**Fix.** Put the headers on the `Response` you return.

```ts
export async function GET() {
  const body = await buildReport()
  return Response.json(body, {
    status: 200,
    headers: { 'Cache-Control': 'private, max-age=60', 'x-request-id': crypto.randomUUID() },
  })
}
```

### `params` used without awaiting it
**Symptom.** `id` is `undefined`, or TypeScript complains that a `Promise` has no such property.
**Cause.** `context.params` became a promise in `v15.0.0-RC`.
**Fix.** `await` it — and use `RouteContext<'/route/[id]'>` so the shape is checked against the
real route rather than a hand-written type that can drift.

### Assuming a `GET` handler is cached
**Symptom.** A handler written against older material sets no cache headers and expects static
behaviour; every request hits the database.
**Cause.** *"The default caching for `GET` handlers was changed from static to dynamic"* in
`v15.0.0-RC`.
**Fix.** Opt in explicitly with the `revalidate` segment config when you want caching.

```ts
// app/posts/route.ts
export const revalidate = 60

export async function GET() {
  const data = await fetch('https://api.vercel.app/blog')
  const posts = await data.json()
  return Response.json(posts)
}
```

## Interview questions

**★ What catches an uncaught throw in a Route Handler?**
Nothing you control. There is no `error.js` for a handler, no boundary, no fallback UI and no
`retry()`; the framework returns a generic error response. Every meaningful error decision — the
status, the body, whether anything is logged — has to be made inside the handler.

**★ The documentation's webhook example returns 400 from a blanket `catch`. What is the risk?**
It maps every failure to a client error. Most webhook senders retry on 5xx and give up on 4xx, so
a database outage inside that `try` produces a 400 and the event is discarded rather than
redelivered. Classifying the parse failure separately from the processing failure is what makes
the retry behaviour correct.

**★ Why can't you set a response header from `headers()` inside a handler?**
Because that instance is read-only and describes the *request*. The reference is explicit: to set
headers you return a new `Response` with new headers. The response is the only place response
headers exist.

**★ What changed about `GET` handlers in `v15.0.0-RC`, and why does it matter for error
handling?**
Two things: `context.params` became a promise, and the default caching for `GET` handlers changed
from static to dynamic. The caching change matters because a handler written against older
guidance may assume its upstream call happens rarely; under dynamic-by-default it happens on
every request, so an upstream failure that used to be invisible is now on the hot path.

**★ If `OPTIONS` is not exported, what happens to a preflight request?**
Next.js implements it automatically and sets the `Allow` header based on the other methods the
handler defines. You only need to write `OPTIONS` yourself when the response must carry something
more than that — CORS headers beyond the defaults, for instance.
