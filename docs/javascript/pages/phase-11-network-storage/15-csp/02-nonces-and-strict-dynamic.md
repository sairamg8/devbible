Documentation-validated; **no timings**.

**A strict policy has to re-admit the scripts you actually wrote.** There are exactly two
mechanisms for that — a **nonce** (a per-response secret) and a **hash** (a fingerprint of
the code) — and one keyword, **`'strict-dynamic'`**, that lets trust flow onwards from them.

## Nonces

```http
Content-Security-Policy: script-src 'nonce-2726c7f26c'
```

```html
<script nonce="2726c7f26c">
  const inline = 1;
</script>
```

**The browser runs an inline script only if its `nonce` attribute matches the policy.** An
injected `<script>` cannot guess the value, so it does not run — even though it is on the
same page, in the same document, in the same position.

🔴 **Two rules, and violating either makes the nonce decorative:**

1. **It must be different on every HTTP response.**
2. **It must be unpredictable** — a CSPRNG value, not a counter, not a timestamp, not a
   build id.

**MDN draws the consequence explicitly: "the server cannot serve static HTML, because it must
insert a new nonce each time."** A nonce baked into a file the CDN caches is a public
constant, and any injected script can copy it out of the DOM.

```js
// the shape, on any server — a fresh value per request, in both places
const nonce = crypto.randomUUID();
res.setHeader("Content-Security-Policy", `script-src 'nonce-${nonce}'`);
res.send(renderHtml(nonce));
```

⚠️ **`nonce` applies to inline scripts, and can also authorise external ones** — putting the
attribute on `<script src>` is how a third-party tag is allowed without listing its domain.
What it cannot do is authorise an inline **event handler**; those are governed by
`script-src-attr` and need `'unsafe-hashes'` (below) or, better, `addEventListener`.

⚠️ **Reading the nonce back from the DOM is deliberately restricted.** Browsers hide the
attribute from `getAttribute("nonce")` for exactly the reason above; frameworks that need it
read `document.currentScript.nonce`, the property rather than the attribute.

## Hashes

```http
Content-Security-Policy: script-src 'sha256-B2yPHKaXnvFWtRChIbabYmUBFZdVfKKXHbWtWidDVF8='
```

**A hash authorises one exact script body**, which makes it the right tool when the HTML is
static and there is no server to inject anything.

🔴 **The hashing rules are unforgiving, and every mistake produces the same silent block:**

- **Do not include the `<script>` tags** — hash the content only.
- **"capitalization and whitespace matter, including leading or trailing whitespace"** — a
  prettier run, a changed indent or a trailing newline invalidates it.

**So a hash-based policy has to be generated by the build**, never maintained by hand. Any
manual copy is correct exactly once.

⚠️ **`sha384-` and `sha512-` are equally valid**, and for **external** scripts the hash in
the `integrity` attribute must also appear in the CSP header — that is where CSP and
[Subresource Integrity](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity)
meet.

### `'unsafe-hashes'` — for handlers you cannot refactor yet

**Hashes allow scripts and styles by their hash "but not event handlers".**
`'unsafe-hashes'` re-admits inline handlers whose bodies match a listed hash:

```http
Content-Security-Policy: script-src 'unsafe-hashes' 'sha256-{HASHED_EVENT_HANDLER}'
```

**Treat it as a migration crutch.** It is far better than `'unsafe-inline'` — only the exact
handler bodies you listed run — and far worse than deleting the handler. Every `onclick=`
removed is one fewer hash in the header.

## 🔴 `'strict-dynamic'` — what it actually does

**MDN's definition:** "The trust explicitly given to a script present in the markup by
accompanying it with a nonce or a hash shall be propagated to all scripts loaded by that root
script. At the same time, **any allowlist or source expressions such as `'self'` or
`'unsafe-inline'` will be ignored**."

```http
Content-Security-Policy: script-src 'strict-dynamic' 'nonce-R4nd0m' https://allowlisted.example.com/
```

**In that policy, `https://allowlisted.example.com/` does nothing.** A script from there
loads only if it carries the nonce or was inserted by an already-trusted script. Read that
as the point of the feature rather than a quirk: **it replaces "which domains do I trust" with
"which scripts did I start from".**

| Loaded by | Allowed? |
|---|---|
| markup, with the matching nonce | ✅ |
| markup, no nonce, from an allow-listed domain | ❌ — **the allow-list is ignored** |
| a trusted script, via `document.createElement("script")` + `appendChild` | ✅ trust propagates |
| a trusted script, via `document.write` or `innerHTML` | ❌ — parser-inserted, no propagation |

🔴 **That last row is the one that breaks real tag managers and older analytics snippets.**
Trust propagates through the DOM API, not through HTML parsing — so a loader that builds its
scripts with `innerHTML` fails under `'strict-dynamic'` and the same loader using
`createElement` works.

⚠️ **What you give up is honest and worth stating:** if a trusted script can be talked into
creating a script element from attacker-controlled input, `'strict-dynamic'` hands that
injected script the same trust. It narrows the attack surface to "your own scripts' DOM
sinks" — which is precisely what Trusted Types then addresses.

⚠️ **Older browsers that do not know `'strict-dynamic'` ignore the keyword and fall back to
the allow-list**, which is why policies often keep `https:` and `'unsafe-inline'` at the end:
modern engines ignore them because of `'strict-dynamic'`, and old ones use them. It looks
alarming in a header and is deliberate.

## The migration order that works

**Do it in this order, because each step makes the next one measurable:**

1. **Ship `Content-Security-Policy-Report-Only`** with the target policy and a reporting
   endpoint ([chunk 1](./01-what-a-policy-breaks.md)). Change nothing else.
2. **Fix what the reports show, category by category** — inline handlers to
   `addEventListener`, `javascript:` links to real handlers, string `setTimeout` to functions,
   runtime template compilation to an ahead-of-time build.
3. **Add nonces** to the inline scripts that must stay, generated per response.
4. **Add `'strict-dynamic'`** and delete the domain allow-list. Watch reports again — this is
   where `document.write`-based loaders surface.
5. **Promote to the enforcing header**, keeping report-only for the *next* tightening.
6. **Then `require-trusted-types-for 'script'`**, again report-only first.

🔴 **Never skip to step 5.** A policy shipped enforcing on an app that has not been through
step 2 breaks the page for every user at once, and the failure mode — script silently not
running — is one that monitoring built on that same script cannot report.

## Trusted Types, briefly

**CSP stops code you did not authorise from loading. Trusted Types stops your own authorised
code from turning a string into code.** It is the answer to DOM XSS, where "data crafted by
an attacker is passed to a browser API that executes that data as code".

```http
Content-Security-Policy: require-trusted-types-for 'script'
```

```js
const policy = trustedTypes.createPolicy("my-policy", {
  createHTML: (input) => DOMPurify.sanitize(input),
});

el.innerHTML = policy.createHTML(userInput);   // ✅
el.innerHTML = userInput;                      // ❌ TypeError, with the directive set
```

**With the directive set, "passing strings into injection sinks will result in a `TypeError`
exception"** — the three sink families being HTML (`innerHTML`, `document.write`), JavaScript
(`eval`, `HTMLScriptElement.text`) and script URLs (`HTMLScriptElement.src`).

⚠️ **It changes a silent vulnerability into a loud runtime error**, which is why it also
belongs behind report-only first. MDN records it as **Baseline 2026 — "Newly available. Since
February 2026, this feature works across the latest devices and browser versions"** — so
check your targets, and note it is available in workers.

The sanitising half of this story is
[Phase 9 · 06](../../phase-9-dom/06-sanitising-html/README.md); Trusted Types is the
enforcement that makes skipping it impossible.

## Gotchas

**Symptom → cause → fix.**

- **The nonce works in development and not in production** → the HTML is served from a cache
  or a static file, so the nonce is constant → generate per response, and mark that HTML
  uncacheable.
- **An injected script runs despite a nonce policy** → the nonce is predictable (a counter, a
  build id, a timestamp) → use a CSPRNG.
- **A hash-based policy breaks after a formatting change** → whitespace and capitalisation are
  part of the hash → generate hashes in the build, never by hand.
- **A hash is listed and the inline script still fails** → the `<script>` tags were included
  in the hashed content → hash the body only.
- **Hashes are listed but `onclick=` still blocked** → hashes do not cover event handlers →
  `addEventListener`, or `'unsafe-hashes'` as a temporary step.
- **A third-party tag stops loading after adding `'strict-dynamic'`** → the domain allow-list
  is now ignored → give its `<script>` the nonce, or let a trusted script insert it.
- **A tag manager loads nothing under `'strict-dynamic'`** → it injects scripts with
  `document.write` or `innerHTML`, which do not propagate trust → use a loader that uses
  `createElement`.
- **`innerHTML` suddenly throws `TypeError`** → `require-trusted-types-for 'script'` is set →
  pass a `TrustedHTML` from a policy.
- **The policy looks wrong because it still contains `'unsafe-inline'`** → intentional
  backwards compatibility; `'strict-dynamic'` makes modern browsers ignore it → leave it.

## Interview questions

**Why must a CSP nonce change on every response?** Because it is a secret shared between the
header and the markup for one page load. A constant nonce can be read out of the DOM or the
cached HTML by injected script, and the policy stops distinguishing your script from an
attacker's. It also means the HTML cannot be a cached static file.

**When is a hash the better choice than a nonce?** When the page is static and there is no
server to inject a fresh value per request — a fully static site or a prerendered SPA shell.
The cost is that the hash covers the exact bytes, whitespace included, so it must be
generated by the build.

**What does `'strict-dynamic'` do to a domain allow-list?** It ignores it entirely, along
with `'self'` and `'unsafe-inline'`. Trust comes only from a nonce or hash on a root script,
and propagates to scripts that root script creates through the DOM API.

**Why does a tag manager sometimes break under `'strict-dynamic'`?** Because trust propagates
through `createElement`/`appendChild`, not through parser-inserted markup — a loader using
`document.write` or `innerHTML` produces scripts with no inherited trust.

**How would you roll out a strict CSP on a large existing app?** Report-only first, fix the
reported categories (inline handlers, `javascript:` URLs, string timers, runtime template
compilation), add per-response nonces, then `'strict-dynamic'` and drop the allow-list, then
promote to enforcing — with report-only always running one step ahead.

**What do Trusted Types add on top of CSP?** CSP controls what may load and run; Trusted
Types control what your own trusted code may pass into DOM sinks, turning a silent DOM-XSS
into a `TypeError` unless the value came from a policy that sanitised it.
