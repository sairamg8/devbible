## What base64 is for

**Base64 encodes arbitrary bytes as 64 safe ASCII characters**, so binary data can travel
through a channel that only accepts text — a JSON field, a URL, an email body, a CSS
stylesheet, `localStorage`.

⚠️ **It costs about a third more space.** Three bytes become four characters, so base64
data is roughly 133% of the original. It is a transport workaround, not a compression or a
security measure — it is trivially reversible and encodes nothing secret.

## 🔴 Why `btoa` throws on `é`

```js
btoa("hello");    // ✅ "aGVsbG8="
btoa("héllo");    // 🔴 InvalidCharacterError
```

**`btoa` does not take a string of text. It takes a "binary string"** — a string in which
every character's code unit is in the range 0–255, each standing for one byte. `é` is code
point 233, which fits; but `"日"` at 26085 does not, and `btoa` throws a
`DOMException` rather than guessing what you meant.

🔴 **The bug in one sentence: `btoa` expects bytes, and a JavaScript string is not bytes.**
The missing step is the encoding from [chunk 1](./01-textencoder-and-textdecoder.md).

⚠️ **It survives testing because ASCII works.** English test data encodes fine; the first
accented name, emoji or non-Latin script in production is the failure.

## The correct pair

**Text → bytes → base64, and the exact reverse:**

```js
function toBase64(str) {
  const bytes = new TextEncoder().encode(str);      // ✅ step 1: text → bytes
  let binary = "";
  for (const b of bytes) binary += String.fromCharCode(b);
  return btoa(binary);                              // ✅ step 2: bytes → base64
}

function fromBase64(b64) {
  const binary = atob(b64);
  const bytes = Uint8Array.from(binary, (c) => c.charCodeAt(0));
  return new TextDecoder().decode(bytes);
}
```

⚠️ **Note the loop rather than `String.fromCharCode(...bytes)`.** Spreading a large byte
array exceeds the engine's argument limit and throws on exactly the big payloads you most
wanted to encode.

**For binary data you already hold as bytes**, only half of this is needed — there is no
text step at all:

```js
const b64 = btoa(String.fromCharCode(...new Uint8Array(smallBuffer)));   // ⚠️ small only
```

## The modern replacement

**Newer engines put base64 directly on `Uint8Array`, which removes the binary-string dance
entirely:**

```js
new TextEncoder().encode("héllo").toBase64();      // ✅ bytes → base64
Uint8Array.fromBase64(b64);                        // ✅ base64 → bytes
bytes.toBase64({ alphabet: "base64url" });         // ✅ the URL-safe variant
bytes.toHex();                                     // and hex, while we are here
```

🔴 **This is the right answer where it is available** — it operates on bytes, which is what
base64 is actually about, and it handles base64url natively. **Check your targets**; the
`btoa` pair above remains the compatible fallback.

## base64url — why JWTs look different

**Standard base64 uses `+` and `/`, and pads with `=`.** All three are awkward in a URL or
a filename, so **base64url** substitutes `-` for `+` and `_` for `/` and drops the padding.

```js
const toUrlSafe = (b64) => b64.replaceAll("+", "-").replaceAll("/", "_").replace(/=+$/, "");
const fromUrlSafe = (u) => u.replaceAll("-", "+").replaceAll("_", "/");
```

⚠️ **`atob` does not accept the URL-safe alphabet** — translate back first. This is exactly
why hand-decoding a JWT payload fails on some tokens and not others: the encoded JSON only
sometimes contains a `-` or `_`.

**Decoding a JWT payload is the standard worked example**, and worth being precise about:

```js
const payload = JSON.parse(fromBase64(fromUrlSafe(token.split(".")[1])));
```

🔴 **That reads the token; it does not verify it.** The signature is the only thing that
makes a JWT trustworthy, and verifying it belongs on the server. Client-side decoding is
for displaying an expiry or a username, never for an authorisation decision.

## Data URLs, and what to use instead

```js
const url = `data:image/png;base64,${b64}`;
```

**A data URL inlines the bytes into the URL itself** — useful for a tiny icon, a generated
image in a canvas export, or an asset that must survive without a network request.

⚠️ **It is usually the wrong tool for anything large.** The 33% growth applies, the string
sits in memory, and browsers impose their own limits. **For a `Blob` or a `File`, the
alternative is better in every way:**

```js
const url = URL.createObjectURL(blob);   // ✅ no copy, no growth
// … use it …
URL.revokeObjectURL(url);                // ✅ and it must be released
```

**`createObjectURL` hands out a reference to bytes the browser already holds**, so nothing
is encoded and nothing grows. The cost is that it leaks until revoked — which is the
trade, and it is the right one for anything but the smallest payloads. `Blob` and object
URLs are **Phase 11 · `Blob`, `File` and `FileReader`** *(not written yet)*.

## When base64 is the wrong answer

✅ **Reach for it when the channel is genuinely text-only** — a JSON string field, a URL
fragment, `localStorage`, an email attachment, an inline SVG or font.

🔴 **Do not reach for it for:**

- **Sending a file to a server.** `FormData` with the `File` sends the raw bytes; base64
  adds a third to the upload for nothing.
- **Storing binary in the browser.** IndexedDB stores `Blob`s and `ArrayBuffer`s directly
  ([21 · `structuredClone`](../21-structuredclone.md)); only `localStorage` forces text.
- **Obscuring anything.** It is an encoding, not encryption. A base64 string in client code
  is a plaintext string with extra steps.
- **Making a string "URL safe".** That is `encodeURIComponent`, which is a different job.

## Gotchas

**Symptom:** `InvalidCharacterError` from `btoa`
**Cause:** The string contains a character above code unit 255 — `btoa` takes bytes, not
text.
**Fix:** `TextEncoder` first, then `btoa` on the resulting binary string.

**Symptom:** It worked in testing and failed on a user's name
**Cause:** ASCII encodes fine; the first accented or non-Latin character does not.
**Fix:** The same — encode before you base64.

**Symptom:** Decoded text came back as mojibake
**Cause:** `atob` output was used as text directly, skipping the `TextDecoder` step.
**Fix:** `atob` → `Uint8Array` → `TextDecoder().decode(...)`.

**Symptom:** `Maximum call stack size exceeded` while encoding
**Cause:** `String.fromCharCode(...bytes)` spreads the whole array into arguments.
**Fix:** Loop, or use `Uint8Array.prototype.toBase64()`.

**Symptom:** `atob` threw on a JWT segment
**Cause:** It is base64**url** — `-` and `_` are not in the standard alphabet, and the
padding is stripped.
**Fix:** Translate the characters back, or decode with the `base64url` alphabet option.

**Symptom:** An upload was a third larger than the file
**Cause:** The file was base64-encoded into JSON.
**Fix:** `FormData` with the `File`, which sends raw bytes.

**Symptom:** A page held on to memory after showing generated images
**Cause:** Object URLs were created and never revoked — or huge data URLs were kept in
state.
**Fix:** `URL.revokeObjectURL` when done.

**Symptom:** A base64 value in client code was treated as hidden
**Cause:** It is an encoding, and reversible by anyone.
**Fix:** Nothing client-side hides anything; move the secret to the server.

## Interview questions

**★ Why does `btoa("héllo")` throw?**
Because `btoa` takes a *binary string* — every character must have a code unit in 0–255,
each representing one byte — and a JavaScript string is UTF-16 text, not bytes. The missing
step is encoding: `TextEncoder` to bytes first, then `btoa`. The bug hides in testing
because ASCII passes.

**★ How do you base64-encode a Unicode string correctly?**
`new TextEncoder().encode(str)` to get bytes, build a binary string from those bytes with a
loop (not a spread, which blows the argument limit on large inputs), then `btoa`. Reverse
with `atob` → `Uint8Array.from` → `TextDecoder().decode`. Where available,
`bytes.toBase64()` and `Uint8Array.fromBase64()` replace all of it.

**★ What is base64url, and why does a JWT need it?**
Base64 with `-` and `_` in place of `+` and `/` and no `=` padding, so the value is safe in
a URL or a filename. `atob` does not accept that alphabet, which is why hand-decoding a JWT
payload fails intermittently — only some payloads happen to contain the substituted
characters.

**★ When should you not use base64?**
Whenever the channel can carry bytes. Uploading a file through `FormData` sends raw bytes;
base64 in JSON adds about 33%. IndexedDB stores `Blob`s and buffers directly. And it hides
nothing — it is an encoding, not encryption.

**★ Data URL or object URL?**
Object URL for anything but the smallest payloads: `URL.createObjectURL` references bytes
the browser already holds, with no encoding and no size growth, at the cost of needing
`revokeObjectURL`. A data URL inlines and inflates the data, which is fine for a tiny icon
and wasteful for anything real.

**What does base64 cost?**
About a third more size — three bytes become four ASCII characters — plus the CPU of
encoding and decoding, and, for a data URL, the memory to hold the whole string.
