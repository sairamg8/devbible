<span className="db-tier t-know">Know</span>

> Verified: 2026-08-14 against **react 19.2.8**, from documentation — react.dev
> [`renderToStaticMarkup`](https://react.dev/reference/react-dom/server/renderToStaticMarkup)
> (description, parameters, returns, all three caveats and the Pitfall).
> No sandbox script backs this page; claims are cited, not measured.

**One function, one job: React as a template engine.**

> `renderToStaticMarkup` renders a non-interactive React tree to an HTML string.

It takes a `reactNode` and an optional options object whose only documented member is
`identifierPrefix` — *"A string prefix React uses for IDs generated by `useId`. Useful to avoid
conflicts when using multiple roots on the same page."* It returns *"An HTML string."*

```js
import { renderToStaticMarkup } from 'react-dom/server';

const html = renderToStaticMarkup(<EmailBody order={order} />);
```

That is the entire API. What makes it worth a topic is the one thing it deliberately does not
do.

## The distinguishing property: no hydration markers

Every other server renderer in this phase emits extra attributes and comment markers so
[`hydrateRoot`](04-hydrateroot.md) can match its render against the existing DOM. This one does
not, and the consequence is stated as a caveat:

> `renderToStaticMarkup` output cannot be hydrated.

React's Pitfall says the same from the intent side:

> This method renders **non-interactive HTML that cannot be hydrated.** This is useful if you
> want to use React as a simple static page generator, or if you're rendering completely static
> content like emails.
>
> Interactive apps should use `renderToString` on the server and `hydrateRoot` on the client.

🔴 **"Cannot be hydrated" is a property, not a limitation to route around.** The markers are what
make hydration possible; removing them is the point. The output is smaller and cleaner, and it is
inert.

## What it is for

Two cases, and the reference names both.

**Email.** HTML email has no JavaScript, is parsed by clients with idiosyncratic and often
ancient rules, and every byte of React's hydration bookkeeping is noise a mail client may or may
not tolerate. Composing an email body from components and rendering it to a string is exactly
this function's shape.

**A static page generator.** Pages with no interactivity at all — a receipt, a report, a
generated documentation page. Note the difference from
[topic 08 · Prerendering](08-prerendering/README.md): `prerender` produces static HTML for a
React app that will still hydrate and become interactive. `renderToStaticMarkup` produces HTML
for something that never will.

| You want | Use |
|---|---|
| HTML that becomes an interactive app | `renderToString` + `hydrateRoot`, or the streaming renderers |
| static HTML for an app that still hydrates | `prerender` / `prerenderToNodeStream` |
| HTML that will never run JavaScript | **`renderToStaticMarkup`** |

## The two caveats you can be caught by

### Suspense support is limited

> `renderToStaticMarkup` has limited Suspense support. If a component suspends,
> `renderToStaticMarkup` immediately sends its fallback as HTML.

**No waiting, no streaming, no second chance.** A boundary that suspends contributes its
`fallback` to the string and the render moves on — so an email template that awaits data
produces a spinner in an email, silently.

This is the same bail-out `renderToString` has, and the reason
[topic 08](08-prerendering/README.md)'s static renderers exist. If the content needs data, get
the data *before* you render:

```js
const order = await loadOrder(id);            // resolve first
const html = renderToStaticMarkup(<EmailBody order={order} />);   // then render
```

### It runs in the browser, and mostly should not

> `renderToStaticMarkup` works in the browser, but using it in the client code is not
> recommended. If you need to render a component to HTML in the browser, get the HTML by
> rendering it into a DOM node.

⚠️ **"Works" is what makes this a trap.** Nothing stops you importing it into client code and
using it to produce a string — for a `dangerouslySetInnerHTML`, a clipboard payload, a preview
pane. It is not what the function is for, it ships a server renderer into your bundle, and React
points at rendering into a DOM node instead.

## What is *not* in the output

Worth stating plainly, because the question comes up as "why is my HTML broken":

- **No hydration markers**, by design.
- **Nothing React adds for the client** — this is not a page, it is a fragment of HTML for
  whatever you paste it into. There is no doctype, no bootstrap script, and no expectation that
  the tree renders `<html>` — which is the opposite of the whole-document requirement the static
  and streaming renderers impose ([topic 08 · 02](08-prerendering/02-calling-them.md)).
- **No streaming.** It returns a string. For anything large enough for streaming to matter, you
  are in the wrong function.

⬜ The reference does not enumerate which attributes differ from `renderToString`'s output, and
this page does not guess. The documented, load-bearing difference is that the result cannot be
hydrated.

## Gotchas

**Symptom:** hydration fails or warns on markup produced by this function.
**Cause:** documented — *"`renderToStaticMarkup` output cannot be hydrated."*
**Fix:** use `renderToString` (with `hydrateRoot`) or a streaming renderer if the page needs to
become interactive.

**Symptom:** an email or generated page contains a loading spinner.
**Cause:** a component suspended, and *"`renderToStaticMarkup` immediately sends its fallback as
HTML."*
**Fix:** await the data before rendering; do not rely on Suspense here.

**Symptom:** the server bundle grew after adding it to client code.
**Cause:** it works in the browser, so nothing stopped you — but it is a `react-dom/server`
import.
**Fix:** render into a DOM node instead, as the reference recommends.

**Symptom:** `useId` values collide across two rendered fragments on one page.
**Cause:** two renders sharing an id space.
**Fix:** pass different `identifierPrefix` values — its documented purpose is *"to avoid
conflicts when using multiple roots on the same page."*

**Symptom:** the output has no `<html>` or doctype.
**Cause:** it renders the node you gave it and nothing more. That is not a bug and not the
whole-document contract of the streaming and static renderers.
**Fix:** wrap or template it yourself.

## Interview questions

**★ What makes `renderToStaticMarkup` different from `renderToString`?**
It emits no hydration markers, so its output *"cannot be hydrated"*. `renderToString` produces
HTML for a tree that `hydrateRoot` will take over; this produces HTML for something that will
never run React again.

**★ When would you actually reach for it?**
Email bodies and genuinely static generated pages — the two cases the reference names. Anything
interactive should use `renderToString` plus `hydrateRoot`, or the streaming renderers.

**★ What happens if a component suspends during `renderToStaticMarkup`?**
Its fallback is emitted as HTML immediately. There is no waiting and no streaming, so data has to
be resolved before you render rather than inside the tree.

**★ Can you use it in the browser?**
It works, and the reference says using it in client code is not recommended — render the
component into a DOM node and read the HTML from there instead.

**★ Why does it take `identifierPrefix`?**
Because `useId` still runs. If two independently rendered fragments end up on the same page,
distinct prefixes keep their generated ids from colliding.
