> Verified: 2026-08-14 against **react 19.2.8**, from documentation — react.dev
> [`hydrateRoot`](https://react.dev/reference/react-dom/client/hydrateRoot) — signature,
> parameters, all four options, returns and every caveat — and
> [`renderToPipeableStream`](https://react.dev/reference/react-dom/server/renderToPipeableStream)
> (`bootstrapScripts` and `identifierPrefix`).
> No sandbox script backs this page; claims are cited, not measured.

**Hydration is not "React skips the work because the HTML is already there."** React renders
your whole tree, in the browser, and *adopts* the existing DOM instead of creating it. The
DOM work is saved. The JavaScript work is not.

```js
const root = hydrateRoot(domNode, reactNode, options?);
```

> `domNode`: **A DOM element that was rendered as the root element on the server.**
>
> `reactNode`: **The "React node" used to render the existing HTML. This will usually be a
> piece of JSX like `<App />` which was rendered with a `ReactDOM Server` method such as
> `renderToPipeableStream(<App />)`.**

Note what the second parameter's description implies: **the same tree, on both sides.** The
API is shaped around the assumption that hydration reproduces a render that already happened
([topic 02](02-hydration-mismatches.md)).

## What it reuses and what it does not

| | |
|---|---|
| **Reused** | the DOM nodes themselves — elements, attributes, text |
| **Created fresh** | the fiber tree, component state, refs, event handling |
| **Run** | every component function, top to bottom |
| **Run after commit** | every effect |

🔴 **This is why hydration costs roughly a full render's worth of JavaScript.** The browser
downloads the bundle, executes it, calls every component, builds React's internal tree, and
runs the effects. The one thing it avoids is *creating and inserting DOM nodes*, which is
often not the expensive part.

So SSR's benefit is precise: the user **sees** content sooner. They can **interact** with it
no sooner than the bundle allows — which is why [topic 07](07-selective-hydration.md) exists,
and why [Phase 10](../phase-10-server-components/01-what-a-server-component-is/README.md)'s
"the code never ships" is a different and larger claim than anything SSR makes.

## The four options

> - `onCaughtError`: **Callback called when React catches an error in an Error Boundary.**
>   Called with the error caught by the Error Boundary, and an `errorInfo` object containing
>   the `componentStack`.
> - `onUncaughtError`: **Callback called when an error is thrown and not caught by an Error
>   Boundary.**
> - `onRecoverableError`: **Callback called when React automatically recovers from errors.**
>   … **Some recoverable errors may include the original error cause as `error.cause`.**
> - `identifierPrefix`: **A string prefix React uses for IDs generated by `useId`.** Useful
>   to avoid conflicts when using multiple roots on the same page. **Must be the same prefix
>   as used on the server.**

The three error callbacks are [topic 13](13-root-error-options.md)'s subject. Two things to
take now:

- **`onRecoverableError` is where hydration mismatches surface in production.** React
  recovered, the page looks fine, and this callback is the only place that says so
  ([topic 02](02-hydration-mismatches.md)). Wiring it to your error reporter is how you find
  out that a mismatch shipped.
- **`identifierPrefix` must match the server's.** `useId` generates ids used for
  `aria-labelledby`, `htmlFor` and similar; a prefix mismatch produces a hydration mismatch
  on every generated id at once — a confusing failure with a one-line cause.

## What it returns

> `hydrateRoot` returns an object with two methods: `render` and `unmount`.

`root.render(<App />)` after hydration is an ordinary client render — useful for a top-level
update — and `root.unmount()` tears the whole thing down.

## The caveats worth acting on

> **You'll likely have only one `hydrateRoot` call in your app. If you use a framework, it
> might do this call for you.**

Which is why most people never write it: a framework's client entry calls it, and
`bootstrapScripts` on the server side is what gets that script onto the page.

> **If your app is client-rendered with no HTML rendered already, using `hydrateRoot()` is
> not supported. Use `createRoot()` instead.**

Not "inefficient" — **unsupported**. Hydration needs something to adopt.

## `createRoot` vs `hydrateRoot`

| | `createRoot` | `hydrateRoot` |
|---|---|---|
| Expects existing HTML | no | **yes, and identical** |
| Creates DOM | yes | adopts it |
| Mismatch handling | n/a | warns; **no guarantee attributes are patched** |
| Wrong choice costs | throws away server HTML and re-renders | unsupported |

⚠️ **Using `createRoot` on server-rendered HTML "works"** — React clears the container and
renders from scratch. You lose everything SSR bought you, silently, and the only symptom is a
flash and a slower first interaction. It is worth checking which one your client entry calls.

## Hydration and Suspense

Hydration is not one atomic operation. A tree with `<Suspense>` boundaries hydrates in
pieces, and React can prioritise the boundary the user just interacted with — that is
selective hydration ([topic 07](07-selective-hydration.md)), and it is the reason boundary
placement affects *interactivity* and not only paint.

## Gotchas

**Symptom:** SSR added, and time-to-interactive did not improve.
**Cause:** hydration still runs every component and every effect in the browser.
**Fix:** expected. SSR improves what is *seen*, not when the bundle finishes.

**Symptom:** every `useId`-generated id mismatches.
**Cause:** `identifierPrefix` differs between server and client.
**Fix:** pass the same prefix to both.

**Symptom:** the server HTML flashes and is replaced.
**Cause:** the client entry calls `createRoot` on server-rendered markup.
**Fix:** `hydrateRoot`.

**Symptom:** `hydrateRoot` on an empty container behaves oddly.
**Cause:** explicitly unsupported.
**Fix:** `createRoot` for a client-rendered app.

**Symptom:** mismatches are known to happen in production and nobody sees them.
**Cause:** React recovered and nothing reported it.
**Fix:** wire `onRecoverableError` to your error reporter.

**Symptom:** two roots on one page collide on ids.
**Cause:** shared `useId` prefix.
**Fix:** distinct `identifierPrefix` per root — matched on the server for each.

## Interview questions

**★ What does hydration actually do?**
It renders your whole tree in the browser and adopts the existing DOM instead of creating it.
Component functions all run, React's internal tree is built fresh, state and refs are created,
event handling is attached and effects run. Only the DOM creation is saved — which is why
hydration costs roughly a full render's worth of JavaScript.

**★ So what does SSR buy?**
Earlier **paint**, not earlier **interactivity**. The user sees content before the bundle
arrives; they can interact with it no sooner than hydration completes. Reducing the
JavaScript itself is RSC's job, not SSR's.

**★ What is `identifierPrefix` for, and what breaks without it?**
It prefixes the ids `useId` generates, so multiple roots on one page do not collide — and it
**must be the same prefix on the server and the client**. Get it wrong and every generated id
mismatches at once, which looks like a catastrophic hydration failure and has a one-line
cause.

**★ Which option tells you about mismatches in production?**
`onRecoverableError` — React recovers from some hydration errors, so the page looks fine and
nothing else reports it. Wiring that callback to an error reporter is how a shipped mismatch
becomes visible instead of quietly attaching handlers to the wrong elements.

**What happens if you call `createRoot` on server-rendered HTML?**
It works, in the sense that the page renders — React clears the container and renders from
scratch, throwing away everything SSR produced. The symptom is a flash and a slower first
interaction, with no error. The reverse — `hydrateRoot` with no server HTML — is explicitly
unsupported.

**Is hydration all-or-nothing?**
No. With `<Suspense>` boundaries the tree hydrates in pieces, and React can prioritise the
boundary the user just interacted with. That is why boundary placement affects interactivity
and not just what paints first.
