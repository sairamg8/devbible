> Verified: 2026-08-14 against **react 19.2.8**, from documentation — react.dev
> [`useId`](https://react.dev/reference/react/useId) and the **React 19.2 release
> post** (1 Oct 2025).
> No sandbox script backs this page; claims are cited, not measured.

**Generating ids that match between the server render and the client render. It
exists for accessibility attributes, and the reference is unusually direct about the
two things it must not be used for.**

> `useId` is a React Hook for generating unique IDs that can be passed to
> **accessibility attributes.**

## The problem it solves

An `aria-describedby` or a `htmlFor` needs an id, and the id must be unique on the
page. A hand-written constant breaks the moment the component renders twice; a
counter or `Math.random()` breaks under server rendering, because the server and the
client generate different values and hydration mismatches.

`useId` produces a value tied to the component's position, so both renders agree:

```jsx
function PasswordField() {
  const passwordHintId = useId();
  return (
    <>
      <label>
        Password:
        <input type="password" aria-describedby={passwordHintId} />
      </label>
      <p id={passwordHintId}>
        The password should contain at least 18 characters
      </p>
    </>
  );
}
```

> `useId` returns a **unique ID string associated with this particular `useId` call
> in this particular component.**

## One call, several ids

Do not call it once per element — derive:

```jsx
function Form() {
  const id = useId();
  return (
    <form>
      <label htmlFor={id + '-firstName'}>First Name:</label>
      <input id={id + '-firstName'} type="text" />
      <label htmlFor={id + '-lastName'}>Last Name:</label>
      <input id={id + '-lastName'} type="text" />
    </form>
  );
}
```

One hook call, suffixed per field. Cheaper, and it keeps the related ids visibly
related.

## 🔴 The two prohibitions

> `useId` **should NOT be used to generate keys in a list.** Keys should be
> generated from your data.

Keys identify *which item this is* across renders
([Phase 3 · 14](../phase-3-state/14-state-in-lists.md)). An id generated by the
render cannot do that — it describes a position in the component tree, so it moves
with the position rather than with the item, which is precisely the failure mode
index keys have.

> `useId` **should NOT be used to generate cache keys** for `use()`. **The ID is
> stable when a component is mounted but may change during rendering.** Cache keys
> should be generated from your data.

The parenthetical is the interesting part and worth carrying: *stable when mounted,
may change during rendering*. So it is safe to hand to the DOM and unsafe to key
anything by.

Both prohibitions have the same root: **`useId` describes a place, not a thing.**
Anything that needs to identify a *thing* must come from your data.

## The other caveats

> `useId` is a Hook, so you can only call it **at the top level** of your component
> or your own Hooks. You can't call it inside loops or conditions.

> `useId` currently **cannot be used in async Server Components.**

> With server rendering, `useId` requires an **identical component tree on the
> server and the client.** If the trees don't match exactly, the generated IDs won't
> match.

The last one is the practical trap. Because the id derives from tree position, any
divergence between server and client output — a `typeof window` branch, a
locale-dependent conditional, a component rendered only after mount — shifts the
positions and produces ids that do not match, on top of the hydration mismatch you
already had.

## Multiple apps on one page

```jsx
const root = createRoot(document.getElementById('root'), {
  identifierPrefix: 'my-app-'
});
```

> Use `identifierPrefix` when rendering **multiple independent React applications on
> a single page** to prevent ID clashes.

For a server-rendered app the prefix goes to both sides and **must match**:

```jsx
// server
renderToPipeableStream(<App />, { identifierPrefix: 'react-app1' });

// client
hydrateRoot(document.getElementById('root'), <App />, { identifierPrefix: 'react-app1' });
```

A mismatch here reintroduces exactly the problem `useId` exists to solve.

## 🔴 The format is not a contract — and it changed in 19.2

The reference documents that `useId` returns a unique string and **nothing about
its shape**. That is not an omission; it is the contract. And 19.2 proves the point
— the release post lists:

> **`useId` prefix update** — Changed from `:r:` or `«r»` to `_r_` for View
> Transitions support.

A cosmetic-looking change that breaks anything depending on the old shape. The
reason is substantive: `:` and `«` are not valid in a CSS selector or a View
Transition name, so the generated ids could not be targeted.

Treat the value as **opaque**: do not parse it, do not assert on it in a snapshot
test, and do not build a selector from it by hand. Concatenating a suffix, as
above, is fine because it only appends.

## Gotchas

**Symptom:** hydration mismatch warnings around ids.
**Cause:** the server and client trees differ, so positions differ and the generated
ids differ.
**Fix:** make the trees identical. `useId` cannot paper over a tree that already
diverges.

**Symptom:** ids collide between two React apps on one page.
**Cause:** both roots generate from the same scheme.
**Fix:** `identifierPrefix` per root — and matching prefixes across server and
client if server-rendered.

**Symptom:** `useId` used as a list key and state attaches to the wrong row.
**Cause:** the id describes tree position, so it stays with the position while data
moves — the index-key failure
([Phase 3 · 14](../phase-3-state/14-state-in-lists.md)).
**Fix:** keys from data.

**Symptom:** a cache keyed by `useId` misses or returns the wrong entry.
**Cause:** documented — the id is stable while mounted but may change during
rendering.
**Fix:** derive cache keys from data.

**Symptom:** `useId` called inside a `map()`.
**Cause:** hook rules.
**Fix:** one call in the component, suffixed per item — or a component per item.

**Symptom:** a snapshot test breaks on a React upgrade.
**Cause:** the generated format was asserted on. It is undocumented and not a
contract — 19.2 changed it from `:r:` / `«r»` to `_r_`.
**Fix:** treat the value as opaque.

## Interview questions

**★ What is `useId` for, and what problem does it solve?**
Generating ids for accessibility attributes — `htmlFor`, `aria-describedby` — that
match between the server render and the client render. A constant breaks when the
component renders twice; a counter or random value breaks hydration because the two
renders disagree. `useId` derives from the component's position in the tree, so both
sides produce the same value.

**★ Why must you not use it for list keys?**
Because it identifies a *place*, not a *thing*. A key's job is to say which item
this is across renders, and an id tied to tree position stays with the position
while the data moves — the exact failure mode index keys have. The docs state
plainly that keys should be generated from your data.

**★ What does "stable when mounted but may change during rendering" rule out?**
Using it as a cache key, which the reference calls out specifically for `use()`.
Anything that must identify a value across time needs to come from the data.
Handing it to the DOM is fine, because by the time it reaches the DOM it is stable
for that mount.

**Why would `useId` produce mismatched ids under server rendering?**
Because it requires an identical component tree on both sides. Any divergence — a
`typeof window` branch, a component that only renders after mount — shifts positions
and therefore the generated ids. It is a symptom of a tree mismatch rather than a
bug in `useId`, and the fix is to make the trees agree.

**When do you need `identifierPrefix`?**
When more than one independent React application renders on the same page, to stop
their generated ids colliding. For a server-rendered app the prefix must be passed
to both the server renderer and `hydrateRoot`, and the two must match — otherwise
you have recreated the mismatch problem the hook exists to prevent.

**Should you generate one `useId` per element?**
No — call it once and suffix it, as the docs' two-field form does. It is fewer hook
calls and it keeps related ids visibly related. And treat the returned string as
opaque: the format is not documented and not a contract — React 19.2 changed it
from `:r:` / `«r»` to `_r_` so that generated ids are valid in CSS selectors and
View Transition names, which broke anything that had assumed the old shape.
