Covers all 17 topic rows of `docs/redis/syllabus/01-how-redis-works.md`: T01-01 to T01-06 phase 0 (how Redis runs), T01-07 to T01-12 phase 1 (keys, expiry, keyspace), T01-13 to T01-17 phase 2 (`redis-cli`).

### T01-02 · Single-threaded command execution — Master · 🔲 not written
- **Read this:** [Diagnosing latency issues](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/) · redis.io · the "Single threaded nature of Redis" section: a *mostly* single-threaded design, one request served at a time, requests served sequentially, multiplexing; background threads exist for slow disk I/O but do not change this (*read*) · covers our angle: **partial** — I/O threads (`io-threads`) are **not mentioned**; "commands are atomic" is implied, not stated · fetched 2026-10-12
- **Also good:** [Benchmarks](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/) · redis.io · "mostly, a single-threaded server" for command execution, though modern versions use threads for other things; not designed to use many cores (*read*) · fetched 2026-10-12
- **Beyond the docs:** [Why and How Single-Threaded Redis Is Fast and Handles Concurrent Connections](https://arpitbhayani.me/videos/why-and-how-single-threaded-redis-is-fast/) · Arpit Bhayani (Oct 14, 2022) · walks through epoll-style I/O multiplexing and the event loop, and shows two clients running `INCR` on one counter to explain why atomicity needs no lock, which the latency page only implies; it does not cover `io-threads` · fetched 2026-10-13 (*read*)
- **Our delta:** atomicity as a consequence of one-at-a-time execution, `INCR` needing no lock, and what I/O threads do and do not change. A primary page that explains `io-threads` is **not confirmed**; the [INFO](https://redis.io/docs/latest/commands/info/) page only lists a `threads` section for I/O thread information (*read*).
- *Checked, not chosen:* oneuptime.com and dev.to blog posts on the single-thread model (search snippets only, *not opened*).

### T01-03 · O(N) commands block everyone — Master · 🔲 not written
- **Read this:** [Diagnosing latency issues](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/) · redis.io · "Latency generated by slow commands": while a slow request runs all others wait; `SORT`, `LREM`, `SUNION` named; a very common cause is `KEYS` in production; check the Slow Log (*read*) · covers our angle: **partial** — `FLUSHALL`, big `LRANGE` and `SMEMBERS` are not named there · fetched 2026-10-12
- **Also good:** [KEYS](https://redis.io/docs/latest/commands/keys/) · redis.io · O(N); a 1-million-key database scanned in 40 ms on an entry-level laptop; "Use extreme care" in production; do not use in regular application code (*read*) · fetched 2026-10-12
- **Our delta:** the `FLUSHALL` / `SMEMBERS` / big `LRANGE` examples and the `UNLINK` / `SSCAN` remedies.

### T01-04 · The RESP protocol and round trips — Understand · 🔲 not written
- **Read this:** [Redis pipelining](https://redis.io/docs/latest/develop/using-commands/pipelining/) · redis.io · opens with request/response protocols and round-trip time (RTT); explains that the cost is socket I/O, `read()` and `write()` syscalls and context switches, which pipelining batches (*read*) · covers our angle: full for "the network, not Redis, is the latency" · fetched 2026-10-12
- **Also good:** [Redis serialization protocol specification](https://redis.io/docs/latest/develop/reference/protocol-spec/) · redis.io · a simple request-response protocol over TCP; RESP is a serialization format whose first byte sets the type; RESP2 is the standard, RESP3 is mostly a superset, opt-in via `HELLO` (*read*) · fetched 2026-10-12

### T01-05 · Redis is not durable by default — Master · 🔲 not written
- **Read this:** [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/) · redis.io · RDB snapshots at intervals, AOF logging every write with fsync policies, no persistence at all ("sometimes used when caching"), or RDB + AOF (*read*) · covers our angle: **partial** — it says "By default Redis saves snapshots" to `dump.rdb` (*read*), but the default `save` thresholds are **not confirmed** on this page, and it does not frame the data-loss window · fetched 2026-10-12
- **Also good:** [Diagnosing latency issues](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/) · redis.io · a ranked durability-versus-latency list from AOF `always` down to RDB (*read*) · fetched 2026-10-12
- **Beyond the docs:** [Redis persistence demystified](https://oldblog.antirez.com/post/redis-persistence-demystified.html) · antirez weblog (Salvatore Sanfilippo per the site copyright; the page shows "26 March 12") · opens "there is no Redis feature that is as misunderstood as its persistence"; walks RDB, the AOF log and rewrite, and the three `appendfsync` modes against what PostgreSQL and InnoDB guarantee, which frames the data-loss window the docs do not · fetched 2026-10-13 (*read*)
- **Our delta:** what you may therefore store in Redis, and the default configuration, to be checked on a running 8.x instance.

## Phase 1 — Keys, expiry and the keyspace

### T01-07 · Key naming as a schema — Master · 🔲 not written

### T01-08 · TTL and expiry — Master · 🔲 not written
- **Read this (1/2):** [EXPIRE](https://redis.io/docs/latest/commands/expire/) · redis.io · setting a timeout; keys expire by wall-clock time, so moving the system clock forward expires them at once (*read*) · covers our angle: **partial** — `SET … EX` is **not covered** here; see the `SET` page under Also good · fetched 2026-10-12
- **Read this (2/2):** [TTL](https://redis.io/docs/latest/commands/ttl/) · redis.io · returns -2 if the key does not exist and -1 if it exists with no expire (*read*) · covers our angle: full for the missing-versus-non-expiring pair · fetched 2026-10-12
- **Also good:** [PERSIST](https://redis.io/docs/latest/commands/persist/) · redis.io · turns a volatile key into a persistent one (*read*) · [SET](https://redis.io/docs/latest/commands/set/) · the `EX`, `PX`, `EXAT`, `PXAT` and `KEEPTTL` options (*read*) · fetched 2026-10-12

### T01-09 · How expiry actually happens — Understand · 🔲 not written
- **Read this:** [Diagnosing latency issues](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/) · redis.io · "Latency generated by expires": a lazy way on access plus an active cycle every 100 ms (10 times a second) sampling 20 keys by default and repeating if more than 25% were expired; many keys expiring in the same second can block the server (*read*) · covers our angle: full — it gives the numbers · fetched 2026-10-12
- **Also good:** [EXPIRE](https://redis.io/docs/latest/commands/expire/) · redis.io · "How Redis expires keys": a passive way on access, an active way that tests a few keys at random, because some keys are never read again (*read*) · fetched 2026-10-12

### T01-10 · `SCAN` instead of `KEYS` — Master · 🔲 not written
- **Read this:** [SCAN](https://redis.io/docs/latest/commands/scan/) · redis.io · cursor-based iteration; the SCAN family gives only limited guarantees because the collection can change; a full iteration returns every element present from start to end; syntax shows `MATCH`, `COUNT`, `TYPE` (*read*) · covers our angle: full · fetched 2026-10-12
- **Also good:** [Redis CLI](https://redis.io/docs/latest/develop/tools/cli/) · redis.io · the `--scan` option, which lists keys with `SCAN` and accepts a pattern (*read*) · fetched 2026-10-12
- **Beyond the docs:** [Making sense of Redis' SCAN cursor](https://engineering.q42.nl/redis-scan-cursor/) · Q42 Engineering, Herman Banken (15 Jul 2019) · explains with a bit-prefix example why the reversed-bit cursor survives the hash table doubling, which the command page only promises; it does not discuss why duplicates appear · fetched 2026-10-13 (*read*)
- **Our delta:** the duplicates-may-appear rule and a worked loop in node-redis and ioredis.

### T01-11 · Key existence, deletion and `UNLINK` — Understand · 🔲 not written
- **Read this:** [UNLINK](https://redis.io/docs/latest/commands/unlink/) · redis.io · O(1) per key for the call, then O(N) memory reclaim in a different thread, N being the number of allocations (*read*) · covers our angle: full for why unlinking a huge key differs from deleting it · fetched 2026-10-12
- **Also good:** [Keys and values](https://redis.io/docs/latest/develop/using-commands/keyspace/) · redis.io · `EXISTS` returns 1 or 0, `DEL` deletes a key of any type (*read*) · fetched 2026-10-12

### T01-12 · Keyspace notifications — Know · 🔲 not written
- **Read this:** [Redis keyspace notifications](https://redis.io/docs/latest/develop/pubsub/keyspace-notifications/) · redis.io · delivered over Pub/Sub, which is "fire and forget" so events during a disconnect are lost; disabled by default, enabled with `notify-keyspace-events`; a `redis-cli` recipe to watch the events (*read*) · covers our angle: full · fetched 2026-10-12
