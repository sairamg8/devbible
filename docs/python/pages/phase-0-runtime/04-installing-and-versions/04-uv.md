**`uv` collapses layers 1 and 2 of [the previous chunk](03-installations-managers-environments.md)
into one tool: it downloads interpreters, records which one a project wants in a
file you commit, and fetches a missing one automatically the first time you run
anything. The reason to learn its resolution order rather than just its commands
is that "automatically" is doing a lot of work in that sentence — uv will
silently use a system interpreter, a managed one, a pre-release or a
free-threaded build depending on rules that are written down and are not
obvious.**

## Managed versus system, which is the distinction everything else rests on

> *"To distinguish between these two types of Python installations, uv refers to
> Python versions it installs as managed Python installations and all other
> Python installations as system Python installations."*

And a note that catches people who arrive from pyenv:

> *"uv does not distinguish between Python versions installed by the operating
> system vs those installed and managed by other tools. For example, if a Python
> installation is managed with pyenv, it would still be considered a system
> Python version in uv."*

So "system" in uv's vocabulary means "not installed by uv" — including your
distro's, Homebrew's, and pyenv's. That single definition explains most
surprising selections.

## Installing an interpreter

```bash
uv python install 3.14          # latest patch of 3.14
uv python install 3.14.7        # an exact patch
uv python install '>=3.12,<3.13'  # anything satisfying a specifier
uv python install 3.13 3.14     # several at once
uv python install pypy          # a different implementation
```

Two facts about this that matter operationally.

**You often do not need it at all.** The docs are explicit: *"By default, Python
versions are automatically downloaded as needed without using uv python
install."* Running `uv run` in a project whose `.python-version` names a version
you do not have will fetch it.

**The available set is frozen per uv release:**

> *"The available Python versions are frozen for each uv release. To install new
> Python versions, you may need upgrade uv."*

That is the answer to "uv says 3.15 does not exist" a week after 3.15 ships:
upgrade uv, not Python.

Installed executables land on your `PATH` — on Unix, `~/.local/bin`, as
`python3.14`. uv will only overwrite an executable it manages itself, and needs
`--force` otherwise. The unversioned `python` and `python3` names are **not**
created unless you ask:

```bash
uv python install 3.14 --default   # also creates `python` and `python3` (experimental)
uv python update-shell             # add ~/.local/bin to PATH if it is missing
```

## Pinning a version: `.python-version`

```bash
uv python pin 3.14          # writes .python-version in the current directory
uv python pin --global 3.14 # writes it in the user configuration directory
```

> *"The .python-version file can be used to create a default Python version
> request. uv searches for a .python-version file in the working directory and
> each of its parents. If none is found, uv will check the user-level
> configuration directory. Any of the request formats described above can be
> used, though use of a version number is recommended for interoperability with
> other tools."*

Two boundaries on that search that are easy to trip over:

> *"uv will not search for .python-version files beyond project or workspace
> boundaries (except the user configuration directory)."*

and discovery can be switched off entirely with `--no-config`.

The interoperability note is the reason to write `3.14` rather than
`cpython-3.14.7-linux-x86_64-gnu` in that file: **pyenv reads the same filename**
with different syntax rules, so a plain version number is the only form both
tools understand. A repository shared between a uv user and a pyenv user works
if and only if the file stays simple.

## What a version request may look like

Almost every uv command takes `--python`, and it accepts far more than a number:

```text
3, 3.12, 3.12.3                       a version
>=3.12,<3.13                          a specifier
3.13t, 3.12.0d                        a version plus a short variant
3.13+freethreaded, 3.14+gil           a version plus a named variant
cpython, cp, pypy, pp, graalpy, gp    an implementation
cpython@3.12, cp312, cpython>=3.12    implementation plus version
/opt/homebrew/bin/python3             an explicit executable path
```

The variant suffixes are the ones worth memorising: `t` is free-threaded, `d` is
a debug build, and `+gil` explicitly demands the GIL-enabled build.

## Running things

```bash
uv venv                       # create .venv using the resolved interpreter
uv venv --python 3.11.6       # ...or a specific one, downloading it if needed
uv run app.py                 # run inside the project environment
uv run --python 3.15 pytest   # run under a different interpreter for one command
```

The docs describe the download behaviour on `uv venv --python 3.11.6` plainly:
*"uv will ensure that Python 3.11.6 is available — downloading and installing it
if necessary — then create the virtual environment with it."*

For project commands, uv also respects your packaging metadata: *"uv will
respect Python requirements defined in requires-python in the pyproject.toml
file during project command invocations. The first Python version that is
compatible with the requirement will be used, unless a version is otherwise
requested."* Note **first compatible**, not newest — which is why an explicit
`.python-version` is worth having even when `requires-python` is set.

## Where the interpreters come from

uv does not build from source. It ships pre-built distributions:

> *"As Python does not publish official distributable CPython binaries, uv
> instead uses pre-built distributions from the Astral python-build-standalone
> project."*

and gives the reasoning against the alternative:

> *"The uv Python distributions are self-contained, highly-portable, and
> performant. While Python can be built from source, as in tools like pyenv,
> doing so requires preinstalled system dependencies, and creating optimized,
> performant builds (e.g., with PGO and LTO enabled) is very slow."*

That is the substantive difference from pyenv, and it cuts both ways — the docs
add that *"These distributions have some behavior quirks, generally as a
consequence of portability"* and link a quirks page. A standalone build is not
byte-for-byte the interpreter your distro would have compiled, and in rare cases
(unusual linking, embedding, some system-integration scenarios) that shows.

How uv decides *which* of the interpreters it can see to use — and how it treats
pre-releases, free-threaded builds and patch upgrades — is
[the next chunk](05-uv-resolution-and-variants.md).

## Gotchas

**Symptom:** `uv python install 3.15` says the version is unknown days after it was released
**Cause:** *"The available Python versions are frozen for each uv release"* — uv ships a list, and a new CPython release is not in an older uv
**Fix:** upgrade uv first. This also applies to new patch releases, so a stale uv silently keeps you on an older patch

**Symptom:** `python` is not found after `uv python install`
**Cause:** uv installs versioned executables (`python3.14`) by default; the unversioned names need the experimental `--default` flag, and `~/.local/bin` may not be on `PATH`
**Fix:** `uv python update-shell`, then a new shell. Or stop needing a global `python` at all and use `uv run`, which is the tool's intended shape

**Symptom:** a `.python-version` file written by uv breaks a pyenv user on the same repository
**Cause:** uv accepts request formats — implementation names, specifiers, variants — that pyenv does not understand
**Fix:** keep a plain version number in the committed file, exactly as the uv docs recommend for interoperability, and put anything more specific in a uv-only setting

**Symptom:** `.python-version` in a parent directory is ignored
**Cause:** uv stops the upward search at a project or workspace boundary; only the user configuration directory is consulted beyond that
**Fix:** put the file inside the project or workspace, or use `uv python pin --global` deliberately for a machine-wide default

**Symptom:** `requires-python = ">=3.11"` and uv used 3.11 when 3.14 was installed
**Cause:** for project commands uv uses *"the first Python version that is compatible with the requirement"*, not the newest one
**Fix:** commit a `.python-version` alongside `requires-python`. The metadata expresses what your package supports; the pin expresses what you develop and test on, and those are different statements

**Symptom:** CI downloads an interpreter on every job and nobody intended it to
**Cause:** automatic downloads are on by default — *"By default, Python versions are automatically downloaded as needed without using uv python install"*
**Fix:** set `python-downloads = "manual"` or pass `--no-python-downloads` in CI, and install the interpreter as an explicit, cacheable step so the job fails loudly rather than fetching quietly

**Symptom:** an embedding or system-integration scenario behaves differently under a uv-installed interpreter
**Cause:** uv ships python-build-standalone distributions, and the docs note these *"have some behavior quirks, generally as a consequence of portability"*
**Fix:** read the linked quirks page before assuming a bug is in your code. For the rare cases where a distro-compiled interpreter is genuinely required, that is what a distro or a source build is for

**Symptom:** `uv python install --force` was needed to replace an executable
**Cause:** uv refuses to overwrite an executable it does not manage — *"uv will only overwrite an existing executable if it is managed by uv"*
**Fix:** that refusal is protecting a `python3.12` some other tool owns. Find out what put it there before forcing past it

## Interview questions

**★ What does `uv` actually do that `pip` and `venv` do not?**
It manages the interpreter as well as the packages. `uv python install` fetches
pre-built CPython distributions, `uv python pin` records the choice in
`.python-version`, and `uv run` will download a missing interpreter and create
the environment before running your command. That merges the version-manager
layer and the environment layer into one tool with one resolution order, which
is why "which Python is this" becomes a question with a single authoritative
answer — `uv python find`.

**★ Why does uv download pre-built interpreters instead of building from source like pyenv?**
Because building well is slow and requires system dependencies. The docs say
that producing optimised builds with PGO and LTO is very slow and needs
preinstalled build dependencies, so uv ships portable pre-built distributions
from the python-build-standalone project instead. The trade-off is stated in the
same docs: those distributions have some behaviour quirks as a consequence of
being portable, so they are not identical to a distro-compiled interpreter.

**What does uv mean by a "system" Python?**
Anything uv did not install itself — including your distribution's interpreter,
Homebrew's, and anything installed by pyenv. The docs call that out explicitly,
because people coming from pyenv expect their pyenv versions to count as
managed, and in uv's vocabulary they do not.

**How does `.python-version` interact between uv and pyenv?**
Both read the same filename, but uv accepts a much richer syntax — specifiers,
implementation names, variant suffixes — that pyenv cannot parse. The uv docs
recommend a plain version number in the file for interoperability, and on a
shared repository that recommendation is effectively a requirement.

**What is the difference between `requires-python` and `.python-version`?**
`requires-python` in `pyproject.toml` is a *range* declaring which interpreters
your package supports, and installers enforce it against consumers.
`.python-version` is a *single* version request declaring which interpreter this
working copy develops and tests against. uv reads both, and for project commands
it takes the first version compatible with `requires-python` unless something
more specific asks otherwise — which is exactly why committing the pin as well
removes the ambiguity.

**Do you still need `uv python install` if `uv run` downloads interpreters automatically?**
Not for correctness, but usually yes for control. Automatic downloads are
convenient on a laptop and undesirable in CI, where an unpinned implicit fetch
turns into a network dependency in every job and a silent version drift when the
uv version changes. Making the install an explicit, cacheable step turns that
into a visible failure instead of a slow surprise.
