> Target: **CPython 3.14**.

**Once the launch-mode entry from [chunk 2](02-sys-path.md) is in place, four
more stages fill in the rest of `sys.path`: `PYTHONPATH`, the standard library,
site-packages, and whatever the `.pth` files in site-packages decide to add or
execute. Every one of them is global to an interpreter rather than local to a
project, and every one of them can silently outrank the package you think you
installed. This is where "the venv is broken" bugs actually live.**

## Stage 2 — `PYTHONPATH`

> *"Augment the default search path for module files. The format is the same as
> the shell's `PATH`: one or more directory pathnames separated by `os.pathsep`
> (e.g. colons on Unix or semicolons on Windows). Non-existent directories are
> silently ignored."*

> *"In addition to normal directories, individual `PYTHONPATH` entries may refer
> to zipfiles containing pure Python modules (in either source or compiled form).
> Extension modules cannot be imported from zipfiles."*

Two properties make `PYTHONPATH` a bad default tool. It is silent — a typo in a
directory name produces no warning, because *"non-existent directories are
silently ignored"*. And it is global; the `sys.path` documentation itself warns:

> *"`PYTHONPATH` will affect all installed Python versions/environments. Be wary
> of setting this in your shell profile or global environment variables. The
> `site` module offers more nuanced techniques as mentioned below."*

A `PYTHONPATH` exported in `.bashrc` is a machine-wide monkeypatch of every
Python you will ever run, including the one inside a virtual environment, and it
sits *ahead of* the standard library and site-packages. It is the single most
common cause of "this venv has the wrong version of a package".

The legitimate uses are narrow: a one-shot `PYTHONPATH=. python -m tool` in a
Makefile, a container image that sets it explicitly for one entrypoint, and
`PYTHONPATH=src` for a project that has not yet been made installable. Everything
else wants an editable install.

## Stages 3–5 — the interpreter's own directories, and site-packages

`prefix` and `exec_prefix` give you the standard library. `site` then adds the
per-installation package directories. The `site` docs describe the construction:

> *"It starts by constructing up to four directories from a head and a tail part.
> For the head part, it uses `sys.prefix` and `sys.exec_prefix`; empty heads are
> skipped. For the tail part, it uses the empty string and then
> `lib/site-packages` (on Windows) or `lib/pythonX.Y[t]/site-packages` (on Unix
> and macOS). (The optional suffix "t" indicates the free-threaded build, and is
> appended if `"t"` is present in the `sys.abiflags` constant.) For each of the
> distinct head-tail combinations, it sees if it refers to an existing directory,
> and if so, adds it to `sys.path` and also inspects the newly added path for
> configuration files."*

The free-threaded suffix is new enough to catch people out: on a 3.14t build the
site-packages directory is `lib/python3.14t/site-packages`, a *different*
directory from the GIL build's. Two interpreters of the same version do not share
installed packages.

`sys.prefix` is also what a virtual environment moves. The `sys.path`
documentation:

> *"If `PYTHONHOME` is not set, and a `pyvenv.cfg` file is found alongside the
> main executable, or in its parent directory, `sys.prefix` and `sys.exec_prefix`
> get set to the directory containing `pyvenv.cfg`, otherwise they are set to the
> same value as `sys.base_prefix` and `sys.base_exec_prefix`, respectively."*

and, as a 3.14 change:

> *"Changed in version 3.14: `sys.prefix` and `sys.exec_prefix` are now set to the
> `pyvenv.cfg` directory during the path initialization. This was previously done
> by `site`, therefore affected by `-S`."*

That is a real behavioural change to know: on 3.14, `python -S` inside a venv
still has venv-correct `sys.prefix` and `sys.exec_prefix`; on 3.13 and earlier it
did not. `-S` still suppresses site-packages itself.

Whether a venv can see the base installation's packages is one line of config:

> *"When running under a virtual environment, the `pyvenv.cfg` file in
> `sys.prefix` is checked for site-specific configurations. If the
> `include-system-site-packages` key exists and is set to `true`
> (case-insensitive), the system-level prefixes will be searched for
> site-packages, otherwise they won't."*

Also: *"`PYTHONHOME` overrides the `pyvenv.cfg` detection."* A stale `PYTHONHOME`
in the environment defeats every virtual environment on the machine.

## `.pth` files — how an editable install actually works

Any `*.pth` file in a site-packages directory adds lines to `sys.path`:

> *"A path configuration file is a file whose name has the form `name.pth` and
> exists in one of the four directories mentioned above; its contents are
> additional items (one per line) to be added to `sys.path`. Non-existing items
> are never added to `sys.path`, and no check is made that the item refers to a
> directory rather than a file. No item is added to `sys.path` more than once.
> Blank lines and lines beginning with `#` are skipped. Lines starting with
> `import` (followed by space or tab) are executed."*

Ordering is alphabetical by filename, and the docs give a worked example ending:

> *"…the `bar` directory precedes the `foo` directory because `bar.pth` comes
> alphabetically before `foo.pth`…"*

That last clause of the first quote — **lines starting with `import` are
executed** — is the mechanism behind editable installs, coverage startup hooks,
and `.pth`-based import hooks. It is also arbitrary code running before your
first line does, in every process started by that interpreter. The docs are
uneasy about it themselves:

> *"An executable line in a `.pth` file is run at every Python startup,
> regardless of whether a particular module is actually going to be used. Its
> impact should thus be kept to a minimum. The primary intended purpose of
> executable lines is to make the corresponding module(s) importable (load 3rd
> party import hooks, adjust `PATH` etc). Any other initialization is supposed to
> be done upon a module's actual import, if and when it happens. Limiting a code
> chunk to a single line is a deliberate measure to discourage putting anything
> more complex here."*

Practical reading: when a project imports fine but you cannot find the directory
on any obvious path, `ls` the site-packages for `*.pth` and read them. That is
where the editable install of your own package is hiding, and it is why an
editable install survives a `cd` while a `PYTHONPATH` hack does not.

## `site` also adds a user site-packages directory

Beyond the prefix-derived directories, `site` adds a per-user one. Its status is
exposed as a tri-state:

> *"Flag showing the status of the user site-packages directory. `True` means
> that it is enabled and was added to `sys.path`. `False` means that it was
> disabled by user request (with `-s` or `PYTHONNOUSERSITE`). `None` means it was
> disabled for security reasons (mismatch between user or group id and effective
> id) or by an administrator."*

That `None` case is worth knowing before you meet it: under `sudo`, under a
setuid wrapper, or under some container user mappings, the user site directory
silently disappears from `sys.path`, and a package installed with
`pip install --user` stops being importable with no message at all.

## Adding a directory the supported way

If a program genuinely must extend the search path at startup, `site` provides
the function that also processes the target's `.pth` files:

> *"Add a directory to `sys.path` and process its `.pth` files. Typically used in
> `sitecustomize` or `usercustomize`."*

```python
import site
site.addsitedir("/opt/company/pylibs")   # also reads /opt/company/pylibs/*.pth
```

A bare `sys.path.append(...)` does not process `.pth` files, which is why it
sometimes "half works" against a directory that was populated by an installer.

## `sitecustomize` and `usercustomize`

After the path manipulations, `site` tries to import `sitecustomize` and then
`usercustomize`. Both are ordinary modules on the path, both run before your
code, and both are invisible from your project. They are a legitimate deployment
tool and an excellent place for a bug to hide: when two machines with identical
requirements files behave differently at import time and the `.pth` files match,
these two modules are the next thing to check.

## Gotchas

**Symptom:** a virtual environment is active but `import requests` finds the system copy
**Cause:** `PYTHONPATH` from a shell profile sits ahead of site-packages in the ordering, or `PYTHONHOME` is set and overrides `pyvenv.cfg` detection entirely
**Fix:** `env | grep PYTHON` first, always. Unset both; if a path really must be added for one command, prefix it on that command rather than exporting it

**Symptom:** a directory added to `PYTHONPATH` has no effect and no error
**Cause:** documented — *"Non-existent directories are silently ignored"*. A typo, a relative path evaluated from the wrong cwd, or a Windows/Unix separator mix-up all fail silently
**Fix:** check `sys.path` from inside the process rather than trusting the environment variable

**Symptom:** two Python 3.14 interpreters on the same machine do not share installed packages
**Cause:** one is a free-threaded build; its site-packages tail is `lib/python3.14t/site-packages`, a different directory
**Fix:** expected behaviour. Install into each build separately, and never assume `python3.14` and `python3.14t` are interchangeable

**Symptom:** a package imports successfully but nothing in the project put it on the path
**Cause:** a `.pth` file in site-packages — typically an editable install — added the source directory, or executed an `import` line that did
**Fix:** read the `.pth` files. They are plain text, and they are the only part of `sys.path` construction that is per-project rather than per-interpreter

**Symptom:** a `.pth`-based tool (coverage, an import hook, a profiler) runs even in processes that never use it
**Cause:** the docs state an executable line *"is run at every Python startup, regardless of whether a particular module is actually going to be used"*
**Fix:** this is by design; if the startup cost matters, remove the distribution rather than trying to make the line conditional

**Symptom:** `sys.path` contains a `.zip` entry for a file that does not exist
**Cause:** documented — *"the expected zip archive location is added to the module search path even if the archive does not exist"*
**Fix:** nothing to fix. It is a normal part of stage 3 and not evidence of a broken installation

**Symptom:** a C extension inside a zipped distribution fails to import
**Cause:** *"Extension modules cannot be imported from zipfiles"*
**Fix:** ship the extension unzipped, or use a packaging tool that unpacks binaries to a cache directory at startup

**Symptom:** `pip install --user` succeeds and the package is not importable
**Cause:** the user site directory was disabled — `site.ENABLE_USER_SITE` is `False` (via `-s`/`PYTHONNOUSERSITE`) or `None`, which the docs attribute to a uid/gid mismatch or an administrator
**Fix:** check `site.ENABLE_USER_SITE`. Under `sudo` or a container user mapping the `None` case is normal and silent; install into a virtual environment instead

**Symptom:** `sys.path.append("/opt/libs")` makes some packages importable and not others
**Cause:** a plain append does not process that directory's `.pth` files, so anything that relied on one is still missing
**Fix:** `site.addsitedir("/opt/libs")`, which the docs describe as adding the directory *and* processing its `.pth` files

**Symptom:** two `.pth` files disagree about which version of a directory wins
**Cause:** they are processed in alphabetical order of filename, so `__editable__foo.pth` and `zz-legacy.pth` are resolved by their names, not by intent
**Fix:** do not depend on `.pth` ordering. If two source trees claim the same package name, remove one

**Symptom:** identical `requirements.txt` on two machines, different import-time behaviour, and the `.pth` files match
**Cause:** a `sitecustomize` or `usercustomize` module on one machine — both are imported by `site` before your code runs and neither is visible from your project
**Fix:** check for them explicitly. They are ordinary importable modules, so `importlib.util.find_spec("sitecustomize")` answers the question

**Symptom:** a venv unexpectedly sees the system's installed packages
**Cause:** `include-system-site-packages = true` in the venv's `pyvenv.cfg`
**Fix:** recreate the venv without `--system-site-packages`. Read `pyvenv.cfg`; it is three or four lines of plain text and it is the venv's entire definition

## Interview questions

**★ Someone reports that a virtual environment "isn't working" — the wrong package
version is imported. How do you diagnose it?**
Check the environment first (`PYTHONPATH`, `PYTHONHOME`), because both sit ahead
of or override the venv. Then print `sys.prefix`, `sys.base_prefix` and
`sys.path` from inside the failing process — if `sys.prefix` equals
`sys.base_prefix`, the venv was never activated for that process at all. Then
print the offending module's `__file__` to see which copy actually loaded. The
answer is almost always an exported `PYTHONPATH`, a `pyvenv.cfg` with
`include-system-site-packages = true`, or the wrong interpreter on `PATH`.

**★ What is a `.pth` file and why should you care?**
A plain-text file in site-packages whose lines are appended to `sys.path`, and
whose lines beginning with `import ` are *executed* at every interpreter startup.
It is how editable installs make a source tree importable and how tools like
coverage hook themselves in before your code runs. You care because it is the one
part of the search path that is invisible from your project's own files: when an
import resolves to somewhere unexpected and nothing in the environment explains
it, a `.pth` file usually does.

**Does a virtual environment change `sys.path` or `sys.prefix`?**
Both, and the causal order matters. Finding `pyvenv.cfg` next to the executable
sets `sys.prefix` and `sys.exec_prefix` to the venv, while `sys.base_prefix` keeps
pointing at the base installation; `site` then builds site-packages paths from the
new prefix. On 3.14 the prefix assignment moved out of `site` into path
initialisation, so it now happens even under `-S`.

**Why is exporting `PYTHONPATH` in your shell profile a bad idea?**
Because it applies to every interpreter on the machine, including ones inside
virtual environments, and it is inserted ahead of both the standard library and
site-packages. So it silently overrides a pinned dependency for every project you
work on, and its failures are silent in the other direction too — a non-existent
directory in it is ignored without a warning. Per-command or per-container is the
only defensible scope.

**What is the difference between `sys.path.append` and `site.addsitedir`?**
`append` adds one string to a list. `addsitedir` adds the directory *and*
processes every `.pth` file inside it, which is how a directory populated by an
installer becomes fully usable. If you are wiring up a vendored library
directory, `addsitedir` is the one that behaves the way the installer expected.

**Why can a package installed with `pip install --user` be invisible?**
Because the user site-packages directory is conditional. The docs describe three
states for `site.ENABLE_USER_SITE`: enabled, disabled by user request through
`-s` or `PYTHONNOUSERSITE`, and disabled *"for security reasons (mismatch between
user or group id and effective id) or by an administrator"*. The third case is
silent and is exactly what happens under `sudo`, which is why "install with sudo
pip --user" produces a package nobody can import.

**What runs before the first line of your program?**
The `.pth` files' `import` lines, then `sitecustomize`, then `usercustomize` — all
during `site` processing, in every process started by that interpreter. This is
the answer to "how does coverage measure code that runs at import time" and also
to "why is startup slow on this machine and not that one".
