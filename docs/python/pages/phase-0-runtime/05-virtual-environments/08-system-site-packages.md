> [`venv` docs](https://docs.python.org/3.14/library/venv.html)
> (`--system-site-packages`, `include-system-site-packages`),
> [`site`](https://docs.python.org/3.14/library/site.html) (the `pyvenv.cfg`
> check and `ENABLE_USER_SITE`), [PEP 405](https://peps.python.org/pep-0405/)
> (default isolation) and [PEP 668](https://peps.python.org/pep-0668/).
> Version spine: **Python 3.14.7**.

**There is exactly one good reason to create an environment with
`--system-site-packages`: a module you need exists only as a system-installed,
non-pip-installable package — distro-built GTK or Qt bindings, a hardware
vendor's SDK, a board-support library. Every other use is a shortcut, and the
price is that the environment's importable contents now depend on the state of
the machine, which is the precise property environments were invented to remove.
The leaks are subtle, they mostly show up in other people's checkouts, and two of
them corrupt your requirements file rather than crashing.**

## What the flag does

> *"--system-site-packages: Give the virtual environment access to the system
> site-packages directory."*

Mechanically it writes one key, and `site` reads it at every startup:

> *"When running under a virtual environment, the `pyvenv.cfg` file in
> `sys.prefix` is checked for site-specific configurations. If the
> `include-system-site-packages` key exists and is set to `true`
> (case-insensitive), the system-level prefixes will be searched for
> site-packages; otherwise they won't."*

Because it is a documented key read at startup, it is also a **switch you can
flip after creation**:

```ini
# .venv/pyvenv.cfg
include-system-site-packages = true
```

No re-creation needed, and it takes effect on the next interpreter start. That
makes it easy to test whether a mysterious import is coming from the base
installation: set it to `false`, run again, and see what breaks.

The default is off, and PEP 405 states the intent: *"By default, a virtual
environment is entirely isolated from the system-level site-packages
directories."*

## The precedence question

The environment's own `site-packages` is added from `sys.prefix`; the base
installation's are added because of this key. In practice imports resolve to the
environment's copy when both contain the same package. The `site` documentation
describes *which* directories are searched but does not state their relative
order in `sys.path` for this case, so if the answer matters to you — you are
debugging a version mismatch and need to know which copy wins — do not reason
about it, look:

```python
import sys, importlib.util
print(*sys.path, sep="\n")
print(importlib.util.find_spec("numpy").origin)   # the file actually chosen
```

`find_spec(...).origin` is the only answer that cannot be argued with.

## The legitimate cases

- **Distro-built GUI bindings.** `gi` (PyGObject), `PyQt5`/`PyQt6` as shipped by
  the distribution, `python3-tk`. These are built against the system's C
  libraries and versions; the PyPI equivalents may not exist for your platform or
  may not match the installed toolkit.
- **Vendor and board packages.** Single-board-computer GPIO and camera stacks,
  proprietary drivers, ML accelerator runtimes that ship as system packages.
- **A system build of a numeric library** linked against a vendor BLAS or MPI
  that the wheel on PyPI is not.
- **A distro-shipped tool's plugin**, which must be importable by the distro's
  copy of that tool — the case PEP 668 explicitly preserves.

What all four have in common: the package cannot be installed with pip, on this
machine, in a form that works. If pip *can* install it, install it.

## The leaks

**1 · `pip freeze` writes a requirements file that is wrong.** With system site
packages visible, `pip freeze` reports what it can see, which now includes the
base installation's packages. Commit that and every other developer gets a
requirements file demanding packages your machine happened to have.

```bash
.venv/bin/python -m pip freeze --local > requirements.txt   # --local excludes the base's
```

`--local` is the mitigation. A lockfile is the cure.

**2 · pip considers a requirement already satisfied.** If the base installation
has `requests 2.28` and your project asks for `requests`, an installer that can
see the base copy may conclude the requirement is met and install nothing into
the environment. The environment then works on your machine and fails on a clean
one, and `pip list` inside the environment does not obviously show the problem.
Use `pip install --ignore-installed` to force a local copy, or stop using the
flag.

**3 · You cannot uninstall or upgrade what you can see.** The base packages are
owned by the OS package manager and, under PEP 668, protected from pip
modification. Trying to upgrade one from inside the environment either fails or —
worse, if someone reaches for `--break-system-packages` — succeeds and damages
the system installation. The correct move is always to install a *local* copy
into the environment, not to modify the base.

**4 · The environment is no longer reproducible.** Two machines with the same
`requirements.txt` and different distro package sets produce different
environments. This is the whole cost, stated plainly, and it is why the flag
should never appear in a Dockerfile or CI config as a convenience.

**5 · The base installation changes underneath you.** An `apt upgrade` can change
the version of a package your project imports, without touching your project, your
environment or your requirements file. Nothing records that dependency.

**6 · Diagnostics get harder.** "Where did this module come from?" now has three
answers instead of two, and the third one changes when the machine is patched.

## What the flag does *not* control

`--system-site-packages` governs the base installation's `site-packages` only. It
does not touch:

- **`PYTHONPATH`**, which prepends its entries regardless and is a leak of its own
  ([`../08-imports/02b-pythonpath-and-site-packages.md`](../08-imports/02b-pythonpath-and-site-packages.md)).
- **`sys.path[0]`** — the script directory or cwd, which precedes everything and
  is the source of the classic shadowing bugs
  ([`../08-imports/03-shadowing-the-stdlib.md`](../08-imports/03-shadowing-the-stdlib.md)).
- **`.pth` files** inside the environment's own `site-packages`, which can add
  arbitrary directories.
- **The per-user site-packages directory.** The `site` documentation records that
  `ENABLE_USER_SITE` is `False` when *"disabled by user request (with `-s` or
  `PYTHONNOUSERSITE`)"* and `None` when disabled for security reasons, but it does
  not state what happens inside a virtual environment. I could not confirm that
  behaviour from the documentation. If it matters to you, check the interpreter
  you actually use — `python -m site` prints `ENABLE_USER_SITE` and the paths —
  and force the outcome you want with `-s` or `PYTHONNOUSERSITE=1`.

## Gotchas

**Symptom:** a colleague's checkout fails to install a requirements file you generated, complaining about distro-specific packages
**Cause:** `pip freeze` in an environment with system site packages visible reports the base installation's packages too
**Fix:** `pip freeze --local`, and prefer a lockfile that records only declared dependencies. Better still, do not create the environment with the flag

**Symptom:** `pip install requests` inside the environment reports the requirement already satisfied, and `.venv/lib/.../site-packages` has no `requests`
**Cause:** the installer can see the base installation's copy and treats the requirement as met
**Fix:** `pip install --ignore-installed requests` to force a local copy, or recreate the environment without `--system-site-packages`

**Symptom:** upgrading a package inside the environment fails with a permissions error or the externally-managed error
**Cause:** the copy being upgraded belongs to the base installation, which is protected by PEP 668 and owned by the OS package manager
**Fix:** never upgrade the base copy from inside an environment. Install a local copy instead. If you find yourself reaching for `--break-system-packages`, the flag was the wrong choice two steps earlier

**Symptom:** an application works in development and fails in a container with an import error for a module nobody declared
**Cause:** development used `--system-site-packages` and the module came from the machine; the container has no such packages
**Fix:** create environments without the flag so that a missing declaration fails immediately and locally, where it is cheap to fix

**Symptom:** you need one system package and now have hundreds of unrelated ones visible
**Cause:** the flag is all-or-nothing — there is no per-package form
**Fix:** if you can locate the single package, a targeted `.pth` file in the environment's `site-packages` containing just that directory is a narrower tool. It is still machine-dependent, but the surface is one path rather than an entire installation

**Symptom:** an environment behaves differently after an unrelated `apt upgrade`
**Cause:** a visible base package changed version. Nothing in your project recorded that it was a dependency
**Fix:** move the dependency into the environment if it is pip-installable. If it genuinely is not, record the system package and its version in your deployment documentation — it is a dependency whether or not a file says so

**Symptom:** someone enables the flag to "reuse" already-downloaded packages and speed up environment creation
**Cause:** treating the flag as a cache
**Fix:** use a real wheel cache. pip and uv both cache downloads and built wheels globally; recreating an environment from a warm cache is fast without any coupling to the machine's installed packages

**Symptom:** turning the flag off on an existing environment does not seem to change anything
**Cause:** the key is read at interpreter startup — long-running processes, an editor's language server, a Jupyter kernel all keep the old behaviour until restarted
**Fix:** restart everything that has an interpreter open, then re-check with `importlib.util.find_spec`

## Interview questions

**★ What does `--system-site-packages` actually change?**
It sets `include-system-site-packages = true` in `pyvenv.cfg`. At startup, `site`
reads that key and, if it is true, also searches the base installation's
site-packages directories. It is a single documented boolean, readable and
editable after creation, and it takes effect on the next interpreter start.

**★ When is using it defensible?**
When the environment needs a module that cannot be pip-installed on that machine:
distro-built GUI toolkit bindings, vendor or board-support packages, a system
build of a numeric library linked against hardware-specific components, or a
plugin that must be importable by a distro-shipped tool. Convenience, speed and
"we already have it installed" are not on the list.

**★ What breaks when you use it casually?**
Reproducibility, first: the environment's contents become a function of the
machine. Then `pip freeze` starts reporting base packages into your requirements
file; installers may consider requirements already satisfied and skip installing
into the environment; base packages cannot be upgraded or removed from inside the
environment because they belong to the OS; and an unrelated system upgrade can
change your application's behaviour with no change to your project.

**★ How would you find out which copy of a package an import is resolving to?**
`importlib.util.find_spec("pkg").origin` — it reports the file the import system
would actually load, which settles the question regardless of how many
site-packages directories are on `sys.path`. Printing `sys.path` shows you the
candidates; `find_spec` shows you the winner.

**★ Does the flag protect you from `PYTHONPATH`?**
No. It only controls whether the base installation's site-packages directories
are searched. `PYTHONPATH` entries, the script directory at `sys.path[0]`, `.pth`
files inside the environment and (depending on the interpreter's configuration)
the user site-packages directory all still contribute, and several of them come
*earlier* in the search order than the environment's own packages.
