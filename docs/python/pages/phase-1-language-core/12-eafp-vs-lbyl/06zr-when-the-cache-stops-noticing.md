> Verified: 2026-09-10 against the Python 3.14 reference — [Cached bytecode invalidation](https://docs.python.org/3.14/reference/import.html#pyc-invalidation),
> [`--check-hash-based-pycs`](https://docs.python.org/3.14/using/cmdline.html#cmdoption-check-hash-based-pycs),
> [`compileall`](https://docs.python.org/3.14/library/compileall.html) (`--invalidation-mode`, `-f`),
> [`sys.dont_write_bytecode`](https://docs.python.org/3.14/library/sys.html#sys.dont_write_bytecode).
> Target: **Python 3.14**. Documentation-validated; **no sandbox run**.

**The previous four chunks were all about *which* file the interpreter opens. This one is
about whether it bothers to ask if that file is still true. Every `.pyc` was written in one of
three invalidation modes, the mode is a property of the file rather than of the interpreter,
and one of the three is documented to skip validation entirely: *"For unchecked hash-based
`.pyc` files, Python simply assumes the cache file is valid if it exists."* That is a
different failure from everything so far. There is no import error and no recompile — the
program runs happily, executing code you edited hours ago and never deployed. The `-O` symptom
from [06m](06m-the-guard-the-platform-deletes.md) arrives this way too: an `assert` added to
the source is simply not in the process.**

## The three modes, and which one you get by default

The import reference is short and complete enough to quote nearly whole:

> *"Before Python loads cached bytecode from a `.pyc` file, it checks whether the cache is
> up-to-date with the source `.py` file. By default, Python does this by storing the source's
> last-modified timestamp and size in the cache file when writing it. At runtime, the import
> system then validates the cache file by checking the stored metadata in the cache file
> against the source's metadata."*

> *"Python also supports 'hash-based' cache files, which store a hash of the source file's
> contents rather than its metadata. There are two variants of hash-based `.pyc` files:
> checked and unchecked. For checked hash-based `.pyc` files, Python validates the cache file
> by hashing the source file and comparing the resulting hash with the hash in the cache file.
> If a checked hash-based cache file is found to be invalid, Python regenerates it and writes
> a new checked hash-based cache file. For unchecked hash-based `.pyc` files, Python simply
> assumes the cache file is valid if it exists."*

| Mode | Validated against | Failure it has |
|---|---|---|
| `timestamp` (default) | stored mtime **and** size vs the source's | two versions with the same mtime and size are indistinguishable |
| `checked-hash` | a hash of the source's contents | none of consequence; it re-hashes on every import |
| `unchecked-hash` | **nothing** — *"assumes the cache file is valid if it exists"* | a stale file is never noticed, ever |

Hash-based files arrived in 3.7 — *"Changed in version 3.7: Added hash-based `.pyc` files.
Previously, Python only supported timestamp-based invalidation of bytecode caches"* — and the
mode is chosen when the file is **written**, not when it is read. That is the fact that makes
this hard to debug: nothing about the running interpreter tells you which rule applies; the
file does.

`compileall` is where you choose:

> *"Control how the generated byte-code files are invalidated at runtime. The `timestamp`
> value, means that `.pyc` files with the source timestamp and size embedded will be generated.
> The `checked-hash` and `unchecked-hash` values cause hash-based pycs to be generated.
> Hash-based pycs embed a hash of the source file contents rather than a timestamp. … The
> default is `timestamp` if the `SOURCE_DATE_EPOCH` environment variable is not set, and
> `checked-hash` if the `SOURCE_DATE_EPOCH` environment variable is set."*

That last sentence is the standard library conceding the point about reproducible builds:
timestamp validation depends on mtimes, reproducible builds normalise mtimes, so the moment
you set `SOURCE_DATE_EPOCH` the default flips to content hashing.

## What a container build should pick

**`checked-hash`, in almost every case.** The build's mtimes are an artefact of the build —
`COPY` order, layer caching, whatever your CI checkout did — and none of that describes
whether the source changed. A content hash does, and an invalid file is repaired rather than
trusted: *"If a checked hash-based cache file is found to be invalid, Python regenerates it
and writes a new checked hash-based cache file."*

```bash
python -m compileall --invalidation-mode checked-hash -f -q /app
```

`-f` is doing real work there, and its documentation says why: *"Force rebuild even if
timestamps are up-to-date."* Without it, a re-run over a tree that already has timestamp-based
`.pyc` files can decide there is nothing to do, and you keep the very files you were trying to
replace.

**`unchecked-hash` only for an artefact you are certain is immutable** — an image where the
source will never be edited in place and the cache ships with it. You are trading all future
correctness for the source `stat` you save per import. The documentation does not quantify
that saving and I have not measured it; treat it as an unproven optimisation with a very well
documented downside.

**`timestamp` when nothing has forced you off it.** It is the default and it is fine on a
developer machine where edits move the mtime.

## Overriding validation at the interpreter, and its limits

One flag changes how hash-based files are treated, process-wide:

> *"`--check-hash-based-pycs default|always|never` — Control the validation behavior of
> hash-based `.pyc` files. … When set to `default`, checked and unchecked hash-based bytecode
> cache files are validated according to their default semantics. When set to `always`, all
> hash-based `.pyc` files, whether checked or unchecked, are validated against their
> corresponding source file. When set to `never`, hash-based `.pyc` files are not validated
> against their corresponding source files."*

> *"The semantics of timestamp-based `.pyc` files are unaffected by this option."*

So `always` is the escape hatch that rescues you from someone else's `unchecked-hash` build —
useful in development, useful when debugging exactly this class of bug — and `never` is the
loaded gun, turning every hash-based file in the process into an unchecked one regardless of
how it was written.

```bash
# Development: never trust a hash-based .pyc without re-hashing the source.
python --check-hash-based-pycs always -m app
```

And read the second quote again before reaching for it: it does **nothing** for a timestamp
cache. If your tree is timestamp-based, `--check-hash-based-pycs always` is a no-op and the
answer is `-f`.

## Gotchas

**★ Symptom: you edit a source file, restart the process, and the change has no effect at
all — no error, no recompile, just the old behaviour.** Cause: the `.pyc` is unchecked
hash-based, and *"for unchecked hash-based `.pyc` files, Python simply assumes the cache file
is valid if it exists."* Nothing will ever invalidate it: not an edit, not a new mtime, not a
different file size. Fix: rebuild the cache in a mode that checks, and force it, because a
non-forced run may decide there is nothing to do.

```bash
python -m compileall --invalidation-mode checked-hash -f -q /app
```

**★ Symptom: an `assert` you added is not firing, and `sys.flags.optimize` is `0`.** Cause:
this is [06m](06m-the-guard-the-platform-deletes.md)'s symptom from a completely different
mechanism. The interpreter is not optimized; it is simply running bytecode compiled before the
`assert` existed, because an unchecked hash-based cache is never revalidated. Fix: prove which
program is running before you go looking for a flag — rebuild the cache, and if that changes
the behaviour the flag was never the issue.

```bash
python -m compileall --invalidation-mode checked-hash -f -q /app
python --check-hash-based-pycs always -m app      # belt and braces while diagnosing
```

**★ Symptom: `--check-hash-based-pycs always` does not fix the stale module.** Cause: the
option is documented as affecting hash-based files only — *"the semantics of timestamp-based
`.pyc` files are unaffected by this option"* — so a timestamp-mode tree ignores it entirely.
Fix: force a rebuild instead; that is the timestamp-mode remedy.

```bash
python -m compileall -f -q /app
```

**★ Symptom: `compileall` re-run over the tree "succeeds" and changes nothing.** Cause: it
skips work when *"timestamps are up-to-date"*, which is exactly the state a stale-but-current-
looking cache is in. Fix: `-f`. Make it the default in any build script; a build that
sometimes skips is worse than one that always costs a few seconds.

```bash
python -m compileall -o 1 --invalidation-mode checked-hash -f -q /app
```

**★ Symptom: a reproducible-build pipeline started shipping stale bytecode after mtimes were
normalised.** Cause: timestamp validation compares *"the source's last-modified timestamp and
size"*, and normalising mtimes across a build removes the only signal it has. The standard
library already anticipates this: the `compileall` default *"is `timestamp` if the
`SOURCE_DATE_EPOCH` environment variable is not set, and `checked-hash` if the
`SOURCE_DATE_EPOCH` environment variable is set."* Fix: set the mode explicitly rather than
relying on whether that variable happens to be exported.

```bash
python -m compileall --invalidation-mode checked-hash -f -q /app
```

**★ Symptom: a bind-mounted source tree in a container keeps running yesterday's code.** Cause:
the `__pycache__` in the mounted directory is shared between the host and the container, and
whichever wrote it chose the invalidation mode. If it was written `unchecked-hash`, neither
side will ever notice an edit. Fix: for a dev container, stop writing a shared cache at all —
this is what [06zq](06zq-where-the-cache-lives.md)'s `-B` is for — and clear what is already
there.

```yaml
services:
  api:
    environment:
      PYTHONDONTWRITEBYTECODE: "1"
    volumes:
      - ./src:/app/src
```

```bash
find ./src -name '__pycache__' -type d -prune -exec rm -rf {} +
```

**Symptom: an edit is ignored inside a *running* process even after the cache is rebuilt.**
Cause: this one is not the bytecode cache at all — a module already imported is held in
`sys.modules` and is not re-read on a later `import` statement. Fix: separate the two
questions before touching `compileall`. A restart that picks up the change means it was
`sys.modules`; a restart that does not means it is the file cache.

**Symptom: nobody can say which mode the shipped `.pyc` files use.** Cause: the mode is a
property of each file, written at compile time, and no interpreter flag reports it. Fix: stop
inferring — make the build state it, by always passing `--invalidation-mode` explicitly, so
the answer is in the build script rather than in a file header.

```dockerfile
RUN python -m compileall -o 1 --invalidation-mode checked-hash -f -q /app
```

## Interview questions

**★ How can editing a Python source file have no effect whatsoever on the next run?**
Because the cached bytecode may be in a mode that never checks. Three invalidation modes
exist, chosen when the `.pyc` is *written*: timestamp, which compares the stored mtime and
size against the source's; checked hash, which re-hashes the source on every import; and
unchecked hash, where *"Python simply assumes the cache file is valid if it exists."* An
unchecked file is permanently authoritative — the edit changes nothing, no error appears, and
`sys.flags.optimize` will tell you the interpreter is not optimized, which sends most people
looking in the wrong direction. The distinguishing test is a forced rebuild:
`python -m compileall --invalidation-mode checked-hash -f`. If that changes the behaviour, the
cache was the program.

**★ Which invalidation mode should a container image use, and why?**
`checked-hash`, with `-f`. Mtimes inside an image are a property of the build process — layer
ordering, checkout method, whether anything normalised them — and describe nothing about
whether the source changed, so timestamp validation is answering a question you did not ask.
A content hash answers the right one, and the checked variant repairs itself: *"If a checked
hash-based cache file is found to be invalid, Python regenerates it and writes a new checked
hash-based cache file."* The documentation effectively concedes this already, since
`compileall`'s default flips to `checked-hash` as soon as `SOURCE_DATE_EPOCH` is set — the
reproducible-builds case. `unchecked-hash` is defensible only for an artefact you are certain
is immutable, and it buys a saving the docs do not quantify in exchange for a permanent
inability to notice a stale file.

**★ What does `--check-hash-based-pycs` do, and what can it not fix?**
It overrides how *hash-based* files are validated for the whole process: `always` validates
every hash-based file including unchecked ones, `never` validates none of them, and `default`
respects what each file asked for. `always` is the right development setting and the right
thing to reach for while diagnosing a stale-bytecode bug, because it neutralises somebody
else's `unchecked-hash` build without rebuilding anything. What it cannot fix is stated in the
next sentence of its own documentation: *"The semantics of timestamp-based `.pyc` files are
unaffected by this option."* A timestamp-mode tree is untouched by all three values, and the
remedy there is a forced rebuild.

**Timestamp mode stores the mtime *and* the size. Why both, and what does it still miss?**
Two cheap fields from one `stat` make an accidental collision much less likely than either
alone — most real edits change the size, and most that do not change the mtime. What it still
misses is any change where both fields come out identical: a same-size edit whose mtime is
restored or normalised, a file replaced by a build tool that sets a fixed timestamp, or a
checkout that rewrites contents while preserving metadata. None of those are exotic in a build
pipeline, which is precisely why hash-based modes were added in 3.7. The honest framing is
that timestamp validation is a *heuristic* about metadata and hash validation is a *fact*
about contents.

**Is `checked-hash` slower than `timestamp`?**
Mechanically it must do more work per import: hashing the whole source file rather than
comparing two numbers from a `stat` the import system already needs. **The documentation does
not quantify the difference and I have not measured it**, so I would not put a number on it,
and I would not choose `unchecked-hash` on the strength of an unmeasured saving when its
failure mode is "a wrong program runs silently, forever". If import time genuinely matters,
that is a measurement to make on your own tree with your own file sizes, not a rule of thumb
to inherit.

**Where does the invalidation mode actually live, and why does that make this class of bug
hard?**
In each `.pyc` file, written at compile time. There is no interpreter flag that reports it, no
attribute on the module, and nothing in a traceback — the only interpreter-side control is
`--check-hash-based-pycs`, which *overrides* the mode without telling you what it was. So the
question "is this cache trustworthy?" cannot be answered from inside the running program the
way [06zp](06zp-the-path-api-for-the-cache.md)'s path question can. The engineering response
is to remove the uncertainty at the source: pass `--invalidation-mode` explicitly on every
`compileall` invocation, so the mode is a line in a build script that anyone can read rather
than a property of a binary file nobody can.
