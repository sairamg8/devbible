**[06c](06c-uv-pip.md) is about how `uv pip` differs from pip. This page is about how its own three
verbs differ from each other, because that is where the day-to-day mistakes are. `uv pip install`
adds and never removes. `uv pip sync` converges, removing anything the file does not name. `uv pip
compile` resolves intentions into pinned versions — for this machine only, unless you pass
`--universal`. None of the three writes anything uv will remember, and that is the property that
makes the pip interface incompatible with the project interface in the same repository: a
`uv pip install` inside a `uv.lock` project creates a package no file mentions, and the next exact
`uv sync` deletes it, hours later and far from the cause.**

## `uv pip install` adds; `uv pip sync` converges

> *"When installing with `uv pip install`, packages that are already installed will not be removed
> unless they conflict with the lockfile."*

> *"To ensure the environment exactly matches the lockfile, use `uv pip sync` instead."*

> *"To sync an environment with a `requirements.txt` file: `$ uv pip sync requirements.txt`"*
> — all three [locking an environment](https://docs.astral.sh/uv/pip/compile/)

So the pip interface has *both* behaviours, under two different command names — and `uv pip sync` is
the `pip-sync` equivalent, not to be confused with `uv sync`, which is the project command
([02c](02c-uv-sync-makes-the-environment-match.md)).

The word "lockfile" in the first two quotes means *the requirements file you are installing from*,
not `uv.lock`. The pip interface does not read `uv.lock` at all.

| Verb | Reads | Adds missing | Removes strays | Re-resolves |
|---|---|---|---|---|
| `uv pip install -r requirements.txt` | a requirements file | ✅ | ❌ | only what the file leaves open |
| `uv pip sync requirements.txt` | a requirements file | ✅ | ✅ | — the file is treated as the answer |
| `uv sync` (project) | `uv.lock` | ✅ | ✅ | only if `pyproject.toml` drifted |

The practical reading: `install` is for *adding one thing to an environment you are experimenting
in*; `sync` is for *making an environment equal a reviewed file*. A CI job, a container build or a
deploy script that uses `install` is accumulating state across runs if the environment is ever
reused — and a cached virtual environment on a CI runner is exactly that reuse.

## `uv pip compile` is platform-specific unless you say otherwise

> *"By default, uv's pip interface, i.e., `uv pip compile`, produces a resolution that is
> platform-specific, like `pip-tools`."*

> *"Universal resolution is also available in uv's pip interface, i.e., `uv pip compile`, with the
> `--universal` flag."*
> — both [resolution](https://docs.astral.sh/uv/concepts/resolution/)

> *"Locking is to take a dependency, e.g., `ruff`, and write an exact version to use to a file."*

> *"To upgrade a dependency, use the `--upgrade-package` flag"* · *"To upgrade all dependencies, there
> is an `--upgrade` flag."*
> — all [locking an environment](https://docs.astral.sh/uv/pip/compile/)

```bash
uv pip compile requirements.in -o requirements.txt              # this platform
uv pip compile --universal requirements.in -o requirements.txt  # all platforms
uv pip sync requirements.txt                                    # converge the environment
uv pip compile --upgrade-package httpx requirements.in -o requirements.txt
```

`--universal` is the option to know if you are stuck with `requirements.txt` for reasons outside your
control: it gives you the cross-platform property of `uv.lock` in a format other tools can read.

### The two-file discipline this recreates

The pip interface formalises the same split `pip-tools` did — and which the floor lacks
([06b](06b-requirements-files-and-the-floors-limits.md)):

```text
# requirements.in — intentions, hand-written, reviewed
httpx>=0.27
sqlalchemy>=2.0

# requirements.txt — generated by `uv pip compile`, never hand-edited, committed
# (every transitive dependency pinned to an exact version)
```

The rule that makes it work is the same rule as for `uv.lock`: the `.in` file is edited by people,
the `.txt` file is edited only by the compiler. A hand edit to the compiled file is overwritten at
the next compile and, until then, is a version nobody resolved.

## 🔴 Do not mix the two interfaces in one project

The interfaces are not layered; they are alternatives.

| | project interface | pip interface |
|---|---|---|
| declares | `pyproject.toml` | nothing |
| records | `uv.lock` | nothing |
| removes strays | ✅ `uv sync` is exact | only `uv pip sync` |
| needs a project | ✅ | ❌ |

A `uv pip install` inside a project managed by `uv.lock` puts a package in the environment that no file
mentions — and the next `uv sync` removes it, because sync is exact. The symptom appears hours later,
far from the cause. Pick one interface per repository.

The configuration surfaces are kept apart for the same reason. Settings under `[tool.uv.pip]` apply to
the pip interface only:

> *"A dedicated `[tool.uv.pip]` section is provided for configuring _just_ the `uv pip` command line
> interface. Settings in this section will not apply to `uv` commands outside the `uv pip`
> namespace."*
> — [configuration files](https://docs.astral.sh/uv/concepts/configuration-files/)

If "pick one interface" means leaving the pip interface behind, the move is its own procedure — the
intentions file becomes the declaration and the compiled file a constraint, so no version moves — and
it is [06f](06f-migrating-from-requirements-to-a-project.md).

## Gotchas

**★ Symptom: `uv pip install -r requirements.txt` left extra packages behind.**
Cause: install is additive: *"packages that are already installed will not be removed unless they
conflict with the lockfile."* Fix: use the converging command.

```bash
uv pip sync requirements.txt
```

**★ Symptom: a `requirements.txt` compiled on macOS installs the wrong things on Linux.**
Cause: `uv pip compile` output is *"platform-specific, like `pip-tools`"* by default. Fix: ask for the
universal resolution.

```bash
uv pip compile --universal requirements.in -o requirements.txt
```

**★ Symptom: a package installed with `uv pip install` disappeared from a project's environment.**
Cause: you mixed interfaces. `uv sync` is exact and removes anything the lockfile does not mention. Fix:
declare it through the project interface.

```bash
uv add httpx
```

**★ Symptom: you cannot tell whether a failing `uv pip install` is a resolution or a build problem.**
Cause: one command runs both phases, as always ([01](01-what-uv-is.md)). Fix: separate them — compile
first, then install from the compiled file.

```bash
uv pip compile requirements.in -o /tmp/req.txt    # resolution only
uv pip sync /tmp/req.txt                          # installation only
```

**★ Symptom: `uv pip sync` removed the debugger, the REPL helper and everything else you had installed by hand.**
Cause: that is what it is for — it makes the environment *"exactly match"* the file. Fix: give dev
machines their own compiled file that includes the production one, or keep the tool outside the
environment entirely.

```text
# requirements-dev.in
-r requirements.in
ipython
```

```bash
uv pip compile --universal requirements-dev.in -o requirements-dev.txt
uv pip sync requirements-dev.txt     # dev machines converge on this file instead
uvx ipython                          # or keep the tool out of the env entirely (07)
```

**★ Symptom: two developers running `uv pip install -r requirements.in` on different days get different versions.**
Cause: the `.in` file holds ranges, so every install re-resolves against whatever the index holds that
day. Fix: compile once, commit the output, and install from the output.

```bash
uv pip compile --universal requirements.in -o requirements.txt
git add requirements.in requirements.txt
uv pip sync requirements.txt
```

**Symptom: an index URL you set under `[tool.uv.pip]` works for `uv pip install` and is ignored by `uv sync`.**
Cause: *"Settings in this section will not apply to `uv` commands outside the `uv pip` namespace."*
Fix: declare the index at the level both interfaces read.

```toml
[[tool.uv.index]]
name = "internal"
url = "https://pypi.internal.example.com/simple"
default = true
```

**Symptom: a hand-fix to a pinned version in `requirements.txt` vanished.**
Cause: the file is compiler output; the next `uv pip compile` rewrote it from `requirements.in`. Fix:
express the change where the compiler reads it.

```bash
echo 'urllib3<2' >> requirements.in
uv pip compile --universal requirements.in -o requirements.txt
```

## Interview questions

**★ What is the difference between `uv pip sync` and `uv sync`?**
They share the word and the *exact* semantics, and nothing else. `uv pip sync requirements.txt` is the
pip interface's equivalent of `pip-sync`: it makes the current environment exactly match a requirements
file you name, removing anything the file does not list, and it records nothing afterwards. `uv sync`
is a project command: it reads `uv.lock`, which is itself derived from `pyproject.toml`, re-locks first
if the declaration drifted, installs your own project editable when a build system is present, and
handles dependency groups and extras. The first operates on a file; the second operates on a project.
Confusing them usually shows up as someone running `uv pip sync` in a `uv.lock` project and wondering
why the lockfile is ignored — the pip interface never reads it.

**★ Why must you never run `uv pip install` in a project managed by `uv.lock`?**
Because the two interfaces disagree about where the truth lives, and the project interface wins by
deleting things. `uv pip install` mutates the environment and writes to no file; the project's
`uv sync` is exact and removes anything `uv.lock` does not mention. So the package works for a while —
`uv run` syncs inexactly and leaves it alone — and then disappears at the next `uv sync`, in a
different command, possibly on a different day. Worse, nobody else ever had it: CI and colleagues
install from the lockfile. The fix is `uv add`, which declares and locks in one step; the discipline is
one interface per repository.

**★ When is `uv pip compile --universal` the right tool rather than `uv lock`?**
When the output has to be a `requirements.txt` that something other than uv consumes, and there is no
`pyproject.toml` to lock — a legacy repository, a deployment platform that only understands
requirements files, a team that has adopted uv's speed but not its project model. Without
`--universal` the compiled file is, in uv's own words, *"platform-specific, like `pip-tools`"*, which is
the exact defect that makes frozen requirements break on the next operating system. With it you get the
cross-platform resolution `uv.lock` gives you, in a format everyone can read. If there *is* a
`pyproject.toml`, `uv lock` plus `uv export` is the better route, because it keeps a single source of
truth.

**When would you deliberately stay on `uv pip` rather than adopting `uv.lock`?**
When the repository cannot or should not become a project. A shared collection of scripts with no
package structure, a legacy service where restructuring `pyproject.toml` is a separate piece of work,
or a team that needs the speed and cache benefits now and the workflow change later — in all of those,
`uv pip install -r requirements.txt` is an immediate improvement that requires no new concepts from
anybody. The trade-off is that you keep every reproducibility limitation of the floor: no
declared-versus-resolved distinction, a platform-specific resolution unless you remember `--universal`,
and no exact syncing unless you consistently use `uv pip sync`. It is a legitimate stopping point, and
it should be a decision on record rather than a drift.

**Why does the pip interface have a separate `[tool.uv.pip]` configuration table?**
Because the two interfaces have different semantics for some of the same-named concepts, and a setting
that is correct for one can be wrong for the other. uv states the scope plainly: settings there *"will
not apply to `uv` commands outside the `uv pip` namespace."* That keeps a pip-interface tweak — a
resolution mode for `uv pip compile`, say — from silently changing how the project's `uv.lock` is
produced. The cost is the mirror image: an index or setting you need in both places has to live at the
top level of `[tool.uv]`, and putting it only under `[tool.uv.pip]` produces a project command that
behaves as if you never configured it.
