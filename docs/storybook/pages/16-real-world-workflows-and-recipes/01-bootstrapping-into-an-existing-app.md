# 📖 Bootstrapping Storybook Into an Existing App With Providers Already Wired In

## 1. Under-The-Hood Mechanics

Adding Storybook to a brand-new, empty project and adding it to a **two-year-old app with a real provider tree** (Router, Redux/RTK store, theme, TanStack Query) are different tasks — the init wizard handles the former completely; the latter needs the app's actual global providers replicated as Storybook global decorators, or every story that touches a connected/routed/themed component crashes with a missing-context error the moment you try to render it.

```text
Real app's actual root (src/main.tsx):
  <QueryClientProvider client={queryClient}>
    <Provider store={store}>
      <ThemeProvider>
        <BrowserRouter>
          <App />
        </BrowserRouter>
      </ThemeProvider>
    </Provider>
  </QueryClientProvider>

.storybook/preview.tsx needs the SAME shape (decorators compose outside-in, same nesting) —
NOT a simplified/partial version, or components depending on outer context will crash:
  decorators: [
    (Story) => <QueryClientProvider client={storybookQueryClient}><Story /></QueryClientProvider>,
    (Story) => <Provider store={storybookStore}><Story /></Provider>,
    (Story) => <ThemeProvider><Story /></ThemeProvider>,
    (Story) => <MemoryRouter><Story /></MemoryRouter>,  // MemoryRouter, not BrowserRouter — see Pitfall 2
  ]
```

The second, less obvious mismatch: Storybook runs its **own** bundler instance (its own Vite or Webpack config, generated by the init wizard) — it does **not** automatically inherit the actual app's `vite.config.ts`/`webpack.config.js` path aliases, CSS handling, or environment variables. Every alias the real app resolves has to be explicitly mirrored into Storybook's own config, or component imports that work fine in the app fail only inside Storybook.

---

## 2. Real-World Engineering Scenario

**Scenario**: The First Story for a Connected Component Crashing Immediately With "could not find react-redux context value."
A team runs `npx storybook@latest init` on an existing app, gets the default example stories working fine, then writes the first REAL story for `<UserMenu>` — a component reading from both Redux (current user) and React Router (active route highlighting). It crashes instantly. The default Storybook setup has zero awareness of the app's actual provider tree; each provider the app depends on has to be deliberately replicated in `.storybook/preview.tsx` as a global decorator, matching the real app's nesting — not assumed to "just work" because the app itself renders fine outside Storybook.

## 3. Production-Grade Setup Sequence

```bash
# Step 1: run the init wizard — auto-detects the framework (React + Vite/Webpack) and
# installs a WORKING baseline, including example stories, before touching anything app-specific
npx storybook@latest init
```

```bash
# Step 2: verify the baseline works BEFORE wiring in anything app-specific — same principle
# as the Jest/RTL setup-from-zero recipe: confirm each layer before adding the next
npx storybook dev -p 6006
# The default example stories (Button, Header, Page) should render with zero errors first
```

```tsx
// Step 3: replicate the app's REAL provider tree as global decorators —
// .storybook/preview.tsx
import type { Preview } from '@storybook/react';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import { Provider } from 'react-redux';
import { configureStore } from '@reduxjs/toolkit';
import { MemoryRouter } from 'react-router-dom';
import { ThemeProvider } from '../src/theme';
import { rootReducer } from '../src/app/rootReducer';
import '../src/index.css'; // the app's actual global stylesheet — components using global
                             // classes/CSS variables render UNSTYLED in Storybook without this

const preview: Preview = {
  decorators: [
    (Story) => {
      const queryClient = new QueryClient({ defaultOptions: { queries: { retry: false } } });
      return <QueryClientProvider client={queryClient}><Story /></QueryClientProvider>;
    },
    (Story) => {
      const store = configureStore({ reducer: rootReducer }); // a FRESH store per story render
      return <Provider store={store}><Story /></Provider>;
    },
    (Story) => <ThemeProvider><Story /></ThemeProvider>,
    (Story) => <MemoryRouter initialEntries={['/']}><Story /></MemoryRouter>,
  ],
};
export default preview;
```

```typescript
// Step 4: mirror the app's ACTUAL bundler aliases into Storybook's own config —
// .storybook/main.ts
import type { StorybookConfig } from '@storybook/react-vite';
import path from 'node:path';

const config: StorybookConfig = {
  stories: ['../src/**/*.stories.@(ts|tsx)'],
  framework: { name: '@storybook/react-vite', options: {} },
  async viteFinal(config) {
    config.resolve = config.resolve ?? {};
    config.resolve.alias = {
      ...config.resolve.alias,
      '@': path.resolve(__dirname, '../src'), // MUST match the app's own vite.config.ts alias exactly
    };
    return config;
  },
};
export default config;
```

```tsx
// Step 5: NOW the connected component's story works — its story file doesn't need to
// know or care about ANY of the providers above; it renders through the global decorators
// UserMenu.stories.tsx
import type { Meta, StoryObj } from '@storybook/react';
import { UserMenu } from './UserMenu';

const meta: Meta<typeof UserMenu> = { component: UserMenu, title: 'Layout/UserMenu' };
export default meta;

export const Default: StoryObj<typeof UserMenu> = {}; // no manual provider wrapping needed at all
```

## 4. Senior Engineer Edge Cases & Pitfalls

### ⚠️ Pitfall 1: Sharing ONE Store/QueryClient Instance Across Every Story
```tsx
// ❌ WRONG: a single store/queryClient created ONCE at module scope means every story
// shares mutable state — interacting with one story (triggering a mutation, changing Redux
// state) can leak into and affect a DIFFERENT story's rendered output on next navigation
const sharedStore = configureStore({ reducer: rootReducer }); // created ONCE, module scope
export const decorators = [(Story) => <Provider store={sharedStore}><Story /></Provider>];

// ✅ CORRECT: create a FRESH instance INSIDE the decorator function (Step 3 above) — it runs
// per story render, giving each story genuinely isolated state, same principle as needing a
// fresh QueryClient per test in the TanStack Query testing guidance
```

### ⚠️ Pitfall 2: Using `BrowserRouter` Instead of `MemoryRouter` in Storybook
`BrowserRouter` reads and writes the **actual browser URL** — inside Storybook's own iframe-based story canvas, this creates confusing interactions with Storybook's own UI navigation and doesn't give each story a controllable, isolated starting route. `MemoryRouter` (with an explicit `initialEntries`) keeps routing state entirely in-memory, scoped to that one story, and lets different stories deliberately render the SAME component at different routes (e.g. testing an active-vs-inactive nav link state) via story-level `initialEntries` overrides.

### ⚠️ Pitfall 3: Forgetting the Global Stylesheet Import, Getting "It Works But Looks Wrong"
A component using Tailwind utility classes, CSS custom properties, or any global stylesheet the app's real entry point imports (but Storybook's generated `preview.ts` never automatically does) renders **structurally correct but visually broken** — no error, just missing styles, which is a much more confusing failure mode to diagnose than an outright crash because nothing LOOKS wrong to a quick glance if you don't know the correct styled version.

### ⚠️ Pitfall 4: Aliases Drifting Out of Sync Over Time, Same Failure Class as Jest's `moduleNameMapper`
Exactly like the Jest configuration drift problem, Storybook's `viteFinal`/`webpackFinal` alias mirroring (Step 4) is a manually-maintained duplicate of the app's real bundler config — a new alias added to the app's `vite.config.ts` six months from now, with nobody remembering Storybook needs the same alias added to `.storybook/main.ts`, produces "works in the app, `Cannot resolve '@/newFeature'` only inside Storybook" with no obvious connection to the recent alias change for whoever hits it next.
