<span className="db-tier t-know">Know</span>

> Verified: 2026-08 — the `--build` option set (`--verbose`, `--dry`, `--force`,
> `--clean`, `--stopBuildOnErrors`) is read from `optionsForBuild` in the
> installed **TypeScript 5.9.3** build, and `TS6369`, `TS6379` and `TS6377` are
> quoted from the compiler's own message table. `composite` and `references` are
> the **TSConfig reference**'s. **No sandbox, no console blocks.**

[Topic 12](../12-sharing-types-across-a-monorepo/README.md) used project
references throughout without explaining them. This topic explains them, and it
starts with the distinction people most often miss:

> **`tsc -p` compiles one project. `tsc -b` is a build orchestrator: it works out
> which projects exist, what order they go in, which are already current, and
> then invokes the compiler on the ones that are not.**

They are different programs wearing the same executable.

## The two pieces

### 1. `references` — the declared graph

```jsonc
// packages/ui/tsconfig.json
{
  "compilerOptions": { "composite": true, "outDir": "dist", "rootDir": "src" },
  "references": [{ "path": "../shared" }],
  "include": ["src"]
}
```

`references` is a **declaration of dependency between projects**, not a module
resolution mechanism. It does three things:

- It makes `tsc -b` build `shared` before `ui`.
- It tells the compiler that `shared`'s files belong to `shared` — which is why
  they are not type-checked as part of `ui`
  ([topic 12 chunk 01](../12-sharing-types-across-a-monorepo/01-the-question-and-the-compilers-answer.md)).
- It enables the **source redirect**, so `ui` is checked against `shared`'s
  source by default.

⚠️ **It does not make `import '@org/shared'` resolve.** That is still ordinary
module resolution — workspaces, `node_modules`, `exports`. A `references` entry
with no way to resolve the specifier gives you build ordering and nothing else,
which is a confusing half-working state.

### 2. `composite: true` — the constraints on being referenced

Already covered in
[topic 12 chunk 02](../12-sharing-types-across-a-monorepo/02-the-built-declaration-route.md):
it forces declaration emit (`TS6304`) and requires the file list to be
enumerable (`TS6307`). One more constraint belongs here:

```text
TS6379: Composite projects may not disable incremental compilation.
```

🔴 **So `composite` implies `incremental`, and refuses to have it turned off.**
Every composite project writes a `.tsbuildinfo`, which is how the up-to-date
check in [chunk 02](./02-the-up-to-date-check.md) is possible at all — and it
means [topic 10 chunk 07](../10-skiplibcheck/07-the-tsbuildinfo-interaction.md)'s
one-buildinfo-path-per-option-set rule applies to **every package**, not just the
ones you thought about.

The compiler enforces that directly:

```text
TS6377: Cannot write file '{0}' because it will overwrite '.tsbuildinfo' file
        generated by referenced project '{1}'
```

📌 That is a genuinely helpful error — it catches the exact collision topic 10
chunk 07 predicted, at build time, by name.

## The solution-style root config

A root `tsconfig.json` that builds everything and contains nothing:

```jsonc
// tsconfig.json at the repo root
{
  "files": [],
  "references": [
    { "path": "./packages/shared" },
    { "path": "./packages/ui" },
    { "path": "./packages/api" }
  ]
}
```

`"files": []` is deliberate: this project has **no sources of its own**. It
exists so `tsc -b` has a single entry point that names the whole graph.

```bash
tsc -b            # builds every referenced project, in order, skipping current ones
```

🔴 **Order inside the `references` array does not matter.** The build order is
computed from the dependency graph, not from the array. The array is a set of
roots.

## The `--build` flags, in full

Read from `optionsForBuild` — this is the complete set, and it is smaller than
people expect:

| Flag | Short | What it does |
|---|---|---|
| `--verbose` | `-v` | *"Enable verbose logging"* — 🔴 the one that makes the up-to-date decisions visible |
| `--dry` | `-d` | *"Show what would be built (or deleted, if specified with `--clean`)"* |
| `--force` | `-f` | *"Build all projects, including those that appear to be up to date"* |
| `--clean` | — | *"Delete the outputs of all projects."* |
| `--stopBuildOnErrors` | — | *"Skip building downstream projects on error in upstream project"* — ⚠️ **default `false`**, and [chunk 03](./03-errors-do-not-stop-the-build.md) is entirely about what that means |

```text
TS6369: Option '--build' must be the first command line argument.
```

📌 A parsing rule with a real cause: `--build` selects a **different option
parser** (`buildOpts` rather than the ordinary declarations), so it has to be
seen before anything else is interpreted. `tsc --noEmit -b` is not a subtly
different build; it is rejected.

⚠️ **`-b` therefore does not accept most `tsc` flags.** Compiler options belong
in each project's `tsconfig.json`, which is the point — a build over many
projects cannot take one project's options from the command line.

## What to reach for first

**`tsc -b --verbose`.** Almost every question in this topic — why did that
rebuild, why did it *not* rebuild, what order did it choose — is answered by the
messages it prints, and [chunk 02](./02-the-up-to-date-check.md) is a guide to
reading them.

## Gotchas

**Symptom:** `references` was added and the import still does not resolve.
**Cause:** `references` declares build order; it does not resolve specifiers.
**Fix:** Workspaces, `node_modules`, `exports` — ordinary resolution, as topic 12
chunk 06's migration order has it.

**Symptom:** `tsc --noEmit -b` is rejected.
**Cause:** `TS6369` — `--build` must come first, because it selects a different
option parser.
**Fix:** `tsc -b`. Compiler options go in the project configs.

**Symptom:** `TS6377` about overwriting a referenced project's `.tsbuildinfo`.
**Cause:** Two projects resolving to the same buildinfo path.
**Fix:** Distinct `outDir` or explicit `tsBuildInfoFile` per project — topic 10
chunk 07.

**Symptom:** `composite: true` with `incremental: false` is rejected.
**Cause:** `TS6379`. Composite requires incremental, because the up-to-date check
depends on it.
**Fix:** Remove the `incremental: false`.

**Symptom:** Reordering the root `references` array changed nothing.
**Cause:** Build order comes from the dependency graph, not the array order.
**Fix:** Expected. The array is a set of roots.

**Symptom:** The root project tries to compile files it should not.
**Cause:** A missing `"files": []` in a solution-style config.
**Fix:** Add it. A solution config has no sources of its own.

**Symptom:** `tsc -b` builds nothing and reports nothing useful.
**Cause:** Everything is up to date, quietly.
**Fix:** `--verbose` to see why, or `--force` to prove the build works.

**Symptom:** A CI script uses `tsc -p` per package and misses cross-package
staleness.
**Cause:** `tsc -p` has no notion of the graph.
**Fix:** `tsc -b` at the root. Ordering and up-to-date checking are the whole
reason it exists.

## Interview questions

**★ What does `tsc -b` do that `tsc -p` does not?**
It orchestrates. It reads the reference graph, computes build order, decides
which projects are already up to date, and invokes the compiler only on the
rest. `tsc -p` compiles exactly one project and knows nothing about the others.

**★ What does a `references` entry actually do?**
Three things: it orders the build, it tells the compiler those files belong to
another project so they are not checked as part of yours, and it enables the
source redirect. It does **not** make the import specifier resolve — that is
ordinary module resolution.

**★ Why does `composite` require incremental compilation?**
`TS6379` — because the up-to-date check depends on the `.tsbuildinfo` a composite
project writes. Without it there is nothing to compare against, so the
orchestration cannot work.

**★ Why must `--build` be the first command-line argument?**
Because it selects a different option parser — `buildOpts` rather than the
ordinary compiler options — so it must be seen before anything else is
interpreted. `TS6369` says so directly.

**What is a solution-style config?**
A root `tsconfig.json` with `"files": []` and a `references` array naming every
project. It has no sources of its own and exists so `tsc -b` has one entry point
for the whole graph.

**Does the order of entries in `references` matter?**
No. Build order is computed from the dependency graph; the array is just a set of
roots.

**What are the five `--build` flags?**
`--verbose`, `--dry`, `--force`, `--clean` and `--stopBuildOnErrors`. That is the
complete set — everything else belongs in the project configs.

**Which one should you reach for first when a build behaves oddly?**
`--verbose`. It prints the up-to-date decision for every project, which answers
almost every question this topic raises.
