A `.d.ts` file is the answer to a question the compiler has to ask about every
import you write: **"what is in that file, and what type is it?"** — asked about a
file that, from `tsc`'s point of view, may not exist in TypeScript at all.

## The one-sentence version

> **A `.d.ts` file is a TypeScript file with the implementations removed.**
> It says *what exists and what type it has*, never *what it does*. It emits no
> JavaScript, and at runtime it is not there.

That is the whole idea, and almost every rule in this topic is a consequence of
it.

## Where they come from

There are only three ways a `.d.ts` ends up on your disk, and knowing which one
you are looking at tells you what you are allowed to do to it:

| Source | Example | Do you edit it? |
|---|---|---|
| **Generated by `tsc`** from your own source | `dist/index.d.ts` | ⛔ **Never.** It is build output; edit the `.ts` it came from |
| **Shipped by a package** | `node_modules/zod/index.d.ts` | ⛔ Never. Augment it instead ([Phase 4 · Module augmentation](../../phase-4-classes-declarations/01-module-augmentation/README.md)) |
| **Written by hand** in your repo | `src/types/legacy-lib.d.ts`, `src/env.d.ts` | ✅ Yes — this is the one this topic is about |

⚠️ **The most common `.d.ts` mistake in a codebase is editing the first row.**
A hand-edit to a generated declaration survives exactly until the next build.
Chunk 02 covers which of the three you should be producing.

## The ambient context — and the five errors that define it

A `.d.ts` file is an **ambient context**: a region where you declare that
something exists without providing it. The compiler enforces that with a small
group of syntax errors, and they are worth reading as a set, because together
they *are* the definition of the file format.

```ts
// types/widgets.d.ts

declare function makeWidget(size: number): Widget;   // ✅ a declaration

declare function makeWidget(size: number) {          // ❌ TS1183
  return { size };                                   //    a body
}

declare const MAX = 12;                              // ❌ TS1039
                                                     //    an initializer
console.log("loading widgets");                      // ❌ TS1036
                                                     //    a statement
```

> **TS1183:** *"An implementation cannot be declared in ambient contexts."*
> **TS1039:** *"Initializers are not allowed in ambient contexts."*
> **TS1036:** *"Statements are not allowed in ambient contexts."*
> **TS1040:** *"'{0}' modifier cannot be used in an ambient context."*
> **TS1038:** *"A 'declare' modifier cannot be used in an already ambient
> context."*

Two of those five are the ones people actually trip on:

- **`TS1038` is the "why is `declare` red?" error.** Inside `declare namespace
  Foo { … }` or `declare module 'x' { … }`, *everything is already ambient*, so
  writing `declare` again on a member is an error rather than emphasis. The
  members take no modifier at all.
- **`TS1039` catches the instinct to write a value.** `declare const MAX: 12`
  declares a constant whose *type* is the literal `12`. `declare const MAX = 12`
  tries to *assign* it, and there is nowhere for that assignment to happen.

```ts
declare namespace GreetingLib {
  declare interface Options { … }   // ❌ TS1038 — already ambient
  interface Options { … }           // ✅
}
```

## `declare` is not decoration — it is the ambient marker

Outside a `.d.ts` file, `declare` is what *creates* an ambient context. Inside
one, most of the file is ambient already, but the compiler still wants each
top-level declaration marked as either ambient or exported:

> **TS1046:** *"Top-level declarations in .d.ts files must start with either a
> 'declare' or 'export' modifier."*

So both of these are correct, and they mean different things:

```ts
declare function greet(s: string): void;   // a GLOBAL function
export function greet(s: string): void;    // a function exported by this MODULE
```

🔴 **That difference is the single most consequential decision in the file**, and
it is the whole of chunk 03. Read it before writing a `.d.ts` from scratch.

**Which** declaration form describes **which** shape of JavaScript API is a
lookup table in its own right, and it comes with a piece of theory that explains
why some declarations merge and others collide. Both are
[chunk 02](./02-declaration-forms-and-spaces.md).

## Why the format exists at all

The reason is [erasure](../../phase-0-how-typescript-runs/02-erasure.md). Types
do not survive compilation, so a compiled package ships JavaScript with every
annotation gone. Something has to carry the types across that boundary, and a
`.d.ts` is that something: it is the type half of a package, shipped alongside
the JavaScript half.

This is also why the format is worth caring about even if you never hand-write
one. **The `.d.ts` your build emits is your package's public API**, and it is the
only part of your code your consumers' compilers will ever read.

## Gotchas

**Symptom:** `TS1183: An implementation cannot be declared in ambient contexts.`
**Cause:** A function body, a class method body, or a variable initializer in a
`.d.ts`.
**Fix:** Delete the body. Declaration files carry signatures only.

**Symptom:** `TS1039: Initializers are not allowed in ambient contexts.`
**Cause:** `declare const MAX = 12` — an assignment, not a type.
**Fix:** `declare const MAX: 12` if you want the literal type, or
`declare const MAX: number`.

**Symptom:** `TS1036: Statements are not allowed in ambient contexts.`
**Cause:** Real code snuck into a `.d.ts` — a `console.log`, an `if`, an
`import()` call at the top level.
**Fix:** Move it to a `.ts` file. If you wanted a side effect at load time, a
declaration file is the wrong place: it emits nothing.

**Symptom:** `TS1038: A 'declare' modifier cannot be used in an already ambient
context.`
**Cause:** `declare` written on a member inside `declare namespace` /
`declare module`.
**Fix:** Remove it. The enclosing declaration already made everything ambient.

**Symptom:** `TS1046: Top-level declarations in .d.ts files must start with
either a 'declare' or 'export' modifier.`
**Cause:** A bare `function`, `const` or `class` at the top level of a `.d.ts`.
**Fix:** Decide which you mean — `declare` for a global, `export` for a module
member — and read chunk 03 before choosing.

**Symptom:** Edits to a `.d.ts` keep disappearing.
**Cause:** It is generated output under `dist/` or `build/`, regenerated by every
`tsc` run.
**Fix:** Edit the `.ts` source. If you cannot change the source shape, the
mechanism you want is augmentation, not editing.

## Interview questions

**★ What is a `.d.ts` file?**
A TypeScript file containing declarations and no implementations: it says what
exists and what type it has, emits no JavaScript, and is absent at runtime. It is
how types cross the compilation boundary, since erasure removes them from the
emitted JavaScript.

**★ Why are function bodies and initializers illegal in one?**
Because the file is an *ambient context* — a promise that something exists
elsewhere. There is nowhere for a body or an assignment to run, so the compiler
rejects them (`TS1183`, `TS1039`) rather than silently discarding code somebody
expected to execute.

**★ What is the difference between `declare function f(): void` and
`export function f(): void` in a `.d.ts`?**
The first declares a **global**; the second declares a member of a **module**.
Which one is legal depends on whether the file has any top-level `import` or
`export` at all — a file with none is a script and contributes to global scope.
That decision governs the whole file and is the subject of chunk 03.

**If a `.d.ts` emits nothing, how does it affect the build at all?**
Only through the type checker — and through which files get *included*. A
declaration file that lands in your `include` glob affects every file in the
program if it is a script (global) file, which is how one stray `.d.ts` can
change types project-wide without anything importing it.
