JSON is the exception in this topic. For every other non-code import you
*declare* a shape; for JSON, TypeScript **reads the file and infers one**. That
is more useful than it first sounds, and it has costs the other mechanisms do
not.

```jsonc
// config.json
{ "port": 3000, "host": "localhost", "features": ["a", "b"] }
```

```ts
import config from './config.json';
config.port;      // number
config.features;  // string[]
config.prot;      // ✅ caught — the type came from the file
```

## What the inference actually produces

Worth being precise, because the widening rules surprise people:

| In the JSON | Inferred as |
|---|---|
| `3000` | `number` — **not** the literal `3000` |
| `"localhost"` | `string` — **not** `"localhost"` |
| `["a", "b"]` | `string[]` — **not** a tuple |
| `{ "a": 1 }` | `{ a: number }` |
| `null` | `null` |

🔴 **Everything widens.** There is no `as const` for a JSON import, so a config
file cannot give you literal types. A `"mode": "production"` field is `string`,
not `"production"`, and cannot be used to narrow a union.

📌 **The workaround is a `satisfies` at the use site:**

```ts
import raw from './config.json';
const config = raw satisfies { port: number; mode: string };
```

…which validates the shape but still does not recover literals. If you need
literal types from configuration, a `.ts` file with `as const` is the honest
answer, and it is worth saying that plainly rather than fighting the JSON path.

## The costs

**1. The file becomes a program input.** `affectsModuleResolution` on the option
record is the clue: turning it on changes which files are in the program. A large
JSON file is parsed and typed on every check, and a *very* large one is a real
cost — this is the mechanism behind "our build got slow after we imported the
locale data".

**2. It couples types to data.** Editing `config.json` changes your program's
types. That is the feature, and it means a data change can break a build in a
file nobody touched — which is correct behaviour and still surprising the first
time.

**3. Emit interacts with `module`.** What `import config from './config.json'`
compiles to depends on your module setting, and under `node16`/`nodenext` in an
ESM file, Node requires an **import attribute**:

```ts
import config from './config.json' with { type: 'json' };
```

⚠️ **This is the same class of problem as everything in
[topic 01](../01-module-and-moduleresolution/README.md)** — the compiler models
the module system and the runtime enforces it. A JSON import that type-checks
under `bundler` resolution can throw in Node without the attribute.

## The diagnostic

```text
TS2732: Cannot find module '{0}'. Consider using '--resolveJsonModule' to
        import module with '.json' extension.
```

📌 **TypeScript names the flag here**, which it pointedly does not do for CSS or
images ([chunk 01](./01-the-three-mechanisms.md)) — because JSON has exactly one
right answer and the compiler knows what it is.

## When not to use it

Three cases where reaching for `resolveJsonModule` is the wrong move:

1. **Large data files.** Locale tables, generated fixtures, anything measured in
   megabytes. They become program inputs. Load them at runtime with `fs` or
   `fetch` and type the result explicitly.
2. **Data that changes independently of the code.** If a JSON file is edited by
   non-engineers or generated by another system, coupling your types to it means
   their edit breaks your build.
3. **When you need literal types.** Use a `.ts` file with `as const`. JSON cannot
   give you them, and no configuration makes it.

🔴 **The good case is small, code-adjacent, engineer-maintained JSON** —
`package.json` fields you read, a small static table, a fixture in a test. That
is where the inference is a genuine safety win.

## Gotchas

**Symptom:** `TS2732` on a `.json` import.
**Cause:** `resolveJsonModule` is off.
**Fix:** Turn it on — TypeScript named the flag because there is one answer.

**Symptom:** A `"mode": "production"` field is `string` and will not narrow a
union.
**Cause:** JSON inference widens everything; there is no `as const`.
**Fix:** A `.ts` config with `as const`, if literals matter.

**Symptom:** The build slowed noticeably after importing a data file.
**Cause:** The JSON is now a program input, parsed and typed on every check.
**Fix:** Load large data at runtime instead.

**Symptom:** Someone edited a JSON file and an unrelated `.ts` file failed to
compile.
**Cause:** The types came from the data.
**Fix:** Correct behaviour. If that coupling is unwanted, the file should not be
imported.

**Symptom:** A JSON import type-checks and throws in Node.
**Cause:** ESM under `node16`/`nodenext` requires `with { type: 'json' }`.
**Fix:** Add the import attribute. Same class of problem as topic 01's.

**Symptom:** An array in JSON is `string[]` where a tuple was wanted.
**Cause:** Widening again.
**Fix:** Assert at the use site, or move the data to `.ts`.

**Symptom:** `satisfies` was added and literals still did not appear.
**Cause:** `satisfies` validates a shape; it does not narrow what was already
widened.
**Fix:** It is doing its job. Literals need a `.ts` source.

**Symptom:** A generated JSON file makes CI flaky.
**Cause:** Types derived from generated data, regenerated at a different time.
**Fix:** Type the boundary explicitly instead of importing the artefact.

## Interview questions

**★ What does `resolveJsonModule` do that the other mechanisms cannot?**
It reads the file and **infers** a type from its contents, rather than having you
declare one. That means a typo in a property name is caught against the real
data — the only case in this topic where the file's contents shape the type
automatically.

**★ What does JSON inference not give you?**
Literal types. Everything widens — `3000` is `number`, `"localhost"` is `string`,
`["a","b"]` is `string[]`. There is no `as const` for a JSON import, so
configuration that needs literals belongs in a `.ts` file.

**★ What does turning it on cost?**
The JSON becomes a program input — its record carries `affectsModuleResolution`
— so it is parsed and typed on every check, and a large data file is a real
build cost. It also couples your types to data, so a data edit can break a build
in a file nobody touched.

**★ Why can a JSON import type-check and still throw in Node?**
Because under `node16`/`nodenext` in an ESM file Node requires an import
attribute — `with { type: 'json' }`. The compiler models the module system; the
runtime enforces it.

**When would you deliberately not use it?**
Large data files, data maintained outside the codebase, and anywhere literal
types are needed. Small engineer-maintained JSON adjacent to the code is where
the inference genuinely pays.

**Why does `TS2732` name the flag when the CSS errors do not?**
Because JSON has one correct answer and TypeScript can read the file. For CSS or
images there is no single right shape, so it cannot suggest one.

**Does `satisfies` recover the literal types?**
No. It validates the shape against a type you write; it does not un-widen what
inference already widened.
