> Verified: 2026-08-27 against the JUnit 6.0.3 User Guide — "Parameter Resolution"
> ([parameter-resolution](https://docs.junit.org/6.0.3/extensions/parameter-resolution.html)).
> JDK 25, Spring Boot 4.1.0, JUnit Jupiter 6.0.3, Spring Framework 7.0.8.

**Every argument a Jupiter test method receives arrives through a `ParameterResolver` —
`TestInfo`, `TestReporter`, `RepetitionInfo`, `@TempDir Path`, a Mockito `@Mock` parameter,
a Spring bean. The API is two methods, and everything difficult about it is contained in
two documented facts: resolvers that claim the same type collide loudly, and reading
annotations off a `java.lang.reflect.Parameter` is broken for `@Nested` constructors.**

## The API, and the two ways to resolve

> *"`ParameterResolver` defines the Extension API for dynamically resolving parameters at
> runtime. If a test class constructor, test method, or lifecycle method … declares a
> parameter, the parameter must be resolved at runtime by a `ParameterResolver`. A
> `ParameterResolver` can either be built-in (see `TestInfoParameterResolver`) or registered
> by the user. Generally speaking, parameters may be resolved by name, type, annotation, or
> any combination thereof."*

There is a base class for the simplest case:

> *"If you wish to implement a custom `ParameterResolver` that resolves parameters based
> solely on the type of the parameter, you may find it convenient to extend the
> `TypeBasedParameterResolver` which serves as a generic adapter for such use cases."*

`TypeBasedParameterResolver` removes the boilerplate of comparing `Class` objects and gets
the generic type right, which hand-written `supportsParameter` implementations frequently
do not.

## Parameter conflicts

> *"If multiple implementations of `ParameterResolver` that support the same type are
> registered for a test, a `ParameterResolutionException` will be thrown, with a message to
> indicate that competing resolvers have been discovered."*

```java
@Test
@ExtendWith({ FirstIntegerResolver.class, SecondIntegerResolver.class })
void testInt(int i) {
    // Test will not run due to ParameterResolutionException
    assertEquals(1, i);
}
```

The failure is loud, which is the right design — the alternative is a silently arbitrary
winner. The fix the guide shows is narrower registration: put each resolver on the method
that needs it, not on the class.

⚠️ In practice this bites when two libraries both resolve a common type. A resolver that
claims `String` or `int` is antisocial; resolve on an **annotation** (`@Random int`), not on
a bare type, and the conflict cannot arise.

## The JDK bug every resolver author must know about

> *"Due to a bug in the byte code generated by `javac` on JDK versions prior to JDK 9,
> looking up annotations on parameters directly via the core `java.lang.reflect.Parameter`
> API will always fail for inner class constructors (e.g., a constructor in a `@Nested` test
> class). The `ParameterContext` API supplied to `ParameterResolver` implementations
> therefore includes the following convenience methods for correctly looking up annotations
> on parameters. Extension authors are strongly encouraged to use these methods instead of
> those provided in `java.lang.reflect.Parameter` in order to avoid this bug in the JDK."*

The three methods are `isAnnotated(Class<? extends Annotation>)`,
`findAnnotation(Class<A>)` and `findRepeatableAnnotations(Class<A>)`. Use them, always —
`parameterContext.isAnnotated(Random.class)` rather than
`parameter.isAnnotationPresent(Random.class)`. The failure mode is that your extension works
everywhere except in `@Nested` classes ([06b](06b-nested-tests.md)), which is the single
most confusing bug report an extension author can receive.## Two facilities worth knowing exist

**Other extensions can borrow your resolvers.**

> *"Other extensions can also leverage registered `ParameterResolver`s for method and
> constructor invocations, using the `ExecutableInvoker` available via the
> `getExecutableInvoker()` method in the `ExtensionContext`."*

That is how an extension can call a user-supplied method — a factory, a callback, a
condition method — and have *its* parameters resolved by whatever resolvers are registered,
instead of demanding a fixed signature.

**Constructor parameters can see a test-scoped context.**

> *"You may override the `getTestInstantiationExtensionContextScope(…)` method to return
> `TEST_METHOD` to support injecting test specific data into constructor parameters of the
> test class instance. Doing so causes a test-specific `ExtensionContext` to be used while
> resolving constructor parameters, unless the test instance lifecycle is set to
> `PER_CLASS`."*

Without it, a resolver asked for a constructor parameter sees the *class-level* context and
cannot know which test method is about to run — because, strictly, the instance is
constructed for a test but the context handed to the resolver is not test-scoped by default.
The corresponding configuration parameter,
`junit.jupiter.extensions.testinstantiation.extensioncontextscope.default`, is one of the
enum-valued parameters that JUnit 6 now **fails** on when set to an invalid value
([02b](02b-what-junit-6-changed.md)).

## Gotchas

**★ A `ParameterResolver` that claims a common type.**
Two resolvers supporting `int` is a `ParameterResolutionException` and the test does not
run. Resolve on your own annotation instead.

**★ Reading parameter annotations via `java.lang.reflect.Parameter`.**
It fails for inner-class constructors because of a pre-JDK-9 `javac` bug, so your extension
breaks only inside `@Nested` classes. Use `ParameterContext.isAnnotated` and
`findAnnotation`.**★ Hand-rolling type comparison instead of extending `TypeBasedParameterResolver`.**
`getType() == List.class` ignores generics entirely, so a resolver for `List<String>` also
claims `List<Integer>`. The adapter exists for this case.

**★ A `supportsParameter` that returns `true` and a `resolveParameter` that returns the
wrong type.**
`resolveParameter` returns `Object`; nothing checks it against the parameter's type until
the reflective invocation fails. Keep the two methods' conditions identical — ideally with a
single private predicate used by both.

**★ Resolving on parameter *name*.**
The guide allows it, and parameter names are only present in the byte code when the class
was compiled with `-parameters`. A resolver keyed on names works in your build and fails in
a consumer's.

## Interview questions

**★ What happens if two registered `ParameterResolver`s support the same type?**
A `ParameterResolutionException` naming the competing resolvers, and the test does not run.
The remedy is finer-grained registration, or resolving on a custom annotation rather than on
a widely used type.

**★ Why should a `ParameterResolver` never call `Parameter.isAnnotationPresent`?**
Because of a `javac` byte-code bug on JDKs before 9, annotation lookup on parameters fails
for inner-class constructors — which includes every `@Nested` test class. `ParameterContext`
provides `isAnnotated`, `findAnnotation` and `findRepeatableAnnotations` to work around it,
and the guide strongly encourages using them.**★ Where do `TestInfo` and `TestReporter` parameters come from?**
Built-in `ParameterResolver` implementations registered by Jupiter itself — the guide names
`TestInfoParameterResolver`. There is no special case in the engine for them: they use the
same public extension API a third-party resolver uses.

**★ What is `TypeBasedParameterResolver` for?**
It is a generic adapter for resolvers that decide purely on the parameter's type, handling
the type comparison — including generics — so the implementation reduces to producing the
value. It is the right base class whenever the answer to "do you support this parameter?" is
"is it a `Foo`?".

**★ How can one extension invoke a user method and have its parameters resolved?**
Through `ExecutableInvoker`, obtained from `ExtensionContext.getExecutableInvoker()`. It
applies the registered `ParameterResolver`s to a method or constructor the extension calls
itself, which is what lets an extension accept flexible user-supplied signatures rather than
one fixed shape.
