> Verified: 2026-08-27 against the JUnit 6.0.3 User Guide — "Display Names"
> ([display-names](https://docs.junit.org/6.0.3/writing-tests/display-names.html)) and
> "Release Notes"
> ([release-notes](https://docs.junit.org/6.0.3/release-notes.html), the 6.0.0 section on
> control characters). JDK 25, Spring Boot 4.1.1, JUnit Jupiter 6.0.3,
> Spring Framework 7.0.9.

**The test report is the only artefact of your test suite that a non-author reads. Jupiter
gives you three ways to control what it says — an explicit `@DisplayName`, a generator
applied to a class, and a project-wide default — with a precedence order that is worth
knowing because it decides which one wins when a team has configured all three.**

## `@DisplayName`

> *"Test classes and test methods can declare custom display names via `@DisplayName` —
> with spaces, special characters, and even emojis — that will be displayed in test
> reports and by test runners and IDEs."*

```java
@DisplayName("Refund policy")
class RefundPolicyTest {

    @Test
    @DisplayName("refunds in full inside the 14-day window")
    void refundsInFullInsideTheWindow() { /* ... */ }

    @Test
    @DisplayName("refunds nothing after the window closes")
    void refundsNothingAfterTheWindow() { /* ... */ }
}
```

The gain is real and the cost is real. The gain: the report reads as English. The cost:
**two names to keep in sync**, and IDE search for a failing test's name now finds a string
literal rather than a method. Teams that adopt `@DisplayName` universally often drift into
a display name that no longer describes the method beneath it — which is worse than not
having one, because the report is now confidently wrong.

## The generators, which remove the duplication

```java
@DisplayNameGeneration(DisplayNameGenerator.ReplaceUnderscores.class)
class A_year_is_not_supported {

    @Test
    void if_it_is_zero() { }
}
```

The four built-ins, from the guide's own table:

| Generator | Behaviour |
|---|---|
| `Standard` | *"Matches the standard display name generation behavior in place since JUnit Jupiter was introduced."* |
| `Simple` | *"Extends the functionality of `Standard` by removing trailing parentheses for methods with no parameters."* |
| `ReplaceUnderscores` | *"Replaces underscores with spaces."* |
| `IndicativeSentences` | *"Generates complete sentences by concatenating the names of the test and the enclosing classes."* |

`Standard` is what you get by default: the method name plus `()`. `Simple` drops the
empty parentheses. `ReplaceUnderscores` is the one worth adopting — it makes
`if_it_is_zero` render as "if it is zero" with no second string to maintain.

`IndicativeSentences` concatenates the enclosing class names with the method name, and can
be tuned:

```java
@IndicativeSentencesGeneration(separator = " -> ", generator = ReplaceUnderscores.class)
class A_year_is_a_leap_year {

    @Test
    void if_it_is_divisible_by_4_but_not_by_100() { }
}
```

The guide states the produced display names for this class as
`A year is a leap year -> if it is divisible by 4 but not by 100`, nested under the class
name `A year is a leap year`.

`@SentenceFragment` lets you supply the fragments without encoding them in identifiers:

```java
@SentenceFragment("A year is a leap year")
@IndicativeSentencesGeneration
class LeapYearTests {

    @SentenceFragment("if it is divisible by 4 but not by 100")
    @Test
    void divisibleBy4ButNotBy100() { }
}
```

## The precedence rules

Verbatim, and worth reading as a list because a team can have all four in play:

> *"the display name for a test class or method is determined according to the following
> precedence rules: value of the `@DisplayName` annotation, if present; by calling the
> `DisplayNameGenerator` specified in the `@DisplayNameGeneration` annotation, if present;
> by calling the default `DisplayNameGenerator` configured via the configuration
> parameter, if present; by calling
> `org.junit.jupiter.api.DisplayNameGenerator.Standard`."*

And it is stated twice in the same page, because people get it wrong:

> *"Values provided via `@DisplayName` annotations always take precedence over display
> names generated by a `DisplayNameGenerator`."*

Setting the project default:

```properties
# src/test/resources/junit-platform.properties
junit.jupiter.displayname.generator.default = \
    org.junit.jupiter.api.DisplayNameGenerator$ReplaceUnderscores
```

⚠️ **Note the `$`** — it is a nested class, and the fully qualified name uses the binary
form. A dot there silently fails to resolve the class.

`@DisplayNameGeneration` on an enclosing class applies to the classes it encloses, so a
generator declared once on a base class or a `@Nested` parent covers everything beneath.

## Control characters, changed in 6.0

> *"Non-printable control characters in display names are now replaced with alternative
> representations. For example, `\n` is replaced with `<LF>`."*

The guide's table: a carriage return renders as `<CR>`, a line feed as `<LF>`, and any
other ISO control character as the Unicode replacement character. This matters for
parameterized tests whose arguments contain newlines, where a display name used to be able
to break a report's layout or an XML report's well-formedness.

## What a good name contains, whichever mechanism you use

The mechanism is the easy part. The content is:

- **The circumstance** — "when the basket is empty", "after the window closes".
- **The expected behaviour** — "rejects the order", "refunds nothing".
- **Not** the method under test. `apply()` has fifteen behaviours; naming the test after
  the method guarantees fifteen names that differ only by a number.
- **Not** the word "should" fifteen times. It is filler by the third test.

Method-name conventions that work without any annotation:

```java
void refundsNothingAfterTheWindowCloses() { }         // behaviour-first
void givenAnEmptyBasket_thenRejectsTheOrder() { }     // given/then, with underscores
void refunds_nothing_after_the_window_closes() { }    // with ReplaceUnderscores
```

The third one plus `ReplaceUnderscores` gives you readable report output with a single
source of truth, which is why it is the default recommendation on this page.

## Gotchas

**★ `@DisplayName` that has drifted from the method.**
Two names, one of them not compiled against anything. Renaming the method does not touch
the string. Prefer a generator when the method name can carry the sentence.

**★ A `.` instead of a `$` in the generator's configured class name.**
`org.junit.jupiter.api.DisplayNameGenerator.ReplaceUnderscores` is not a resolvable binary
name. The nested class needs `DisplayNameGenerator$ReplaceUnderscores`.

**★ Expecting `@DisplayNameGeneration` to override `@DisplayName`.**
It never does. The explicit annotation wins, always — the guide states it twice. A class
where half the methods have `@DisplayName` and half rely on the generator produces a report
in two different styles.

**★ Emoji and box-drawing characters in display names.**
Supported, and they end up in XML surefire reports, CI dashboards, Slack notifications and
terminal output with varying encodings. The guide's own examples use them; your build
server may not thank you.

**★ Naming tests after methods.**
`testCalculate1` through `testCalculate9`. No generator repairs this, because the
information was never written down.

**★ Relying on a display name to make an unclear test clear.**
If the body needs a sentence of explanation, the name is compensating for a test that does
too much. Split it.

**★ Changing the default generator project-wide mid-project.**
Every test's report name changes at once, which breaks flaky-test dashboards, test-history
graphs and any tooling keyed on display name rather than on the unique id.

**★ Assuming the display name is the test's identity.**
It is not. The platform identifies tests by a unique id derived from the class and method.
Two tests can share a display name; tooling that keys on the display name will merge them.

## Interview questions

**★ What is the precedence between `@DisplayName`, `@DisplayNameGeneration` and the
default generator?**
`@DisplayName` first, always. Then the generator named by `@DisplayNameGeneration` on the
class or an enclosing class. Then the generator configured by
`junit.jupiter.displayname.generator.default`. Then `DisplayNameGenerator.Standard`.

**★ Which built-in generator would you adopt and why?**
`ReplaceUnderscores`, configured once as the project default. It gives readable report
output from the method name itself, so there is exactly one name to keep correct —
`@DisplayName` requires two and they drift.

**★ What does `IndicativeSentences` do?**
It builds the display name by concatenating the names of the test and its enclosing
classes into a sentence, with a configurable separator and an underlying generator via
`@IndicativeSentencesGeneration`. With `@Nested` classes carrying "when …" fragments, the
report reads as a specification.

**★ What changed about display names in JUnit 6.0?**
Non-printable control characters are now replaced with textual representations — `<CR>`,
`<LF>`, and the Unicode replacement character for anything else. It applies to Jupiter,
`@SuiteDisplayName`, and any engine subclassing `AbstractTestDescriptor`.

**★ Is a display name a stable identifier for a test?**
No. The Platform's unique id is derived from the class and method; the display name is
presentation. Two tests may legitimately share one, and CI tooling that tracks flakiness by
display name will conflate them.

**★ What makes a test name good, independent of the mechanism?**
It names the circumstance and the expected behaviour, and it does not name the method under
test. The test to apply: read the name alone, out of context, and see whether you could
state the rule of the system it defends.
