**[06g](06g-the-clocks-you-do-not-own.md) listed the seams: `DateTimeProvider` for Spring Data
auditing, `source` for Hibernate, nothing at all for the database. When you have taken every seam
available and the value still comes from a clock you do not own, you are left asserting on
something you did not choose — and this is where suites acquire the tolerance that grows every
quarter. There is a better move, and it is not a bigger number: measure the window instead of
guessing it. The second half of this chunk is the other reason a timestamp comes back "wrong" when
nothing is wrong at all — precision.**

## Measure the window, do not guess a tolerance

The reflex is `isCloseTo(Instant.now(), within(5, SECONDS))`. That five is a guess about how long
CI will take, and its whole history is being widened: five seconds, then thirty, then a minute,
until the assertion excludes nothing. Under parallel execution a test can be descheduled for
arbitrarily long ([12 · Parallel execution](../01-junit-5/12-parallel-execution.md)), so no
constant is safe.

Capture the bounds instead:

```java
Instant before = Instant.now();
Order saved = repository.save(anOrder().build());
Instant after = Instant.now();

assertThat(saved.getCreatedAt()).isBetween(before, after);
```

That cannot flake for scheduling reasons, because the bound is **measured**: the operation took as
long as it took, and the generated timestamp is inside that interval by construction. If the
machine stalls for a minute, the window is a minute wide and the assertion still holds — and it
still fails if the timestamp is a day out, which is the failure you actually wanted to catch.
`isBetween` is inclusive at both ends, which is what you want here; `isStrictlyBetween` would
reject a timestamp landing exactly on a bound, which is entirely possible at millisecond
precision.

The full catalogue — `isCloseTo`, `within` versus `byLessThan`, `isBetween` versus
`isStrictlyBetween`, `isCloseToUtcNow`, and why the `isEqualToIgnoringX` family is a trap — belongs
to [02 · AssertJ · 08b · Dates and times](../02-assertj/08b-dates-and-times.md).

⚠️ The window assumes **one clock**. If the timestamp is generated by a database on another host,
`before` and `after` come from the JVM and the value comes from the engine, and the skew between
them is unbounded. On a Testcontainers PostgreSQL the container shares the host's clock so it
usually holds; against a shared or remote engine it does not, and the honest assertion there is
about the *relationship between two database-generated values*, not their relationship to a JVM
instant.

## Assert the property, not the value

Before reaching for any temporal assertion, ask what the test is actually about. Most assertions
on a generated timestamp are not about time at all:

| What you wrote | What you meant | Better assertion |
|---|---|---|
| `createdAt` is close to now | the row was created by this call | `isNotNull()`, and assert the *business* fields |
| `updatedAt` is after `createdAt` | the update path ran | assert the field the update changed |
| `expiresAt` is 30 days out | the policy is 30 days | fix the clock and assert a literal |

The third row is the important one: if you *can* control the clock, do that instead — a literal
expectation is strictly better than any tolerance ([06](06-random-and-time.md)). Reach for a
window only after the seams in [06g](06g-the-clocks-you-do-not-own.md) are exhausted.

## Precision: the value comes back different and nothing is wrong

Even when you own the clock, the value that returns is not always the value you wrote. The JVM
clock's resolution is unspecified — `Clock.systemUTC()` is documented only as *"based on the best
available system clock. This may use `System.currentTimeMillis()`, or a higher resolution clock if
one is available"* — while the column has a fixed precision. Write microseconds into a
`timestamp(3)` and the read-back value is truncated, so `assertThat(read).isEqualTo(written)` fails
on a difference no human would call a difference.

Three fixes, in order of preference:

**1 · Truncate at the source.** Make the production bean
`Clock.tick(Clock.systemUTC(), Duration.ofMillis(1))` ([06e](06e-the-clock-bean.md)). The
application then never produces a value the column cannot hold, and the problem stops existing
everywhere at once rather than being handled at each assertion.

**2 · Truncate where the value is created.**

```java
Instant createdAt = clock.instant().truncatedTo(ChronoUnit.MILLIS);
```

Same effect, narrower blast radius — and easier to forget at the next call site, which is why it
is second.

**3 · Assert with a tolerance matched to the column, not to CI.**

```java
assertThat(read).isCloseTo(written, within(1, ChronoUnit.MILLIS));
```

Last, because a tolerance introduced to fix a precision problem is invariably reused later to
paper over a clock problem, and by then nobody remembers which it was for.

⚠️ Storing `LocalDateTime` rather than `Instant` adds a **zone** conversion to the round trip on top
of the precision one, and JDBC drivers differ in which zone they apply.
[Phase 7 · Instant in the data](../../phase-7-io-time-stdlib/01-java-time/03-instant-in-the-data.md)
is the modelling argument; the testing consequence is that the value now has two independent ways
to come back different, and the failure message looks the same for both.

## Ordering, which is where ties become bugs

A timestamp is a bad sort key and a test is where you find that out. Two rows written in one
PostgreSQL transaction with `now()` carry **identical** timestamps by design — *"their values do
not change during the transaction"* — and two rows written by a millisecond-truncated JVM clock
carry identical timestamps whenever the code is fast, which is most of the time.

```sql
-- a tie, and the order returned is whatever the plan produced
SELECT * FROM events WHERE aggregate_id = ? ORDER BY occurred_at;
```

```sql
-- deterministic
SELECT * FROM events WHERE aggregate_id = ? ORDER BY occurred_at, sequence_no;
```

If a test asserts on the order of two rows sorted by a timestamp, either the production query needs
a tiebreaker or the fixture needs distinct literal timestamps — usually both. A test that passes
today because the plan happened to return insertion order is
[01b](01b-what-the-fix-is-not.md)'s kind of accident: green, and evidence of nothing.

## Gotchas

**★ A tolerance chosen to survive CI rather than to describe the value.**
`within(5, SECONDS)` is a guess about scheduling, and its documented life cycle is being widened
until it asserts nothing. Under parallel execution no constant is safe, because a test can be
descheduled for arbitrarily long. A measured `before`/`after` window scales with the machine and
never needs adjusting.

**★ Comparing a database-generated timestamp to `Instant.now()` from the JVM.**
Two hosts, two clocks, unbounded skew. The window trick is only sound when the database shares the
host's clock — true for a Testcontainers container on the same machine, not true for a shared or
remote engine. Against a remote engine, assert the ordering of two database-generated values
rather than their relationship to a JVM instant.

**★ `isStrictlyBetween` on a measured window.**
The bounds were produced by the same clock as the value, at millisecond or coarser resolution, so
the value landing exactly on `before` or `after` is not a corner case — it is common. `isBetween`
is inclusive; use it.

**★ A precision mismatch diagnosed as a clock bug.**
`timestamp(3)` truncates a microsecond-precision `Instant`, so the read-back value differs from the
written one by less than a millisecond and the equality assertion fails. The usual response is to
widen a tolerance to five seconds, which then hides a genuine clock problem for a year. Truncate at
the source with `Clock.tick`, and keep any remaining tolerance matched to the column's precision.

**★ Assuming the JVM clock's resolution.**
The javadoc promises only *"the best available system clock. This may use
`System.currentTimeMillis()`, or a higher resolution clock if one is available"*. A test that
depends on two reads differing, or on nanosecond precision surviving a round trip, depends on
something undocumented and platform-specific.

**★ Asserting `isAfter` between two rows written in the same transaction.**
If the timestamps came from `now()` they are equal by design and `isAfter` fails; if they came from
a truncated JVM clock they may be equal by coincidence and the test is flaky rather than broken.
Order by something that is genuinely ordered — a sequence, an explicit sort key — and assert on
that.

**★ A timestamp used as the only `ORDER BY` key.**
Ties are not rare; they are the normal case for rows written in one transaction or in one
millisecond. The test that "passes" is relying on the plan returning insertion order, which changes
with statistics, with an index, or with a version upgrade. Add a tiebreaker to the production query
and distinct literals to the fixture.

**★ Asserting on `updatedAt` to prove the update path ran.**
It proves a timestamp changed, which is one of the weakest facts available, and it needs a
tolerance to state. Assert on the field the update was supposed to change; if there is no such
field, ask what the update was for.

**★ Reaching for a window when the clock was actually injectable.**
A measured window is the fallback for values produced by clocks you do not own. If the value came
from your own service, fix the clock and assert a literal — a window on a controllable timestamp is
a weaker assertion dressed as a careful one.

## Interview questions

**★ How do you assert on a timestamp your code did not choose, without a growing tolerance?**
Capture the window. Read `Instant.now()` immediately before the operation and immediately after,
then assert that the value `isBetween` those two. The bound is measured rather than guessed, so it
cannot flake because CI was slow — the window simply grows with the operation, while still failing
if the timestamp is a day out. A fixed tolerance like `within(5, SECONDS)` is a guess about
scheduling and gets widened every time it fails until it no longer asserts anything, and under
parallel execution no constant is defensible because a test can be descheduled for arbitrarily
long. The window assumes one clock, though: if the timestamp is generated by a remote database,
compare database-generated values with each other instead.

**★ An entity's `createdAt` comes back from the database differing from what you wrote by a fraction of a millisecond. What is going on and how do you fix it?**
A precision mismatch, not a clock bug. The JVM clock's resolution is unspecified — the javadoc only
says "the best available system clock. This may use `System.currentTimeMillis()`, or a higher
resolution clock if one is available" — and on a modern platform it typically exceeds what a
`timestamp(3)` column can store, so the value is truncated on the way in. Fix it at the source:
make the production clock `Clock.tick(Clock.systemUTC(), Duration.ofMillis(1))` so the application
never produces a value the column cannot hold. Failing that, truncate where the value is created,
or assert with a tolerance matched to the column's precision rather than to CI's mood. Widening the
tolerance to seconds "fixes" it and destroys the assertion.

**★ A test asserts that two events come back in the order they were written and it fails intermittently. What do you look at?**
Whether the sort key can tie. If the rows were written in one transaction with `now()`, PostgreSQL
gives them the same timestamp deliberately — the manual calls a transaction-wide consistent "now" a
feature — so the `ORDER BY` has nothing to distinguish them and the returned order is whatever the
plan produced. If they were written by application code with a millisecond-truncated clock, they
tie whenever the code is fast. Either way the fix is the same shape: a real tiebreaker in the
production query (a sequence, an explicit ordering column) and distinct literal timestamps in the
fixture, so the ordering is a property of the data rather than of the execution plan.

**★ When is a tolerance the right answer rather than a smell?**
When the value genuinely comes from a clock you cannot reach and a window cannot be measured —
typically a timestamp set by a remote system whose clock you do not share. Then the tolerance is
expressing a real, known bound (clock skew across hosts) rather than a guess about your CI
machine's load, and it should be documented as such and sized to the skew, not to the last failure.
Everywhere else there is a better assertion available: fix the clock and assert a literal, wire a
`DateTimeProvider`, or measure the window.

**★ You inherit a suite where every timestamp assertion is `isCloseTo(now(), within(30, SECONDS))`. Where do you start?**
By sorting them into three piles. The ones whose value comes from your own code get the clock
injected and a literal expectation — that is the largest pile and it also removes real bugs, not
just flakiness. The ones whose value comes from Spring Data auditing get a `DateTimeProvider` backed
by the same clock, after which they too can assert a literal. The remainder — database defaults,
third-party systems — get a measured window, or get their assertion deleted, because in a
surprising number of cases `isCloseTo(now(), within(30, SECONDS))` was never testing anything: it
was asserting that a clock exists.
