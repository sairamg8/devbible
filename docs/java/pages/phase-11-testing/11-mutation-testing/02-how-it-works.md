**Mutation testing is conceptually trivial and computationally brutal: break the code, run the
tests, repeat a few thousand times. Every mutation testing system that is actually usable is
usable because of the shortcuts it takes, and PIT's shortcuts are the reason it can analyse a
whole codebase where its predecessors handled one class at a time. Four decisions do all the work
— mutate bytecode rather than source, measure per-test line coverage up front, insert mutants by
re-writing a class inside a JVM that is already running, and run only the covering tests, ordered
by speed. Everything surprising in the rest of this topic is a consequence of one of the four.**

## Decision 1 · It mutates bytecode, not source

PIT never touches your `.java` files and never produces mutated source. Its docs:

> *"Mutations are performed on the byte code generated by the compiler rather than on the source
> files. This approach has the advantage of being generally much faster and easier to incorporate
> into a build, but it can sometimes be difficult to simply describe how the mutation operators
> map to equivalent changes to a Java source file."*

Three consequences you will meet:

**It needs your compiler's debug information.** From basic concepts:

> *"In order to do this PIT requires that the following debug information is present in the
> bytecode: Line numbers; Source file name"*

Without it, pitest cannot map a mutated instruction back to a line, cannot use the line coverage
it gathered, and cannot render a report. Its error catalogue has dedicated entries for both
failures — *"No classes found with line number debug information. All classes should be compiled
with source and line number debug information."* and *"The class %s does not contain source debug
information."* Maven and Gradle both emit debug info by default, so this bites only builds that
have deliberately turned it off to shrink jars.

**It mutates what the compiler produced, including what you did not write.** A `record`'s
generated `equals`, `hashCode` and `toString`; the synthetic class behind a `switch` on a `String`;
the `values()` array copy in an enum; Lombok's generated setters. Pitest ships filters for exactly
these, on by default — `FRECORD` (*"Filters mutations in compiler generated record code"*),
`FENUM`, `FESWITCH`, `FSTRSWITCH`, `FASSERT` (*"Filters mutations in compiler generated code for
assertions"*) and `lombok` (*"Filters out junk mutations generated by lombok"*). Every one of those
filters exists because someone once got a report full of mutants in code they never typed.

**It cannot show you the mutated source, and it says so.** The FAQ:

> *"Pitest mutates bytecode. It does not produce mutated source code, so is not able to display
> it. In theory, it is possible to generate source code from the mutated bytecode using a
> decompiler, but in practice, the results are poor for anything other than very simplistic
> code."*

What the report shows instead is the source line, plus a human-readable description of the
mutator that fired on it. Reading that description as the change it would make to the source is
usually right and occasionally misleading — [chunk 03](03-mutators.md) has the cases where the
bytecode and the source diverge, and the `MATH` mutator on a member-variable `i++` is the classic.

## Decision 2 · A coverage pass first, per test

Before generating anything, PIT runs your suite once and records, for each test case, which lines
it executed. From basic concepts:

> *"Before running the tests PIT performs a traditional line coverage analysis for the tests, then
> uses this data along with the timings of the tests to pick a set of test cases targeted at the
> mutated code. This approach makes PIT much faster than previous mutation testing systems such as
> Jester and Jumble, and enables PIT to test entire code bases, rather than single classes at a
> time."*

Note the granularity: **per test case**, not per suite. That is what lets pitest answer "which
tests could possibly notice a change on line 47 of `PricingService`" with a short list rather than
"all of them".

Two immediate consequences:

**Your suite must be green.** The whole method reads "a test failed" as "the mutant was detected".
If tests were failing already, that reading is worthless. Pitest aborts, with the message defined
in `org.pitest.help.Help`:

> *"%s tests did not pass without mutation when calculating line coverage. Mutation testing
> requires a green suite."*

**Uncovered code is nearly free.** From the FAQ:

> *"Due to the way PIT picks which tests to run, there is little or no execution time cost for
> mutations on lines that have no test coverage."*

Mutants are still *generated* for uncovered lines and still appear in the report, as
`NO_COVERAGE`. They just never get run against anything, because there is nothing to run.

## Decision 3 · Mutants are inserted into a running JVM

This is the decision that makes pitest fast and also the one that produces its weirdest edge
cases. PIT forks child JVMs — it calls them **minions** — and inside a minion it re-writes the
target class *after the JVM has already loaded and warmed it*. The FAQ, discussing why static
initializers are a problem, states the mechanism directly:

> *"Pitest inserts mutants into a jvm by re-writing the class after it has loaded. This is orders
> of magnitude faster than starting a new jvm or creating a new classloader, but code in static
> initializer blocks is not re-run so the mutants have no effect."*

So the cost of one more mutant is roughly the cost of one class redefinition plus the runtime of a
handful of tests — not the cost of a JVM start, a Spring context, and a full suite. That is the
difference between mutation testing being a research technique and a usable one.

The price is paid in [what pitest cannot mutate](02b-what-it-cannot-mutate.md), which is its own
chunk.

## Decision 4 · Test selection and ordering

For each mutant, pitest picks the tests to run. The FAQ:

> *"PIT chooses and prioritises tests based on three factors: Line coverage; Test execution speed;
> Test naming convention"*

and:

> *"Per test case line coverage information is first gathered and all tests that do not exercise
> the mutated line of code are discarded. The remaining tests are then ordered by increasing
> execution time - test cases that belong to a class that is identified as a unit test for the
> mutated class are however weighted above other tests. A class is considered to be the unit test
> for a particular class if it matches the standard JUnit naming convention of FooTest or TestFoo.
> Unlike earlier systems, PIT does not require that your tests follow this naming convention in
> order for it to work. Test names are used only as part of a heuristic to optimise run order."*

Three things fall out of this:

- **Execution stops at the first failure.** Once one test fails, the mutant is killed and there is
  nothing more to learn, so the remaining covering tests are not run. That is why fast tests go
  first: the cheapest possible way to reach a kill.
- **Killed mutants are cheap; surviving mutants are expensive.** A survivor is a mutant for which
  *every* covering test ran to completion without failing. A class covered by twenty slow
  integration tests and no unit tests pays twenty full test runs per surviving mutant.
- **`FooTest` naming is a performance optimisation, not a requirement.** Rename `PricingServiceTest`
  to `PricingSpec` and pitest still works; it just loses a hint about which tests to try first.

There is one exception worth knowing: `fullMutationMatrix`, documented as

> *"When set to true causes pitest to continue processing after a test fails and record addition
> failing tests when XML output is enabled. This is a partially supported feature added due to
> demand from the research community. Other pitest features are not guaranteed to work correctly
> when it is enabled."*

Turning it on to get "which tests killed this mutant" data removes the early exit and multiplies
the cost. The documentation's own hedge — *"other pitest features are not guaranteed to work
correctly"* — is the reason not to.

## Gotchas

**★ A red suite is not a slow mutation run — it is no mutation run at all.**
Pitest computes coverage first and refuses to continue if any test fails, naming the count in its
error. Teams that habitually run with one or two known-failing tests, or with `-DfailIfNoTests` or
`testFailureIgnore` masking them, discover this the first time they add pitest. Note the Maven
plugin's `failWhenNoMutations` defaults to `true` as well, so an empty or badly-filtered scope also
breaks the build rather than passing quietly.

**★ Turning off debug information to shrink jars silently disables pitest.**
`-g:none`, or a shading step that strips `LineNumberTable`, leaves a build where JaCoCo reports no
line coverage and pitest refuses to run with *"No classes found with line number debug
information"*. This appears in obfuscated or heavily-optimised release builds and never in the
developer build, so it surfaces in CI only.

**★ Anything that makes a test slow makes every surviving mutant on that line expensive.**
A killed mutant stops at the first failing test. A survivor runs every covering test to completion.
So the worst possible input to pitest is a class whose only coverage comes from slow
`@SpringBootTest` or Testcontainers tests *and* which has weak assertions — precisely the case you
most wanted to measure. The fix is not a pitest setting; it is unit tests for that class, which is
[05 · The test pyramid](../05-the-test-pyramid/README.md)'s argument arriving from an unexpected
direction.

**★ Renaming test classes away from `FooTest` costs performance, not correctness.**
The naming convention is documented as a run-order heuristic only. But losing it on a large
codebase means pitest tries an arbitrary fast test before the obvious unit test, so more tests run
per mutant. If a team migrated to `FooSpec` or `FooShould` and pitest got slower, that is the
mechanism.

**★ `fullMutationMatrix` looks like the feature you want and is documented as partially supported.**
"Which tests killed this mutant" is genuinely useful information, and enabling it disables the
first-failure exit, so every covering test runs against every mutant. Pitest's own documentation
warns that other features are not guaranteed to work with it. It is an analysis tool for a
one-off investigation, not a setting to leave on.

**★ Mutants are never written to disk unless you ask, so they cannot leak into a release.**
The FAQ: *"The mutations that PIT generates are held in memory and never written to disk, except if
explicitly enabled using the EXPORT feature. But even then they are only dumped inside the report
directory."* Worth knowing because "we can't run a tool that deliberately corrupts our classes" is
a real objection from people who have not read this.

## Interview questions

**★ How does PIT avoid re-running the whole suite for every mutant?**
Two mechanisms. First, it gathers per-test-case line coverage in an initial clean run, so for any
mutant it knows the exact set of tests that execute the mutated line and can discard all the
others; uncovered lines cost essentially nothing because there is no test to run. Second, it does
not restart a JVM per mutant — it forks minion JVMs and re-writes the target class inside one that
is already running and warm, then runs the covering tests in ascending order of measured execution
time, stopping at the first failure. The combination is what pitest's docs credit for making it
usable on whole codebases rather than single classes.

**★ Why does mutating bytecode rather than source change what you see in the report?**
Because the bytecode contains code you never wrote. Records, enum switches, string switches,
assertions and Lombok output all compile to instructions that the mutators will happily mutate,
producing "junk" mutants in code with no source line a human would recognise as theirs. Pitest
ships default-on filters for each of those categories. It also means pitest cannot show you the
mutated source — its docs say decompiling the mutant gives poor results — so the report shows the
original line plus a description of the operator that fired.

**★ Does PIT need my tests to be named `SomethingTest`?**
No. The naming convention is used only as a heuristic to run the most likely killer first; the FAQ
says so explicitly. Coverage, not naming, decides which tests are candidates. The convention has a
measurable effect on run time on large projects and none at all on correctness.

**★ Why must the suite pass before PIT will run, and what would break if it did not enforce that?**
Because pitest's signal is "at least one covering test failed while this mutant was loaded". A
test that fails regardless of the mutant would mark every mutant on every line it covers as
killed, inflating the score without any relationship to the tests' actual strength — and it would
do so most on exactly the lines you least trust. Enforcing green up front makes "failed" mean
"detected the change", which is the only reading that makes the technique meaningful.
