**Bytecode mutation sees everything the compiler emitted, and the compiler emits a great deal you
did not write. Left unfiltered, a mutation report on a modern Spring service is mostly mutants in
generated `record` accessors, Lombok setters and the hash-lookup table behind a `switch` on a
`String` — none of which anyone will ever write a test for. PIT's answer is a stack of
interceptors, most of them on by default, each addressable by a short feature name. This chunk
lists them, states which are on, explains the two that are off and should probably be on, and
explains why "turn off the filters to find more bugs" is the single most reliably
counterproductive thing you can do to a pitest configuration.**

## The filter inventory

Filters are pitest **features** — named strings you switch with `+name` and `-name`. Read from the
`Feature.named(...)` declarations in pitest 1.30.0's source, quoting their own descriptions:

| Feature | Default | Description (verbatim from source, where the source gives one) |
|---|---|---|
| `FLOGCALL` | on | *"Filters mutations in code that makes calls to logging frameworks"* |
| `FRECORD` | on | *"Filters mutations in compiler generated record code"* |
| `FENUM` | on | Filters mutations in compiler-generated enum code |
| `FESWITCH` | on | Filters mutations in the compiler's enum-`switch` scaffolding |
| `FSTRSWITCH` | on | Filters mutations in the compiler's `String`-`switch` scaffolding |
| `FASSERT` | on | *"Filters mutations in compiler generated code for assertions"* |
| `lombok` | on | *"Filters out junk mutations generated by lombok"* |
| `FRETEQUIV` | on | *"Filters return vals mutants with bytecode equivalent to the unmutated class"* |
| `FSEQUIVDIV` | on | *"Filters equivalent mutations of the form x * -1 -> x / -1"* |
| `FSEQUIVEQUALS` | on | *"Filters equivalent mutations that affect only performance in short cutting equals methods"* |
| `FINFINC` | on | *"Filters mutations to increments that may cause infinite loops"* |
| `FFLOOP` | on | Filters mutations to `for`-loop counters that would loop forever |
| `FINFIT` | on | Filters mutations that would produce an infinite iterator loop |
| `FFEACH` | on | Filters mutations in the compiler's `for`-each scaffolding |
| `FKOTLIN` | on | Filters junk mutations in Kotlin-generated bytecode |
| `FGROOVY` | on | Filters junk mutations in Groovy-generated bytecode |
| `funmodifiablecollection` | **off** | *"Filter mutations to defensive wrappers such as unmodifiableCollection on return or field write"* |
| `nofirstline` | **off** | Skips mutations on the first line of each method |
| `CLASSLIMIT` | **off** | Caps mutants per class — `+CLASSLIMIT(limit[42])` |
| `EXPORT` | **off** | Writes the mutated class files into the report directory |

Note the shape of the list: the three `FSEQUIV*`/`FRETEQUIV` entries and the three timeout
entries (`FINFINC`, `FFLOOP`, `FINFIT`) exist to remove mutants that are *unkillable* or
*expensive*, not merely noisy — they are the reason a default pitest run does not report a wall of
timeouts and permanent survivors.

The syntax, from the quick-start page:

> *"Some features are enabled by default and must be disabled with -featureName, others must be
> enabled explicitly with +featureName."*

```xml
<features>
  <feature>-frecord</feature>
  <feature>+auto_threads</feature>
</features>
```

Feature names are matched case-insensitively in practice — the documentation's own example writes
`-frecord` for the feature the source names `FRECORD`. New in 1.30.0: *"Accept comma separated
feature parameters"*, so one string may carry several.

**`extraFeatures` exists specifically so a command line does not clobber a POM.** From the docs:

> *"This parameter allows additional features to be activated from the command-line or build
> scripts without overwriting existing configuration."*

```
mvn -Ppitest -DextraFeatures="+CLASSLIMIT(limit[20])" test-compile org.pitest:pitest-maven:mutationCoverage
```

Using `-Dfeatures=` there instead would silently discard every feature the POM had set, which is
the bug `extraFeatures` was added to prevent.

## Getting the authoritative list

The table above is 1.30.0 read from source, and it will drift. Pitest prints the real list for the
version you are running:

> *"features — List of pitest features to enable or disable. Available options are shown in the
> console output when verbose logging is enabled. Additional features may be added by pitest
> plugins."*

```xml
<configuration>
    <verbose>true</verbose>
</configuration>
```

That last sentence matters: **plugins add features.** arcmutate's git integration appears as
`+GIT(from[HEAD~1])` and its history implementation as `+arcmutate_history(run_tests[false])` —
feature strings that simply do not exist until the plugin is on pitest's classpath, and that fail
as unknown options if it is not.

## Two filters that are off, and worth turning on

**`funmodifiablecollection`** — *"Filter mutations to defensive wrappers such as
unmodifiableCollection on return or field write"*. If your domain objects do this:

```java
public List<OrderLine> lines() {
    return Collections.unmodifiableList(this.lines);
}
```

then `NON_VOID_METHOD_CALLS`-style mutation of the wrapper produces a mutant that returns the
mutable list. Almost no test suite asserts that a returned collection throws on modification, so
the mutant survives permanently. Turning the filter on removes a class of survivor you were never
going to kill:

```xml
<features>
  <feature>+funmodifiablecollection</feature>
</features>
```

**`nofirstline`** skips the first line of each method. This is aimed at codebases with a
guard-clause or logging convention on line one of everything; it is bluntly a heuristic, and unlike
the others it can hide real findings. Reach for it only if you have looked at the report and know
what it is removing.

## Other JVM languages

The FAQ is unusually blunt:

> *"Pitest mutates bytecode, does that mean it works with all JVM languages? Sort of yes, but
> mainly no. Although Pitest can mutate the bytecode of other languages, the results are not
> generally useful. Unless Pitest explicitly supports the language, the mutations it generates will
> include many 'junk' mutations - mutants that do not correspond to a source file a programmer
> might produce. Currently supported languages are: Java; Kotlin (via the Arcmutate kotlin
> plugin)."*

So Kotlin is supported only through the commercial plugin, notwithstanding the `FKOTLIN` filter in
the open-source build — that filter removes some junk, not enough to make the report actionable.
Release 1.30.0 added *"Check non jvm lang dirs"*, and 1.25.6 *"Auto disable quarkus jacoco
extension"*: the project is still actively working on the seams between pitest and non-Java
toolchains, which is itself a signal about how rough they are.

## Gotchas

**★ Disabling a filter to "get more mutants" reliably makes the report worse.**
`-frecord`, `-flogcall` or disabling `lombok` produces hundreds of extra mutants in code nobody
wrote and nobody will test. The score drops, the report becomes unreadable, and the run gets
slower. These filters are not hiding findings from you; they are the reason the findings are
visible.

**★ Using `features` on the command line silently discards the features set in your POM.**
`-Dfeatures="+EXPORT"` replaces the whole list. That is exactly why `extraFeatures` exists, and its
documentation says so. A one-off command-line investigation that turns off `FRECORD` and `lombok`
by accident produces a completely different mutant set from CI, and nothing warns you.

**★ Feature names from a blog post may not exist on your version, and a plugin feature does not exist without the plugin.**
`+GIT(...)` and `+arcmutate_history(...)` come from arcmutate. `CLASSLIMIT` replaced
`maxMutationsPerClass` in 1.2.3. The authoritative list is what pitest prints with `verbose`
logging enabled on the version you are running — read that before copying a feature string.

**★ `funmodifiablecollection` is off by default and is probably the one you want on.**
A defensive `Collections.unmodifiableList(...)` on a getter generates a mutant that returns the
mutable list, and essentially no suite asserts that a returned collection rejects modification. The
result is a permanent survivor in every value object you wrote carefully. The filter exists; it is
just not on.

**★ Kotlin without the commercial plugin produces a report you cannot act on.**
Open-source pitest will mutate Kotlin bytecode and generate mutants in null-check preambles,
`copy`, `componentN` and delegated properties. The `FKOTLIN` filter removes some of this and the
FAQ still says the results *"are not generally useful"*, listing Kotlin as supported only via
arcmutate. On a Kotlin service, the choice is that plugin or not doing this.

**★ `EXPORT` is the only way mutated classes ever reach the disk, and it is off.**
If someone asks whether a mutation testing tool could ship a corrupted class into production, the
answer is in the FAQ: mutants are held in memory, and even with `EXPORT` on they are written only
inside the report directory. This objection comes up in regulated environments and is worth
answering from the source rather than from confidence.

## Interview questions

**★ A colleague turns off `FRECORD` and `lombok` "so we see the real picture". What do you say?**
That the picture gets bigger and less real. Those filters remove mutants in bytecode the compiler
and an annotation processor generated — `record` accessors and `equals`, Lombok's setters and
builders — for which the only possible test is a test of `javac` and Lombok. The report fills with
survivors nobody will act on, the mutation score falls for reasons unrelated to the tests, and
because survivors are the expensive case (every covering test runs to completion) the run gets
slower too. If the concern is that the filters hide something, the way to check is to look at what
they removed on one class, not to disable them project-wide.

**★ How do you find out which features your version of PIT supports?**
Turn on `verbose` and read the console output — the Maven documentation states that the available
options are printed there, and adds that plugins may contribute more. That matters because feature
names change between releases (`maxMutationsPerClass` became the `CLASSLIMIT` feature in 1.2.3) and
because arcmutate's `GIT` and history features exist only when its jars are on pitest's classpath.
Copying a feature string from a blog post and getting "unknown option" is usually one of those two.

**★ What is `extraFeatures` for and why does it exist separately from `features`?**
Because `features` is a list, and setting it from the command line replaces the list rather than
adding to it — so `-Dfeatures="+EXPORT"` for a one-off investigation would discard every filter
decision the POM had made, quietly changing the mutant set. `extraFeatures` is applied on top of
whatever is already configured. The documentation gives the intended use directly: activating
arcmutate's git and history features from a CI script without disturbing the project's own
configuration.

**★ Your value objects return defensive copies and pitest reports a survivor on every one of them. What now?**
That is the `funmodifiablecollection` case. The mutant strips the `Collections.unmodifiableList`
wrapper and returns the underlying mutable list, and nothing in a normal suite fails, because
almost nobody writes a test asserting that a getter's return value throws
`UnsupportedOperationException`. You have two honest options: write that assertion once per value
object, which is real but low-value work, or enable the filter — `+funmodifiablecollection` — which
pitest ships precisely because this survivor is not worth anyone's time. Deciding a category of
mutant is not worth killing, and recording that decision in the build file, is a legitimate move;
leaving twenty permanent survivors in the report is not.
