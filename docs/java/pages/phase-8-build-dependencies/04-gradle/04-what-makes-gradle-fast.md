**"Gradle is faster" is not one claim, it is four unrelated mechanisms with
different scopes, different enablement and different failure modes. Up-to-date
checks skip work within a workspace. The build cache reuses outputs across
workspaces and machines. Incremental compilation recompiles a subset of one
module's classes. The configuration cache skips the configuration phase
entirely. Knowing which one you are relying on is the difference between a
build that got faster and a team that switched on a cache and is disappointed.**

| Mechanism | Skips | Scope | Default in Gradle 9 |
|---|---|---|---|
| Up-to-date checks (incremental build) | a task's action | this workspace, since the last build | **on** |
| Build cache | a task's action, by fetching its outputs | any build, any machine, ever | off — `org.gradle.caching=true` |
| Incremental compilation | recompiling unaffected classes | within one `JavaCompile` task | **on** |
| Configuration cache | the entire configuration phase | this workspace, per requested task set | off, but *recommended*; on for `gradle init` projects |

## Up-to-date checks

The baseline. Gradle fingerprints each task's declared inputs and outputs; if
neither changed since the last run the action is skipped and the task reports
`UP-TO-DATE`. Free, on by default, and entirely dependent on correct
input/output declarations — which is why chunk 1 dwelt on them. A task with
an undeclared input is skipped when it should have run, and that is not a bug
in Gradle.

## The build cache

The same intelligence with a wider reach. The docs put it exactly: task
output caching "allows Gradle to reuse task outputs from any earlier build in
any location", rather than only the previous build in the same workspace.

```properties
# gradle.properties
org.gradle.caching=true
```

A task must opt in with `@CacheableTask` — the Java, Groovy and Scala
compilers, the test tasks and the common quality plugins already do. The
cache key derives from the task type and its classpath, its output property
names, and the names and values of its annotated inputs. Notably the **task
path is not part of the key**, so an identical task in a differently-named
project can still hit.

There are two layers. The **local** cache is a directory under the Gradle
user home, on by default once caching is enabled. The **remote** cache is an
HTTP backend shared by the team and CI: Gradle checks local first, then
remote, and stores a remote hit locally.

The remote cache is where both the biggest wins and the biggest
disappointments live. Well fed, a developer's first build after pulling
`main` fetches CI's outputs instead of compiling. Badly configured — CI reads
but never writes, or some task has a non-reproducible input like a timestamp,
an absolute path or a hostname — hit rates sit near zero and nobody can say
why. **Hit rate is the metric**, and a build scan reports it along with the
per-task miss reasons.

## Incremental compilation

On by default. When sources change, Gradle works out which classes are
actually affected and recompiles those rather than the whole source set.

It degrades on purpose. Changes to an inlined compile-time constant, changes
on the annotation-processor path, or classpath changes Gradle cannot narrow
will force a full recompile of that task. That degradation is normal, and it
is one reason build times are less uniform than people expect — the same
one-line edit can cost a second or a minute depending on *which* line.

## The configuration cache

The newest mechanism and the most consequential. It serialises the *result*
of the configuration phase — the task graph and the state it references — and
reuses it when the same tasks are requested with the same inputs. On a large
multi-module build, configuration can be a large share of a short build;
skipping it is what makes `./gradlew :service:test` feel instant.

```properties
org.gradle.configuration-cache=true
```

Gradle 9.0 made it the **preferred** execution mode and enables it for
projects generated by `gradle init`, but it is still not on by default for
existing builds; Gradle's stated goal is to enable it by default in Gradle
10. The caution is justified — it imposes real constraints. Build logic may
not read arbitrary environment state at configuration time, may not reference
`Project` at execution time, and everything captured must be serialisable. An
incompatible build is reported as such, with the offending script lines
named, which makes the report a useful audit even before you enable it.

**Isolated Projects** continues the same road: it configures projects in
parallel and in isolation from each other, and it graduated from experimental
to incubating in Gradle 9.7. It is the deeper reason `allprojects {}` and
`subprojects {}` are discouraged — cross-project configuration is exactly
what isolation forbids.

## The daemon

A long-lived background JVM that Gradle reuses between invocations, on by
default. It matters more than it sounds. It keeps the JVM warm, so HotSpot's
JIT has already optimised the build code
([JIT compilation](../../phase-0-platform-jvm/07-jit-compilation.md)), and it
holds in-memory caches — file hashes, dependency resolution results, compiled
build scripts — across builds. Without it every invocation pays JVM startup
and cold interpretation.

The costs are equally real. It holds heap between builds
(`org.gradle.jvmargs` sizes it, and an undersized daemon spends the build in
GC), a stale daemon can hold corrupted cached state, and daemons accumulate —
a new one starts for each distinct JVM and JVM-args combination, so an IDE, a
terminal and a CI agent can each spawn their own.

```bash
./gradlew --status      # list daemons and their state
./gradlew --stop        # stop them
```

Maven ships no equivalent, though the third-party `mvnd` project exists to
provide one.

## What none of this buys you

Speed mechanisms have a precondition in common: **scale**. A remote cache
needs a team feeding it. ABI-based recompilation avoidance needs enough
modules for "recompile one instead of twelve" to mean anything. The
configuration cache needs a configuration phase large enough to be worth
skipping. On a five-module service, all four together save seconds on a build
that already took seconds — which is the argument chunk 5 makes when it comes
to choosing a tool.

## Gotchas

**Symptom:** the build cache is enabled and the hit rate is near zero
**Cause:** some task input is not reproducible across machines — an absolute path, a timestamp baked into a jar, a hostname, a JDK that differs between CI and laptops — so keys never match
**Fix:** make archives reproducible, use toolchains so the compiler version matches everywhere, and read the cache-miss reasons in a build scan rather than guessing

**Symptom:** CI builds are fast and developers see no benefit from the remote cache
**Cause:** CI is configured read-only, or only CI writes but its build configuration is one nobody reproduces locally
**Fix:** let a trusted CI job push to the cache and let developers pull; align Gradle version, JDK and toolchain so the keys can match at all

**Symptom:** `--configuration-cache` reports the build incompatible with a list of problems
**Cause:** build logic reads environment or project state at configuration time, or a task action holds a reference to `Project`
**Fix:** convert those reads into declared inputs and lazy `Provider`s; the report names exact script lines, so treat it as the to-do list

**Symptom:** a change to a `public static final int` upstream has no effect downstream until a clean build
**Cause:** compile-time constant inlining — the old value is already baked into the consumer's bytecode, and the ABI-based check sees no reason to recompile
**Fix:** a `javac` semantic rather than a Gradle bug; avoid exposing constants that change, or force a recompile when one does

**Symptom:** builds slow to a crawl and the daemon appears to thrash
**Cause:** the daemon heap is undersized for the build, so it spends its time in GC
**Fix:** raise `org.gradle.jvmargs` in `gradle.properties`; check with `./gradlew --status` and stop stale daemons with `--stop`

**Symptom:** several Gradle daemons are running and the machine is out of memory
**Cause:** one daemon starts per distinct JVM and JVM-args combination — IDE, terminal and CI each get their own
**Fix:** standardise `org.gradle.jvmargs` and the toolchain across IDE and CLI so they share a daemon; `--stop` clears the accumulation

**Symptom:** incremental compilation quietly stops helping after an annotation processor is added
**Cause:** a processor that does not declare itself incremental forces full recompilation of the source set
**Fix:** check the processor supports incremental annotation processing; a build scan reports the recompilation reason

**Symptom:** a task is cached but its outputs are wrong on a colleague's machine
**Cause:** the task declared incomplete inputs, so two genuinely different invocations produced the same cache key
**Fix:** fix the input declarations — an undercached-key task is a correctness bug, not a performance one, and `--rerun-tasks` only hides it

## Interview questions

**★ Someone says "Gradle is faster". Make them be specific.**
Four separate mechanisms: up-to-date checks (skip a task in this workspace),
the build cache (fetch a task's outputs from any earlier build anywhere),
incremental compilation (recompile a subset of classes inside one compile
task), and the configuration cache (skip the configuration phase entirely).
Different scopes, different defaults, different failure modes — "we turned on
caching" tells you nothing about which one is actually helping.

**★ Up-to-date checks vs the build cache — what is the real difference?**
Same fingerprinting intelligence, different reach. Up-to-date checks compare
against the previous build *in this workspace*; the build cache is keyed by
task inputs alone, so it can supply outputs produced by a different build, a
different directory or a different machine. That is also why cache keys must
be reproducible across machines while up-to-date checks can tolerate
machine-local details.

**★ What makes a task cacheable, and what goes into the key?**
The task type must be annotated `@CacheableTask` and its inputs and outputs
must be declared. The key comes from the task type and its classpath, the
output property names, and the names and values of the annotated inputs. The
task *path* is deliberately excluded, so identical work in differently-named
projects can share an entry.

**★ Why is the configuration cache not on by default yet?**
Because it constrains build logic: configuration must be deterministic and
serialisable, `Project` may not be referenced at execution time, and
environment reads must be declared as inputs. Many existing builds and
third-party plugins violate that. Gradle 9 made it the preferred mode and
enables it for newly generated projects, aiming to make it the default in
Gradle 10.

**★ What is the daemon buying, and what does it cost?**
A warm JVM whose JIT has already optimised the build code, plus in-memory
caches of file hashes, resolution results and compiled build scripts across
invocations. It costs resident heap between builds, it accumulates one daemon
per distinct JVM-args combination, and an undersized one spends the build in
garbage collection.

**★ Your remote build cache has a poor hit rate. How do you diagnose it?**
Read the cache-miss reasons in a build scan — they name the task and the
input that differed. The usual culprits are non-reproducible inputs (absolute
paths, timestamps in jars, a JDK that differs between CI and laptops) and a
CI setup that reads from the cache but never writes to it. Aligning the
toolchain and making archives reproducible is most of the fix.

**★ Why does the same one-line edit sometimes cost a second and sometimes a minute?**
Incremental compilation degrades to a full recompile for certain changes:
inlined compile-time constants, anything on the annotation-processor path,
and classpath changes Gradle cannot narrow. That is designed behaviour, not
a fault, and it is why average build time is a misleading metric compared
with the distribution.

**★ How is a build cache different from a dependency cache?**
The dependency cache stores downloaded artifacts — it saves network time. The
build cache stores *your own* task outputs keyed by their inputs — it saves
compute. Enabling one says nothing about the other, and "our builds are still
slow but everything is cached" almost always means only the dependency cache
is in play.
