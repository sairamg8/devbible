**OAuth 2.0 is not the first attempt and it is not obviously the better one. OAuth 1.0
delivered a stronger property — every request cryptographically signed by the client, so
possession of the token alone was not enough to use it — and the industry abandoned it
anyway. Understanding *why* explains most of what people find frustrating about OAuth2: it
did not fail to provide proof-of-possession, it deliberately traded it away for
implementability, and RFC 9700's push toward sender-constrained tokens is the industry
slowly buying it back.**

## The three pre-OAuth answers, and what each could not do

**HTTP Basic with the user's own credentials.** Covered in
[01 · The password anti-pattern](01-the-password-anti-pattern.md): all five of RFC 6749 §1's
failures, in their purest form.

**A shared, account-wide API key.** Better: it is not the password, so failures (1) and (2)
go away — the user can keep passwords, or drop them entirely, without breaking anything.
Failures (3), (4) and (5) survive intact. The key is unscoped, immortal, and usually
identical for every integration the account has enabled, so it cannot express *this client,
these resources, until this date*, and revoking it revokes everything.

**A forwarded session cookie.** The worst of the three in practice, because it looks
cheapest. It is a bearer credential for the entire account with no scope and a lifetime you
do not control, and revoking it means terminating every session the user has anywhere.

None of the three has a place to record **consent**. There is no moment at which the
resource owner is shown what is being asked for and says yes. That absence is the shape of
the hole OAuth 1.0 filled.

## What OAuth 1.0 actually did

RFC 5849's central idea is that the token is **not** sufficient on its own. Every request
carries a signature computed over the request itself, using a secret the client holds and
never transmits.

The client builds a **signature base string** (§3.4.1.1) by concatenating, with `&`
separators: the HTTP method in uppercase, the base string URI, and the normalized request
parameters. It signs that (§3.4) with one of three methods:

| Method | RFC 5849 § | What it uses |
|---|---|---|
| `HMAC-SHA1` | §3.4.2 | HMAC-SHA1 keyed with the concatenated client and token secrets |
| `RSA-SHA1` | §3.4.3 | RSASSA-PKCS1-v1_5 with a SHA-1 hash |
| `PLAINTEXT` | §3.4.4 | No signature at all — *"MUST be used with a transport-layer mechanism such as TLS or SSL"* |

Alongside the signature go the protocol parameters of §3.1 — `oauth_consumer_key`,
`oauth_token`, `oauth_signature_method`, `oauth_timestamp`, `oauth_nonce` — where the nonce
is, per §3.3, *"a random string, uniquely generated by the client to allow the server to
verify that a request has never been made before"*, and the timestamp is seconds since the
epoch. Nonce plus timestamp give the server replay detection.

🔴 **Read `PLAINTEXT` in that table again.** RFC 5849 itself offered a mode with no signature
that leans entirely on TLS. OAuth 2.0's much-criticised design decision was already present,
as an option, inside OAuth 1.0.

## The property OAuth 1.0 had that OAuth 2.0 gave up

Because the signature covers the request and the secret never travels, an OAuth 1.0 token
intercepted in transit is **not usable**. The attacker has the token and not the secret, and
cannot produce a valid signature for any request they want to make. This is
**proof-of-possession**: holding the credential is necessary but not sufficient.

OAuth 2.0's bearer tokens (RFC 6750) invert exactly this. Possession *is* sufficient. A
leaked access token — in a log, a `Referer` header, a crash report, an error page, a browser
extension — is immediately usable by anyone who finds it, for its whole remaining lifetime.
Everything OAuth2 does about that is compensating control: keep the lifetime short, keep it
off the URL, mandate TLS. Those are mitigations for a property the previous version did not
have.

## So why did OAuth 1.0 lose?

**Signing is brutally hard to get right, and it fails silently.** The signature base string
is a normalization problem, and normalization problems are where interoperability goes to
die. Every one of these produces a valid-looking request that the server rejects with an
opaque error:

- Percent-encoding rules that differ from the language's default URL encoder — most
  standard library encoders are wrong for this purpose in at least one character class.
- Parameter sorting, including how to order parameters with identical names.
- Whether the port belongs in the base string URI when it is the scheme's default.
- Which body parameters participate, and what happens for a body that is not
  form-encoded — which by the 2010s meant almost every body, because everything became JSON.
- Whether the proxy in front of the service rewrote the scheme, host or path before the
  signature was verified. TLS-terminating load balancers broke signatures constantly.

The failure mode is a `401` with no indication of *which* of those went wrong. Developers
lost days per integration.

**And 1.0 had a real vulnerability that needed a fix.** §2.2 introduced `oauth_verifier` —
*"the server MUST generate a verification code: an unguessable value passed to the client
via the resource owner and REQUIRED to complete the process"* — closing a session-fixation
hole in the original callback design. This is the direct ancestor of OAuth 2.0's
authorization code, and the same reasoning reappears in PKCE's `code_verifier`: bind the
completion of the flow to the party who started it.

**It also assumed the client can keep a secret.** HMAC-SHA1 with the client secret is
meaningless in JavaScript in a browser, or in a mobile binary anyone can unzip. As the
client population shifted from server-side web applications to SPAs and native apps, the
foundation stopped holding — and OAuth 2.0's public/confidential client distinction is the
explicit acknowledgement of that, covered in [02 · The four roles](../02-the-four-roles/README.md).

## What OAuth 2.0 changed, item by item

| OAuth 1.0 | OAuth 2.0 | Consequence |
|---|---|---|
| Per-request signature | Bearer token over TLS | Trivial client; a leaked token is instantly usable |
| Client secret needed to *use* a token | Secret only at the token endpoint, and only for confidential clients | Public clients (SPA, native) become expressible |
| One protocol | A **framework** with four grant types plus extensions | Fits more cases; two implementations may not interoperate |
| Signature methods | TLS, mandatory | Security moved from the application into the transport |
| `oauth_verifier` | The authorization code | Same idea, cleaner separation of channels |

The trade is stated plainly by RFC 6749 §1.8, which concedes the framework "on its own …
is likely to produce a wide range of non-interoperable implementations" and expects
"prescriptive profiles and extensions" to fix it. OIDC, RFC 9068 and RFC 9700 are those
profiles arriving over the following fifteen years.

## And the pendulum swinging back

Proof-of-possession was never a bad idea; it was an unaffordable one. It is returning now
that it can be bought rather than hand-rolled — RFC 9700 §2.2.1 recommends that
*"Authorization and resource servers SHOULD use mechanisms for sender-constraining access
tokens, such as mutual TLS for OAuth 2.0 [RFC8705] or OAuth 2.0 Demonstrating Proof of
Possession (DPoP) [RFC9449]"*. Both give back OAuth 1.0's guarantee — a stolen token is not
usable by the thief — without asking application developers to normalize a base string.
mTLS is **14 · mTLS and workload identity** *(not written yet)*.

## Gotchas

**★ "OAuth 2.0 is less secure than 1.0" is half true and usually deployed as a slogan.**
The precise claim: 2.0's bearer tokens have a weaker *stolen-credential* property. The
counter-claim, equally precise: 1.0's signing was so error-prone that real deployments got
it wrong, and a correctly implemented 2.0 beats an incorrectly implemented 1.0 every time.
Compare like with like — a hand-rolled signature layer is not a free win.

**★ Bearer tokens are only as safe as every place the token can end up.**
Logs, `Referer` headers on outbound links, crash reporters, APM traces, browser history,
proxy access logs, screenshots in bug reports. Each is a full-privilege credential leak for
the token's remaining lifetime. This is why access-token lifetimes are minutes, and why
putting a token in a query string is effectively forbidden.

**★ TLS is load-bearing in OAuth2 in a way it was not in OAuth 1.0.**
1.0 could survive a compromised channel; 2.0 cannot. Terminating TLS at a load balancer and
running plaintext behind it means every hop behind that balancer can read and reuse every
token. "It is our internal network" is the sentence that precedes the incident.

**★ Do not implement OAuth 1.0 today, and do not implement OAuth 2.0's crypto by hand
either.** 1.0's HMAC-SHA1 and RSA-SHA1 both hang on SHA-1. If you must integrate with a
legacy 1.0a provider, use a maintained library and never hand-roll the base string.

**★ `PLAINTEXT` mode means "OAuth 1.0 required signatures" is not quite true.**
§3.4.4 defines a no-signature mode, conditional on TLS. It matters because it shows the
2.0 decision was a change of default rather than an invention.

**★ The 1.0 → 1.0a `oauth_verifier` fix is the same lesson PKCE teaches later.**
Both bind the completion of an authorization flow to the party that started it. Recognising
the shape means PKCE reads as a repeat rather than a novelty — see [03 · Authorization code flow with PKCE](../03-authorization-code-pkce/README.md).

**★ Signature verification breaks behind proxies, and the symptom is a mystery 401.**
If a reverse proxy rewrites the scheme, host, port or path, the base string the server
computes differs from the one the client signed. This defeated many 1.0 deployments and is
worth remembering whenever anyone proposes reintroducing request signing.

**★ "We use API keys, so we do not need OAuth2" answers a different question.**
An account-wide API key has no consent step, no per-user scoping and no expiry. For an
internal service-to-service call that may be entirely fine — see
**06 · When you do not need OAuth2** *(not written yet)*. For third-party access to a
user's data it reproduces failures (3), (4) and (5) exactly.

## Interview questions

**★ What did OAuth 2.0 change relative to OAuth 1.0, and what did it give up?**
It replaced per-request cryptographic signatures with bearer tokens carried over mandatory
TLS, made the client secret relevant only at the token endpoint and only for confidential
clients, and turned a single protocol into a framework of grant types. What it gave up is
proof-of-possession: in 1.0 an intercepted token was useless without the secret needed to
sign requests; in 2.0 possession of the token is sufficient. Everything OAuth2 says about
short lifetimes, TLS and keeping tokens out of URLs is compensation for that.

**★ Why was OAuth 1.0's signing so hard in practice?**
Because it is a normalization problem. The signature base string (RFC 5849 §3.4.1.1)
concatenates the uppercase method, the base string URI and the normalized parameters — and
every party must agree exactly on percent-encoding rules, parameter sorting, default-port
handling, which body parameters participate, and what a non-form-encoded body contributes.
A TLS-terminating proxy that rewrites any of the URI components silently invalidates the
signature. The failure mode is an opaque `401`, which makes it expensive to debug.

**★ Was OAuth 1.0 signature-mandatory?**
No. RFC 5849 §3.4.4 defines a `PLAINTEXT` method that employs no signature algorithm and
"MUST be used with a transport-layer mechanism such as TLS or SSL". So the "trust the
transport" model 2.0 is criticised for already existed in 1.0 as a permitted option; 2.0
made it the only option.

**★ What is `oauth_verifier` and what does it correspond to in OAuth 2.0?**
RFC 5849 §2.2's fix for a session-fixation weakness in the original callback design: an
unguessable value the server generates and passes to the client via the resource owner,
required to complete the flow. Its OAuth 2.0 descendant is the authorization code, and the
same binding idea reappears in PKCE's `code_verifier`/`code_challenge` — in each case the
point is that only the party who started the flow can finish it.

**★ Given bearer tokens are strictly weaker, why did the industry accept them?**
Because the alternative was not "1.0 done correctly", it was "1.0 done incorrectly by
thousands of teams". Signing raised the cost of every integration and produced silent,
undiagnosable failures. Bearer-over-TLS made a correct client a few lines of code, which
raised the *average* deployed security even though it lowered the ceiling. The rising
population of public clients — SPAs and mobile apps, which cannot keep a signing secret at
all — made 1.0's model unworkable regardless.

**★ Is proof-of-possession coming back?**
Yes, and RFC 9700 §2.2.1 says so: authorization and resource servers "SHOULD use mechanisms
for sender-constraining access tokens, such as mutual TLS for OAuth 2.0 [RFC8705] or OAuth
2.0 Demonstrating Proof of Possession (DPoP) [RFC9449]". The difference from 1.0 is where
the work sits — mTLS is handled by the transport stack or a service mesh, and DPoP signs a
small proof rather than a normalized rendering of the whole request, so neither asks
application developers to reproduce a base string byte for byte.

**★ Your team proposes signing every internal API request "like OAuth 1.0 did" instead of
using bearer tokens. What do you say?** That the guarantee is real and worth wanting, but
hand-rolling it repeats the failure that killed 1.0 — canonicalization disagreements,
proxies that rewrite the request, opaque 401s, and a SHA-1-era design if you copy it
literally. Buy the property instead of building it: mTLS between services (RFC 8705), or
DPoP (RFC 9449) if the caller is a browser or mobile client. Both are standardised, both
have library and infrastructure support, and neither puts a normalization algorithm in your
application code.
