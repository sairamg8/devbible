> Codes), §10.6 (Authorization Code Redirection URI Manipulation), §4.1.3 (Access Token
> Request) ([rfc-editor.org/rfc/rfc6749](https://www.rfc-editor.org/rfc/rfc6749.txt));
> RFC 7636 §4.4 (Server Associates the Code Challenge with the Authorization Code)
> ([datatracker.ietf.org/doc/html/rfc7636](https://datatracker.ietf.org/doc/html/rfc7636)).
> JDK 25 · Spring Boot 4.1.0 · Spring Framework 7.0.8 · Spring Security 7.x.

**A code is a row in the authorization server's database with an expiry, a used flag, a
`client_id`, a `redirect_uri`, a set of granted scopes, the authenticated subject, and — since
RFC 7636 — a `code_challenge` and `code_challenge_method`. It is not a token, it carries no
claims, and nothing about it is meaningful to the client: it is an opaque handle whose entire
value is that the authorization server can look it up once and then can never look it up
again. Everything a client is tempted to do with a code — parse it, cache it, log it, replay
it, pass it to another service — is a bug that follows from forgetting that.**

## What the response looks like

RFC 6749 §4.1.2. Two parameters, and the RFC's own example:

```http
HTTP/1.1 302 Found
Location: https://client.example.com/cb?code=SplxlOBeZQQYbYS6WxSbIA
          &state=xyz
```

| Parameter | Status | RFC's definition |
|---|---|---|
| `code` | REQUIRED | *"The authorization code generated by the authorization server."* |
| `state` | REQUIRED if present in the request | *"The exact value received from the client."* |

*"Exact value"* is doing real work. Some servers have historically re-encoded it; a `state`
that survives a round trip through URL encoding unchanged is one you generated from the
unreserved character set, which is another reason to base64url-encode random bytes rather
than to use, say, a JSON blob.

## The four properties, quoted

RFC 6749 §4.1.2 and §10.5 carry identical text. This is the single most important paragraph
in the flow:

> *"The authorization code MUST expire shortly after it is issued to mitigate the risk of
> leaks. A maximum authorization code lifetime of 10 minutes is RECOMMENDED. The client MUST
> NOT use the authorization code more than once. If an authorization code is used more than
> once, the authorization server MUST deny the request and SHOULD revoke (when possible) all
> tokens previously issued based on that authorization code. The authorization code is bound
> to the client identifier and redirection URI."*

Unpacked:

**1 · Expiry — `MUST` expire, 10 minutes `RECOMMENDED` as a maximum.**
Note the shape: the MUST is on expiring, the ten minutes is a recommended *ceiling*. Real
authorization servers sit well under it — sub-minute lifetimes are common, and the value is
per-server configuration rather than anything the specification fixes. *(I could not confirm
a specific default for Keycloak or Spring Authorization Server from primary documentation
without a running instance, so no number is quoted here.)* Do not build anything that assumes
a particular lifetime — redeem immediately.

**2 · Single use — a `MUST NOT` on the client.**
The obligation is stated on the client, which is unusual; the corresponding server obligation
is in the next sentence.

**3 · Reuse triggers denial (`MUST`) and revocation (`SHOULD`).**
This is the sentence that surprises people. Reuse does not merely fail — a conforming server
`SHOULD` revoke *the tokens the first, legitimate use produced*. From the server's
perspective a second presentation of a code means two parties hold it, and one of them is not
the client. Failing closed means invalidating the whole exchange.

**4 · Bound to `client_id` and `redirect_uri`.**
Re-checked at redemption, not only at issuance. RFC 6749 §4.1.3 makes the server *"ensure
that the authorization code was issued to the authenticated confidential client, or if the
client is public, ensure that the code was issued to `client_id` in the request"* and *"if
included ensure that their values are identical"* for `redirect_uri`.

## What the server stores alongside it

RFC 7636 §4.4 adds two more columns:

> *"The server MUST associate the `code_challenge` and `code_challenge_method` values with
> the authorization code so it can be verified later."*

So the conceptual row, at issuance:

```text
code                 opaque, high-entropy, unguessable
client_id            the client the code was issued to
redirect_uri         the URI the code was delivered to
subject              the authenticated resource owner
scopes               what the resource owner actually granted
issued_at / expires  short
used                 false
code_challenge       from the authorization request, or null
code_challenge_method S256 | plain | null
nonce                if the request was an OIDC request
```

Every check at the token endpoint is a comparison against one of those columns. When you can
recite this row, [08 · Server-side PKCE verification](08-server-side-pkce-verification.md)
and **20 · Reading the errors** *(not written yet)* stop needing memorisation.

## Codes are opaque — including to you

Nothing in RFC 6749 defines the format of a code. Some authorization servers issue random
strings; some issue self-contained encrypted or signed structures so the code needs no
server-side row (in which case the single-use property is enforced by a separate replay
cache). A client that notices its provider's codes look like JWTs and starts parsing them has
coupled itself to an internal representation the provider is free to change on a Tuesday.

This is the same argument the phase makes about access tokens, one layer earlier, and both
follow from the same rule: **a client only ever treats a credential it did not define as an
opaque string.** The access-token version of the argument is **05 · The three tokens** *(not
written yet)*.

## Where the code physically goes

Front channel, in the query string of the redirect. Not the fragment — a fragment would never
reach your server. This is a deliberate difference from the implicit grant, which used the
fragment specifically so the token would *not* reach a server, and it is why the code lands in
your access logs unless you strip it. See
[15 · Referrer and history leakage](15-referrer-and-history-leakage.md).

## Gotchas

**★ Reuse can log the user out, because reuse `SHOULD` revoke the first use's tokens.**
An HTTP retry, a double-submitted callback (browser prefetch, a user double-clicking, a
link-scanner in an email client following the URL), or a duplicated event consumer will
present the code twice. The first exchange succeeded; §4.1.2 then has the server revoke what
it issued. Symptom: users are logged in for a fraction of a second. Cause: something fetched
your callback URL twice.

**★ Corporate link scanners and mail security products fetch URLs, including callback URLs.**
If any part of your flow can put a callback URL into an email or a chat message, something
will GET it before the user does, spend the code, and the user's own click will get
`invalid_grant`. Callback URLs must never be shareable artefacts.

**★ A code sitting unused past its lifetime is not "expired soon", it is gone.**
The lifetime is measured from issuance, and the user's time on the consent screen is *not*
part of it — but their time between the redirect back and your token call is. A callback
handler that does slow work (creating a user record, calling three internal services) before
exchanging the code can exceed a 30-second server-side lifetime under load. Exchange first,
then do the work.

**★ "Bound to the redirection URI" fails when your app computes the URI differently on the
two requests.**
Behind a load balancer, `https://app.example.com/login/oauth2/code/x` on the way out and
`http://10.0.1.7:8080/login/oauth2/code/x` on the way back are different strings. Spring
Security resolves the redirect URI from the request, so `server.forward-headers-strategy` and
correct `X-Forwarded-Proto`/`Host` handling are a *functional* requirement for this flow, not
a cosmetic one. Details in
**19 · Where the defaults leave you exposed** *(not written yet)*.

**★ The code is high-entropy but you must still not compare it yourself.**
Clients never compare codes. If you find code comparing an incoming `code` against a stored
one, someone has re-implemented the authorization server's job in the client and probably with
`String.equals` on a secret. The client's only comparison in this flow is `state`, and that one
should be constant-time.

**★ Logging the full callback URL logs the code.**
Access logs, APM traces, error reports with the request URI attached, and browser
`performance.getEntries()` all capture it. Strip the query string on the callback path
specifically; do not rely on a global redaction list that has to know the parameter name.

**★ Storing a code to "exchange it later" is never right.**
There is no legitimate deferred-exchange pattern. If your architecture needs the token later,
exchange the code now and store the *refresh token* under the rules of [05 · The three tokens](../05-the-three-tokens/README.md).

**★ A server that does not revoke on reuse is not obviously non-conforming.**
Revocation is a `SHOULD`, not a `MUST` — only denial is a `MUST`. So "our provider does not
log people out on a double-submit" does not prove your double-submit is harmless; it proves
your provider chose the weaker of two permitted behaviours. Fix the double-submit.

## Interview questions

**★ What exactly is an authorization code?**
An opaque, high-entropy handle to a record on the authorization server holding the client it
was issued to, the redirect URI it was delivered to, the authenticated subject, the granted
scopes, an expiry, a used flag, and — with PKCE — the `code_challenge` and its method. It has
no format defined by the specification, carries no claims, and is meaningful only to the
authorization server. Its value to the protocol is entirely negative: it is safe to put on the
front channel because it is worthless without the further checks at the token endpoint.

**★ How long does a code live, and where does that number come from?**
RFC 6749 §4.1.2 says it *"MUST expire shortly after it is issued"* and recommends *"a maximum
authorization code lifetime of 10 minutes"*. That is a ceiling, not a target; production
servers commonly use 30–60 seconds. The correct client behaviour is to exchange it in the
callback handler before doing anything else, so the number never matters.

**★ Your users report being logged out immediately after signing in, intermittently. Walk me
through the diagnosis.**
Something is presenting the authorization code twice. RFC 6749 §4.1.2 says that on reuse the
authorization server *"MUST deny the request and SHOULD revoke (when possible) all tokens
previously issued based on that authorization code"* — so the second, failing exchange
destroys the session the first, successful exchange created. Candidates: an HTTP client retry
policy on the token endpoint; a browser prefetch or a double-click on the callback; a
link-scanner following the callback URL out of an email; two application instances processing
the same callback because of a proxy retry; or a service worker replaying the navigation. The
fix is at whichever of those is duplicating the request, not at the authorization server.

**★ Why does the token endpoint re-check the `redirect_uri` when the authorization endpoint
already validated it?**
Because they answer different questions. At the authorization endpoint the check is "may this
client receive a response at this URI" — it decides where to send the code. At the token
endpoint the check is "is the party redeeming this code the same party the code was delivered
to" — it decides whether to honour the code. Without the second check, an attacker who
obtained a code delivered to a different registered URI, or who exploited a loose matching
rule, could redeem it. RFC 6749 §10.6 is exactly this attack, and §4.1.3 is the countermeasure.

**★ Is it acceptable for an authorization server to issue a self-contained, signed
authorization code with no database row?**
Yes — nothing in RFC 6749 constrains the format — but the server still has to enforce single
use, which a stateless token cannot do on its own. So a self-contained code needs a replay
cache keyed by a code identifier, which is most of the state it was trying to avoid, just with
a shorter retention. The client side is unaffected and must not care: from the client, a code
is an opaque string in both designs.

**★ The client wants to pass the authorization code to a backend microservice to do the token
exchange. Any problem?**
Not intrinsically — the code is designed to travel — but three things must hold. The service
doing the exchange must be the one holding the `code_verifier`, or PKCE verification fails, so
the verifier has to travel with it and must travel on a channel at least as protected as the
code. The service must present the same `client_id` and `redirect_uri` the code was issued
against. And exactly one service must attempt the exchange: if the code is published to a
topic with more than one consumer, you have built the double-redemption scenario above on
purpose.
