**Three opaque random values travel through an OIDC login and they are not variations on a
theme. `state` is checked by *your client*, at *your redirect endpoint*, against *your
session*. The PKCE `code_verifier` is checked by *the authorization server*, at *the token
endpoint*, against a challenge it stored beside the code. `nonce` is checked by *your
client*, when *validating the ID token*, against a value it stored before the redirect. Three
checkers, three moments, three stored values — and each one is the only defence against the
attack it covers. Deleting any of them because "the other one handles replay" is the most
reliably wrong sentence in this phase.**

The confusion has a real source. Every description of all three uses the word *replay*, and
every one is technically accurate, because they defend against replay of three different
objects: a response, a code, and an assertion. Naming the object is what makes the table
below memorable rather than something to look up.

## The table that settles it

| | `state` | PKCE `code_verifier` | `nonce` |
|---|---|---|---|
| Defined in | RFC 6749 §4.1.1, §10.12 | RFC 7636 §4 | OIDC Core §3.1.2.1 |
| Protects | your **redirect endpoint** | the **authorization code** | the **ID token** |
| Generated by | the client | the client | the client |
| Sent on | the authorization request | the authorization request (as a hash) | the authorization request |
| Comes back in | the authorization **response** (query) | never — the verifier goes up separately | the **`nonce` claim** of the ID token |
| Checked by | **the client** | **the authorization server** | **the client** |
| Checked at | the redirect endpoint | the token endpoint | ID token validation |
| Checked against | the value in the user's session | the challenge stored with the code | the value stored before the redirect |
| Attack it stops | CSRF on the callback | interception and redemption of a stolen code | injection of an ID token from another flow |
| Force | RFC 9700 §2.1: a **MUST** on the *protection*, not the parameter | RFC 9700 §2.1.1: **MUST** for public clients, **RECOMMENDED** for confidential | OIDC §3.1.3.7 r11: **MUST** check *if you sent one* |

Read the "Checked by" row twice. **PKCE is the only one of the three you cannot verify
yourself** — you hand a hash to the authorization server and it does the comparison. That is
also why PKCE has a downgrade attack and the other two do not: a check performed by somebody
else is a check somebody else can be persuaded to skip.

## What each one actually stops

### `state` — somebody else's authorization response arrives at your callback

The attacker starts their own legitimate login at the same provider, captures the resulting
`code=...` redirect before following it, and then induces the victim's browser to visit your
callback URL with the attacker's code. Without `state`, your application dutifully exchanges
a valid code, receives valid tokens — for the *attacker's* account — and binds the victim's
session to it. Everything the victim then does happens inside the attacker's account, which
is how this becomes a data-exfiltration bug rather than a nuisance.

`state` closes it because the victim's session has no stored `state` matching the one in the
inbound response.

```java
// Before the redirect: mint and store.
String state = randomUrlSafe(32);
session.setAttribute("oidc:pending:" + state, new PendingAuth(nonce, codeVerifier, Instant.now()));

// At the callback: the stored entry must exist, and it is consumed.
PendingAuth pending = (PendingAuth) session.getAttribute("oidc:pending:" + state);
if (pending == null) {
    throw new OAuth2AuthenticationException("unknown or replayed state");
}
session.removeAttribute("oidc:pending:" + state);   // single use, like the code itself
```

🔴 **`state` must be *consumed*, not merely compared.** A value that is checked and left in
place makes the callback replayable for the life of the session.

### PKCE — the code was stolen and someone else tries to redeem it

The verifier never travels on the front channel; only its SHA-256 hash does, as
`code_challenge`. Whoever intercepts the redirect gets a code they cannot spend, because
redeeming it requires the pre-image. The authorization server stores the challenge beside the
code and demands the verifier at the token endpoint.

This is [03 · Authorization code + PKCE](../03-authorization-code-pkce/README.md)'s whole
argument, and the reason it appears here is the negative: **PKCE does not look at your
session at all.** It cannot tell whether the browser that arrived at your callback is the one
that started the flow — only that whoever redeems the code is the software that began the
exchange. In an attacker-starts-the-flow scenario, the attacker *is* that party, and PKCE is
satisfied.

### `nonce` — an ID token from a different flow is injected

The attacker obtains a genuine, correctly signed ID token — from their own session at the
same provider, or from a flow they induced — and gets your client to treat it as the result
of the flow it just ran. `nonce` closes it because your client generated a fresh value before
the redirect, and the ID token that comes back must echo it.

§3.1.2.1 explains the mechanism in one clause: the value *"is passed through unmodified from
the Authentication Request to the ID Token."* §3.1.3.7 rule 11 makes the check mandatory once
you have sent one:

> *"If a `nonce` value was sent in the Authentication Request, a `nonce` Claim MUST be present
> and its value checked to verify that it is the same value as the one that was sent."*

```java
// After the token exchange, before trusting a single claim.
String expectedNonce = pending.nonce();
String actualNonce = idToken.getClaimAsString("nonce");
if (expectedNonce != null && !expectedNonce.equals(actualNonce)) {
    throw new OAuth2AuthenticationException("nonce missing or mismatched");
}
```

The `expectedNonce != null` guard is there because you may not have sent one; the
`!equals` — rather than a null-tolerant comparison — is there because *absence is a failure*
when you did.

## Where the overlap actually is, and why it is narrower than people think

RFC 9700 §2.1.1 grants a conditional overlap: a client that uses PKCE gets the CSRF
protection `state` was providing, *because* the token exchange will fail for a flow the
client did not start. Two things about that.

**First, it is conditional on PKCE actually being enforced end to end** — including at the
authorization server, which is the party doing the checking, and which may not enforce it. A
client that dropped `state` on the strength of PKCE has made its CSRF defence depend on
somebody else's configuration.

**Second, it says nothing about `nonce`.** The overlap is between two protections of the
*code path*; the ID token is a third object with a third attack. A login that uses PKCE and
skips `nonce` accepts ID tokens from flows it did not start, and the token will be genuine,
correctly signed and unexpired.

The practical rule, and it costs nothing: **send and check all three.** They are three random
strings and three comparisons.

## Gotchas

**★ `nonce` is checked only when present in the token.**
Symptom: an ID token with no `nonce` claim is accepted even though the request sent one.
Cause: `if (idToken.getNonce() != null) { compare }`. Fix: rule 11 requires the claim to be
**present** and equal — the guard belongs on what *you sent*, not on what came back.

**★ `state` is verified against a cookie that is `SameSite=None`.**
Symptom: the CSRF defence is weaker than intended on cross-site navigations. Cause: the
session cookie carrying the stored `state` is sent on requests the user did not initiate.
Fix: `SameSite=Lax` is the right default for a redirect-based login, because the callback is
a top-level GET navigation — which `Lax` allows and cross-site subresource requests do not
get.

**★ PKCE is implemented, `state` is dropped, and the authorization server does not enforce
PKCE.**
Symptom: no symptom at all — until the CSRF that `state` would have stopped. Cause: RFC 9700
§2.1.1's conditional overlap read as unconditional. Fix: keep `state`; it is one comparison.
If you genuinely intend to rely on the overlap, verify that the AS rejects a token request
with no `code_verifier` for a code that had a challenge — which is
[09 · The PKCE downgrade attack](../03-authorization-code-pkce/09-the-pkce-downgrade-attack.md).

**★ A framework is assumed to be doing all three.**
Symptom: a hand-rolled callback endpoint added "temporarily" next to a framework-managed one,
with none of the checks. Cause: the framework does do all three — Spring Security's
`OAuth2LoginAuthenticationFilter` and `OidcIdTokenValidator` between them — so nobody has
ever had to write them. Fix: if you write the callback yourself, you own all three checks;
there is no partial credit.

**★ `nonce` is sent on a client-credentials or refresh request.**
Symptom: an ignored parameter, or an `invalid_request` from a strict provider. Cause: copying
the authorization-request builder. Fix: `nonce` is a parameter of the *authentication*
request only. There is no user, no authentication event and no ID token in the
client-credentials grant — see
[04 · Client credentials](../04-client-credentials/README.md).

## Interview questions

**★ You have PKCE. Do you still need `state`?**
Yes, and the reason is who does the checking. PKCE is verified by the authorization server at
the token endpoint against a challenge stored with the code — it proves the software
redeeming the code is the software that started the exchange, and it never looks at your
session. `state` is verified by your client at your redirect endpoint against a value in the
user's session — it proves the response arriving belongs to a flow *this browser session*
started. RFC 9700 §2.1.1 grants a narrow conditional overlap, but it depends on the
authorization server enforcing PKCE, which is not your configuration. One comparison is not
worth outsourcing your CSRF defence.

**★ You have `state`. Do you still need `nonce`?**
Yes. `state` binds the *authorization response* to your session; `nonce` binds the *ID token*
to your request. An attacker who cannot forge a response can still try to get a genuine ID
token from a different flow accepted as the result of yours, and only the `nonce` claim
distinguishes them. They protect two different objects at two different moments.

**★ Which of the three can you not verify yourself, and what follows from that?**
PKCE. You send a hash and the authorization server performs the comparison, which means your
protection is only as good as its enforcement. That is exactly why the PKCE downgrade attack
exists — an AS that treats `code_verifier` as optional silently disables PKCE for every
client — and why "PKCE covers `state`" is a claim about somebody else's server rather than
about your code.

**★ Does `nonce` apply to the refresh flow?**
No. `nonce` is a parameter of the authentication request, checked in the ID token that
results from it. A refresh exchange has no authorization request, no user interaction and no
new authentication event — and if a provider returns a fresh ID token on refresh, §3.1.3.7's
rule 11 does not apply to it, because no nonce was sent. What you should check on such a
token is that its `sub` still matches the session you are refreshing.
