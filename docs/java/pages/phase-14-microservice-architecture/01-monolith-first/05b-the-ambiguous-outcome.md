**Every failure-handling instinct a Java developer has was trained on a two-outcome world:
the method returned, or it threw. Remote calls have a third outcome, it is the most common
one under load, and it is the one that turns a correct-looking retry into a duplicate
charge. This is the cost that shows up last, hurts most, and appears in no split proposal.**

## The third outcome

```java
try {
    PaymentResult result = paymentClient.charge(orderId, amount, method);
    orders.markPaid(orderId, result.reference());
} catch (RestClientException e) {
    orders.markPaymentFailed(orderId);   // ← wrong, and it will cost real money
}
```

The `catch` block asserts something the exception does not support: that the charge did not
happen. A `SocketTimeoutException` is compatible with all of:

- the request never left your host;
- the request arrived, the payment service crashed before processing it;
- the request arrived, was processed, committed, and the response was lost;
- the request arrived, was processed, committed, and the response is *still in flight* and
  will arrive after you gave up.

In the last two the customer has been charged and your database says `PAYMENT_FAILED`. No
amount of care inside the `catch` block fixes this, because the information required is not
present.

In a monolith there is no analogue. `payments.charge(…)` either returned or threw, and if it
threw, the transaction rolled back. The `catch`-means-it-did-not-happen assumption was
*correct*, for the whole life of the codebase, which is exactly why it is so hard to
unlearn.

## The consequences, in order of how much they cost

**1. Retries become dangerous, so idempotency becomes mandatory.** The only safe response to
"I do not know" is to ask again in a way that cannot double-apply. That requires an
idempotency key generated by the caller, stored by the callee, and honoured for a defined
retention window:

```java
// The caller generates the key ONCE, per business operation, and reuses it on every retry.
record ChargeCommand(String idempotencyKey, OrderId orderId, Money amount, PaymentMethod method) {}
```

Note what that is: a **contract change**. The receiving service must store keys, define how
long it stores them, decide what "same key, different body" means, and return the original
result rather than reprocessing. You cannot add idempotency from the client side with an
annotation, which is the mistake people make first.

**2. "Exactly once" is not available, so every consumer must tolerate duplicates.** At-least-once
delivery plus idempotent processing is the achievable target. Every handler that mutates
state needs to answer "what if I see this message twice?" — and the answer must be in the
handler, not in a hopeful comment about broker guarantees.

**3. The unknown state must be modelled explicitly.** Your order status enum acquires a
value that has no meaning in a monolith:

```java
public enum PaymentStatus {
    NOT_ATTEMPTED,
    AUTHORISED,
    CAPTURED,
    DECLINED,
    UNKNOWN          // ← charge attempted, outcome unknown, requires reconciliation
}
```

And with it: a reconciliation job that queries the payment provider for orders stuck in
`UNKNOWN`, an alert when the count exceeds a threshold, and a human process for the ones
reconciliation cannot resolve. Three artefacts, per ambiguous integration.

**4. Timeouts become a design parameter with a wrong answer in both directions.** Too short
and you abandon operations that were about to succeed, generating `UNKNOWN` states under
normal load. Too long and a slow dependency exhausts your threads and takes you down with
it. There is no safe default, and the number depends on the downstream's actual latency
distribution — which you cannot know until you are in production. Timeouts as a client-side
obligation are owned by **05 · Inter-service REST** *(not written yet)*; the availability
and latency-budget arithmetic across hops is owned by **04 · Sync vs async** *(not written
yet)*.

**5. Retry storms turn a slow dependency into an outage.** Every caller retrying a timing-out
service multiplies load on the thing that is already struggling. The mitigations — backoff,
jitter, circuit breaking, bulkheads — are a body of work owned by **phase 16 ·
Resilience**. Naming it here so it appears on the bill.

## Why the monolith genuinely does not have this problem

It is worth being precise, because "the monolith has this too" is a common and incorrect
objection.

- **In-process calls do not time out.** A method call either returns, throws, or the process
  is gone — and if the process is gone, nothing committed either.
- **The database transaction makes partial completion unobservable.** There is no state
  between "nothing happened" and "everything happened".
- **The one genuine analogue is calls to *external* systems** — the payment provider, the
  email gateway, the tax service. Those are ambiguous in a monolith too, and that is where
  your team should learn this discipline. The difference is quantitative and large: a
  monolith has a handful of such integrations, deliberately chosen and carefully written; a
  twelve-service system has that many again *plus* every internal hop, written casually
  because "it's just our own service".

That last point is the real cost. Ambiguity goes from being a special case handled by
specialists at the system's edge to being the default property of every call.

## What the in-process seam gives you, and what it does not

Spring Modulith's event publication registry removes one specific class of this problem
inside the monolith: the lost publication. The reference:

> *"On event publication, it finds out about the transactional event listeners that will get
> the event delivered and writes entries for each of them (dark blue) into an event
> publication log as part of the original business transaction."*
>
> *"Each transactional event listener is wrapped into an aspect that marks that log entry as
> completed if the execution of the listener succeeds. In case the listener fails, the log
> entry stays untouched so that retry mechanisms can be deployed depending on the
> application's needs."*

Because the log entry is written **in the original business transaction**, there is no
window where the order commits and the notification of it is lost. That is the outbox
property, and it is the single most important thing to have in place *before* you extract a
module — see [47 · The event publication registry](14c-the-event-publication-registry.md)
and [48 · Publication lifecycle and failure](14d-publication-lifecycle-and-failure.md).

What it does not give you: the listener still runs in the same JVM, so there is no network,
no timeout, and no ambiguous outcome. Practising with the registry teaches you the
*retry-and-completion* half of the discipline, not the *unknown outcome* half. Be honest
about which half you have rehearsed.

## Gotchas

**★ `catch (Exception e)` around a remote call encodes a false assertion.** It reads as "it
failed" and means "I did not hear back". Every such block in a split system is a latent
double-charge, double-ship or double-send. The fix is not better logging; it is an
idempotency key on the request and an explicit `UNKNOWN` state on the caller's side.

**★ Idempotency is a change to the *receiving* service's contract and storage, not a client
concern.** A client-side `@Retryable` with no server-side key handling produces duplicates
by design. The receiver must persist the key with the result, honour it for a defined
window, and define what happens when the same key arrives with a different body — normally
a 409, never silent overwrite.

**★ The retention window for idempotency keys is a real decision with a real failure
mode.** Too short and a retry after a long outage double-applies; too long and the table
grows without bound and slows down the write path. Pick a window longer than your maximum
plausible retry horizon — including manual replays during an incident — and put a purge job
in the same pull request that adds the table.

**★ An `UNKNOWN` state with no reconciliation job is a silent money leak.** Adding the enum
value is the easy part and teams stop there. It needs: a scheduled reconciliation against
the authoritative system, an alert on the backlog size, and a documented human procedure for
the residue. If nobody owns the queue, orders sit in `UNKNOWN` until a customer complains.

**★ Timeout tuning has no safe default and both errors are expensive.** Too short manufactures
ambiguous outcomes during normal traffic spikes; too long converts a slow dependency into
thread-pool exhaustion and takes your service down with it. It cannot be got right before
production because it depends on the downstream's real latency distribution, so plan to
tune it, alert on it, and revisit it after every significant traffic change.

**★ Retrying is the correct response to ambiguity and also the mechanism by which one slow
service becomes an outage.** Every caller retrying multiplies load on something already
struggling. Backoff with jitter, a circuit breaker and a bounded concurrency budget are
mandatory companions to any retry policy, not enhancements — phase 16 owns them, and they
belong on the split's bill.

**★ Teams rehearse this on external integrations and then assume internal calls are
different.** They are not. The payment provider and your own inventory service both live
across a socket. The habit of writing careful, idempotent, reconciled integrations for
third parties and casual ones for internal services is extremely common and produces
exactly the bugs you would expect.

**★ Message consumers inherit the same problem from the broker, not just from HTTP.**
At-least-once delivery means every listener can see the same event twice — after a
redelivery, a rebalance, or a resubmission from an outbox. A handler that increments a
counter or sends an email must be idempotent on the event identifier, and Spring Modulith's
own resubmission machinery makes this concrete rather than theoretical.

## Interview questions

**★ How many outcomes does a remote call have?**
Three: success, definite failure, and unknown. The third arises whenever the response is
lost, which includes timeouts, connection resets after the request was sent, and the caller
process dying mid-call. It is the common case under load, and it is the one a Java
developer's instincts are untrained for, because in-process calls only ever return or
throw, and if they throw inside a transaction the state is rolled back. Every `catch` block
around a remote call that assumes "failed" is asserting something the exception does not
support.

**★ Where does idempotency have to live, and why is the client-side answer wrong?**
In the receiving service, keyed on an identifier the caller generates once per business
operation and reuses across all retries. The receiver stores the key with the result of the
first execution, returns that stored result for repeats, keeps the key for a defined
retention window longer than any plausible retry horizon, and defines a behaviour for "same
key, different body" — normally rejecting it. A client-side retry annotation without any of
that produces duplicates on purpose: it is precisely the mechanism that turns an ambiguous
outcome into two charges.

**★ What state does an ambiguous outcome force into your domain model?**
An explicit "unknown" value on whatever status the operation was setting — payment
attempted, outcome undetermined — plus everything that value implies: a reconciliation
process that asks the authoritative system what actually happened, an alert on the size of
the unknown backlog, and a human procedure for the cases reconciliation cannot settle.
Adding the enum constant is the trivial part; the operational apparatus around it is the
cost, and it repeats for every ambiguous integration in the system.

**★ Does a monolith have this problem at all?**
Only at its external edges — the payment provider, the email gateway, the tax service. Those
calls are ambiguous in any architecture and are where a team should learn the discipline.
Internally there is no analogue: an in-process call cannot time out, and the database
transaction makes partial completion unobservable, so there is no state between "nothing
happened" and "everything happened". The change on splitting is quantitative and severe:
ambiguity moves from a handful of carefully written edge integrations to being the default
property of every call in the system, including the ones written casually because they go
to a service the same team owns.

**★ How much of this can you rehearse before splitting?**
The retry-and-completion half, quite well. Spring Modulith's event publication registry
writes a log entry per transactional listener inside the original business transaction and
marks it complete only when the listener succeeds, so you get at-least-once delivery, a
durable record of what has not been processed, and a resubmission API — which forces
listeners to be idempotent and teaches the operational habit of watching an incomplete-work
queue. What you cannot rehearse in-process is the unknown outcome itself, because there is
no network between publisher and listener. So the honest position is that the modular
monolith prepares you for duplicate delivery and stuck work, and not for "I do not know
whether the card was charged".
