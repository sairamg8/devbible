**G1 is the default collector, which means most Java services in production are running it,
which means most people reading a GC log are reading a G1 log without having read what G1
does. The single idea worth carrying is this: G1 does not collect "the young generation" or
"the old generation" — it collects a *set of regions it chose*, and it chose them by
predicting how long evacuating each one will take. Everything else on this page, and every
G1 pathology in [03d](03e-g1-when-it-goes-wrong.md), follows from the collector being allowed
to pick its own workload. The heap's generational *shape* is already covered in
[01 · Memory layout → 03 · The heap](../01-memory-layout/03-the-heap.md); this page is what
the collector does with it.**

## What kind of collector it is, in six adjectives

> *"G1 is a generational, incremental, parallel, mostly concurrent, stop-the-world, and
> evacuating garbage collector which monitors pause-time goals in each of the
> stop-the-world pauses."*

Unpacking those, because each one is load-bearing:

- **Generational** — eden, survivor and old regions, with the aging and promotion policy of
  [01 · Memory layout → 03d](../01-memory-layout/03d-aging-and-promotion.md).
- **Incremental** — the old generation is reclaimed a few regions at a time across many
  collections, not in one operation. This is the headline difference from Parallel:
  *"Parallel GC can compact and reclaim space in the old generation only as a whole. G1
  incrementally distributes this work across multiple much shorter collections."*
- **Parallel** — the stop-the-world work is done by `ParallelGCThreads` workers.
- **Mostly concurrent** — marking runs alongside the application; evacuation does not.
- **Stop-the-world** — every *reclamation* happens in a pause. G1 has no concurrent
  evacuation; that is what distinguishes it from ZGC and Shenandoah.
- **Evacuating** — *"G1 reclaims space mostly by using evacuation: live objects found within
  selected memory areas to collect are copied into new memory areas, compacting them in the
  process. After an evacuation has been completed, the space previously occupied by live
  objects is reused for allocation by the application."*

Evacuating is the property that makes G1 immune to old-generation fragmentation in the way
CMS was not, and it is also the property that makes G1 *need somewhere to copy to*, which is
where it fails — see [03d](03e-g1-when-it-goes-wrong.md).

And the design intent, which is a claim about *predictability* rather than speed:

> *"G1 achieves predictability by tracking information about previous application behavior
> and garbage collection pauses to build a model of the associated costs. It uses this
> information to size the work done in the pauses."*

## Regions

> *"G1 partitions the heap into a set of equally sized heap regions, each a contiguous range
> of virtual memory. A region is the unit of memory allocation and memory reclamation. At any
> given time, each of these regions can be empty or assigned to a particular generation,
> young or old. As requests for memory arrive, the memory manager hands out free regions."*
>
> *"The young generation contains eden regions and survivor regions. These regions provide
> the same function as the respective contiguous spaces in other collectors, with the
> difference that in G1 these regions are typically laid out in a noncontiguous pattern in
> memory. Old regions make up the old generation. Old generation regions may be humongous for
> objects that span multiple regions."*
>
> *"An application always allocates into a young generation, that is, eden regions, with the
> exception of humongous objects that are directly allocated as belonging to the old
> generation."*

The region size is ergonomic, and the ergonomic is stated as a target region *count*:

> *"`-XX:G1HeapRegionSize=<ergo>` — The size of the heap regions. The default value is based
> on the maximum heap size and it is calculated to render roughly 2048 regions, with a
> maximum ergonomically determined value of 32 MB. A size given by the user must be a power
> of 2, and valid values range from 1 to 512 MB."*

⚠️ **The man page gives a different range for the same flag**: *"The value is a power of 2 and
can range from 1 MB to 32 MB."* The source settles it:

```cpp
product(size_t, G1HeapRegionSize, 0,
        "Size of the G1 regions.")
        range(0, NOT_LP64(32*M) LP64_ONLY(512*M))
```

On a 64-bit JVM the accepted range goes to **512 MB**; 32 MB is the ceiling *ergonomics* will
choose on its own, not the ceiling you may set. The man page conflates the two. The tuning
guide is right and the man page is stale.

The consequence of "roughly 2048 regions" is that region size is a step function of `-Xmx`,
and that step function is what makes an object humongous or not — see
[03c · Humongous allocations](03d-humongous-allocations.md). It is also why *"the currently
selected heap region size is printed at the beginning of the log"* is a line worth reading
before anything else in a G1 log.

## The cycle: two phases, and the transition between them is the whole story

> *"On a high level, the G1 collector alternates between two phases. The Young-Only phase
> contains garbage collections that fill up the currently available memory with objects in
> the old generation gradually. The Space-Reclamation phase is where G1 reclaims space in the
> old generation incrementally, in addition to handling the young generation. Then the cycle
> restarts with a Young-Only phase."*

**Young-Only phase.** Normal young collections. Each promotes some survivors into old
regions, so old-generation occupancy creeps up.

> *"The transition between the Young-Only phase and the Space-Reclamation phase starts when
> the old generation occupancy reaches a certain threshold, the Initiating Heap Occupancy
> threshold. At this time, G1 schedules a Concurrent Start young collection instead of a
> Normal young collection."*

**Concurrent Start.** A normal young collection *plus* the start of concurrent marking:

> *"This type of collection starts the marking process in addition to performing a Normal
> young collection. Concurrent marking determines all currently reachable (live) objects in
> the old generation regions to be kept for the following Space-Reclamation phase. While
> marking hasn't completely finished, Normal young collections may occur. Marking finishes
> with two special stop-the-world pauses: Remark and Cleanup."*
>
> *"The Concurrent Start pause may also determine that there is no need to follow through
> with marking: in this case, a short Concurrent Mark Undo phase occurs, and the Young-Only
> phase continues. In this case no Remark and Cleanup pauses will occur."*

**Remark.** *"This pause finalizes the marking itself, performs reference processing and
class unloading, reclaims completely empty regions and cleans up internal data structures."*

Note what is in that sentence: **class unloading happens at Remark**, not continuously. If
you are chasing a metaspace or classloader leak, the Remark pause is when the JVM would have
freed the classes, and its absence is diagnostic. That belongs to
[01 · Memory layout → 04c · The classloader leak](../01-memory-layout/04c-the-classloader-leak.md).
Note also *"reclaims completely empty regions"* — regions that became entirely garbage are
freed here for free, without any evacuation.

**Cleanup.** *"This pause determines whether a Space-Reclamation phase will actually follow.
If a Space-Reclamation phase follows, the Young-Only phase completes with a single Prepare
Mixed young collection."*

**Space-Reclamation phase.**

> *"This phase consists of multiple young collections that in addition to young generation
> regions, also evacuate live objects of sets of old generation regions. These collections
> are also called Mixed collections. The Space-Reclamation phase ends when G1 determines that
> evacuating more old generation regions wouldn't yield enough free space worth the effort."*

And the failure mode, stated by the guide immediately after:

> *"As backup, if the application runs out of memory while gathering liveness information, G1
> performs an in-place stop-the-world full heap compaction (Full GC) like other collectors."*

That sentence names the two things that have to be true for G1 to work: **concurrent marking
has to finish before the old generation fills**, and **evacuation has to find somewhere to
copy to**. Both are [03d](03e-g1-when-it-goes-wrong.md).

## What G1 chooses to collect, and what that bookkeeping costs

The collection set, the remembered sets that make choosing one possible, and the four phases
of a pause (with the `gc+phases` logging that exposes them) are
[03b · The collection set and remembered sets](03b-the-collection-set-and-remembered-sets.md).

## Marking is SATB, and what that costs

> *"G1 marking uses an algorithm called Snapshot-At-The-Beginning (SATB). It takes a virtual
> snapshot of the heap at the time of the Concurrent Start pause. All objects that were live
> at the start of marking are considered live for the remainder of marking. This means that
> objects that become dead (unreachable) during marking are still considered live for the
> purpose of space reclamation (with some exceptions). This may cause some additional memory
> wrongly retained compared to other collectors. However, SATB potentially provides better
> latency during the Remark pause. The too conservatively considered live objects during that
> marking will be reclaimed during the next marking."*

Two consequences people trip over. First, **an object that died during a marking cycle is not
collected in that cycle** — it is "floating garbage", and it is reclaimed one cycle later.
Second, **a heap dump taken with `live` semantics and a G1 log disagree about what is
garbage**, because the dump forces a full collection and the log reflects SATB's conservative
view. Neither is wrong.

## What G1 is not

The comparison section, verbatim, is a better summary than any table anyone has drawn:

> *"Parallel GC can compact and reclaim space in the old generation only as a whole. G1
> incrementally distributes this work across multiple much shorter collections. This
> substantially shortens pause time at the potential expense of throughput."*
>
> *"G1 performs part of the old generation Space-Reclamation concurrently."*
>
> *"G1 may exhibit higher overhead than the above collectors, affecting throughput due to its
> concurrent nature."*
>
> *"ZGC aims to provide significantly smaller pause times at further cost of throughput."*

## Gotchas

**★ G1 never collects "the old generation". It collects a chosen set of regions.**
There is no operation in G1 that sweeps the whole old generation except a Full GC, which is a
failure mode rather than a phase. Mixed collections take *some* old regions, chosen by
predicted efficiency and bounded by the pause target. Reading a G1 log expecting "minor" and
"major" collections in the Parallel sense produces a wrong mental model immediately.

**★ Class unloading happens only at Remark.**
The guide lists it in the Remark pause's responsibilities. If concurrent marking is not
completing — because the heap is filling faster than marking runs — classes are not being
unloaded either, so a metaspace growth problem can be a *symptom* of a heap problem rather
than an independent leak.

**★ Objects that die during concurrent marking survive that cycle.**
SATB treats everything live at the snapshot as live for the whole cycle. The guide is explicit
that this *"may cause some additional memory wrongly retained compared to other collectors"*
and that the floating garbage is *"reclaimed during the next marking"*. Comparing a heap dump
against a GC log will show this as an apparent discrepancy; it is not one.

**★ The man page's `G1HeapRegionSize` range is wrong for 64-bit.**
Man page: *"can range from 1 MB to 32 MB"*. Tuning guide: *"valid values range from 1 to
512 MB"*. Source: `range(0, LP64_ONLY(512*M))`. 32 MB is the largest size *ergonomics* will
pick by itself; you may set up to 512 MB. This matters because raising region size is the
documented remedy for humongous fragmentation and the man page's number suggests you have
already hit the ceiling when you have not.

**★ The region size is derived from `-Xmx`, so changing `-Xmx` changes which of your objects
are humongous.**
Ergonomics targets roughly 2048 regions. Halve the heap and you halve the region size and
therefore halve the humongous threshold, and arrays that were ordinary become humongous. A
memory-limit change in a Kubernetes manifest can do this without a single line of Java
changing.

**★ Nothing in G1 evacuates concurrently.**
It is *mostly* concurrent, meaning marking is concurrent. Every byte that moves, moves inside
a stop-the-world pause. If your requirement is "no pause proportional to live data", G1 cannot
meet it at any setting and you need ZGC — [04 · ZGC](04-zgc.md).

**★ A "Concurrent Start" that is followed by no Remark is not a bug.**
The guide documents a Concurrent Mark Undo path: G1 can decide mid-flight that marking is not
worth completing, in which case *"no Remark and Cleanup pauses will occur"* and the Young-Only
phase simply continues. A log with Concurrent Start entries and no matching Remark is normal.

## Interview questions

**★ Explain G1's collection cycle.**
G1 alternates between two phases. In the Young-Only phase it performs normal young
collections, each promoting some survivors, so old-generation occupancy climbs. When
occupancy crosses the Initiating Heap Occupancy threshold, the next young collection is a
Concurrent Start — a normal young collection that additionally begins concurrent marking of
the old generation. Marking runs alongside the application (normal young collections continue
during it) and finishes with two short stop-the-world pauses, Remark and Cleanup. Remark
finalises marking, does reference processing and class unloading, and frees completely empty
regions outright. Cleanup decides whether reclamation is worth doing; if it is, a Prepare
Mixed collection ends the Young-Only phase and the Space-Reclamation phase begins, consisting
of Mixed collections that evacuate young regions plus a chosen set of old regions. It ends
when further old regions are not worth collecting, and the cycle restarts. The backstop, if
the heap fills before any of this completes, is a stop-the-world Full GC.

**★ What does SATB mean and what does it cost?**
Snapshot-At-The-Beginning: at the Concurrent Start pause G1 takes a virtual snapshot of the
reachable set, and everything live at that instant is treated as live for the whole marking
cycle. The benefit is that marking can proceed concurrently with a mutating application while
still terminating correctly, and the Remark pause stays short. The cost is floating garbage —
objects that die during the cycle are not reclaimed in it. The guide states both: it *"may
cause some additional memory wrongly retained compared to other collectors"* but *"potentially
provides better latency during the Remark pause"*, and the retained objects *"will be
reclaimed during the next marking"*. Practically, it means a G1 heap sits slightly higher
than its true live set, and that is by design.

**★ Is G1 a concurrent collector?**
Only partly, and the distinction decides whether it can meet your requirement. Marking is
concurrent. Reclamation is not: every object G1 moves, it moves inside a stop-the-world
pause, and the length of that pause is proportional to how much live data is in the regions it
chose. The tuning guide's own adjective list is *"generational, incremental, parallel, mostly
concurrent, stop-the-world, and evacuating"* — "mostly concurrent" and "stop-the-world" are
both in there, and both are true of different parts of the cycle. If a requirement says pause
time must not scale with live data, G1 cannot satisfy it at any flag setting, and ZGC or
Shenandoah is the answer.
