**Two things about unified logging change how an incident goes. The first is that its default
decorators are unusable for correlation — a GC log stamped in seconds-since-start cannot be
lined up against anything else, and fixing that is one word on a command line. The second is
that logging is reconfigurable on a live JVM through `jcmd`, at Low impact, which means the
detail you did not enable at startup is available without a restart that would have destroyed
the evidence.**

## Decorators

> *"Logging messages are decorated with information about the message. You can configure each
> output to use a custom set of decorators. **The order of the output is always the same as
> listed in the table.** You can configure the decorations to be used at run time. Decorations are
> prepended to the log message. For example: `[6.567s][info][gc,old] Old collection complete`"*
>
> *"Omitting decorators defaults to `uptime`, `level`, and `tags`. The `none` decorator is special
> and is used to turn off all decorations."*

| Decoration | Description |
|---|---|
| `time` / `t` | *"Current time and date in ISO-8601 format."* |
| `utctime` / `utc` | *"Universal Time Coordinated or Coordinated Universal Time."* |
| `uptime` / `u` | *"Time since the start of the JVM in seconds and milliseconds. For example, 6.567s."* |
| `timemillis` / `tm` | *"The same value as generated by `System.currentTimeMillis()`"* |
| `uptimemillis` / `um` | *"Milliseconds since the JVM started."* |
| `timenanos` / `tn` | *"The same value generated by `System.nanoTime()`."* |
| `uptimenanos` / `un` | *"Nanoseconds since the JVM started."* |
| `hostname` / `hn` | *"The host name."* |
| `pid` / `p` | *"The process identifier."* |
| `tid` / `ti` | *"The thread identifier."* |
| `level` / `l` | *"The level associated with the log message."* |
| `tags` / `tg` | *"The tag-set associated with the log message."* |

**The defaults are the wrong choice for production.** `uptime` is seconds since JVM start, which
cannot be correlated with anything — not an application log, not a metrics dashboard, not an
incident timeline. The first thing to add to any production GC logging configuration is `time`:

```
-Xlog:gc*:file=/var/log/gc.log:time,uptime,level,tags
```

Note that the *order you write them in does not matter* — *"the order of the output is always
the same as listed in the table"* — so `time` will always precede `uptime` in the output
regardless of how you spell the option. A parser must be written against the table's order.

Two more worth considering. `pid` if several JVMs on a host ship to one aggregator, since the
filename may not survive the pipeline. And `utctime` rather than `time` if your fleet spans
time zones — the tuning guide's own example log lines use a locale-dependent decimal separator,
which is a reminder that this output is formatted for a machine you may not control.

## Reconfiguring a running JVM

> *"Logging can also be controlled at run time through Diagnostic Commands (with the `jcmd`
> utility). Everything that can be specified on the command line can also be specified
> dynamically with the `VM.log` command. As the diagnostic commands are automatically exposed as
> MBeans, you can use JMX to change logging configuration at run time."*

The `jcmd` man page gives the options and rates the impact as **Low**:

> *"`VM.log [options]` — Lists current log configuration, enables/disables/configures a log
> output, or rotates all logs. Impact: Low"*
>
> *"`output`: (Optional) The name or index (#) of output to configure. … `output_options`:
> (Optional) Options for the output. … `what`: (Optional) Configures what tags to log. …
> `decorators`: (Optional) Configures which decorators to use. Use 'none' or an empty value to
> remove all. … `disable`: (Optional) Turns off all logging and clears the log configuration. …
> `list`: (Optional) Lists current log configuration. … `rotate`: (Optional) Rotates all logs."*

```
jcmd <pid> VM.log list                                   # what is configured right now
jcmd <pid> VM.log what=gc*=debug output=stdout           # turn detail on
jcmd <pid> VM.log what=gc*=info  output=stdout           # turn it back down
jcmd <pid> VM.log output=gc.log decorators=time,level,tags   # add a decorator you forgot
jcmd <pid> VM.log rotate                                 # force a rotation before collecting
jcmd <pid> VM.log disable                                # stop all logging
```

**This is the single most under-used diagnostic in the JVM.** A service that is misbehaving
right now can have `gc+phases=debug` turned on without a restart, be observed for two minutes,
and have it turned off again — which means the argument "we did not have detailed GC logging
enabled" is never a reason to restart a process you are trying to diagnose. `VM.log rotate` is
the companion: force a rotation, then collect the closed file, rather than copying a file that
is being appended to.

⚠️ `VM.log disable` is documented as *"Turns off all logging and clears the log configuration"*,
which includes the default warning/error configuration. Turning logging back on afterwards
requires reconfiguring it, so prefer changing `what=` over disabling and re-enabling.

## The recipes worth memorising

| Goal | Selection |
|---|---|
| One line per collection, always on in production | `-Xlog:gc` |
| Everything GC, the tuning guide's own starting point | `-Xlog:gc*=debug` |
| Why is a pause long | `-Xlog:gc+phases=debug` ([03b2](03b2-the-four-phases-of-a-pause.md)) |
| Region counts per generation | `-Xlog:gc+heap=info` ([03d2](03d2-humongous-fragmentation.md)) |
| Survivor age histogram | `-Xlog:gc+age=debug` ([08b · Premature promotion](08c-premature-promotion.md)) |
| CPU breakdown per collection | `-Xlog:gc+cpu=info` ([01b](01b-what-the-pause-number-leaves-out.md)) |
| Sizing decisions and why | `-Xlog:gc+ergo*=debug` |
| Mixed-collection region choice | `-Xlog:gc+ergo+cset=debug` |
| TLAB allocation behaviour | `-Xlog:gc+tlab=debug` ([01 · Memory layout → 03c2](../01-memory-layout/03c2-tlab-sizing-and-the-flags.md)) |
| Time to safepoint | `-Xlog:safepoint` ([10 · Safepoints](10-safepoints.md)) |

The tuning guide's own recommendation for a starting point: *"For diagnosis purposes, G1
provides comprehensive logging. A good start is to use the `-Xlog:gc*=debug` option and then
refine the output from that if necessary."*

The production default should be narrower than that. `-Xlog:gc` costs one line per collection
and answers "when, why, how long, how much" for every collection that has ever happened, which
is the information you most regret not having. Everything else can be turned on with `jcmd`
when it is needed.

## Gotchas

**★ The default decorators cannot be correlated with anything.**
`uptime`, `level`, `tags` gives you seconds since JVM start. Not a wall-clock time, not a PID,
not a hostname. Add `time` — and add `pid` too if several JVMs write to the same aggregator.

**★ Decorator order in the option is ignored.**
*"The order of the output is always the same as listed in the table."* Writing
`level,time,tags` produces the same output as `time,level,tags`. Log parsers should be written
against the table's order, not against the option's.

**★ `jcmd VM.log` can turn detailed GC logging on without a restart, and almost nobody knows.**
Impact is rated Low. `VM.log what=gc*=debug` on a live, misbehaving JVM gets you the diagnosis
that would otherwise cost a restart — and a restart destroys the state you were trying to
observe. The same is reachable over JMX, since diagnostic commands are exposed as MBeans.

**★ `VM.log disable` clears the default warning configuration too.**
It *"turns off all logging and clears the log configuration"*. After it, the JVM is not even
reporting warnings and errors until you reconfigure. Use `what=...` to change a selection
rather than `disable` to remove one.

**★ `VM.log rotate` exists, and copying a live log file instead is how you get a truncated
one.**
Forcing a rotation closes the current file and starts a new one, so what you collect is a
complete file rather than a snapshot of one being appended to. It is one word and it removes a
whole class of "the log ends mid-line" confusion.

**★ Adding decorators at runtime requires naming the output.**
`VM.log` takes `output` and `decorators` together; changing decorators without specifying which
output you mean will not do what you expect. `VM.log list` first, then act on a named output or
its index.

**★ `-Xlog:gc*=debug` is a diagnostic setting, not a production one.**
It is the tuning guide's *starting point* for investigation, followed by refinement. On a busy
service it produces many lines per collection, and those lines are written synchronously inside
the safepoint unless `-Xlog:async` is set — see
[07d · Rotating and shipping GC logs](07d-rotating-and-shipping-gc-logs.md).

**★ `-Xlog:gc` in production is nearly free and answers most questions retrospectively.**
One line per collection carries the type, the cause, heap before, heap after, capacity and
duration. Almost every "what happened at 03:14" question about GC is answerable from it, and
you cannot enable it retroactively for an event that has already occurred.

**★ `uptime` is still worth keeping alongside `time`.**
It makes "how long had this JVM been up when this happened" answerable from the line itself,
which matters when a restart loop is part of the incident. The two decorators cost a few bytes
per line between them.

**★ There is no decorator for the GC id.**
The `GC(26)` in a G1 line comes from the log message itself, not from a decorator — the man page
notes under the legacy flag mapping that *"GC ID is now always logged"*. So it is present for GC
messages and absent for everything else, which matters if you are writing one parser for the
whole log.

## Interview questions

**★ You are on a call with a misbehaving JVM and no detailed GC logging. What do you do?**
Not restart it. `jcmd <pid> VM.log list` shows what is currently configured, and
`jcmd <pid> VM.log what=gc*=debug output=stdout` turns on full GC logging on the running
process — the `jcmd` man page rates the impact as Low and says *"everything that can be
specified on the command line can also be specified dynamically with the `VM.log` command"*. I
would observe for a few minutes, then set it back to `gc*=info` or the previous configuration.
Restarting would have destroyed exactly the state I needed to look at, and the same commands
are available over JMX because diagnostic commands are exposed as MBeans.

**★ What decorators would you put on a production GC log and why?**
`time` at minimum, because the default set — `uptime`, `level`, `tags` — timestamps everything in
seconds since JVM start, which cannot be aligned with an application log, a metrics dashboard or
an incident timeline. `pid` if several JVMs on a host ship to the same aggregator, and
`hostname` if the aggregator does not add one. `uptime` is worth keeping alongside `time`
because it makes "how long had this JVM been up" answerable from the line itself. Note that the
order you write the decorators in is irrelevant — the man page says *"the order of the output is
always the same as listed in the table"* — so parsers must be written against the table's order.

**★ How would you find out which log tags exist on the JDK you are running?**
`java -Xlog:help`. The man page deliberately does not enumerate them — it says *"There are
literally dozens of log tags"* and points at the command, which prints the syntax, the full tag
list, the levels, the decorators and worked example command lines for that exact build. Any tag
list from an article or a blog is a snapshot of some other version, and tags do come and go
between releases. It is also the fastest way to discover useful tags nobody talks about, which
is how most people find `gc+ergo+cset` and `gc+age`.

**★ What is the minimum GC logging you would insist on in production, and what would you leave
off?**
On: `-Xlog:gc` to a rotated file with `time` in the decorators. One line per collection is a
negligible cost and it retroactively answers when a collection happened, why, how long it took
and how much it freed — which is precisely the information nobody can obtain after the fact.
Off by default: everything else. `gc*=debug` is many lines per collection written synchronously
inside the safepoint, `gc+heap=trace` is more again, and all of it can be switched on in seconds
with `jcmd VM.log` when something is actually wrong. The asymmetry is the point: the always-on
setting must be cheap enough that nobody is tempted to turn it off, and the diagnostic setting
does not need to be always on because it can be added live.

**★ How do you collect a GC log from a running container without risking a truncated file?**
`jcmd <pid> VM.log rotate` first, which closes the current file and starts a new one, then copy
the closed file. Copying a file that the JVM is still appending to gives you whatever was
flushed at the moment of the read, which routinely ends mid-line and confuses parsers. The same
command is worth putting in the runbook before any log collection, and it pairs naturally with
`filecount`/`filesize` rotation — [07d](07d-rotating-and-shipping-gc-logs.md) — because the
rotated files are the ones that are safe to ship.
