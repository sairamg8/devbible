**A Spring Boot application is, by design, a program that decides its own shape while starting: it scans, parses, evaluates conditions, resolves profiles and generates proxies. Every one of those is a dynamic feature that a closed world forbids. Spring's answer is to do all of it during the build and write the answers down as ordinary Java source, cglib bytecode and GraalVM hint files. Topic 10 owns what that engine is and how it works on a plain JVM; this page is what it means specifically for the native path, and what it still cannot do for you.**

This page adds the three things that only matter when the target is a native image: the **hints**, the **build-time proxies**, and the **custom-hint API** you will need for anything Spring cannot infer. [05b](05b-what-spring-gives-up.md) is the native-specific half of the restrictions.

## Boot's framing: the closed world is *assumed*, not merely tolerated

> *"Typical Spring Boot applications are quite dynamic and configuration is performed at runtime. In fact, the concept of Spring Boot auto-configuration depends heavily on reacting to the state of the runtime in order to configure things correctly."*

> *"Although it would be possible to tell GraalVM about these dynamic aspects of the application, doing so would undo most of the benefit of static analysis. So instead, when using Spring Boot to create native images, a closed-world is assumed and the dynamic aspects of the application are restricted."*

⚠️ **"Doing so would undo most of the benefit"** is the argument for why Spring did not simply generate exhaustive metadata for everything. Registering the whole auto-configuration surface reflectively would produce a working image with none of the size or start-up advantage.

## The three artefacts, and which one is native-specific

> *"A Spring AOT processed application will typically generate:*
> *- Java source code*
> *- Bytecode (for dynamic proxies, etc.)*
> *- GraalVM JSON hint files in `META-INF/native-image/<groupId>/<artifactId>/`"*

**Source code** is useful on the JVM too — that is topic 10's subject. **Bytecode and hints exist for GraalVM.**

Where to find each, which is the single most useful debugging fact on this page:

| Artefact | Maven | Gradle |
|---|---|---|
| Generated sources | `target/spring-aot/main/sources` | `build/generated/aotSources` |
| Generated hint files | `target/spring-aot/main/resources` | `build/generated/aotResources` |
| Generated proxy classes | `target/spring-aot/main/classes` | `build/generated/aotClasses` |

Boot's own note on the last one is honest: *"Unlike source code generation, generated bytecode isn't particularly helpful when debugging an application. However, if you need to inspect the contents of the `.class` files using a tool such as `javap` you can find them in `target/spring-aot/main/classes`."*

## Hints — what they are for

> *"In addition to generating source files, the Spring AOT engine will also generate hint files that are used by GraalVM. Hint files contain JSON data that describes how GraalVM should deal with things that it can't understand by directly inspecting the code."*

> *"For example, you might be using a Spring annotation on a private method. Spring will need to use reflection in order to invoke private methods, even on GraalVM. When such situations arise, Spring can write a reflection hint so that GraalVM knows that even though the private method isn't called directly, it still needs to be available in the native image."*

🔴 **Generated source removes *most* reflection but not all of it**, and hints cover the remainder. That is why an AOT-processed Boot application still ships a metadata directory.

⚠️ **Boot 4.1's reference names the five legacy file names** — `resource-config.json`, `reflect-config.json`, `serialization-config.json`, `proxy-config.json`, `jni-config.json` — while GraalVM's reference documents `reachability-metadata.json` as the current format. Both are read by the builder. [03b](03b-reachability-metadata.md) records this divergence in full; **do not rewrite generated output to match either page.**

**And the scope limit, stated by Boot itself:**

> *"Spring itself doesn't contain hints for 3rd party libraries and instead relies on the reachability metadata project."*

So the division of labour is: Spring hints *your* beans and *Spring's* machinery; the GraalVM Reachability Metadata Repository hints *your dependencies*; you hint whatever falls between.

## Proxies move from run time to build time

> *"Spring sometimes needs to generate proxy classes to enhance the code you've written with additional features. To do this, it uses the cglib library which directly generates bytecode."*

> *"When an application is running on the JVM, proxy classes are generated dynamically as the application runs. When creating a native image, these proxies need to be created at build-time so that they can be included by GraalVM."*

**Everything that depends on a Spring proxy therefore depends on a build-time decision**: `@Transactional`, `@Async`, `@Cacheable`, `@Retryable`, Spring Security method security, and `@Configuration` classes with `proxyBeanMethods = true`. If the AOT engine did not see a reason to generate a proxy, there is no mechanism at run time to make one.

⚠️ **This is a good reason to prefer `proxyBeanMethods = false`** in your own `@Configuration` classes — one fewer proxy to generate, and the style the engine is designed around.

## Custom hints — the API you will need

Spring cannot infer everything. The escape hatch is `RuntimeHintsRegistrar`:

```java
package com.example.billing;

import org.springframework.aot.hint.MemberCategory;
import org.springframework.aot.hint.RuntimeHints;
import org.springframework.aot.hint.RuntimeHintsRegistrar;

public class BillingRuntimeHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.resources().registerPattern("rules/*.drl");
        hints.reflection().registerType(InvoiceTemplate.class,
                MemberCategory.INVOKE_DECLARED_CONSTRUCTORS,
                MemberCategory.INVOKE_PUBLIC_METHODS);
        hints.serialization().registerType(AuditRecord.class);
    }
}
```

activated by annotating any `@Configuration` class — Boot suggests the application class itself:

```java
@SpringBootApplication
@ImportRuntimeHints(BillingRuntimeHints.class)
public class BillingApplication {
    public static void main(String[] args) {
        SpringApplication.run(BillingApplication.class, args);
    }
}
```

**Hints are testable, and Boot documents the API for it** — `RuntimeHintsPredicates`, which *"provides methods that build a `Predicate` that can be used to test a `RuntimeHints` instance."* A hint you never assert on is a hint that silently stops matching when you rename a class:

```java
@Test
void registersTheRulesResources() {
    RuntimeHints hints = new RuntimeHints();
    new BillingRuntimeHints().registerHints(hints, getClass().getClassLoader());
    assertThat(RuntimeHintsPredicates.resource().forResource("rules/pricing.drl"))
            .accepts(hints);
}
```

**For serialization-style binding**, Boot points at a narrower annotation:

> *"If you have classes which need binding (mostly needed when serializing or deserializing JSON), you can use `@RegisterReflectionForBinding` on any bean. Most of the hints are automatically inferred, for example when accepting or returning data from a `@RestController` method. But when you work with `WebClient`, `RestClient` or `RestTemplate` directly, you might need to use `@RegisterReflectionForBinding`."*

🔴 **That is a precise and frequently-hit rule.** A DTO in a `@RestController` signature is inferred. The same DTO used only as the body type of an outbound `RestClient` call is **not**, because nothing in the signature graph declares it. This is one of the most common "works on the JVM, fails in native" defects in a Boot application, and it fails at the moment of the outbound call — often in an error path.

You can also provide hints statically as JSON, and Boot names the collision to avoid:

> *"The hints generated during AOT processing are written to a directory named `META-INF/native-image/<groupId>/<artifactId>/`. Place your static hint files in a directory that does not clash with this location, such as `META-INF/native-image/<groupId>/<artifactId>-additional-hints/`."*

## Configuration properties: the one annotation you must not forget

> *"Reflection hints are automatically created for configuration properties by the Spring ahead-of-time engine. Nested configuration properties which are not inner classes, however, **must** be annotated with `@NestedConfigurationProperty`, otherwise they won't be detected and will not be bindable."*

> *"Without the `@NestedConfigurationProperty` annotation on the `nested` field, the `my.properties.nested.number` property would not be bindable in a native image."*

```java
@ConfigurationProperties("my.properties")
public class MyProperties {

    private String name;

    @NestedConfigurationProperty
    private Nested nested = new Nested();      // Nested is a separate top-level class

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public Nested getNested() { return nested; }
    public void setNested(Nested nested) { this.nested = nested; }
}
```

The annotation goes on the **field** for constructor binding, on the **parameter** for records, and on the parameter of a Kotlin data class. And a separate requirement that catches people: *"Please use public getters and setters in all cases, otherwise the properties will not be bindable."*

⚠️ **The failure mode is silence.** The property is not bound; it is not an error. A nested block of configuration is simply ignored, and the defaults win.

## How it is wired into the build

The `native` profile in `spring-boot-starter-parent` 4.1.0 does three things, readable directly in the published POM:

- adds a manifest entry `Spring-Boot-Native-Processed: true` to the jar, which is how downstream tooling — buildpacks in particular — knows the jar carries AOT assets;
- binds the Spring Boot plugin's **`process-aot`** goal;
- binds Native Build Tools' **`add-reachability-metadata`** goal, and configures `classesDirectory` to the project's output directory plus an exclusion for `spring-boot-devtools`.

The `nativeTest` profile binds **`process-test-aot`** and Native Build Tools' **`test`** goal, and adds `junit-platform-launcher` as a test dependency.

If you do not use the starter parent, Boot tells you what to reproduce: *"you'll need to configure executions for the `process-aot` goal from Spring Boot's plugin and the `add-reachability-metadata` goal from the Native Build Tools plugin."* [06](06-building-one.md) is the full build story.

## Gotchas

**★ Symptom: a DTO serialises fine from a controller but fails when sent through `RestClient` or `WebClient`.** Cause: binding hints are inferred from controller signatures, not from outbound call sites. Fix: annotate the type — `@RegisterReflectionForBinding(PaymentRequest.class)` on any bean — exactly as Boot's reference instructs for the `WebClient`/`RestClient`/`RestTemplate` case.

**★ Symptom: a nested configuration block is silently ignored in the native image.** Cause: the nested type is a separate top-level class and the field was not annotated, so no reflection hint was created. Fix: `@NestedConfigurationProperty` on the field, the constructor parameter or the record component, plus public getters and setters. Assert on the bound value in a test rather than trusting it.

**★ Symptom: `@Transactional` or `@Cacheable` has no effect in the native image.** Cause: the behaviour comes from a cglib proxy, and proxies are generated at build time in the native path. If the AOT engine did not generate one — because the bean was registered in a way it could not analyse, or because the annotation is on a class it never saw — nothing creates it later. Fix: inspect `target/spring-aot/main/classes`, confirm the proxy exists, and check the bean is registered in a form AOT can process ([05b](05b-what-spring-gives-up.md)).

**★ Symptom: a hand-written hint file is overwritten or ignored.** Cause: it was placed in `META-INF/native-image/<groupId>/<artifactId>/`, which is where the AOT engine writes. Fix: use a non-clashing directory such as `META-INF/native-image/<groupId>/<artifactId>-additional-hints/`, which is Boot's own recommendation.

**★ Symptom: hints for a third-party library are missing and nobody knows whose job it is.** Cause: *"Spring itself doesn't contain hints for 3rd party libraries and instead relies on the reachability metadata project."* Fix: check the GraalVM Reachability Metadata Repository, run `./mvnw native:list-libraries-missing-metadata` to see the gaps, and either contribute metadata upstream or add a `RuntimeHintsRegistrar` locally.

**★ Symptom: a `RuntimeHintsRegistrar` exists but is never applied.** Cause: it was written but not activated — the class does nothing unless a `@Configuration` class carries `@ImportRuntimeHints`. Fix: add the annotation, and add a `RuntimeHintsPredicates` test so the registrar's contents are asserted rather than assumed.

**★ Symptom: `spring-boot-devtools` breaks the native build.** Cause: devtools' restart classloader is fundamentally incompatible with a closed world. Fix: nothing — the starter parent's `native` profile already excludes it from the Native Build Tools configuration. If you are not using the starter parent, reproduce that exclusion.

**★ Symptom: buildpacks refuse to produce a native image from an executable jar.** Cause: the jar was not AOT-processed, so it does not carry the generated assets or the `Spring-Boot-Native-Processed` manifest entry. Boot: *"Your executable jar must include AOT generated assets such as generated classes and JSON hint files."* Fix: build with `-Pnative` so `process-aot` runs, then hand the jar to `pack`.

**★ Symptom: `@Configuration` classes behave differently in the native build.** Cause: `proxyBeanMethods = true` requires a proxy, generated at build time here. Fix: prefer `proxyBeanMethods = false` and call collaborating `@Bean` methods through injected parameters rather than through direct method calls on the configuration class.

## Interview questions

**★ Why can a Spring Boot application not simply be compiled by `native-image` without the AOT engine?**
Because a Boot application's shape is computed at start-up: classpath scanning, `@Configuration` parsing, condition evaluation, profile resolution and cglib proxy generation are all dynamic features that a closed world forbids. Boot's reference explains why brute force is not the answer either: *"Although it would be possible to tell GraalVM about these dynamic aspects of the application, doing so would undo most of the benefit of static analysis."* The AOT engine instead performs the discovery at build time and emits the answers as generated source, pre-generated proxy bytecode and hint files.

**★ What exactly does Spring generate for GraalVM, as opposed to for the JVM?**
Three artefacts, of which the JVM benefits from one. Generated Java source for bean definitions is useful on a plain JVM too — it removes runtime `@Configuration` parsing. cglib **bytecode** for proxies and **GraalVM hint files** exist for the native path: the proxies because they cannot be generated at run time, and the hints because generated source removes most reflection but not all of it — Boot's example is a Spring annotation on a private method, which still needs reflective invocation and therefore a reflection hint.

**★ Whose responsibility is metadata for a third-party library?**
Not Spring's, and the reference says so: *"Spring itself doesn't contain hints for 3rd party libraries and instead relies on the reachability metadata project."* So the ladder is: the library ships its own metadata; if not, the GraalVM Reachability Metadata Repository carries it and Native Build Tools consumes it automatically; if not, you write a `RuntimeHintsRegistrar` or a JSON file yourself and, ideally, contribute it upstream. `native:list-libraries-missing-metadata` tells you which rung you are on before you start.

**★ A DTO works in a controller and fails in an outbound HTTP call. Explain.**
Spring infers binding hints from the shapes it can see, and a `@RestController` method's parameter and return types are visible. A type used only as the body of a `RestClient`, `WebClient` or `RestTemplate` call appears nowhere in a signature the engine analyses, so no reflection hint is generated and Jackson cannot introspect it in the native image. Boot documents the fix directly: `@RegisterReflectionForBinding` on any bean. It is worth flagging as a review rule, because the failure typically surfaces on an outbound call in an error path that no smoke test exercises.

**★ Why does `@NestedConfigurationProperty` matter more in a native image than on a JVM?**
Because in a native image the absence of a reflection hint is the absence of the capability. On a JVM, binder reflection just works; the annotation is mostly a documentation aid for metadata generation. In a native image, the AOT engine creates reflection hints for configuration properties, and Boot states that a nested type which is not an inner class *"must be annotated with `@NestedConfigurationProperty`, otherwise they won't be detected and will not be bindable."* The failure is silent — the nested block is ignored and defaults apply — which is why it belongs in a test assertion rather than a code-review checklist.

**★ What does the `native` Maven profile actually do, and what happens if you do not use `spring-boot-starter-parent`?**
Reading the published 4.1.0 POM: it adds a `Spring-Boot-Native-Processed: true` manifest entry to the jar, binds the Spring Boot plugin's `process-aot` goal, and binds Native Build Tools' `add-reachability-metadata` goal while excluding `spring-boot-devtools` and pointing the classes directory at the project output. The `nativeTest` profile binds `process-test-aot` and Native Build Tools' `test` goal and adds `junit-platform-launcher`. Without the starter parent, Boot tells you to configure `process-aot` and `add-reachability-metadata` yourself — and in practice you also want the devtools exclusion and the manifest entry, because buildpacks use the latter to decide whether the jar is native-ready.
