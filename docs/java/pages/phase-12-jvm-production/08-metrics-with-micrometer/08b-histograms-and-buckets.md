**[08](08-percentiles.md) concluded that on Prometheus you want a histogram. This page is what a
histogram costs, where the number seventy-three comes from, and the three ways the clamp that
produces it gets silently removed. It is the most expensive single configuration option in
Micrometer, and it is one boolean in a properties file.**

## The number, from the documentation

> *"`publishPercentileHistogram`: Used to publish a histogram suitable for computing aggregable
> (across dimensions) percentile approximations in Prometheus (by using `histogram_quantile`), Atlas
> (by using `:percentile`), and Wavefront (by using `hs()`). For Prometheus and Atlas, the buckets
> in the resulting histogram are preset by Micrometer based on a generator that has been determined
> empirically by Netflix to yield a reasonable error bound on most real world timers and
> distribution summaries. **By default, the generator yields 276 buckets, but Micrometer includes
> only those that are within the range set by `minimumExpectedValue` and `maximumExpectedValue`,
> inclusive. Micrometer clamps timers by default to a range of 1 millisecond to 1 minute, yielding
> 73 histogram buckets per timer dimension.**"*

Three facts in one paragraph:

1. The full generator produces **276** buckets.
2. The default timer clamp is **1 ms to 1 minute**.
3. That clamp leaves **73** buckets **per tag combination**.

## Where the boundaries come from

The generator is not arbitrary and you can read it. From `PercentileHistogramBuckets`:

> *"The set of buckets is generated by using powers of 4 and incrementing by one-third of the
> previous power of 4 in between as long as the value is less than the next power of 4 minus the
> delta."*

```
Base: 1, 2, 3

4 (4^1), delta = 1
5, 6, 7, ..., 14,

16 (4^2), delta = 5
21, 26, 31, ..., 56,

64 (4^3), delta = 21
...
```

*(That is the comment block from the source, reproduced.)*

Two useful consequences. The boundaries are **roughly logarithmic**, which is exactly the shape the
SRE book recommends for latency — *"distributing the histogram boundaries approximately
exponentially … is often an easy way to visualize the distribution of your requests"*. And the
resolution is *relative*, not absolute: the error bound near 5 ms is a few percent of 5 ms, and near
5 s is a few percent of 5 s. That is the right trade for latency and the wrong one if you need
precision at one specific value — which is what SLO boundaries exist for
([08c](08c-slos-and-the-bucket-budget.md)).

## The budget

Per tag combination, a timer with a percentile histogram publishes roughly:

```
73 bucket series  +  count  +  sum  +  max   ≈  76 series
```

So the total for one meter name is:

```
series = 76  ×  ∏(distinct values of each tag)  ×  ∏(distinct values of each common tag)
```

A timer tagged `uri` (40), `method` (4) and `outcome` (3) is 480 combinations, which is **36,480
series** from one `Timer.builder(...)` call. The same timer without the histogram is 1,440.

*(Arithmetic on Micrometer's documented bucket count; not a measurement.)*

🔴 This is why `management.metrics.distribution.percentiles-histogram.all=true` is one of the most
expensive lines you can write in a Spring Boot service, and why the recommendation is always
per-meter.

## What a bucket series actually is

Prometheus defines the exposition precisely, and the two details people get wrong are both in it:

> *"A classic histogram with a base metric name of `<basename>` results in the following time
> series: **cumulative counters** for the observation buckets, exposed as
> `<basename>_bucket{le="<upper inclusive bound>"}`; the total sum of all observed values, exposed
> as `<basename>_sum`; the count of events that have been observed, exposed as `<basename>_count`
> (identical to `<basename>_bucket{le="+Inf"}` above)."*

and, when you query one directly:

> *"You can operate directly on the buckets of a classic histogram, as they are represented as
> individual series … Remember, however, that these buckets are **cumulative**, i.e. every bucket
> counts all observations less than or equal to the upper boundary provided as a label."*

So `orders_process_seconds_bucket{le="0.1"}` is *"how many observations were at most 100 ms"*, not
*"how many landed in this bucket"*. Getting the count in a band means subtracting two buckets, and
forgetting that is the reason a hand-rolled "requests between 100 ms and 300 ms" panel is always
wrong high.

The `+Inf` identity is worth remembering for a different reason: it is a free consistency check. If
`_bucket{le="+Inf"}` and `_count` disagree, something is dropping series in the pipeline.

## Classic versus native

Everything above is a **classic** histogram: one counter series per boundary, carrying an `le`
label. Prometheus now prefers the alternative:

> *"Native histograms are generally much more efficient than classic histograms, allow much higher
> resolution, do not require explicit configuration of bucket boundaries during instrumentation,
> and provide atomicity when transferred over the network … Their bucketing schema ensures that
> they are always aggregatable with each other, even if the resolution might have changed, while
> classic histograms with different bucket boundaries are not generally aggregatable. If the
> instrumentation library you are using supports native histograms (currently this is the case for
> Go and Java), you should probably prefer native histograms over classic ones."*

⚠️ **I could not confirm that Micrometer 1.17.0's Prometheus registry can emit them.** Neither
`PrometheusConfig` nor `PrometheusMeterRegistry` at tag `v1.17.0` contains any reference to native
histograms, and the reference documentation for that registry does not mention them. The
Prometheus Java *client* supporting a feature is not the same as Micrometer exposing it. Treat any
native-histogram advice as applying to direct use of the Prometheus client until you have checked
your own version — and note the last clause of the quote above, which is the practical reason it
matters: **classic histograms with different bucket boundaries are not generally aggregatable**, so
two services with different clamps cannot have their histograms summed.

## Three levers, one page

The bucket count is controlled by the expected-value clamp, by a `MeterFilter`'s `configure`
method, and by Boot's per-meter properties — and all three interact with the SLO boundaries that
add buckets of their own. Because those are one decision rather than three, they live together in
[08c · SLOs and the bucket budget](08c-slos-and-the-bucket-budget.md).

## What this does not include

⚠️ Prometheus's **native histograms** are a different exposition format with a different cost
profile, and I could not find support for emitting them in Micrometer 1.17.0's Prometheus registry —
neither `PrometheusConfig` nor `PrometheusMeterRegistry` at tag `v1.17.0` mentions them. Everything
on this page is about **classic** histograms: one `_bucket` series per boundary, with an `le` label.
If you are reading advice about native histograms, check whether it applies to your client version
before acting on it.

## Gotchas

**★ `percentiles-histogram.all=true` is the single most expensive line in a Boot metrics
configuration.** It multiplies every timer and distribution summary in the process — yours and the
binders' — by roughly seventy-six per tag combination. It is almost never what you want; name the
meters.

**★ `publishPercentileHistogram` does nothing at all on backends without aggregable percentile
support.** *"No histogram is shipped for these systems."* So the same configuration is free on
Datadog and enormous on Prometheus, which makes "it was fine in the other service" a bad argument.

**★ Histogram accuracy is relative, not absolute.** The generator's buckets are spaced
logarithmically, so the error near 5 ms is proportionally similar to the error near 5 s. If you need
to know exactly how many requests exceeded 500 ms, that is an SLO boundary, not a quantile
([08c](08c-slos-and-the-bucket-budget.md)).

**★ Bucket series are counters, so they carry the counter contract.** They are exported cumulatively
on Prometheus and must be `rate()`d before aggregation, and `le` must survive the `sum by`
([03e](03e-rate-aggregation-and-the-step-registry.md)).

**★ Turning a histogram on for `http.server.requests` interacts with the URI cardinality cap.** The
`uri` tag is bounded at 100 values by default; at 76 series per combination and four HTTP methods,
the worst case is a five-figure series count from one meter. Both limits are working as designed and
their product is the number that matters.

**★ Enabling both `percentiles` and `percentiles-histogram` on one meter is unsupported on the
Prometheus 1.x client.** Micrometer states it outright, and Boot 4.1 manages that client.

**★ A histogram enabled in a shared library is imposed on every consumer.** Micrometer's guidance is
to leave distribution statistics unconfigured in libraries and let applications opt in with a
filter.

**★ Bucket series are cumulative, so a single bucket is not a band.** `le="0.1"` counts everything
at or below 100 ms. A "how many took between 100 ms and 300 ms" panel needs a subtraction, and the
version without it silently overcounts.

**★ `_bucket{le="+Inf"}` and `_count` are the same number by definition.** Useful as a sanity check
on your pipeline; if they differ, series are being dropped somewhere between the scrape and the
query.

**★ Classic histograms with different bucket boundaries are not aggregatable.** Prometheus says so.
Two services that clamped their timers differently cannot have their `_bucket` series summed
meaningfully, which is a real constraint on fleet-wide dashboards and an argument for setting the
clamp once, centrally.

**★ Since Prometheus v3.0 the `le` values of classic histograms are normalised at ingestion.**
*"The values of the `le` label of classic histograms are normalized during ingestion to follow the
format of OpenMetrics Canonical Numbers."* A query or recording rule pinning a literal `le` string
can therefore stop matching across a Prometheus upgrade.

## Interview questions

**★ Where does the number 73 come from?**
From Micrometer's bucket generator and the default clamp. The generator — powers of four with
thirds interpolated between them, empirically derived at Netflix — yields 276 boundaries across the
whole `long` range. Micrometer ships only the ones inside `minimumExpectedValue` to
`maximumExpectedValue`, and for timers those default to 1 millisecond and 1 minute, which leaves 73.
Those 73 are per *tag combination*, not per meter name, which is what makes the option expensive.

**★ Why are Micrometer's default bucket boundaries logarithmic rather than evenly spaced?**
Because latency distributions are heavy-tailed and interesting across several orders of magnitude.
Evenly spaced buckets waste almost all their resolution in a range where nothing happens and have
none where the tail is. The generator's powers-of-four-with-thirds scheme gives roughly constant
*relative* error across the range, which is the right property when you care about "is the p99 30%
worse than yesterday" rather than "is it exactly 412 ms". The SRE book independently recommends
approximately exponential boundaries for the same reason.

**★ You need to know precisely how many requests took longer than 500 ms. Can a percentile
histogram tell you?**
Only approximately, and the approximation is a function of where the nearest bucket boundaries
happen to fall — `histogram_quantile` interpolates within the bucket the quantile lands in, so a
count derived from bucket boundaries near but not at 500 ms is interpolated too. The exact answer
comes from adding 500 ms as a service-level objective boundary, which makes Micrometer publish a
bucket at exactly that value; the count in it is then a real count and not an estimate. That is what
`serviceLevelObjectives` is for, and it is the subject of [08c](08c-slos-and-the-bucket-budget.md).

**★ Two services have identical timer configuration and wildly different metric costs. What
explains it?**
Tag cardinality, almost certainly. The histogram cost is per tag combination, so a timer with one
bounded tag and a timer with three tags of forty, four and three values differ by a factor of
several hundred for the same one-line configuration. The second candidate is the backend: a
percentile histogram is a no-op on systems without aggregable percentile support, so the same code
that costs nothing on Datadog can dominate a Prometheus scrape. Compare series counts, not
configuration.

**★ What does `histogram_quantile` need that a naive `sum by (uri)` destroys, and why?**
The `le` label. A classic histogram is a family of cumulative counter series distinguished only by
`le`, and the quantile function reconstructs the distribution from that family — so an aggregation
that collapses `le` leaves it with a single meaningless series per group. Prometheus states the
requirement directly. The correct form keeps `le` in the `by` clause alongside whatever else you are
grouping by, and puts the `rate()` innermost so each series is reset-corrected before summation.

**★ Someone builds a panel for "requests that took between 100 ms and 300 ms" from
`_bucket{le="0.3"}`. What is wrong?**
Buckets are cumulative: `le="0.3"` counts every observation at or below 300 ms, including all the
ones under 100 ms. The band requires subtracting the `le="0.1"` series from the `le="0.3"` series,
and both need `rate()` first. The panel as written is not slightly off — it includes the entire
fast majority of your traffic, so it will look reassuringly large and move with total volume rather
than with latency.
