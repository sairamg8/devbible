**The link table already exists in your database. `@ManyToMany` hides it; a link entity
maps it. Once you do that, you no longer have a many-to-many mapping at all — you have
two perfectly ordinary bidirectional one-to-manys, each with the well-behaved
`@ManyToOne` owning side from [chunk 3](03-many-to-one.md). The 7.4 *User Guide* calls
this "the most natural" shape and recommends it outright: "it's much better to map the
link table."**

## The mapping

```java
@Entity
public class Book {

    @Id @GeneratedValue
    private Long id;

    @NaturalId
    private String isbn;

    @OneToMany(mappedBy = "book", cascade = CascadeType.ALL, orphanRemoval = true)
    private Set<BookAuthorship> authorships = new HashSet<>();
}

@Entity
public class Author {

    @Id @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "author")
    private Set<BookAuthorship> authorships = new HashSet<>();
}

@Entity
public class BookAuthorship {

    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "book_id")
    private Book book;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "author_id")
    private Author author;

    // the columns that made this necessary in the first place
    private int contributionPercent;
    private String role;
    private Instant addedAt;
}
```

```sql
CREATE TABLE book_authorship (
    id                   bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    book_id              bigint NOT NULL REFERENCES book (id),
    author_id            bigint NOT NULL REFERENCES author (id),
    contribution_percent int    NOT NULL,
    role                 text   NOT NULL,
    added_at             timestamptz NOT NULL,
    UNIQUE (book_id, author_id)
);

CREATE INDEX book_authorship_author_id_idx ON book_authorship (author_id);
```

Look at what is now true. Two `@ManyToOne` associations, each owning its own foreign-key
column. Two `@OneToMany(mappedBy)` collections, each an inverse view. There is no
`@ManyToMany` anywhere, no `@JoinTable`, and no association whose behaviour you have to
reason about specially. The 7.4 *User Guide* describes the target shape exactly: *"Each
`FOREIGN KEY` column will be mapped as a `@ManyToOne` association. On each parent-side, a
bidirectional `@OneToMany` association is going to map to the aforementioned `@ManyToOne`
relationship in the link entity."*

## The helper methods, which now do more work

The link entity has to be constructed, so the helper does that too. Hibernate's own
example uses precisely this shape:

```java
// on Book
public void addAuthor(Author author, int contributionPercent, String role) {
    BookAuthorship authorship = new BookAuthorship(this, author, contributionPercent, role);
    authorships.add(authorship);
    author.getAuthorshipsInternal().add(authorship);
}

public void removeAuthor(Author author) {
    authorships.removeIf(a -> {
        if (a.getAuthor().equals(author)) {
            author.getAuthorshipsInternal().remove(a);
            a.setBook(null);
            a.setAuthor(null);
            return true;
        }
        return false;
    });
}
```

Note the `setBook(null)` / `setAuthor(null)` in the removal path. The guide's example does
the same. It matters because `orphanRemoval = true` on `Book.authorships` will delete the
link row, and you do not want a detached-but-still-referenced link entity floating around
pointing at both parents.

## Choosing the link entity's primary key

Three options. They are genuinely different and the choice is worth a minute.

**A surrogate id** — `@Id @GeneratedValue Long id`, plus a `UNIQUE (book_id, author_id)`
constraint, as shown above. Simplest to work with: `equals`/`hashCode` are ordinary, the
row has a stable handle, and a repository can find it by id. This is the default choice.

**A composite key made of the two associations** — Hibernate's own example does this:

```java
@Entity
public class BookAuthorship implements Serializable {

    @Id @ManyToOne
    private Book book;

    @Id @ManyToOne
    private Author author;
}
```

`@Id` on a `@ManyToOne` is legal and means "this association contributes to the primary
key". It expresses the uniqueness in the key itself rather than in a separate constraint,
and it needs `equals`/`hashCode` over both associations plus `Serializable` on the class.
Correct, and heavier to work with.

**An `@EmbeddedId` with the two ids plus `@MapsId`** — a middle ground, giving you both a
key object and navigable associations. More annotations, same outcome as the second
option.

⚠️ **If you use a surrogate id, the `UNIQUE (book_id, author_id)` constraint is not
optional.** It is the only thing preventing the same pair appearing twice, which the
composite primary key gave you for free in the `@ManyToMany` mapping.

## What you gain

**Extra columns.** The reason you are here. `contributionPercent`, `role`, `addedAt` all
have somewhere to live, and adding a fourth is a one-line change rather than a remodelling.

**Its own lifecycle.** The association can be created, updated and deleted as a thing.
"Change this author's contribution from 40% to 60%" is an update of one row, expressible
in the domain model. Under `@ManyToMany` it is not expressible at all.

**Ordinary owning sides.** Both writes go through `@ManyToOne` fields — the shape with the
fewest surprises in this entire topic.

**Queryability.** `SELECT a FROM BookAuthorship a WHERE a.role = 'EDITOR'` is a normal
query over a normal entity. Under `@ManyToMany` there is no type to select from.

**Auditability.** A link entity gets `@CreatedDate`, `@LastModifiedBy`, soft-delete flags,
Envers auditing — everything an entity gets. A hidden join table gets none of it.

## What you lose

**Directness.** `book.getAuthors()` becomes
`book.getAuthorships().stream().map(BookAuthorship::getAuthor)`. You can add a convenience
method returning the authors, but the collection you map is the authorships.

**A class.** One more file, one more table mapping to maintain. Real, and small.

**A hop.** Navigating book → author now passes through the link entity. In SQL it is the
same join it always was — the join table was always there — but a lazily-loaded link
entity means the author is two lazy steps away rather than one, so fetching needs a little
more thought.

**The "just add it to the set" ergonomics.** Adding an association now means constructing
an object with its required fields, which is more ceremony and also more honest, because
those fields were always required.

## When `@ManyToMany` is still fine

It is not banned. It is fine when **all** of these hold:

- the relationship genuinely has no attributes and you can state why it never will;
- both collections are small;
- you never need to query the association itself;
- you never need to audit when the association was created.

Tagging is the usual honest example: `Post` ↔ `Tag`, where the pair really is the whole
fact. Even there, `added_at` shows up eventually more often than not.

## Gotchas

**Migrating from `@ManyToMany` to a link entity is a code change, not a schema change — if
you used a surrogate key you must add one.** The two-column table maps fine to a composite
key. If you want a surrogate id you need a migration to add the column, and the old
composite primary key becomes a unique constraint.

**Cascade on the link entity is directional and must be thought about.** `Book.authorships`
with `cascade = ALL, orphanRemoval = true` means deleting a book deletes its authorships,
which is correct. `Author.authorships` should usually cascade **nothing**, because deleting
an author should not silently delete authorship rows belonging to books — and if it should,
say so deliberately.

**A link entity with two `EAGER` `@ManyToOne`s is worse than the `@ManyToMany` it replaced.**
Each link row now drags both parents along. Both associations must be `LAZY`; the default
for `@ManyToOne` is `EAGER`, so you have to write it.

**`@Id @ManyToOne` requires `Serializable` and a real `equals`/`hashCode`.** Hibernate's
example implements both. A composite key backed by associations that do not implement
`equals` correctly produces a key that does not work as a key.

**The `UNIQUE` constraint is easy to forget with a surrogate key.** Nothing in the Java
model stops `addAuthor` being called twice with the same author. The database has to.

**Two `@OneToMany` collections of the same link entity type on the same entity need
different `mappedBy` values.** Obvious when stated, and a genuine trap for
self-referencing link entities — a `Person` ↔ `Person` "follows" relationship has
`follower` and `followee` collections both of type `Set<Follow>`.

## Interview questions

**★ Why replace a `@ManyToMany` with a link entity?**
Because the association table almost always turns out to need columns of its own — a role,
a timestamp, an ordering, a contribution — and `@ManyToMany` provides no Java type in
which to put them. Hibernate's documentation predicts this outcome and recommends
avoiding `@ManyToMany` from the start for that reason. Promoting the table to an entity
also converts an awkward mapping into two ordinary bidirectional one-to-manys, each owned
by a well-behaved `@ManyToOne`.

**★ What does the mapping look like afterwards?**
The link entity gets a `@ManyToOne` to each side, each with its own `@JoinColumn`, both
`LAZY`. Each parent gets a `@OneToMany(mappedBy = …)` collection of link entities. There
is no `@ManyToMany` and no `@JoinTable` left. The user guide describes exactly this: each
foreign-key column is a `@ManyToOne`, and each parent side is a bidirectional `@OneToMany`
mapping onto it.

**★ How do you key the link entity?**
Either a surrogate generated id plus a unique constraint on the two foreign keys, or a
composite key made of the two associations using `@Id` on each `@ManyToOne` — which is what
Hibernate's own example does, and which requires the class to be `Serializable` and to
implement `equals`/`hashCode` over both associations. The surrogate is easier to work with
day to day; the composite expresses the uniqueness in the key rather than in a separate
constraint. If you take the surrogate, the unique constraint is mandatory, not optional.

**★ What do you give up?**
Directness and one class. `book.getAuthors()` becomes a mapping over
`book.getAuthorships()`, navigating from book to author passes through an extra entity, and
adding an association means constructing an object rather than adding to a set. In
exchange you get attributes, a lifecycle, queryability and auditing on the association —
and every one of those is something `@ManyToMany` cannot give you at any price.

**★ Is `@ManyToMany` ever the right answer?**
When the relationship is genuinely attribute-free and will stay that way, both collections
are small, and you never need to query or audit the association itself. Post-to-tag is the
usual example. The test is whether you can say confidently that the table will never need a
third column — and the reason Hibernate's documentation is sceptical is that people are
usually wrong about that.
