**Two annotations, one foreign key, and a clear division of labour: the child's
`@ManyToOne` writes the column, the parent's `@OneToMany(mappedBy = …)` reads it back as
a collection. The 7.4 *User Guide* says plainly that "behind the scenes, the relational
database has only one foreign key for this relationship" and that the bidirectional form
"is much more efficient when managing the collection persistence state". This is the
mapping the previous two chunks have been arguing towards.**

## The complete pair

```java
@Entity
public class Publisher {

    @Id @GeneratedValue
    private Long id;

    private String name;

    @OneToMany(mappedBy = "publisher",
               cascade = CascadeType.ALL,
               orphanRemoval = true)
    private Set<Book> books = new HashSet<>();

    public void addBook(Book book) {
        books.add(book);
        book.setPublisher(this);
    }

    public void removeBook(Book book) {
        books.remove(book);
        book.setPublisher(null);
    }

    public Set<Book> getBooks() {
        return Collections.unmodifiableSet(books);
    }
}

@Entity
public class Book {

    @Id @GeneratedValue
    private Long id;

    @NaturalId
    private String isbn;

    private String title;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "publisher_id")
    private Publisher publisher;

    void setPublisher(Publisher publisher) {   // package-private: use addBook
        this.publisher = publisher;
    }
}
```

Every element of that is deliberate, and every one has been argued somewhere in the last
four chunks:

| Element | Why |
|---|---|
| `@ManyToOne` on `Book` | the many side always holds the key — **[2](02-the-owning-side.md)** |
| `fetch = LAZY` on the `@ManyToOne` | the JPA default is `EAGER` — **[12](12-fetch-type-defaults.md)** |
| `optional = false` | the domain says a book has a publisher; the DDL should say so too |
| `mappedBy = "publisher"` | this collection maps no column; the field on `Book` does |
| `addBook` / `removeBook` | both sides in one place — **[2c](02c-keeping-both-sides-in-step.md)** |
| `Set`, not `List` | avoids bag semantics — **[10b](10b-what-a-list-costs.md)** |
| `unmodifiableSet` on the getter | makes the helper unavoidable |
| `@NaturalId` on `isbn` | a stable basis for `equals`/`hashCode` — **[15](15-equals-hashcode-tostring.md)** |
| `setPublisher` package-private | the public path is `addBook`; the setter is plumbing |

And the schema is two tables with one key:

```sql
CREATE TABLE publisher (
    id   bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name text NOT NULL
);

CREATE TABLE book (
    id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    isbn         text NOT NULL UNIQUE,
    title        text NOT NULL,
    publisher_id bigint NOT NULL REFERENCES publisher (id)
);

CREATE INDEX book_publisher_id_idx ON book (publisher_id);
```

⚠️ **That index is not optional.** `publisher.getBooks()` runs
`SELECT … FROM book WHERE publisher_id = ?`. PostgreSQL creates an index for a primary
key and for a unique constraint; it does **not** create one for a foreign key. Without
it, loading one publisher's books is a sequential scan of the whole `book` table. This
is the single most common missing index in a JPA schema.

## Why this shape is efficient and the unidirectional one is not

The 7.4 *User Guide* draws the comparison itself:

> Unlike the unidirectional `@OneToMany`, the bidirectional association is much more
> efficient when managing the collection persistence state. Every element removal only
> requires a single update (in which the foreign key column is set to `NULL`) […]

The mechanism is worth stating rather than accepting. The child owns the column, so:

- **Adding** a book: the key is part of `Book`'s own insert. One statement, no follow-up.
- **Moving** a book to another publisher: one `UPDATE book SET publisher_id = ? WHERE id = ?`.
- **Removing** a book from the collection: one `UPDATE … SET publisher_id = NULL`, or one
  `DELETE` if `orphanRemoval = true`.

None of these touch a link table, and none of them require Hibernate to work out *which*
row among many represents the association, because the row is the child itself.

## What the collection actually is at runtime

`publisher.getBooks()` is not the `HashSet` you assigned. Once the entity is managed,
Hibernate replaces the field with its own **persistent collection** wrapper — an
implementation of `Set` that knows which entity and which attribute it belongs to, and
that fetches its contents on first access.

Two consequences that matter now:

- **The field must be declared as an interface type.** The Hibernate *Introduction* is
  explicit: *"Hibernate needs to proxy unfetched associations at runtime. Therefore, the
  many-valued side must be declared using an interface type like `Set` or `List`, and
  never using a concrete type like `HashSet` or `ArrayList`."* Declaring
  `private HashSet<Book> books` breaks the mapping.
- **Never reassign the field.** Hibernate tracks the instance it installed. Replacing it
  with a fresh `HashSet` discards the tracking. Mutate in place — this is why
  `replaceBooks` in **[2c](02c-keeping-both-sides-in-step.md)** calls `clear()` rather
  than assigning.

The rest of what a persistent collection is — when it initialises, what happens when it
cannot — is **[14 · What a lazy association actually is](14-what-a-lazy-association-is.md)**.

## Should the collection be there at all?

Even with the mapping done correctly, the collection is the risky half. It is unbounded,
it cannot be filtered, and it cannot be paged. The 7.4 *User Guide* says so directly:

> Just because you have support for collections, it does not mean that you have to turn
> any one-to-many database relationship into a collection. Sometimes, a `@ManyToOne`
> association is sufficient, and the collection can be simply replaced by an entity query
> which is easier to paginate or filter.

A usable rule:

- **Map the collection** when the children are a bounded, cohesive part of the parent —
  an `Order` and its lines, an `Invoice` and its items, a `Poll` and its options. You
  load them together, you save them together, and you can state a realistic upper bound.
- **Do not map it** when the children are an open-ended log — a `User` and their events,
  a `Publisher` and every book it has printed, a `Product` and its reviews. Use a
  repository query with a `Pageable`.

The test that settles it: *can you say what the maximum size is, and would you be
comfortable loading that many objects into memory at once?* If not, it is a query.

## Gotchas

**A missing index on the foreign-key column turns every collection load into a table
scan.** PostgreSQL does not index foreign keys automatically. Add the index in the same
Flyway migration that adds the column, every time.

**`optional = false` on the `@ManyToOne` does not create the `NOT NULL` on an existing
schema.** It affects generated DDL only. With Flyway owning the schema, write the
constraint in the migration and the annotation in the entity; they are two statements of
the same fact and both are needed.

**`cascade = ALL` on the parent includes `REMOVE`, and that is usually what you want here
— but read [8b](08b-cascade-remove-and-the-hibernate-extras.md) before copying it.** It
is right for `Order`/`OrderLine` and wrong the moment the child is shared.

**Declaring the field as `HashSet` rather than `Set` breaks lazy loading.** Hibernate
cannot substitute its persistent collection for a concrete type, so the mapping is
rejected or the collection never behaves lazily.

**`getBooks().size()` initialises the whole collection.** It looks like a cheap metadata
call and it is a full load of every child row. If you only need a count, query for one.
(Hibernate has a `size()` on unfetched collections that avoids this in some
configurations, but relying on it is fragile — a `SELECT count(*)` query is explicit and
always correct.)

**Two collections on the same parent, both `EAGER`, is where the trouble starts.** Not
covered here — see **[13b · How it multiplies](13b-how-it-multiplies.md)**.

**Adding the collection later is a bigger change than it looks.** It introduces the
owning-side problem, the helper methods, the `equals`/`hashCode` obligation and a fetch
decision, all at once. Adding a repository method introduces none of them.

## Interview questions

**★ Walk me through the canonical bidirectional one-to-many mapping.**
The child gets `@ManyToOne` with an explicit `@JoinColumn` and `fetch = LAZY`, because the
child's table holds the foreign key and the JPA default fetch for `@ManyToOne` is `EAGER`.
The parent gets `@OneToMany(mappedBy = "<child field>")`, declared as a `Set` typed by the
interface, initialised at the field, with `addChild`/`removeChild` helpers that mutate both
sides and a getter that returns an unmodifiable view. Cascade and orphan removal go on the
parent's collection if the children are lifecycle-dependent. And the schema needs an index
on the foreign-key column, which the database will not create for you.

**★ Why is the bidirectional mapping more efficient than the unidirectional one?**
Because the child owns the key. Adding a child writes the key as part of the child's own
insert; moving a child is one column update; removing a child is one column update, or one
delete with orphan removal. The unidirectional mapping puts ownership on the parent's
collection, which cannot identify individual link rows, so Hibernate deletes every link row
for the parent and reinserts the survivors. The user guide states both halves of that
comparison directly.

**★ Why must the collection field be declared as `Set` and not `HashSet`?**
Because Hibernate substitutes its own persistent-collection implementation for the field
when the entity becomes managed — that wrapper is what makes lazy loading and change
tracking possible. It can only do that if the declared type is an interface it can
implement. Hibernate's documentation states the rule explicitly: use `Set` or `List`, never
`HashSet` or `ArrayList`.

**★ Why should you never assign a new collection to a mapped field?**
Hibernate tracks changes through the specific collection instance it installed. Assigning a
different instance throws that tracking away; depending on the mapping, the collection may
be treated as entirely new, which for a bag means deleting and reinserting every row. Mutate
the existing instance instead — `clear()` and re-add.

**★ When would you deliberately not map the `@OneToMany` side?**
When the child count is unbounded or large, or when you always need the children filtered,
sorted or paged. A mapped collection loads all of it, has nowhere to put a `WHERE` clause,
and cannot express `LIMIT`. A repository query taking a `Pageable` does all three. The
Hibernate guide makes the same point: a collection can often be replaced by an entity query
that is easier to paginate or filter.

**★ Which side do you put `cascade` and `orphanRemoval` on, and why not the other side?**
On the parent's `@OneToMany`. Cascade propagates lifecycle operations from a parent to its
children, and the parent's collection is what identifies the children to propagate to. The
user guide puts it as: the `@OneToMany` association is by definition a parent association,
and only the parent side of an association makes sense to cascade its entity state
transitions to children. Putting `CascadeType.REMOVE` on the child's `@ManyToOne` says
"deleting this book deletes its publisher", which is almost never what anyone means.

**★ What index does this mapping require, and who creates it?**
An index on the child's foreign-key column. You create it, in the migration. PostgreSQL
indexes primary keys and unique constraints automatically but not foreign keys, and
`publisher.getBooks()` is a lookup by exactly that column — so without the index every
collection load scans the child table.
