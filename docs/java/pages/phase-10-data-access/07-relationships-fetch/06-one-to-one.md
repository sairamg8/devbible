> JDK 25, Spring Boot 4.1.1, Hibernate ORM 7.4.1, Jakarta Persistence 3.2, PostgreSQL 18.

**A one-to-one association is stored exactly like a many-to-one — a foreign key on one
of the two tables — with a `UNIQUE` constraint added so the "one" holds in both
directions. Hibernate's introduction puts it as: "The simplest sort of one-to-one
association is almost exactly like a `@ManyToOne` association, except that it maps to a
foreign key column with a `UNIQUE` constraint." The mapping is easy. The hard part is
the lazy behaviour on the inverse side, and that gets its own two chunks.**

## The unidirectional mapping

```java
@Entity
public class Author {

    @Id @GeneratedValue
    private Long id;

    private String penName;

    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "person_id", unique = true)
    private Person person;
}
```

`Person` has no field pointing back. The schema:

```sql
CREATE TABLE person (
    id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name  text NOT NULL
);

CREATE TABLE author (
    id        bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    pen_name  text NOT NULL,
    person_id bigint NOT NULL UNIQUE REFERENCES person (id)
);
```

The `UNIQUE` is what makes it one-to-one rather than many-to-one. Without it, two
`Author` rows could point at the same `Person` and the mapping would be lying. Hibernate
generates the constraint when it exports schema; when Flyway owns the schema — as it
should — **you write it, and it is the whole difference between the two mappings.**

⚠️ **A missing `UNIQUE` on the join column does not fail at startup.** It fails much
later. The 7.4 *User Guide* documents what happens when the constraint is absent and two
children point at the same parent: on reload Hibernate finds more than one row where it
expected one, and the guide's own example comments the failure as
`org.hibernate.HibernateException: More than one row with the given identifier was
found: 1`. That is a runtime error on a read, at some indeterminate point after the bad
data was written.

## Which table gets the key is a real decision

Unlike a one-to-many, there is nothing in the relational model that forces the key onto
one side. `author.person_id` and `person.author_id` are both valid schemas for the same
relationship. So you choose, and the choice has consequences.

**Put the key where the dependent side is.** In a `Phone`/`PhoneDetails` pair, the
details cannot exist without the phone, so `phone_details.phone_id` is the natural
column. The 7.4 *User Guide* makes this argument explicitly about its own example: a
mapping with the key on `Phone` is *"unusual […] because the details cannot exist
without an actual phone. A much more natural mapping would be [if] the `Phone` were the
parent-side, therefore pushing the foreign key into the `PhoneDetails` table."*

**Put the key where the optional side is.** If every `Person` has an `Author` but only
some `Author`s have a `Bio`, the key goes on `Bio`, so the nullable column sits on the
table where absence is normal.

**Put the key where you can make it `NOT NULL`.** This is the decision that unlocks a
lazy inverse side — see **[6b](06b-why-lazy-one-to-one-fails.md)**.

## The bidirectional mapping

```java
@Entity
public class Author {

    @Id @GeneratedValue
    private Long id;

    @OneToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "person_id", unique = true)
    private Person person;                          // OWNING — maps author.person_id
}

@Entity
public class Person {

    @Id @GeneratedValue
    private Long id;

    @OneToOne(mappedBy = "person")
    private Author author;                          // INVERSE — maps nothing
}
```

Everything from **[2](02-the-owning-side.md)** applies unchanged. `Person.author` maps no
column. Assigning it changes nothing in the database. The `@OneToOne` javadoc's wording
for `mappedBy` is the same as for the collection annotations: *"The field that owns the
relationship. This element is only specified on the inverse (non-owning) side of the
association."*

So the same helper-method discipline applies, with one field instead of a collection:

```java
public void setAuthor(Author author) {
    this.author = author;
    if (author != null) {
        author.setPerson(this);   // the side that writes the column
    }
}
```

And the same silent bug is available: setting `person.author` alone persists nothing.

## When a `@OneToOne` is really inheritance in disguise

Hibernate's introduction raises this and it is worth taking seriously:

> A one-to-one association often models a "type of" relationship. In our example, an
> `Author` is a type of `Person`. An alternative — and often more natural — way to
> represent "type of" relationships in Java is via entity class inheritance.

and elsewhere:

> A one-to-one association is the usual way we implement subtyping in a fully-normalized
> relational model. It's related to the `JOINED` inheritance mapping strategy.

If your `Author`/`Person` pair really means "an author *is a* person with extra fields",
`@Inheritance(strategy = JOINED)` gives you the same two tables, the same join, and one
Java type instead of two. If it means "an author *has a* person record" — a genuinely
separate thing with its own lifecycle — the association is right. The test is whether you
ever have a `Person` who is not an `Author` and vice versa.

## `@OneToOne` to a join table

Less common, and worth recognising when you meet it:

```java
@OneToOne(optional = false, fetch = FetchType.LAZY)
@JoinTable(name = "author_person")
private Person person;
```

The 7.4 *Introduction* documents this and adds the constraint you must not omit: *"there
should be a UNIQUE constraint or PRIMARY KEY on both columns of the association table."*
Both, because the relationship is one-to-one in both directions.

Reach for this only when neither table may be altered — a legacy schema, or two tables
owned by different teams. It costs an extra join on every read.

## Gotchas

**Forgetting `unique = true` turns your one-to-one into an unenforced many-to-one.**
The Java side still says `@OneToOne`, so Hibernate loads at most one row and throws when
it finds two. Nothing catches the bad write; everything breaks on the subsequent read.

**`fetch = LAZY` on the *owning* side works; on the inverse side it usually does not.**
This is the biggest surprise in the topic and it has its own chunk —
**[6b](06b-why-lazy-one-to-one-fails.md)**. Do not assume that because you wrote `LAZY`
on both sides, both sides are lazy.

**`optional = false` on a `@OneToOne` is load-bearing, not decorative.** On the owning
side it generates `NOT NULL`. On the inverse side it is what tells Hibernate the row is
guaranteed to exist, which is one of the three ways to get a lazy inverse side at all.

**A `@OneToOne` with `mappedBy` on both sides fails at startup.** So does a `@OneToOne`
with `mappedBy` and `@JoinColumn` on the same field. Both are the mapping equivalent of
saying two contradictory things in one sentence.

**Cascading `REMOVE` across a `@OneToOne` deletes the other row.** For a genuine
whole/part pair (`Order` → `Invoice`) that is intended. For a shared reference
(`Employee` → `Address`) it is a data-loss bug. See
**[8b](08b-cascade-remove-and-the-hibernate-extras.md)**.

**Two `@OneToOne` fields pointing at the same target type need distinct join columns.**
`@JoinColumn(name = "billing_address_id")` and `@JoinColumn(name = "shipping_address_id")`
— the default naming rule would give both the same name, and the mapping fails.

## Interview questions

**★ How is a one-to-one stored, and how does it differ from a many-to-one?**
Identically, except for a unique constraint. Both are a foreign-key column on one of the
two tables. Adding `UNIQUE` to that column is what stops two rows on the owning side
referring to the same target, which is what makes the relationship one-to-one in both
directions. Hibernate's documentation describes the simplest `@OneToOne` as "almost
exactly like a `@ManyToOne` association, except that it maps to a foreign key column with
a `UNIQUE` constraint".

**★ What happens if you forget the unique constraint?**
Nothing, until two rows point at the same target. Then a read that expects one row finds
several, and Hibernate fails with a "more than one row with the given identifier was
found" error — the 7.4 user guide shows exactly that failure for a bidirectional
`@OneToOne` whose uniqueness is violated. The write that created the bad data succeeded
silently, so the error appears far from its cause.

**★ How do you decide which entity holds the foreign key?**
Three criteria, usually agreeing. Put it on the dependent side — the one that cannot
exist without the other; the user guide argues its own example that way. Put it on the
optional side, so the nullable column lives where absence is expected. And prefer the
arrangement where you can declare the column `NOT NULL`, because a guaranteed-present
association is the one case where the inverse side can be lazy.

**★ When is a `@OneToOne` the wrong tool?**
When the relationship is really "is a" rather than "has a". Hibernate's documentation
notes that a one-to-one is the usual way subtyping is represented in a normalised schema,
and that `JOINED` inheritance expresses the same two tables as one Java type hierarchy.
If you never have one side without the other, and the second table is just "more columns
about the same thing", inheritance or an `@Embedded`/`@SecondaryTable` mapping is a better
fit than two entities.

**★ Does the owning-side rule apply to `@OneToOne`?**
Fully. The side with `@JoinColumn` owns the column; the side with `mappedBy` maps nothing
and its assignments are never written. The only difference from a one-to-many is that you
get to choose which side owns it, because either table can carry the key. The consequence
is the same: set the owning side, and use a helper that sets both.
