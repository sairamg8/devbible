**A relational database records a relationship in exactly one place: a foreign-key
column on one of the two tables. Java has no such restriction. A `Book` can hold a
field pointing at its `Publisher`, and the same `Publisher` can hold a collection
pointing back at its `Book`s — two references, two ways to navigate, and both of them
in memory at once. That extra freedom is the whole reason JPA needs the words "owning
side" and `mappedBy`. Get this asymmetry clear before you look at a single annotation
and the rest of the topic stops being arbitrary.**

## The database side is smaller than you think

Here is the schema. Two tables, one relationship.

```sql
CREATE TABLE publisher (
    id        bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name      text NOT NULL
);

CREATE TABLE book (
    id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    isbn         text NOT NULL UNIQUE,
    title        text NOT NULL,
    publisher_id bigint NOT NULL REFERENCES publisher (id)
);
```

Count the places that record "this book belongs to that publisher". There is exactly
one: the `book.publisher_id` column. The `publisher` table has no column pointing at
books. It does not need one, and it *cannot* have one — a publisher has many books,
and a single column holds one value.

That is not a quirk of this schema. It is how a one-to-many relationship is always
stored in a relational database. **The many side carries the key.** So:

- To find a book's publisher: read `book.publisher_id`. One column, already there.
- To find a publisher's books: run `SELECT * FROM book WHERE publisher_id = ?`. A
  query — not a column.

The relationship is **directional in storage** even though it feels symmetric when you
talk about it. "A book has a publisher" is a column lookup. "A publisher has books" is
a search of another table.

## The object side is bigger than the database side

Now the same relationship in Java. Nothing stops you writing both directions:

```java
@Entity
public class Book {
    @Id @GeneratedValue
    private Long id;
    private String isbn;
    private String title;

    private Publisher publisher;      // one reference
}

@Entity
public class Publisher {
    @Id @GeneratedValue
    private Long id;
    private String name;

    private Set<Book> books;          // and another, pointing back
}
```

Two fields. Both describe the *same* row-level fact. And Java gives you no way to keep
them consistent automatically — `book.publisher` and `publisher.books` are just fields,
and either can be changed without the other noticing.

So the object model can be in a state the database cannot represent:

```java
Publisher oreilly = new Publisher("O'Reilly");
Book book = new Book("978-1", "Java Concurrency");

oreilly.getBooks().add(book);   // the collection says: this book is mine
// book.getPublisher() is still null — the book disagrees
```

Ask the object graph "who publishes this book?" and you get `null`. Ask "what does
O'Reilly publish?" and you get the book. Both answers came from the same object graph,
in the same instant, and they contradict each other.

The database can never be in that state. There is one column, it holds one value, and
that value is either O'Reilly's id or it is not.

## The provider has to pick a winner, and it picks in advance

When you call `flush()` (see **Topic 06 · JPA and the persistence context** *(not
written yet)* for what triggers that), Hibernate has to write one value into
`book.publisher_id`. It is holding two Java fields that both claim to describe that
column, and they may disagree. It cannot ask you at that moment. So the decision is
made **once, at mapping time, in the annotations** — not per flush, not per object.

That decision is what "the owning side" means, and it is the subject of the next chunk.
The rule Hibernate's *Introduction* states for it is blunt:

> Changes made to the unowned side of an association are never synchronized to the
> database. If we desire to change an association in the database, we must change it
> from the owning side.

Read that sentence again with the `oreilly.getBooks().add(book)` example above in mind.
If `Publisher.books` is the unowned side — which is the normal, correct mapping — then
that `add` call writes **nothing**. Not "writes it later". Not "writes it if you also
flush". Nothing, ever.

## Why not just have one reference and be done?

You can. It is a legitimate design and Hibernate's *Introduction* explicitly blesses it:

> It's not a requirement to represent every foreign key relationship as an association
> at the Java level.

A `Book` with a `@ManyToOne Publisher` and a `Publisher` with **no** `books` collection
is a complete, working, unambiguous mapping. There is one Java reference for one
foreign key. Nothing to keep in step, nothing to get wrong, no owning-side question to
answer. When you want a publisher's books you write a query, which is what the database
was going to do anyway.

The reason people add the collection is navigation: `publisher.getBooks()` reads better
than injecting a repository and calling `findByPublisherId`. That is a real benefit.
It is also the single largest source of JPA bugs in this topic. Both facts are true.

**The practical rule that falls out of this chunk:** add the inverse collection when you
genuinely navigate it, not reflexively because the relationship is "one-to-many".

## Three words you need for the rest of the topic

Define them now, because every remaining chunk uses them.

**Owning side** — the side whose Java field maps to the actual foreign-key column.
Changing this field changes the database. In a `Book`/`Publisher` pair mapped the normal
way, that is `Book.publisher`, because `book.publisher_id` is where the key lives.

**Inverse side** (Hibernate's docs say *unowned* side) — the other one. It is marked
with `mappedBy`, and it is a **read-oriented view** of the same foreign key from the
other direction. Changing it changes nothing in the database.

**Direction** — a *unidirectional* association is navigable one way (only one entity has
a field for it). A *bidirectional* association is navigable both ways, and is exactly
one relationship represented by two fields, never two relationships.

⚠️ **"Bidirectional" does not mean two foreign keys.** It means two Java references over
one foreign key. Newcomers frequently expect a second column to appear. It does not, and
if it did the schema would be denormalised and could contradict itself.

## Where the annotations map onto the picture

| Java side | Annotation | Where the FK lives | Owning? |
|---|---|---|---|
| `Book.publisher` | `@ManyToOne` | `book.publisher_id` | **yes** |
| `Publisher.books` | `@OneToMany(mappedBy="publisher")` | same column, viewed from the other end | no |

Notice the annotation names describe **multiplicity from the annotated field's point of
view**. `@ManyToOne` on `Book.publisher` reads "many books to one publisher".
`@OneToMany` on `Publisher.books` reads "one publisher to many books". They are the same
sentence read from opposite ends, which is why they always come in that pair.

## Gotchas

**The object graph is allowed to lie, and it will.**
Nothing in Java or JPA validates that `book.getPublisher().getBooks().contains(book)`.
Two fields, no constraint between them, and the compiler is happy. Every "why wasn't it
saved?" question in this topic is a version of this.

**Reading back in the same transaction hides the bug.**
If you add to the inverse collection and then read that collection, you get your object
back — from the in-memory collection, not the database. The bug only appears in a later
transaction, or after a restart, when the data was never written. That delay is exactly
what makes it expensive to find.

**A "many-to-many" in the database is not one column either.**
It is a third table with two foreign keys. So the same asymmetry applies twice over, and
the owning-side question still has to be answered. See **[7 · Many-to-many](07-many-to-many.md)**.

**Thinking in terms of "linking two objects" instead of "setting one column" is the
root confusion.** The mental model that survives contact with JPA is: *there is one
column; which Java field writes it?* Every time an association behaves strangely, ask
that question first.

**A `@OneToMany` without a matching `@ManyToOne` does not map the schema above.**
It is legal, but by default Hibernate maps it to a **third table**, not to
`book.publisher_id`. That surprise gets a chunk of its own —
**[4 · Unidirectional one-to-many](04-one-to-many-unidirectional.md)**.

## Interview questions

**★ Why does JPA need the concept of an "owning side" at all? SQL does not have one.**
Because SQL does not have the problem. A relational database stores a relationship as a
single foreign-key column on a single table, so there is exactly one place to write and
no ambiguity about who writes it. An object model can represent the same relationship
twice — a reference on one entity and a collection on the other — and those two
representations can disagree, because Java gives you no way to link two fields' values.
When the provider flushes, it must produce one value for one column. Rather than
guessing, or trying to reconcile the two at runtime, JPA makes you declare up front
which Java field is the authoritative view of that column. That declaration is the
owning side, and `mappedBy` marks the other one as "not authoritative".

**★ Which side is the owning side in a one-to-many, and why is it always that side?**
The many side — the `@ManyToOne`. It is not a convention, it follows from the schema: a
one-to-many relationship is stored as a foreign-key column on the many table, because a
single column can only hold a single value and the "one" side would need many. Since the
owning side is defined as the side that maps the foreign-key column, and the column is
on the many side, the many side owns it. The one side gets `mappedBy` and is a query
over that column presented as a collection.

**★ Is a bidirectional association two relationships or one?**
One. It is a single foreign key, represented twice in Java for navigational convenience.
This matters practically: you do not get two rows, two columns or two sets of cascade
behaviour, and you cannot have `book.publisher` point at O'Reilly while
`publisherA.books` and `publisherB.books` both contain the book — well, in memory you
can, which is precisely the problem, but the database will only ever record one answer.

**★ Is it acceptable to map only the `@ManyToOne` and skip the collection entirely?**
Yes, and it is often the better design. Hibernate's own introduction says it is not a
requirement to represent every foreign-key relationship as an association at the Java
level. A unidirectional `@ManyToOne` is unambiguous, has no synchronisation problem, and
costs nothing to maintain. You give up `publisher.getBooks()` and use a repository query
instead — which is what the database does regardless. Add the collection when you
actually navigate it and when the collection is bounded; a `@OneToMany` onto a table with
millions of matching rows is a mapping you will regret.

**★ If I only ever read data, does the owning side still matter?**
For writing, no — there is nothing to write. But it still matters for two things.
Fetching behaviour differs by annotation (`@ManyToOne` defaults to `EAGER`, `@OneToMany`
to `LAZY`, covered in **[12 · The fetch-type defaults](12-fetch-type-defaults.md)**), so
which sides you map decides which queries run. And a read-only model tends not to stay
read-only; the first write against an inverse-side collection will silently do nothing,
and by then the mapping is spread across the codebase.
