> the Hibernate ORM 7.4 *Introduction* §3.17 *Many-to-one*

> JDK 25, Spring Boot 4.1.1, Hibernate ORM 7.4.1, Jakarta Persistence 3.2, PostgreSQL 18.

**One Java field, one foreign-key column, one owning side, no synchronisation problem
and no collection to go stale. Hibernate's own introduction calls many-to-one "the most
basic sort of association we can imagine" and says almost all associations in your
domain model are going to be of this form. It has exactly one landmine, and it is the
fetch default.**

## The mapping

```java
@Entity
public class Book {

    @Id @GeneratedValue
    private Long id;

    private String isbn;
    private String title;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "publisher_id")
    private Publisher publisher;
}
```

That maps to:

```sql
CREATE TABLE book (
    id           bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    isbn         text NOT NULL UNIQUE,
    title        text NOT NULL,
    publisher_id bigint NOT NULL REFERENCES publisher (id)
);
```

Four things are being decided here and all four are worth knowing individually.

## `@JoinColumn` names the column, and its default is usually wrong for your schema

Leave `@JoinColumn` off entirely and the mapping still works. Jakarta Persistence
defines a default column name: the **name of the association attribute**, an underscore,
and the **name of the referenced primary-key column**. For `Book.publisher` referencing
`publisher.id` that is `publisher_id`, which happens to be what you want.

It stops being what you want as soon as the schema was not designed by JPA:

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "pub_fk")          // legacy column name
private Publisher publisher;
```

**Write `@JoinColumn` explicitly even when the default is correct.** It costs one line,
it survives a field rename, and it makes the column visible to anyone reading the entity
who does not have the default-naming rules memorised.

Two more elements you will meet:

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "publisher_code",
            referencedColumnName = "code",              // not the PK — a unique column
            foreignKey = @ForeignKey(name = "fk_book_publisher"))
private Publisher publisher;
```

`referencedColumnName` points the foreign key at a column other than the primary key; it
must be unique. `foreignKey` controls the constraint name in generated DDL — useful when
you generate schema, irrelevant when Flyway owns the schema, which it should.

⚠️ **`@JoinColumn(nullable = …)` and `@ManyToOne(optional = …)` are two different
settings that look like one.** `optional` is the JPA-level statement about whether the
association may be absent; `nullable` on `@JoinColumn` is the DDL-level statement about
the column. Set them consistently. Hibernate uses `optional = false` as the signal that
the association is guaranteed present, which matters for the lazy `@OneToOne` case in
**[6b](06b-why-lazy-one-to-one-fails.md)**.

## `optional = false` is a promise you make to the provider

The `@ManyToOne` javadoc gives `optional` a default of `true` and describes it as
"whether the association can be null". Setting it `false` does two things:

- generates `NOT NULL` on the join column during schema export;
- tells Hibernate it may assume a row is always there.

The second is not free information. Hibernate uses it when deciding whether a proxy is
safe — and, for `@OneToOne`, it is the difference between lazy working and not working.
For `@ManyToOne` it does not change the fetch behaviour, but it does mean a `null`
assigned to the field is a mapping violation rather than a valid state.

Set it `false` whenever the domain says the parent is mandatory. It is documentation
that the provider actually reads.

## The fetch default is `EAGER`, and it is the one thing to override

The Jakarta Persistence javadoc for `@ManyToOne.fetch` reads: *"If not specified,
defaults to `EAGER`."* Hibernate's own documentation does not attempt to defend it:

> A very unfortunate misfeature of JPA is that `@ManyToOne` associations are fetched
> eagerly by default. This is almost never what we want. Almost all associations should
> be lazy.

What `EAGER` means here concretely: every time a `Book` is loaded — by `find`, by a
query, by navigation from somewhere else — the `Publisher` is loaded too. Not when you
ask for it. Always. Usually as an extra `JOIN` bolted onto the query you wrote, and
sometimes as a separate `SELECT` per book.

So the mapping you almost always want is the one at the top of this chunk, with
`fetch = FetchType.LAZY` written out. The full argument, the exception Hibernate allows
(a very high second-level cache hit rate), and what the four defaults are across all
four annotations, is **[12 · The fetch-type defaults](12-fetch-type-defaults.md)**.

## Why this is the shape to reach for first

The Hibernate 7.4 *User Guide*'s own best-practice chapter puts it plainly: *"the
`@ManyToOne` and the `@OneToOne` child-side association are best to represent a FOREIGN
KEY relationship."* The reasons stack up:

- **One field maps one column.** No owning-side question, because there is only one side.
- **Nothing goes stale.** There is no collection to keep in step, so the entire
  **[2b](02b-mappedby-and-the-silent-nothing.md)** class of bug cannot occur.
- **Updates are a single `UPDATE`** of one column. Compare with the unidirectional
  `@OneToMany`, which can delete and reinsert join-table rows —
  **[4](04-one-to-many-unidirectional.md)**.
- **It cannot fetch an unbounded amount of data.** A `@ManyToOne` loads at most one row.
  A collection loads however many rows exist, which may be a hundred thousand.

The guide follows it with advice that reads like heresy the first time and is correct:

> Just because you have support for collections, it does not mean that you have to turn
> any one-to-many database relationship into a collection. Sometimes, a `@ManyToOne`
> association is sufficient, and the collection can be simply replaced by an entity
> query which is easier to paginate or filter.

`bookRepository.findByPublisherId(id, pageable)` is paginated, filterable, and bounded.
`publisher.getBooks()` is none of those.

## When you do add the inverse collection

Add it when you genuinely navigate parent → children *and* the child count is small and
bounded. An `Order` with a handful of `OrderLine`s: yes. A `Publisher` with every book
it has ever printed: no.

And when you add it, add it with the helper methods from
**[2c](02c-keeping-both-sides-in-step.md)** in the same commit. A bidirectional
association added without them is a bug waiting for its first writer.

## Replacing the association with a plain id

Sometimes the honest mapping is not an association at all:

```java
@Column(name = "publisher_id", nullable = false)
private Long publisherId;
```

Hibernate's introduction explicitly permits this: *"It's perfectly acceptable to replace
a `@ManyToOne` mapping with a basic-typed attribute holding an identifier, if it's
inconvenient to think of this relationship as an association at the Java level."*

It also warns, at length, against taking the idea too far — if Hibernate does not know
an attribute is an association, it cannot join-fetch it, batch-fetch it, or cache it,
and you lose every tool for avoiding N+1 later. Use the plain id where the target is
genuinely a foreign reference you only ever pass through (a `tenant_id`, an
`audit_user_id`), not as a general style.

**And note the middle ground:** you can keep the association *and* read its id without
loading anything, because the identifier of a proxy is available without initialising it
— `book.getPublisher().getId()`. That is covered in
**[14 · What a lazy association actually is](14-what-a-lazy-association-is.md)**.

## Gotchas

**Forgetting `fetch = LAZY` on a `@ManyToOne` is the default state of every codebase.**
It is not a mistake anybody makes actively; it is what happens when nobody writes
anything. Grep your entities for `@ManyToOne` and count how many specify a fetch type.

**`@JoinColumn` on the inverse side of a bidirectional pair is a different mapping, not a
clarification.** Putting `@JoinColumn` on a `@OneToMany` changes the strategy from join
table to foreign key — see **[4](04-one-to-many-unidirectional.md)**. It does not
"annotate the existing column".

**`optional = false` does not create the constraint on an existing database.** It only
affects generated DDL. If Flyway owns your schema — and it should — write the `NOT NULL`
in the migration and set `optional = false` to match. Two places, both needed.

**`referencedColumnName` pointing at a non-unique column is undefined behaviour dressed
as a mapping.** The referenced column must be unique; the database will refuse the
foreign key otherwise, and Hibernate's row lookup assumes at most one match.

**Changing the parent means assigning the field, not mutating the old parent's
collection.** `book.setPublisher(other)` is the change. Removing the book from
`oldPublisher.getBooks()` on its own does nothing at all.

**A `@ManyToOne` to an entity with a composite key needs `@JoinColumns`, plural.**
One `@JoinColumn` per key column, each with `referencedColumnName`. Easy to forget, and
the failure is at startup.

## Interview questions

**★ Why is `@ManyToOne` considered the safest association to map?**
Because it is a one-to-one correspondence between a Java field and a database column. It
is unconditionally the owning side, so there is no `mappedBy` decision. There is no
collection, so nothing can go stale and nothing can silently fail to persist. Writing it
is a single-column `UPDATE`. And it loads at most one row, so it cannot become an
unbounded fetch. Hibernate's own best-practice guidance says the `@ManyToOne` and the
child side of a `@OneToOne` are the best way to represent a foreign key.

**★ What is the default join column name if you omit `@JoinColumn`?**
The association attribute name, an underscore, and the name of the referenced primary-key
column — so `Book.publisher` pointing at `publisher.id` defaults to `publisher_id`. It is
still worth writing explicitly, because the default is derived from a Java identifier and
a field rename silently changes the column your entity maps to.

**★ What does `optional = false` actually buy you?**
Two things. It generates `NOT NULL` on the join column in exported DDL, and it tells the
provider that the association is guaranteed present. The second is real information:
Hibernate uses it when deciding whether it can safely hand you a proxy without checking
the database, which is precisely what makes a lazy `@OneToOne` on the inverse side work
when it otherwise cannot.

**★ Would you ever map a foreign key as a plain `Long` instead of an association?**
For a genuinely opaque reference — a tenant id, a created-by user id you never navigate —
yes, and the Hibernate documentation says that is perfectly acceptable. What it warns
against is doing it systematically. Once an attribute is a plain id rather than a mapped
association, Hibernate cannot join-fetch it, batch it, apply an entity graph to it, or
serve it from the second-level cache, so you have given up every mechanism for solving
the N+1 problem before you have met it.

**★ You need "all books by this publisher" on a page with paging and a title filter.
Collection or query?**
Query. `publisher.getBooks()` loads the whole collection and gives you no place to put a
`WHERE` clause or a `LIMIT`; filtering it in Java means fetching everything first. A
repository method taking a `Pageable` pushes both the filter and the paging into SQL.
The Hibernate guide makes this point directly: a collection can often be replaced by an
entity query that is easier to paginate or filter.
