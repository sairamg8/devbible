**The previous chunk explained why the inverse side of a `@OneToOne` cannot be lazy: the
provider must know whether the row exists before it can choose between `null` and a
proxy. There are exactly three ways out, and they correspond to the three ways of
removing that uncertainty — make the id predictable, make absence impossible, or change
what a field access does. Hibernate's own best-practice chapter ranks them, and its
first choice is the one that also simplifies the schema.**

## Option 1 · `@MapsId` and a shared primary key — the recommended answer

Instead of `author` having its own generated id plus a foreign key to `person`, make
`author.id` **be** the person's id.

```java
@Entity
public class Person {

    @Id @GeneratedValue
    private Long id;

    private String fullName;

    @OneToOne(mappedBy = "person", fetch = FetchType.LAZY)
    private Author author;
}

@Entity
public class Author {

    @Id                              // NOT @GeneratedValue
    private Long id;

    @OneToOne(optional = false, fetch = FetchType.LAZY)
    @MapsId                          // the association supplies the id
    @JoinColumn(name = "id")
    private Person person;

    private String penName;
}
```

The Hibernate *Introduction* describes exactly this change: *"the `@Id` attribute is no
longer a `@GeneratedValue` and, instead, the `author` association is annotated `@MapsId`.
This lets Hibernate know that the association to `Person` is the source of primary key
values for `Author`."*

The schema loses a column:

```sql
CREATE TABLE person (
    id        bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name text NOT NULL
);

CREATE TABLE author (
    id       bigint PRIMARY KEY REFERENCES person (id),   -- PK and FK, one column
    pen_name text NOT NULL
);
```

The guide: *"there's no extra foreign key column in the `Author` table, since the `id`
column holds the identifier of `Person`. That is, the primary key of the `Author` table
does double duty as the foreign key referring to the `Person` table."* And because the
key is the primary key, the uniqueness that a plain `@OneToOne` needs a `UNIQUE`
constraint for comes free.

**What this buys for laziness.** Look at the inverse side again. Hibernate has a `Person`
with id 7 and needs to fill `person.author`. It knows the author's id would be 7, because
that is the mapping. So a proxy is constructible without a query — the id was already
determined. The 7.4 *User Guide* recommends this exact route: *"it's much more efficient
to use unidirectional `@OneToOne` associations with the `@MapsId` annotation in place."*

⚠️ **The residual honesty.** Hibernate still cannot prove a row *exists* at id 7 without
looking. The best-practice chapter's framing is that with `@MapsId` **the parent-side
association becomes redundant** — you fetch the `Author` by the `Person`'s id when you
want it, rather than mapping the inverse side at all. That is the strongest version of
this option: drop `Person.author`, keep the shared key, and load the author explicitly.

> I could not confirm against a Hibernate 7.4 primary source that a `mappedBy` side is
> initialised lazily *purely* because the target uses `@MapsId`. What the documentation
> does say is to prefer the unidirectional `@MapsId` mapping and treat the inverse side
> as unnecessary. Take the recommendation at that strength.

## Option 2 · `optional = false` — remove the possibility of null

If the association is guaranteed present, the null-versus-proxy dilemma disappears: it is
always a proxy.

```java
@Entity
public class Person {
    @OneToOne(mappedBy = "person", optional = false, fetch = FetchType.LAZY)
    private Author author;
}
```

The Hibernate *Introduction* sets this out step by step. It first explains why the
default case fails — *"not every `Person` has an associated `Author`, and the foreign key
is held in the table mapped by `Author`, not in the table mapped by `Person`. Therefore,
Hibernate can't tell if the reference from `Person` to `Author` is null without fetching
the associated `Author`."* — and then gives the fix:

> On the other hand, if every `Person` was an `Author`, that is, if the association were
> non-optional, we would not have to consider the possibility of null references, and we
> would map it like this:
>
> ```java
> @OneToOne(optional=false, mappedBy = Author_.PERSON, fetch=LAZY)
> Author author;
> ```

**This is a promise, not a preference.** You are telling the provider that a row always
exists. If one does not, the proxy will fail when touched — a missing-row error rather
than a clean `null`. Only use it where a database constraint or an invariant of your
domain actually guarantees it.

**Where it fits.** Genuine whole/part pairs whose halves are created together in one
transaction: `Order`/`OrderPayment`, `User`/`UserSettings`, `Shipment`/`ShipmentLabel`.
Not `Person`/`Bio`, where absence is normal.

## Option 3 · Bytecode enhancement — change what a field access does

The 7.4 *User Guide* names this as the general answer:

> However, if you really need to use a bidirectional association and want to make sure
> that this is always going to be fetched lazily, then you need to enable lazy state
> initialization bytecode enhancement.

Enhancement rewrites your compiled entity classes at build time so that reading a field
goes through interception code. That removes the constraint entirely, because the field no
longer has to hold a decided value — the decision is deferred to the moment of access, and
at that moment a query is allowed.

Enabled with the Hibernate build plugin. For Gradle:

```groovy
plugins {
    id 'org.hibernate.orm' version '7.4.1.Final'
}

hibernate {
    enhancement {
        enableLazyInitialization = true
    }
}
```

The 7.4 *User Guide* §6.2 lists what enhancement provides overall: lazy attribute
loading, in-line dirty tracking, bidirectional association management, and internal
performance optimizations. Laziness for a singular association is part of the first.

**The costs, stated plainly:**

- It is a build step. Classes behave differently before and after it, so a plain unit
  test that never runs the plugin exercises unenhanced classes.
- It applies to your whole entity model, not to one field.
- It makes a debugger's view of an entity harder to trust, because reading a field in the
  debugger can trigger a fetch.
- The N+1 exposure does not go away — it moves. A lazily-loaded singular association still
  costs one query per entity when you do touch it. It is now *your* query, at a moment
  you chose, which is a genuine improvement and not a free lunch.

## Which to choose

| Situation | Option |
|---|---|
| You control the schema and the child is a strict extension of the parent | **1** — `@MapsId`, and consider dropping the inverse side entirely |
| Both rows are always created together, and a constraint enforces it | **2** — `optional = false` |
| Legacy schema, genuinely optional, and you need the inverse side | **3** — bytecode enhancement |
| Anything else | do not map the inverse side; load the child by query when you need it |

That last row is not a cop-out. The whole difficulty is that the inverse side is a
relationship the parent's row knows nothing about. A repository call —
`authorRepository.findByPersonId(id)` — states that honestly, runs one query when you ask
for it, and never runs one when you do not.

## Gotchas

**`@MapsId` means the child's id is not generated.** Remove `@GeneratedValue`. Leaving it
on produces a mapping where two mechanisms both claim to supply the primary key, and the
failure is at startup.

**With `@MapsId`, persist order matters.** The parent must have an id before the child
can take it. In practice: create the `Person`, associate it with the `Author`, and let
cascade or an explicit `persist` handle the rest — but do not try to persist the `Author`
against a transient `Person`.

**`optional = false` on the inverse side with no enforcing constraint is a time bomb.**
Hibernate will hand out a proxy for a row that does not exist; the failure surfaces the
first time somebody touches it, in code far from the mapping. Back the promise with a
`NOT NULL` foreign key and a creation path that cannot skip the child.

**Bytecode enhancement changes behaviour between environments.** If your integration tests
run enhanced classes and your unit tests do not, an assertion about laziness passes in one
and fails in the other. Decide once, apply everywhere, and document that the build does it.

**Enhancement is not a licence to leave associations lazy and hope.** It gives you the
ability to defer; deciding *when* to fetch is still your job, and doing it badly is the
N+1 problem — [Topic 08 · The N+1 problem](../08-the-n-plus-1-problem/README.md) owns that.

**`@MapsId` with a composite key needs the attribute name.** `@MapsId("parentId")` names
which part of the child's `@IdClass` or `@EmbeddedId` this association supplies. The
Hibernate *Introduction* adds a rule that is easy to miss: *"we must place column mapping
information on the association annotated `@MapsId`, not on the `@Id` field."*

## Interview questions

**★ Name the three ways to get lazy behaviour on the inverse side of a `@OneToOne`, and
say why each works.**
Shared primary key with `@MapsId`: the child's id is the parent's id, so the identifier a
proxy needs is already known and the extra column disappears from the schema — Hibernate's
best-practice guidance recommends this and adds that the inverse side then becomes
redundant. `optional = false`: you promise the row always exists, so the null-versus-proxy
question has only one answer and the provider can always build a proxy — the Hibernate
introduction shows exactly this mapping. Bytecode enhancement: the compiled class is
rewritten so field access is intercepted, which means the value does not have to be decided
at load time at all; the user guide names it as the requirement if you really need a lazy
bidirectional association.

**★ What does `@MapsId` actually do to the schema?**
It removes a column. Instead of the child having its own generated primary key plus a
foreign key to the parent, the child's primary key *is* the foreign key — one column doing
both jobs. That also gives you the one-to-one uniqueness for free, since a primary key is
unique by definition, so you no longer need a separate `UNIQUE` constraint on a join
column.

**★ What is the risk of `optional = false` on an inverse `@OneToOne`?**
It is a claim about your data, and the provider believes it. If a parent row exists with no
child, Hibernate installs a proxy for a row that is not there, and the failure appears when
something touches it — potentially in a completely different part of the application. Only
assert it when a constraint or an invariant genuinely enforces it, and make sure every
creation path writes both rows.

**★ Why not just enable bytecode enhancement everywhere and stop worrying?**
Because it is a build-time transformation with real trade-offs. Your classes behave
differently enhanced and unenhanced, so tests that skip the plugin test different code.
Debugging becomes less trustworthy, because inspecting a field can trigger a query. And it
does not remove the underlying cost — a lazy singular association still costs one query per
entity when accessed. It converts an unavoidable fetch into a deferred one, which is
valuable, but the fetch is still there.

**★ Your schema has `person` and `author` as separate tables, the association is genuinely
optional, and you cannot change the schema or the build. What now?**
Do not map the inverse side. Keep the owning `@OneToOne` on `Author` — lazy works there,
because the foreign key is in `author`'s own row — and load the author for a person through
a repository query when you actually need it. That gives you one query, issued deliberately,
instead of one query per person issued invisibly. It is also the mapping that is honest
about what the `person` row knows, which is nothing about authors.
