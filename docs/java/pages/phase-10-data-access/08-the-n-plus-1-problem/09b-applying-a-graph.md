**There are two ways to get a graph object and three ways to attach it to an
execution, and the differences between them are not stylistic: one builder
returns `null` for a bad name while the other throws, and two of the three
application mechanisms accept a wrong argument without complaint and quietly do
nothing.**

## Building one programmatically

The portable form takes attribute names as strings:

```java
EntityGraph<Order> graph = entityManager.createEntityGraph(Order.class);
graph.addAttributeNode("customer");
graph.addAttributeNode("lines");
```

Hibernate's `Session` adds overloads that take metamodel attributes, so the
compiler checks them:

```java
var graph = session.createEntityGraph(Order.class);
graph.addSubgraph(Order_.customer);
graph.addPluralSubgraph(Order_.lines).addSubgraph(OrderLine_.product);
```

`Order_` and `OrderLine_` are generated by Hibernate Processor — the same
metamodel classes criteria queries use. `addPluralSubgraph` is Hibernate's, not
JPA's; the portable equivalent is `addSubgraph("lines")` with the string.

**Prefer the typed form in new code.** A graph built from strings is a set of
identifiers the compiler never sees, and the failure when one goes stale is
described in the gotchas.

## The two ways to obtain a *named* graph, and why they differ

```java
EntityGraph<?> a = entityManager.getEntityGraph("Order.forInvoice");     // immutable
EntityGraph<?> b = entityManager.createEntityGraph("Order.forInvoice");  // mutable copy
```

The specification's javadoc is precise about both, and they behave differently in
two ways that matter:

| | `getEntityGraph(name)` | `createEntityGraph(name)` |
|---|---|---|
| Spec wording | "The returned instance … **should be considered immutable**" | "Obtain a **mutable copy** of a named `EntityGraph`" |
| Unknown name | throws `IllegalArgumentException` | **returns `null`** |
| Use it for | applying a named plan as-is | taking a base plan and adding to it |

🔴 **That `null` is a trap.** `createEntityGraph("Odrer.forInvoice")` does not
throw; it hands back `null`, and the next line — `graph.addAttributeNode(…)` —
throws a `NullPointerException` from somewhere unrelated to the typo. Or, worse,
the `null` is passed straight to a hint and is silently ignored. Use
`getEntityGraph` unless you actually intend to mutate the copy.

## Applying it to `find()`

Jakarta Persistence 3.2 added an overload taking the graph directly, which is the
cleanest form available:

```java
var graph = entityManager.createEntityGraph(Order.class);
graph.addSubgraph(Order_.lines);

Order order = entityManager.find(graph, orderId);
```

The introduction guide describes exactly what this does to the SQL: *"This code
adds a left outer join to our SQL query, fetching the associated `Publisher`
along with the `Book`."* Two attribute nodes means two left outer joins; a
subgraph one level down means a third.

There is a matching `findMultiple(EntityGraph, List<Object>, FindOption...)` for
loading a batch of ids under one plan, and Hibernate's older
`session.byMultipleIds(Order.class).withFetchGraph(graph).multiLoad(ids)` remains
for the cases where you also want to control the batch size or the cache mode.

🔴 **A graph passed to `find()` is always a *load* graph.** The specification's
javadoc for the overload says "interpreting the `EntityGraph` as a load graph",
and the Hibernate introduction guide states it as a rule: *"An `EntityGraph`
passed directly to `find()` is always interpreted as a load graph."* There is no
parameter to change it. If you need fetch semantics you must go through a hint or
`setEntityGraph` — see [chunk 9f](09f-fetchgraph-vs-loadgraph.md).

## Applying it to a query — the hint

The portable mechanism is a hint with one of two standard keys:

```java
List<Order> orders = entityManager
        .createQuery("select o from Order o where o.placedAt > :cutoff", Order.class)
        .setParameter("cutoff", cutoff)
        .setHint("jakarta.persistence.loadgraph", graph)
        .getResultList();
```

`setHint` is defined to ignore hints it does not recognise. That is the right
behaviour for a portability mechanism and a hazard for you: a mistyped key is not
an error, it is a no-op, and the query runs with the default graph.

Hibernate exposes the two keys as constants so you never type them:

```java
.setHint(GraphSemantic.FETCH.getJakartaHintName(), graph)
```

⚠️ `GraphSemantic.getJpaHintName()` is **deprecated since 6.0** — it returns the
pre-Jakarta `javax.persistence.*` spelling, which nothing on this stack honours.

## Applying it to a query — `setEntityGraph`

Since Hibernate 6.3 there is a typed method, and it is what to use in
Hibernate-targeted code:

```java
List<Order> orders = session
        .createSelectionQuery("from Order where placedAt > :cutoff", Order.class)
        .setParameter("cutoff", cutoff)
        .setEntityGraph(graph, GraphSemantic.LOAD)
        .getResultList();
```

Its javadoc: *"Apply an `EntityGraph` to the query. This is an alternative way to
specify the associations which should be fetched as part of the initial query."*
The phrase **as part of the initial query** is the point — the graph shapes the
statement that runs, it does not schedule work afterwards.

The signature is `setEntityGraph(EntityGraph<? super R> graph, GraphSemantic
semantic)`, so the graph's root type is checked against the query's result type
at compile time. That single fact is the reason to prefer it: the two silent
failure modes of the hint — wrong key, wrong root — both become compile errors.

## Gotchas

**⚠️ Attribute names as strings.**
`graph.addAttributeNode("lines")` compiles whatever you type. Rename the field
and the graph goes stale; depending on where it is built you get an
`IllegalArgumentException` at construction, or nothing at all until first use.
Use the metamodel overloads in new code — they are checked by `javac`, and the
generated `Order_` class is free if you are already using criteria queries.

**⚠️ `createEntityGraph(String)` returning `null` for an unknown name.**
The spec says so explicitly, and it is the opposite of `getEntityGraph(String)`,
which throws. A typo in a graph name therefore surfaces as an NPE several lines
later, or as a silently ignored hint. If you are not mutating the graph, use
`getEntityGraph`.

**⚠️ A mistyped hint key.**
`"jakarta.persistence.fetchGraph"` with a capital G, `"javax.persistence.fetchgraph"`
from a pre-Jakarta tutorial, `"jakarta.persistence.fetch_graph"` — all are simply
unrecognised hints. No exception, no warning, no graph, and the N+1 you were
fixing is still there. `setEntityGraph` removes the string; the `GraphSemantic`
constants are the fallback if you need the hint form.

**⚠️ A graph rooted at the wrong type.**
`setHint` takes an `Object`, so a graph rooted at `Customer` handed to a query
returning `Order` is accepted by the compiler and does nothing useful at runtime.
`setEntityGraph(EntityGraph<? super R>, …)` makes this a compile error, which is
the strongest single argument for it.

**⚠️ Mutating a graph you got from `getEntityGraph`.**
The spec says that instance "should be considered immutable" — advisory wording,
not a guaranteed exception. A provider may let the mutation through, in which
case you have modified a graph shared by every other caller of that name, and the
symptom appears in a completely different endpoint. Take a copy with
`createEntityGraph(name)` when you intend to add nodes.

**⚠️ Treating a dynamically built graph as shared, cacheable state.**
Neither the specification nor the Hibernate 7.4 documentation states that an
`EntityGraph` instance is thread-safe, and a graph built from an `EntityManager`
belongs to that persistence unit's metamodel. Build per-request graphs
per-request; for a constant plan use a `@NamedEntityGraph`
([chunk 9c](09c-named-entity-graphs.md)), which is what named graphs are for.

**⚠️ Expecting a graph to work on a native query.**
Entity graphs describe how the provider should shape SQL that *it* generates.
A `createNativeQuery` supplies the SQL itself, so there is nothing for the graph
to shape. I could not find any statement in the Jakarta Persistence 3.2
specification or the Hibernate 7.4 documentation that a graph hint is honoured
for a native query, and would not rely on it: use `@SqlResultSetMapping`, or a
projection, or move the query to HQL.

**⚠️ Building the graph inside the loop you are trying to fix.**
It happens: the graph is constructed per element in the very iteration that
produced the N+1, so the plan is right and the pattern is not. The graph belongs
at the point where you decide *what to load*, which is before the loop, not
inside it.

**⚠️ Applying a graph and never confirming it took effect.**
Every mechanism here has a silent failure mode. Assert the statement count
([chunk 6b](06b-asserting-the-count-in-a-test.md)); it is the only check that
distinguishes "the graph worked" from "the graph was ignored and the association
happened to be already loaded in this test's persistence context".

**⚠️ `find(graph, id)` on an entity already in the persistence context.**
`find` returns the managed instance if there is one, and the graph cannot
retroactively change what was fetched for it. The graph works from a clean
context; in a long-running one it may appear to do nothing, which is a
persistence-context behaviour rather than a graph behaviour — see
[topic 06 chunk 11b](../06-jpa-hibernate-model/11b-find-that-issues-no-sql.md).

## Interview questions

**★ What are the ways to apply an entity graph?**
Three. Pass it to `find()` — Jakarta Persistence 3.2 added
`find(EntityGraph<T>, Object, FindOption...)` and a matching `findMultiple`. Set
it as a query hint under `jakarta.persistence.fetchgraph` or
`jakarta.persistence.loadgraph`. Or, on Hibernate 6.3 and later, call
`SelectionQuery.setEntityGraph(graph, GraphSemantic.FETCH | LOAD)`. In
Hibernate-targeted code I would use the third, because the hint keys are
unvalidated strings and the hint value is an untyped `Object`, so both of the
ways to get it wrong are silent.

**★ Which semantic does `find(graph, id)` use, and can you change it?**
Load, always, and no. The specification's javadoc for that overload says it is
"interpreting the `EntityGraph` as a load graph", and Hibernate's introduction
guide states the same as a rule. There is no option parameter for it. Whether
that matters depends entirely on whether your associations are mapped lazy — if
they are, fetch and load semantics coincide.

**★ What is the difference between `getEntityGraph` and `createEntityGraph` for a
named graph?**
`getEntityGraph(name)` returns the named graph itself, which the spec says
"should be considered immutable", and throws `IllegalArgumentException` if the
name is unknown. `createEntityGraph(name)` returns a *mutable copy*, and returns
**`null`** for an unknown name. The null is the important half: a typo in a graph
name does not fail where you made it, it fails as an NPE further down or as a
silently ignored hint.

**★ You applied a graph and the N+1 is still there. How do you debug it?**
Check the mechanism before the plan. If it is a hint, check the key spelling
against `GraphSemantic.FETCH.getJakartaHintName()` and check the graph is not
`null`. Check the graph's root type matches the query's result type. Then check
the plan itself — attribute names against the actual field names, since the
string form is unchecked. Then check whether the association you expected to be
fetched is reached through a path the graph does not cover, which is a subgraph
question ([chunk 9e](09e-subgraphs.md)). Throughout, count statements rather than
reading SQL, because the count is the thing that changes.

**★ Why prefer `setEntityGraph` over `setHint`?**
Because it turns two runtime silences into compile errors. The hint key is a
string that `setHint` is defined to ignore when unrecognised, and the hint value
is an `Object`, so a graph rooted at the wrong entity is accepted too.
`setEntityGraph(EntityGraph<? super R> graph, GraphSemantic semantic)` types both:
the semantic is an enum, and the graph's root must be the query's result type or
a supertype. The cost is that the code is Hibernate-specific.

**★ Can you build a graph once and reuse it?**
For a constant plan, yes — but express it as a `@NamedEntityGraph` rather than as
a static field holding a programmatically-built instance. Neither the spec nor
the Hibernate documentation promises that a dynamically built `EntityGraph` is
thread-safe, and the instance is tied to the persistence unit's metamodel. Named
graphs exist precisely for the "constant plan, many callers" case, and they are
resolved by the provider rather than held by your code.

**★ How do you fetch a batch of entities under one plan?**
`findMultiple(graph, ids, options...)` in Jakarta Persistence 3.2, or
`session.byMultipleIds(Order.class).withFetchGraph(graph).withBatchSize(20).multiLoad(ids)`
when you also want to control batching or cache interaction. The introduction
guide notes that the id list "will be broken into batches, and each batch will be
fetched from the database in a single select", and that a batch size is chosen
automatically if you do not give one — which is the same batching machinery
[chunk 10](10-batch-size.md) is about, reached from a different door.

**★ Does an entity graph work on a native query?**
A graph tells the provider how to shape the SQL it generates, and for a native
query you supply the SQL, so there is nothing to shape. I could not find an
explicit statement either way in the Jakarta Persistence 3.2 specification or the
Hibernate 7.4 documentation, so I would treat it as unsupported rather than rely
on it. If a native query genuinely needs a wider fetch, the honest tools are
`@SqlResultSetMapping`, a projection, or rewriting it in HQL.
