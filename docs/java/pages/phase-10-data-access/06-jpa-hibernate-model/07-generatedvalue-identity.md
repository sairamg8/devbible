**`@GeneratedValue(strategy = IDENTITY)` looks like the simplest choice on the menu: the
database owns the counter, you write nothing, it just works. It does just work. But it
is the one strategy whose value cannot be known until the row physically exists, and
that single constraint propagates outwards into the most consequential default in this
whole topic — it turns off JDBC batching for the entity. This chunk establishes the
mechanism; [7b](07b-identity-kills-batching.md) works through what it costs.**

## The five strategies, in one place

The User Guide §3.7.7 lists what `jakarta.persistence.GenerationType` offers:

| Strategy | What it uses | Java types (per the Introduction) |
|---|---|---|
| `AUTO` (the default) | provider's choice — see [9](09-table-auto-uuid.md) | `Long`, `Integer`, `UUID`, `String` |
| `IDENTITY` | an identity / autoincrement column | `Long`, `Integer` |
| `SEQUENCE` | a database sequence — see [8](08-sequence-and-allocationsize.md) | `Long`, `Integer` |
| `TABLE` | a database table used as a counter | `Long`, `Integer` |
| `UUID` | a UUID generated in Java | `UUID`, `String` |

A bare `@GeneratedValue` means `AUTO`. That is worth saying out loud, because "we use
`@GeneratedValue`" and "we use `IDENTITY`" are frequently assumed to be the same
sentence, and on PostgreSQL they are not.

## What `IDENTITY` means at the SQL level

```java
@Entity
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
}
```

On PostgreSQL, Hibernate 7.4 generates the column as a SQL-standard identity column. The
dialect support class is one method long and it settles the question:

```java
// PostgreSQLIdentityColumnSupport, Hibernate ORM 7.4
@Override
public String getIdentityColumnString(int type) {
    return "generated by default as identity";
}
```

So the DDL is `id bigint generated by default as identity`, not the older `bigserial`.
The two are close relatives — PostgreSQL implements both with a sequence — but identity
columns are the SQL standard form, they own their sequence properly (dropping the table
drops it), and `generated by default` still lets you supply an explicit value when you
need to, which `generated always` would not.

## How Hibernate gets the value back

The User Guide §3.7.10 lists the three routes, in preference order:

1. If Hibernate believes the JDBC environment supports
   `java.sql.Statement#getGeneratedKeys`, that is used.
2. Otherwise, if the dialect reports `supportsInsertSelectIdentity`, Hibernate uses the
   dialect-specific INSERT+SELECT syntax.
3. Otherwise it asks for the most recently inserted identity value with a separate SQL
   command, per `Dialect#getIdentitySelectString`.

On PostgreSQL route 1 applies, because pgJDBC supports generated keys. This is the same
JDBC facility covered in [Topic 01 · JDBC](../01-jdbc/README.md) — generated keys are not
a JPA invention, and everything that page says about them applies here unchanged.

## The consequence: `persist` is no longer deferred

Everywhere else in this topic, `persist` schedules work and nothing reaches the database
until flush. That is the model: the persistence context is, in the User Guide's words,
"a transactional write-behind cache". See **15 · Flush** *(not written yet)*.

`IDENTITY` cannot participate in that model. The User Guide states the constraint
exactly:

> It is important to realize that using IDENTITY columns imposes a runtime behavior
> where the entity row must be physically inserted prior to the identifier value being
> known.

And the identifier value is needed *immediately*, because the persistence context is an
identity map keyed by identifier — a managed entity with no key cannot be filed. So
`persist` on an `IDENTITY` entity executes the INSERT then and there.

Everything else about `IDENTITY` is downstream of that sentence:

**Batching is disabled for that entity.** The User Guide again: "There is yet another
important runtime impact of choosing IDENTITY generation: Hibernate will not be able to
batch INSERT statements for the entities using the IDENTITY generation." That is
[7b · Why IDENTITY disables batching](07b-identity-kills-batching.md), and it deserves
its own page.

**Extended persistence contexts suffer.** "This can mess up extended persistence
contexts (long conversations). Because of the runtime imposition/inconsistency,
Hibernate suggests other forms of identifier value generation be used (e.g. SEQUENCE)
with extended contexts."

**The row exists earlier than you expect.** Between `persist` and commit, the row is
physically in the table. It is invisible to other transactions under normal isolation
and will vanish on rollback — but within *your* transaction it is real, it holds any
locks the INSERT took, and it participates in unique-constraint checks. A `persist` in a
loop holds a growing set of row locks for the rest of the transaction. That interacts
with everything in
[Topic 04 · Spring `@Transactional`](../04-spring-transactional/README.md).

**You cannot pre-assign ids in Java.** With `SEQUENCE` you can obtain identifiers before
writing anything, which lets you build an object graph with all its keys already in
place. With `IDENTITY` the key exists only after the insert.

## Gotchas

**`@GeneratedValue` with no argument is not `IDENTITY`.**
It is `AUTO`, and on PostgreSQL `AUTO` resolves to sequence-style generation for a
numeric id — see [9 · TABLE, AUTO and UUID](09-table-auto-uuid.md). Teams routinely
believe they are on `IDENTITY` when they are on a sequence, or the reverse, and the
difference shows up as a batching question months later.

**`IDENTITY` on a `bigserial` column that a migration created still works — but the DDL
Hibernate would generate no longer matches.**
`bigserial` and `generated by default as identity` are both backed by a sequence and
both accept the generated-keys round trip, so runtime behaviour is the same. What
changes is `ddl-auto: validate`, and what your next Flyway migration should be written
against. If your schema is old, be deliberate about which form you are standardising on.

**Switching `IDENTITY` → `SEQUENCE` on an existing table is a migration, not an
annotation change.**
The new sequence must be created and, crucially, started *above* the current maximum id,
or the first insert collides with an existing row. On PostgreSQL an identity column
already owns a sequence you can read the current value from — but reusing it means
matching its increment to `allocationSize`, which is
[8 · SEQUENCE and allocationSize](08-sequence-and-allocationsize.md)'s subject and a
place Hibernate 7 will throw at you rather than guess.

**`persist` inside a long loop with `IDENTITY` is one INSERT per iteration, immediately.**
There is no accumulation to flush. Batch size settings do nothing. This is the shape of
the problem in [7b](07b-identity-kills-batching.md).

**`generated always as identity` breaks data loading.**
If you or a DBA writes `generated always`, PostgreSQL refuses any explicit value for the
column, which makes bulk-loading fixtures or migrating data awkward — you need
`OVERRIDING SYSTEM VALUE`. Hibernate generates `generated by default` precisely to keep
that door open.

**Two rows in one transaction, and you already have both ids.**
Because the INSERT is immediate, an `IDENTITY` entity has its id right after `persist`,
before flush. This *feels* convenient and it is — but relying on it is relying on the
one strategy that behaves differently from all the others, which makes the code harder
to move later.

## Interview questions

**★ What does `GenerationType.IDENTITY` actually do?**
It maps the identifier to a database-managed autoincrement or identity column, and asks
the database for the value as part of the INSERT — on PostgreSQL through JDBC's
`getGeneratedKeys`. The defining property is that the value does not exist until the row
does, so Hibernate cannot know it in advance.

**★ Why does `persist` behave differently under `IDENTITY` than under `SEQUENCE`?**
Because a managed entity has to be filed in the persistence context under its
identifier, and under `IDENTITY` the identifier is only produced by inserting the row.
So `persist` executes the INSERT immediately rather than queuing an action for flush.
Under `SEQUENCE` Hibernate can fetch the next value first, assign it, file the entity,
and defer the INSERT to flush like every other write.

**★ What is the practical cost of that immediacy?**
Two things. Hibernate cannot batch INSERTs for the entity, because each statement must
be executed on its own to get its key back — so a loop that creates a thousand rows makes
a thousand round trips no matter what `hibernate.jdbc.batch_size` says. And the rows
exist, and hold locks, from the moment of `persist` rather than from flush, which
lengthens the window in which they can block other transactions.

**★ On PostgreSQL, what DDL does Hibernate 7 generate for an `IDENTITY` column?**
`generated by default as identity`. That is the SQL-standard identity column, not the
older PostgreSQL-specific `bigserial`. Both are backed by a sequence, but the identity
column owns its sequence — dropping the table drops it — and `by default` rather than
`always` means an explicit value may still be supplied, which matters for data loading.

**★ Someone says "`@GeneratedValue` means `IDENTITY`". Correct them.**
A bare `@GeneratedValue` is `AUTO`, and how `AUTO` is interpreted is explicitly left to
the provider. Hibernate looks at the Java type: a `UUID` id gets a UUID generator, a
numeric id gets `SequenceStyleGenerator`, which resolves to a real sequence when the
database supports one and to a table otherwise. On PostgreSQL that means a bare
`@GeneratedValue Long id` is a *sequence*, not an identity column — and therefore does
not have the batching problem people often assume it has.

**★ Can you get an entity's id before flushing, under `IDENTITY`?**
Yes, and that is a rare advantage of the strategy: since the INSERT has already run,
the id is populated as soon as `persist` returns. Under `SEQUENCE` you also get it after
`persist`, because Hibernate fetches the value before assigning it — but there the row
does not exist yet. The genuinely different case is `TABLE` and, historically, entities
with no generator at all, where the id may not be assigned until flush.

**★ How would you migrate an existing `IDENTITY` mapping to `SEQUENCE`?**
Create a sequence in a migration, set its start value above the current maximum
identifier in the table so the first generated value cannot collide, and set its
`increment by` to match the `allocationSize` the mapping will use — Hibernate validates
that match at bootstrap and, by default, throws when it disagrees. Then change the
mapping. Doing the annotation first and the migration afterwards gives you either a
duplicate key on the first insert or a bootstrap failure, depending on which mismatch
you hit first.
