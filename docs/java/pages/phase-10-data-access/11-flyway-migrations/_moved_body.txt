## The other race: creating the history table

There is a second concurrency hazard before the lock is even useful — on a brand-new database, the
history table does not exist yet, and every instance wants to create it. `JdbcTableSchemaHistory`
handles it with a retry loop inside `connection.lock(table, …)`: it loops while the table does not
exist, catching `FlywayException`, sleeping one second, and giving up after **10** attempts.

The lock is taken on a table that does not exist yet, which is fine precisely because the lock is
*advisory* — the key is derived from the table's name, not from the table.

## The lock is taken per migration, not per run

`DbMigrate.migrateAll()` is a loop, and the lock is inside it:

```java
final int count = configuration.isGroup()
    // With group active a lock on the schema history table has already been acquired.
    ? migrateGroup(firstRun)
    // Otherwise acquire the lock now. The lock will be released at the end of each migration.
    : schemaHistory.lock(() -> migrateGroup(firstRun));
```

`migrateGroup` is documented in its own javadoc as *"Migrate a group of one (`group = false`) or
more (`group = true`) migrations"*, and the first thing it does inside the lock is build a fresh
`MigrationInfoServiceImpl` and call `infoService.refresh()` — it re-reads the history table every
time it holds the lock.

So the default cycle is **acquire → re-read history → apply exactly one migration → write its
history row → release → repeat**. With `group: true` the lock is taken once around everything, which
is what the comment in the source means.

🔴 **The consequence is that a ten-pod rollout can interleave migrations between pods.** Pod 3 wins
the lock and applies `V42`. It releases. Pod 7 wins the next round and applies `V43`. Pod 1 applies
`V44`. Every one of those is correct, because each acquisition re-reads the history table before
deciding what is pending — but `installed_by` in `flyway_schema_history`
([03 · The history table](03-the-history-table.md)) will not tell a single story about who ran the
deployment, and that surprises people the first time they look.

## What a well-behaved rollout actually looks like

1. All ten pods call `migrate()`. One wins `pg_try_advisory_xact_lock`; nine get `false` and sleep.
2. The winner applies one pending migration, commits, and releases the lock.
3. Any of the ten — including one of the nine — wins the next round, re-reads the history, and
   applies the next pending migration.
4. Eventually an acquisition finds **nothing pending**, `count` comes back `0`, and that instance's
   loop breaks. It starts normally.
5. Every remaining instance reaches the same conclusion on its own acquisition.

Step 4 is why this works at all. `migrate()` is safe to call concurrently because the lock serialises
it and the history table is authoritative — the tenth call is not a second migration, it is a query
that finds nothing to do.

⚠️ **This changes what `lockRetryCount` has to cover.** A fresh `RetryStrategy` is constructed for
each acquisition, so the fifty-second budget applies to *one* acquisition. With the default
`group: false`, that budget has to cover the longest **single** migration, not the whole run. Turn
`group: true` on and it has to cover the entire run instead — which is a second reason, beyond the
lock exposure in [08b](08b-locks-and-long-migrations.md), to leave `group` alone.
