**A versioned migration describes a *step*: "add this column". A repeatable migration describes a
*state*: "this view is defined like this". That is the whole test, and it is a better one than any
list of allowed object types, because it explains the exceptions too. The complication is that
PostgreSQL's replace-in-place statements are narrower than the phrase `CREATE OR REPLACE` implies,
and the moment you exceed what they can do, a repeatable migration stops being idempotent without
anybody noticing until the second run.**

## The four things that genuinely belong

### Views

The archetype. A view has no data of its own, `CREATE OR REPLACE VIEW` exists, and the definition
in the repository becomes the readable description of the object.

⚠️ **But `CREATE OR REPLACE VIEW` is much narrower than it sounds.** From the PostgreSQL 18
documentation, the new query must generate

> *"the same columns that were generated by the existing view query (that is, the same column
> names in the same order and with the same data types), but it may add additional columns to the
> end of the list."*

So the allowed changes are: **the logic behind any column**, and **appending new columns**. The
documentation is explicit that *"the calculations giving rise to the output columns may be
completely different"* — the body is free, the shape is not.

What that forbids is exactly what people do:

| Change | Works with `CREATE OR REPLACE`? |
|---|---|
| Rewrite the `WHERE`, the joins, the aggregation | ✅ yes |
| Add a column at the **end** | ✅ yes |
| Add a column in the **middle** | ⛔ no |
| Rename a column | ⛔ no |
| Change a column's type | ⛔ no |
| Remove a column | ⛔ no |
| Reorder columns | ⛔ no |

Everything in the forbidden half needs a `DROP VIEW` first — which is not a small thing, because
dropping cascades to dependent views and, per the documentation, `CREATE OR REPLACE VIEW` is
precisely what preserves *"ownership, permissions, and non-SELECT rules"*. A drop-and-recreate loses
all three unless you re-grant.

The workable pattern in a repeatable migration is therefore explicit rather than clever:

```sql
-- R__020_order_summary_view.sql
DROP VIEW IF EXISTS order_summary;

CREATE VIEW order_summary AS
SELECT o.customer_id,
       count(*)         AS order_count,
       sum(o.total)     AS lifetime_value
  FROM orders o
 WHERE o.status <> 'cancelled'
 GROUP BY o.customer_id;

GRANT SELECT ON order_summary TO reporting;
```

It is idempotent, it survives a shape change, and the `GRANT` is there because the drop threw the
old one away. ⚠️ It also fails against a dependent view unless that view is dropped and recreated
in the same file or a later-sorting one — which is the ordering problem from
[05](05-repeatable-migrations.md) again, and the reason the numeric prefixes matter.

### Functions and stored procedures

`CREATE OR REPLACE FUNCTION` is the standard tool, and it has its own hard limit, quoted:

> *"It is not possible to change the name or argument types of a function this way (if you tried,
> you would actually be creating a new, distinct function). Also, `CREATE OR REPLACE FUNCTION` will
> not let you change the return type of an existing function. To do that, you must drop and
> recreate the function."*

Two consequences that bite:

- **Changing the argument types creates a second function** rather than replacing the first,
  because PostgreSQL overloads on the argument list. The repeatable migration succeeds, and you now
  have two functions with the same name and different signatures — one of them dead, and both
  callable. Nothing errors.
- **Changing the return type errors outright**, so at least that one is loud.

And the documentation names the reason to prefer replacing over dropping:

> *"If you drop and then recreate a function, the new function is not the same entity as the old;
> you will have to drop existing rules, views, triggers, etc. that refer to the old function."*

So a signature change is a real migration with real fallout, and the honest way to handle it is a
**versioned** migration that drops the old signature explicitly, plus the repeatable migration
carrying the new definition.

### Reference data that the application does not own

Country codes, currency lists, permission names, feature flags with fixed keys — rows that are part
of the schema's meaning rather than user data. The idempotent form is an upsert:

```sql
-- R__100_reference_countries.sql
INSERT INTO countries (code, name, region) VALUES
    ('GB', 'United Kingdom', 'Europe'),
    ('IN', 'India',          'Asia'),
    ('US', 'United States',  'Americas')
ON CONFLICT (code) DO UPDATE
   SET name   = EXCLUDED.name,
       region = EXCLUDED.region;
```

`ON CONFLICT` needs a unique constraint or index on `code` to have something to conflict on, and
that constraint belongs in a **versioned** migration. This is the common shape: the *structure* is
versioned, the *content* is repeatable.

⚠️ **The upsert never deletes.** Remove a country from the file and it stays in the table forever.
If the list is meant to be authoritative, the file has to say so — and that is a much bigger
decision than it looks, because a `DELETE` against rows something else references will fail or
cascade.

### Grants and other declarative permissions

`GRANT` is naturally idempotent — granting twice is not an error — which makes it a good fit, and
it pairs with the drop-and-recreate pattern above.

## That is the "belongs" half — the "does not belong" half is where the damage is

Everything above is an object you can legitimately describe as a state. The complementary list —
what must never go in a repeatable migration, why exactly one entry on that list fails *silently*,
the materialized-view trap, and the naming convention that keeps the ordering honest — is
[05c · What does not belong](05c-what-does-not-belong.md).

## Gotchas

**★ `CREATE OR REPLACE VIEW` cannot rename, remove, reorder or retype a column.** It can only change
the logic behind existing columns and append new ones at the end. Almost every real view change
eventually needs a drop.

**★ Dropping and recreating a view loses its permissions.** The documentation says `CREATE OR
REPLACE` is what preserves *"ownership, permissions, and non-SELECT rules"* — so a
`DROP VIEW; CREATE VIEW` needs the `GRANT` statements repeated in the same file.

**★ `DROP VIEW` fails or cascades when another view depends on it.** Dependent objects must be
handled in the same file or in a later-sorting one, which is why the ordering prefixes matter.

**★ Changing a function's argument types creates a SECOND function instead of replacing it.**
PostgreSQL overloads on the argument list, the migration succeeds, and you are left with two
callable functions. Nothing warns.

**★ Changing a function's return type errors instead**, which is the better failure of the two
because it is visible.

**★ Dropping and recreating a function breaks everything that referenced it** — views, triggers,
rules. The documentation says so explicitly, and it is the reason `CREATE OR REPLACE` is preferred
where it is possible at all.

**★ An `INSERT … ON CONFLICT` upsert never deletes.** Rows removed from the file stay in the table
forever, and making the file authoritative is a much bigger decision than it looks.

**★ `ON CONFLICT` needs a unique constraint to conflict on**, and that constraint belongs in a
versioned migration. Structure versioned, content repeatable.

**★ The `GRANT` after a `DROP VIEW` is the line everybody forgets**, and the failure shows up as a
permission error in a service that was working yesterday.

## Interview questions

**★ What is the test for whether something belongs in a repeatable migration?**
Whether the file describes a desired end state rather than a step. A view definition is a state; an
`ALTER TABLE ADD COLUMN` is a step. The operational form of the same test is to ask whether running
the file twice leaves the database identical.

**★ Name three things that belong in a repeatable migration.**
View definitions, function and procedure bodies, and reference data written as an upsert. Grants
are a reasonable fourth, because granting twice is not an error.

**★ Why is `CREATE OR REPLACE VIEW` not enough on its own?**
Because it requires the new query to produce the same column names, in the same order, with the
same types — it may only append columns at the end. Renaming, removing, reordering or retyping a
column needs a `DROP VIEW` first.

**★ What do you lose when you drop and recreate a view?**
Ownership, permissions and non-SELECT rules — the documentation names all three as the things
`CREATE OR REPLACE` preserves. Any `GRANT` has to be repeated in the same file.

**★ You change a function's parameter types in a repeatable migration and it succeeds. Is that
good?**
No, it is the worst outcome. PostgreSQL overloads on argument types, so you created a second
function rather than replacing the first. Both are callable, one is dead, and nothing warned. A
signature change needs an explicit `DROP FUNCTION` in a versioned migration.

**★ Why does changing a function's return type behave differently?**
Because `CREATE OR REPLACE FUNCTION` refuses it outright — the documentation says so. The
signature is the identity, so changing the argument list creates a new function while changing the
return type of the same signature is a genuine conflict.

**★ How do you write reference data so it can be re-applied?**
`INSERT … ON CONFLICT (key) DO UPDATE`, with the unique constraint created by a versioned
migration. Be explicit that this never deletes: rows removed from the file remain in the table
until something else removes them.

**★ Two views, one built on the other, and you need to change the base view's column list. What is
the sequence?**
The dependent view has to be dropped before the base view can be, and recreated after. In practice
that means both live in repeatable migrations ordered so the dependent one is dropped first, or —
more honestly for a one-off shape change — a versioned migration that does the whole thing in
order, with the repeatable files carrying the new definitions afterwards.
