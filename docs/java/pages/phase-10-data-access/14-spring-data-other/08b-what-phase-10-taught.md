**Phase 10 started with a `Connection` and ended with a store that has no schema. In
between there are fourteen topics, several hundred pages and a great many annotations —
and underneath all of it there are only four ideas. This chunk names them, because a reader
who leaves with the four will reconstruct the details, and a reader who leaves with the
details will not reconstruct the four.**

## One · Everything is a connection and a round trip

`EntityManager`, `MongoTemplate`, `RedisTemplate`, a jOOQ `DSLContext`, a
`@Cacheable` method — every one of them ends at a socket carrying a request to a server and
waiting for a reply. The whole phase's performance material is one question asked in a dozen
dialects: **how many round trips, and how much on each?**

- [01 · Batch updates](../01-jdbc/19-batch-updates.md) — collapse round trips in JDBC.
- [02 · Why a small pool is faster](../02-connection-pooling/02-why-a-small-pool-is-faster.md)
  — connections are a scarce resource, not a free one.
- [08 · The N+1 problem](../08-the-n-plus-1-problem/06-count-do-not-read.md) — the same
  question, with the round trips generated by something you did not write.
- [03c · Bulk writes](03c-fluent-api-and-bulk-writes.md) and Redis pipelining — the same
  answer in two more stores.

The abstractions get better at hiding the round trip and never at removing it. **The higher
the layer, the more important it is to be able to count.**

## Two · The transaction boundary is the only place correctness lives

Every layer redefines it and none of them removes it:

| Layer | The boundary is |
|---|---|
| [JDBC](../03-jdbc-transactions/01-autocommit-is-a-transaction-you-did-not-choose.md) | autocommit, until you turn it off |
| [Spring](../04-spring-transactional/03-the-self-invocation-trap.md) | a proxy around a method, which self-invocation defeats |
| [JPA](../06-jpa-hibernate-model/14-dirty-checking.md) | also a flush, whose timing you do not control |
| [MongoDB](04-transactions-in-mongo.md) | a deployment property first, and a bean you must declare second |
| [Redis](06c-redis-transactions.md) | isolation without rollback, in someone else's transaction |

The recurring lesson is that **the annotation is not the boundary; the boundary is what the
manager and the store actually do**. A `@Transactional` with no manager, on a self-invoked
method, or against a standalone MongoDB is the same failure three times: an annotation that
looks like a guarantee and is not one.

## Three · Every convenience that watches your objects is a trade

Dirty checking, the persistence context, lazy loading, cascade, the second-level cache and
`@Cacheable` all do work you did not ask for at a time you did not choose. That is the whole
value proposition and the whole risk:

- [06 · Dirty checking](../06-jpa-hibernate-model/14-dirty-checking.md) writes an `UPDATE`
  you never wrote.
- [07 · Fetch type defaults](../07-relationships-fetch/12-fetch-type-defaults.md) decides
  how much of the graph a `findById` drags in.
- [10 · Lazy loading](../10-lazy-loading/02-the-exception.md) moves a query to a place where
  the session may already be gone.
- [12 · Caching](../12-caching/01-caching-is-a-decision.md) returns a value that was true
  earlier.

The stores in this topic have none of it, which is why
[07 · What does not carry across](07-what-does-not-carry-across.md) reads as a list of
losses and is really a list of decisions returned to you. **Neither position is the mature
one. Knowing which you are in is.**

## Four · The failure mode is silence

Collect the phase's worst bugs and almost none of them throws:

- a `@Transactional` on a self-invoked or non-public method — nothing happens;
- a MongoDB service with no `MongoTransactionManager` — nothing happens;
- `spring.data.mongodb.auto-index-creation` left at `false` — no index, no warning;
- a Redis finder on an unindexed property — no set to read;
- a misspelled property in a typed aggregation since 3.2 — an empty column;
- two `RedisTemplate` beans with different key serializers — one writes, the other reads
  `null`;
- the Redis keyspace listener disabled by default — no expiry events, forever;
- a `save` that replaces a whole document or a whole hash — a lost update, reported as
  success;
- [11 · a repaired checksum](../11-flyway-migrations/04-checksums-and-immutability.md) — a
  migration history that no longer describes the database.

Which produces the phase's single most transferable habit: **assert the mechanism, not the
result**. Count the statements rather than reading the log
([08 · Count, do not read](../08-the-n-plus-1-problem/06-count-do-not-read.md)). Assert that
a transaction is active. Assert that an index exists. Assert that the annotation you rely on
is actually being applied. A test that only checks the returned value passes for every one
of the failures above.

## The layer you are at, and the layer you should be at

The phase is arranged as a ladder and the point was never to climb to the top and stay
there:

`Connection` → `JdbcTemplate` → jOOQ → Hibernate → Spring Data JPA → Spring Data for another
store.

Each rung buys expressiveness and costs visibility. The mature codebases in this phase's
examples use several at once, deliberately:
[05 · When SQL-first beats an entity](../05-sql-first-access/10-when-sql-first-beats-an-entity.md),
[13 · jOOQ vs JPA](../13-jooq/08-jooq-vs-jpa.md),
[03 · MongoTemplate](03-mongotemplate.md) beside a `MongoRepository`, a `RedisTemplate`
beside — or instead of — a Redis repository.

**An escape hatch used deliberately is a design decision. An escape hatch used because the
abstraction confused you is a symptom.** The difference is whether you can say what the
lower layer buys.

## The schema never disappears

It is in DDL and versioned ([11 · Flyway](../11-flyway-migrations/04-checksums-and-immutability.md)),
or in generated code ([13 · jOOQ](../13-jooq/08-jooq-vs-jpa.md)), or in the mapping class,
or in every reader that has to cope with a document written two years ago
([07b](07b-queries-schema-and-exceptions.md)). Choosing a store does not choose whether you
have a schema. It chooses **where it lives and who checks it**, and the options run from
"the database refuses bad data" to "a `NullPointerException` in a mapper at 3am".

## Gotchas that recur in every topic of this phase

**★ A default was chosen for compatibility, not for you.** Open-session-in-view on,
`auto-index-creation` off, Java native serialization, the Redis keyspace listener disabled,
autocommit on. Every one of them is a decision made by somebody who did not know your
application.

**★ The convenient thing and the correct thing diverge under concurrency, always.** Read,
modify, save is fine alone and wrong in parallel — in JPA without `@Version`, in MongoDB
without a partial update, in Redis without `INCR`.

**★ It works on the developer machine because the developer machine has one user, no
latency and no data.** N+1, pool exhaustion, lock contention, a standalone MongoDB and an
empty Redis all look healthy under those conditions.

**★ A framework that generates something will generate something surprising eventually.**
The defence is to be able to see what was generated — SQL logging, statement counting, the
commands a Redis save issues — not to hope.

**★ Two of anything means the composition is now your problem.** Two data sources, two
transaction managers, two stores, two caches. Nothing composes them for you, and no
annotation spans them.

**★ The abstraction's failure mode is not the store's failure mode.** Spring Data's
exception translation is a genuine gift and it makes it easy to forget that a
`DuplicateKeyException` in MongoDB came from an index somebody had to create.

**★ Every "this is just a cache" acquires state that exists nowhere else.** Cache, session
store, queue — the drift is universal and it is only ever noticed during an incident.

## Interview questions

**★ Summarise Phase 10 in four sentences.**
Everything is a connection and a round trip, so learn to count them. Correctness lives at
the transaction boundary, which every layer redefines and none removes. Every convenience
that watches your objects trades visibility for effort. And the dominant failure mode is
silence, so assert the mechanism rather than the result.

**★ What is the most transferable habit from this phase?**
Asserting mechanism. Counting statements instead of reading logs, checking that a
transaction is really active, verifying an index exists, proving an annotation is applied. A
test that checks only the returned value passes for a dead `@Transactional`, a missing
index, and a lost update.

**★ Which layer should a team standardise on?**
None exclusively. Entities for aggregates that are edited, SQL-first or jOOQ for reporting
and bulk work, a template when the repository cannot express the operation. What matters is
that each choice can be defended in one sentence — a codebase where every read is an entity
graph and a codebase where every read is hand-written SQL are both making one decision for
every situation.

**★ Why do so many of these bugs fail silently rather than throwing?**
Because they are mostly *absences* — a missing manager, a missing index, an annotation that
was never applied, a serializer that does not match. Absence has no exception to throw. The
code runs the fast path and returns a plausible answer.

**★ What did the MongoDB and Redis topic teach that the JPA topics could not?**
That most of what JPA gives you is optional, and that the interface being the same does not
make the semantics the same. Removing the persistence context makes visible how many
decisions it was making — and every one of those decisions becomes a line of your code.

**★ If you had to give one piece of advice to a team starting a data-access layer today?**
Default to the relational database, learn where its abstractions leak, and make every escape
from them a decision someone can explain. Almost every expensive failure in this phase came
from an abstraction being trusted in a place its documentation said it should not be — and
the documentation, in nearly every case, said so in one sentence that nobody had read.
