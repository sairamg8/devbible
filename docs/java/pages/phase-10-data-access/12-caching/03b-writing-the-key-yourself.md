**The default key is right for a method whose arguments are exactly what identifies the answer.
When they are not, you write the key — and you write it as a string that the compiler does not
check, the IDE only half-checks, and no test exercises unless you write one. Everything below
is about keeping that string small enough to be obviously correct.**

## `key` is SpEL, evaluated against a cache-specific root

```java
@Cacheable(cacheNames = "prices", key = "#sku")
public Money priceFor(String sku) { … }

@Cacheable(cacheNames = "prices", key = "#product.sku")
public Money priceFor(Product product) { … }

@Cacheable(cacheNames = "quotes", key = "#from + '-' + #to")
public Rate rate(String from, String to) { … }
```

The expression is evaluated before the method runs, against a root object the framework
supplies. The reference lists what is on it:

| Name | Description |
|---|---|
| `#root.methodName` | the name of the method being invoked |
| `#root.method` | the `Method` being invoked |
| `#root.target` | the target object |
| `#root.targetClass` | the target object's class |
| `#root.args` | the arguments as an `Object[]` |
| `#root.caches` | the collection of caches this operation runs against |
| `#argName`, `#a0`, `#p0` | a specific argument |
| `#result` | the return value — *"only in `unless`, cache put, or cache evict expressions"* |

`#root` may be omitted for its own properties, so `key = "methodName"` works, but writing it
out is worth the seven characters when the alternative reads like a variable.

## Three ways to name an argument, and one of them depends on your build

`#p0` and `#a0` are positional and always available — they read out of `#root.args`. `#sku`
is the *parameter name*, and parameter names only exist in a class file when the compiler was
told to keep them. Spring Framework 6.1 removed the fallback that used to reconstruct them
from debug symbols:

> *"If you experience issues with dependency injection, property binding, SpEL expressions, or
> other use cases that depend on the names of parameters, you should compile your Java sources
> with the common Java 8+ `-parameters` flag for parameter name retention."*

Spring Boot's Maven and Gradle plugins configure that flag for you, which is why nobody in a
standard Boot project ever notices. The places it goes missing are the ones outside that
happy path: a module built by a hand-rolled Maven configuration that does not inherit
`spring-boot-starter-parent`, a library jar compiled elsewhere, an IDE compiling with its own
settings, or an annotation processor generating sources with a different compiler invocation.

The failure is a runtime expression-evaluation error the first time that method is called,
not a startup failure and not a compile error. In Maven the flag is:

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <configuration>
    <parameters>true</parameters>
  </configuration>
</plugin>
```

🔴 **Prefer `#p0` when you are writing a library or a module with an unfamiliar build**, and
prefer `#sku` in ordinary application code, where the name is documentation and the flag is
already on. What you should not do is mix the two styles in one codebase, because then a
missing flag breaks some caches and not others and the pattern looks random.

## `#result` exists on the write annotations, and it is genuinely useful

`key` on `@Cacheable` cannot see `#result` — there is no result yet, which is the entire point
of a read-through cache. On `@CachePut` there is, and it solves a real problem:

```java
@CachePut(cacheNames = "orders", key = "#result.id")
public Order place(OrderRequest request) { … }
```

The id is generated by the database. It is not in the arguments, so no expression over the
arguments could ever produce the key the reader uses. `#result.id` can. This is the one case
where a write-through cache and a generated identifier can be made to agree, and it is worth
knowing because the alternative — evict, then let the next read repopulate — is what everybody
falls back to when they conclude it is impossible.

⚠️ The reference is specific that `#result` "always refers to the business entity and never a
supported wrapper", so on a method returning `Optional<Order>` the expression is still
`#result.id` and not `#result.get().id`.

## `key` and `keyGenerator` are mutually exclusive, and the framework enforces it

> *"The `key` and `keyGenerator` parameters are mutually exclusive and an operation that
> specifies both results in an exception."*

This is one of the few cache misconfigurations that fails loudly, and it fails at startup
rather than on first use. Take the win.

## A custom `KeyGenerator`

```java
@Component("tenantKeyGenerator")
class TenantKeyGenerator implements KeyGenerator {

    private final TenantContext tenants;

    TenantKeyGenerator(TenantContext tenants) {
        this.tenants = tenants;
    }

    @Override
    public Object generate(Object target, Method method, Object... params) {
        return new SimpleKey(tenants.currentTenantId(), method.getName(), params);
    }
}
```

```java
@Cacheable(cacheNames = "prices", keyGenerator = "tenantKeyGenerator")
public Money priceFor(String sku) { … }
```

Three things that expression-based keys cannot do as well:

- **It is a class, so it can be unit-tested.** A SpEL string cannot; the only way to exercise
  it is to invoke the cached method through the proxy and inspect the store.
- **It can inject.** A tenant id, a locale resolver, a schema version — anything that belongs
  in the key but is not an argument. SpEL can reach a bean with `@beanName.method()`, but that
  is a string reference to a bean name, which is the same fragility one level deeper.
- **It can include the method name**, which the default generator deliberately does not, and
  which turns the shared-cache-name collision from
  [3 · Keys](03-keys.md) into a non-issue by construction.

To replace the default for the whole application, implement `CachingConfigurer` and override
`keyGenerator()`. That is a much bigger decision than it looks: it changes the key layout of
every cache in the application, including ones written by other teams and ones already
populated in a persistent store.

## What makes a key expression maintainable

**Short.** `#sku` is auditable at a glance. `#a0.customer.address.country.code + ':' +
#a1.name()` is a small program with no tests.

**Made of stable things.** An expression navigating three levels into a domain object is a
silent dependency on that object's shape. Renaming `Address.country` to `Address.countryCode`
compiles, passes every test, and turns the cache into a runtime error on the first request —
or, if the rename was to a field that still exists with different meaning, into wrong answers.

**Total.** `#product.sku` throws if `product` is null. `key = "#product?.sku"` returns null
instead, which is a valid key and quietly merges every null-product call into one entry.
Neither is obviously right; the point is to decide, rather than to discover which one you got.

**Independent of the cache name.** If the expression has to include a discriminator to keep two
methods apart, the discriminator wanted to be a cache name.

## Gotchas

**★ `#argName` silently depends on a compiler flag.** Without `-parameters` the name is not in
the class file and the expression fails at runtime, on first invocation, in whichever module
was built differently. `#p0` has no such dependency.

**★ SpEL in an annotation is an unchecked string.** No compile error, no IDE rename support in
the general case, no test coverage unless you specifically write one that goes through the
proxy. It is the least-verified line in the method.

**★ Navigating deep into an object makes the key a dependency on that object's field names.**
A refactor that is safe everywhere else is not safe here.

**★ `key` on `@Cacheable` cannot use `#result`.** It is available in `unless`, `@CachePut` and
`@CacheEvict` only, and the reference says so explicitly.

**★ `#result` refers to the unwrapped value, not the `Optional`.** Writing `#result.get().id`
against an `Optional`-returning method is wrong even though it looks more careful.

**★ Specifying both `key` and `keyGenerator` throws.** Merging two branches that each added one
is the usual way to produce it, and it is the good kind of failure — at startup.

**★ A `KeyGenerator` bean is referenced by name, as a string.** Renaming the bean, or removing
the explicit `@Component("…")` name and relying on the class-derived default, breaks the
reference at startup rather than at compile time.

**★ Replacing the default generator via `CachingConfigurer` changes every cache in the
application.** Including the ones with entries already sitting in Redis under the old layout.

**★ A key expression that reads mutable state from a bean is a key that varies with the
clock.** `@clock.today()` in a key means yesterday's entries are unreachable, forever, at
whatever memory they occupy.

**★ Null-safe navigation collapses distinct calls into one entry.** `#product?.sku` yields
`null` for every null argument, so every null-product call shares a single cached answer.

**★ `#root.args` is the raw array, so an expression over it is positional even when it looks
named.** `#root.args[0].sku` breaks the moment a parameter is inserted before it — and unlike
`#p0`, it does not even look positional.

**★ A key generator that includes the method name is not automatically safe across a rename.**
Renaming a method changes every key it produces, which on a persistent store orphans the lot.

## Interview questions

**★ When would you write an explicit `key` rather than take the default?**
When the method's arguments are not exactly what identifies the answer. That is either too many
arguments — a `Pageable`, a callback, a flag that does not change the result — or too few, where
something outside the parameter list matters: a tenant, a locale, a currency, a schema version.
It is also worth writing explicitly when the natural argument is a large object, because on a
remote store the key gets serialized and a fat key costs memory and bandwidth on every single
lookup.

**★ Why might `key = "#sku"` work on your machine and fail in another module?**
Because parameter names are only in the class file when the code was compiled with
`-parameters`. Spring Framework 6.1 removed the old bytecode-parsing fallback and its release
notes say plainly to compile with the flag if you depend on parameter names in SpEL. Boot's
build plugins set it, so the failure shows up in modules built outside that setup — a
hand-configured Maven module, a library jar, or an IDE compiling with its own settings. The
symptom is a runtime expression failure on first invocation, not a startup error, which is why
it lands in production rather than in CI.

**★ How do you cache an entity whose id is generated by the database?**
`@CachePut(key = "#result.id")` on the method that saves it. The id does not exist in the
arguments, so no expression over the arguments can produce the key the reader will use, but the
result has it. That is the one shape where write-through genuinely works with generated
identifiers. If the method returns something other than the persisted entity — and in JPA
`merge` returns a copy — then what you cache is not what the database holds, so I would check
the return value before relying on it.

**★ SpEL key or a custom `KeyGenerator`?**
SpEL for a short expression over the arguments, because it lives next to the method and reads
as documentation. A `KeyGenerator` when the key needs something that is not an argument, when
the same key logic repeats across several methods, or when I want to unit-test it — which I
cannot do with a string in an annotation. The one thing I would not do casually is replace the
application-wide default generator, because that changes the key layout of every cache at once,
including caches with entries already persisted under the old format.

**★ What is wrong with `key = "#a0.customer.address.country.code"`?**
It is a program with no tests, expressed as a string the compiler does not check. Every field
name in it is a silent dependency: a rename anywhere along that path compiles cleanly, passes
the test suite, and either throws on the next request or — worse — resolves to a different
field with a plausible value. If the key genuinely needs a country code, I would rather pass the
country code as an argument, or compute the key in a `KeyGenerator` I can test, and keep the
annotation to something I can verify by reading it.

**★ Is `#p0` better than `#sku`?**
It is more robust and less readable, so it depends on where the code lives. In an application
built by Boot's plugins, `#sku` is fine and it says what it means. In a library, a shared module,
or anywhere the build is not under my control, `#p0` cannot fail for a reason that has nothing
to do with my code. What I would avoid is mixing them, because then a missing compiler flag
breaks an apparently arbitrary subset of the caches.

**★ Can a key expression call a bean?**
Yes — `@beanName.method(#p0)` resolves a bean by name from the context. It is occasionally the
right answer for logic you cannot express inline, but it trades one unchecked string for two:
the bean name and the method name, neither verified until the expression runs. At that point a
`KeyGenerator` gives you the same capability with constructor injection, compile-time checking,
and a test.

**★ You have to add a tenant id to every cache key in a multi-tenant application. How?**
A `KeyGenerator` that reads the current tenant from context and includes it, applied via
`keyGenerator = "…"` on each annotation — or as the application default if every cache in the
application is genuinely tenant-scoped. Doing it with SpEL on every annotation means the same
expression repeated dozens of times, and the risk is not the ones you write, it is the one
somebody adds next year without it. That failure is a tenant reading another tenant's data, so
it is worth making structurally impossible rather than conventionally avoided.
