**A cache is a map. The value is whatever your method returned, and the key is computed for
you from the arguments — nothing else. Not the method name, not the declaring class, not the
bean instance. Almost every "the cache does not hit", "the cache returned the wrong thing" and
"user A saw user B's data" bug in this topic is one sentence: the key does not identify what
you thought it identified.**

## The key is a pair, and the method is not in it

An entry is found by two things only: **the cache name** on the annotation, and **the key**
the generator produced. The interceptor does not consult the method, the class or the target
bean when it looks a value up. It builds a key, asks the named `Cache` for it, and returns
whatever comes back.

That is worth stating plainly because the mental model people carry is "Spring caches this
method". It does not. It caches *a value under a key in a named cache*, and a method is just
the thing that happened to produce it. Two different methods pointed at the same cache name
share one keyspace, and nothing in the framework notices.

## The default algorithm, exactly

The reference gives the algorithm in three sentences:

> *"If no parameters are given, return `SimpleKey.EMPTY`. If only one parameter is given,
> return that instance. If more than one parameter is given, return a `SimpleKey` that
> contains all parameters."*

The source is the same three cases, with one detail the prose leaves out:

```java
public static Object generateKey(@Nullable Object... params) {
    if (params.length == 0) {
        return SimpleKey.EMPTY;
    }
    if (params.length == 1) {
        Object param = params[0];
        if (param != null && !param.getClass().isArray()) {
            return param;
        }
    }
    return new SimpleKey(params);
}
```

So the single-argument shortcut applies **only** when that argument is non-null and is not an
array. A single `null` argument and a single `String[]` argument both fall through to
`SimpleKey`, which is the correct behaviour in both cases and is not obvious from the prose.

`SimpleKey` itself clones the element array, pre-computes a hash from
`Arrays.deepHashCode(...)`, implements `equals` with `Arrays.deepEquals(...)`, and is
`Serializable` — with the cached hash marked `transient` and recomputed on deserialization, so
a key that travels to a remote store and back still equals itself. Its `toString()` is the
class name plus `Arrays.deepToString(params)`, which is what you will see in a Redis keyspace
and is the reason those keys are readable at all.

## What the javadoc's "no collisions" claim actually promises

`SimpleKeyGenerator`'s class javadoc says:

> *"Returns the parameter itself if a single non-null value is given, otherwise returns a
> `SimpleKey` of the parameters. No collisions will occur with the keys generated by this
> class."*

Read that narrowly, because it is a narrow promise. It means the three cases cannot produce
the same key as each other for different argument lists — a lone `Long` is never equal to a
`SimpleKey` holding that `Long`, and two different argument lists produce two different
`SimpleKey`s.

**It does not promise that two methods cannot collide**, because the method is not an input.
This compiles, runs, and is wrong:

```java
@Cacheable("lookups")
public Product findProduct(Long id) { … }

@Cacheable("lookups")
public Customer findCustomer(Long id) { … }
```

Both key on the bare `Long`. Call `findProduct(7L)`, then `findCustomer(7L)`, and the second
call is a *hit* that returns a `Product`. The cast to `Customer` is inserted by the compiler at
the call site, so what surfaces is a `ClassCastException` in code that looks entirely
unrelated to caching.

🔴 **The dangerous version of that bug is the one that does not throw.** If both methods return
the same type — `findByAccountId(Long)` and `findByCustomerId(Long)` both returning
`AccountSummary` — the collision produces the wrong row with no exception, no log line and no
symptom until somebody notices a number is another tenant's number.

**The fix is one word: a distinct cache name per method.** Cache names are free, they are the
only namespace the abstraction gives you, and sharing one across methods buys nothing.

## The zero-argument case is a single slot

`SimpleKey.EMPTY` is a constant. A no-argument cached method therefore has exactly **one** entry
in its cache, forever, until something evicts it:

```java
@Cacheable("app-config")
public Configuration current() { … }
```

That is usually exactly right — it is the natural shape for reference data, a feature-flag
snapshot, a currency table. Two consequences follow, and both catch people:

- **`@CacheEvict(cacheNames = "app-config")` and `@CacheEvict(cacheNames = "app-config",
  allEntries = true)` do the same thing here**, because there is only one entry. Code that
  relies on the difference is relying on nothing.
- **Two no-argument methods on the same cache name are the collision above, in its purest
  form.** Both key `SimpleKey.EMPTY`. Whichever ran last wins, and the other method returns
  its neighbour's value from then on.

## The single-argument case hands your domain object the job

This is the case that runs in most codebases, and it is the one worth pausing on: when there is
one argument, **that argument object is the key**. Not a hash of it, not a string of it — the
object. Every lookup is therefore `argument.hashCode()` and `argument.equals(...)`, using
whatever your class implements.

For a `Long`, a `String`, a `UUID` or an enum, that is fine and boring. For an entity, it is
the whole ballgame:

```java
@Cacheable("prices")
public Money priceFor(Product product) { … }
```

If `Product` does not override `equals` and `hashCode`, the key is compared by identity. A
freshly-loaded `Product` for the same row is a different object, so **the cache misses every
single time** while looking, from the outside, exactly like a working cache: no errors, entries
accumulating, hit rate flat at zero and memory climbing. That is the same trap entity equality
causes everywhere else —
[../06-jpa-hibernate-model/10-equals-and-hashcode.md](../06-jpa-hibernate-model/10-equals-and-hashcode.md)
— arriving through a different door.

And if `Product` *does* implement `equals` over mutable fields, the key changes when the object
changes, which is the inverse failure: entries written under a key that no longer exists.

**Pass the identifier, not the entity.** `priceFor(String sku)` has none of these properties.

## Gotchas

**★ The method name is not part of the key.** Two methods sharing a cache name share a
keyspace, and the framework will not warn you. This is the root cause of most "the cache
returned something impossible" reports.

**★ The colliding-methods bug is only loud when the return types differ.** A `ClassCastException`
is the lucky outcome. Two methods returning the same type collide silently and serve the wrong
row.

**★ A single `null` argument does not produce a `null` key.** It falls through to
`new SimpleKey(null)`, which is a perfectly good, distinct key. Code that special-cases "the
key will be null" is guarding against something that does not happen.

**★ A single array argument is wrapped, so it compares by `deepEquals` and works.** People
often assume the opposite and write a custom key for it. Two arrays with the same contents *do*
hit. It is the single *non-array* object that gets used raw.

**★ An entity used as an argument becomes the key, with its own `equals`.** No `equals` means
100% miss rate, growing memory, and no error. A mutable `equals` means orphaned entries.

**★ `SimpleKey`'s hash is cached in a `transient` field.** It is recomputed on deserialization,
so remote stores are safe — but any custom key class of your own that caches a hash and does
*not* handle this will deserialize with a hash of zero and never match.

**★ Two no-argument methods on one cache name is the collision at its purest**, and it looks
harmless in review because neither method has any arguments to think about.

**★ `SimpleKey` clones the array it is given, but not the elements.** Mutating an object you
already used as a key element mutates the key. The entry is then unreachable, and it is
unreachable for eviction too.

**★ The default generator is per-`CacheManager`-wide, not per-annotation.** Replacing it
globally to fix one awkward method changes the key layout of every cache in the application,
including ones somebody else owns.

**★ Changing the key strategy on a persistent store orphans every existing entry.** Deploying
a new key format against a live Redis leaves the old keys occupying memory until their TTL
expires — and if there is no TTL, forever.

**★ Overloaded methods collide with themselves.** `find(Long)` and `find(Long, boolean)` on one
cache name produce a bare `Long` and a `SimpleKey` respectively, so those two are safe — but
`find(Long)` and `find(String)` both produce bare keys, and a `Long` never equals a `String`, so
those are safe too. The unsafe overload pair is the one where both signatures have the same
*arity and types* in a different order: `move(Long from, Long to)` and `move(Long to, Long
from)` cannot both exist, but `transfer(Long a, Long b)` cached alongside `swap(Long a, Long b)`
on one cache name will happily serve each other's results.

**★ A key is only as stable as the class it is made of.** Renaming a package, changing an enum
constant's name or altering a record's component order changes the serialized form of a key on
a remote store even when the Java-side `equals` is unaffected.

## Interview questions

**★ What does Spring use as the cache key if you do not specify one?**
The `SimpleKeyGenerator`, and its algorithm is three cases: no arguments gives the constant
`SimpleKey.EMPTY`, exactly one non-null non-array argument gives that argument itself, and
anything else gives a `SimpleKey` wrapping all the parameters. `SimpleKey` compares with
`Arrays.deepEquals` and hashes with `Arrays.deepHashCode`, so it behaves sensibly for arrays and
nested arrays. The important part is what is *not* in there: the method, the class and the bean
are not inputs, so the key identifies the arguments and nothing else.

**★ Two methods in the same class are annotated `@Cacheable("data")`. What goes wrong?**
They share one keyspace. If they take the same argument types, calling one populates entries the
other will find. When their return types differ you get a `ClassCastException` at the caller,
which is confusing but at least visible; when their return types are the same you get the wrong
value with no error at all. The fix is not a clever key expression, it is a separate cache name
per method — cache names cost nothing and they are the only namespace the abstraction provides.

**★ Why does caching a method that takes an entity often produce a zero hit rate?**
Because with a single argument the entity *is* the key, so lookups go through its `equals` and
`hashCode`. JPA entities frequently inherit `Object`'s identity-based versions, and a re-loaded
row is a different instance, so every lookup misses. Nothing fails: entries keep being written,
memory keeps growing, and the cache looks enabled. I would pass the identifier instead of the
entity, which sidesteps entity-equality entirely and also keeps the key small on a remote store.

**★ Is the default key generator safe for arrays?**
Yes, and deliberately so. The single-argument shortcut explicitly excludes arrays — the source
checks `!param.getClass().isArray()` — so a lone array falls through to `SimpleKey`, which uses
`Arrays.deepEquals` and `Arrays.deepHashCode`. Two distinct arrays with equal contents therefore
hit the same entry, which is what you want. It is one of the few places where the default does
the careful thing on your behalf.

**★ The documentation mentions the key generation strategy changed in Spring 4.0. Why does that
matter today?**
The old strategy "considered only the `hashCode()` of parameters and not `equals()`", which the
reference says "could cause unexpected key collisions" — two different argument lists with the
same hash returning each other's values. Nobody is running Spring 3, but custom `KeyGenerator`
implementations written then still exist, get copied between projects, and reproduce the bug
faithfully. If I see a hand-rolled generator that concatenates or XORs hash codes, that is the
same defect wearing a newer version number.

**★ How would you decide between the default key and a custom one?**
I start from what uniquely identifies the answer. If the method's arguments are exactly that
set — an id, a SKU, a date range — the default is right and I leave it alone. I write an
explicit key when the arguments include something irrelevant (a callback, a `Pageable` I do not
want in the key), when they exclude something relevant (a tenant, a locale, a currency taken
from context rather than parameters), or when the natural argument is a large object I do not
want serialized into a remote keyspace.

**★ What happens to a no-argument `@Cacheable` method?**
It gets exactly one entry, keyed by `SimpleKey.EMPTY`, which is a shared constant. That is the
normal and correct shape for a snapshot of reference data. It also means `allEntries = true`
and a targeted evict are the same operation for that cache, and it means a second no-argument
method sharing the cache name will overwrite it — which is easy to miss precisely because
neither method has arguments to reason about.

**★ You change the key expression on a cache backed by Redis and deploy. What have you done to
the old entries?**
Orphaned them. They are still in Redis under the previous key format, nothing will ever read
them, and nothing will ever evict them either unless the cache has a TTL. On a large cache that
is a memory step-change at deploy time with no corresponding change in behaviour. If the entries
matter I would prefer a new cache name — which the prefix keeps separate — plus a deliberate
cleanup, over silently changing the shape of keys under a name that is already populated.

**★ Can two different `@Cacheable` methods safely share a cache name on purpose?**
Only if they genuinely compute the same thing from the same key — for example a public overload
that delegates and a package-private implementation that does the work, where sharing is the
point. Even then I would rather have one cached method and one uncached delegator, because
"these two methods must keep the same key semantics forever" is an invariant that lives only in
somebody's head and dies at the first refactor.
