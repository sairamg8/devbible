<span className="db-tier t-know">Know</span>

> Verified: 2026-08 on **Node 24.19.0** (Active LTS).

**`node:os` reports what the *host* looks like. In a container that is a lie —
it reports the machine's 64 CPUs and 256 GB, not your pod's 0.5 CPU and 512 MB —
and sizing a worker pool from it is a classic production bug.**

```js
// os.mjs
import os from 'node:os';

console.log('platform            :', os.platform());
console.log('cpus                :', os.cpus().length);
console.log('availableParallelism:', os.availableParallelism());
console.log('totalmem GB         :', (os.totalmem() / 1e9).toFixed(1));
console.log('tmpdir              :', os.tmpdir());
console.log('endianness          :', os.endianness());
```

```console
$ node os.mjs
platform            : linux
cpus                : 8
availableParallelism: 8
totalmem GB         : 16.5
tmpdir              : /tmp
endianness          : LE
```

## The ones worth knowing

| Call | Returns | Used for |
|---|---|---|
| `os.tmpdir()` | `/tmp`, `%TEMP%` on Windows | The only portable temp location |
| `os.homedir()` | User's home | Config files, credential caches |
| `os.platform()` | `'linux'`, `'darwin'`, `'win32'` | Platform branching |
| `os.availableParallelism()` | Usable parallelism | **Sizing worker pools** — prefer over `cpus().length` |
| `os.cpus()` | Array of core descriptors | Diagnostics, per-core times |
| `os.totalmem()` / `os.freemem()` | Host bytes | Diagnostics only — see below |
| `os.hostname()` | Host name | Log field for identifying an instance |
| `os.type()` / `os.release()` | Kernel details | Bug reports |
| `os.networkInterfaces()` | Addresses | Rarely — bind to a config value instead |
| `os.EOL` | `'\n'` or `'\r\n'` | Writing platform-native text files |
| `os.uptime()` / `os.loadavg()` | Host stats | Diagnostics; `loadavg` is `[0,0,0]` on Windows |

`os.platform()` returns `'win32'` on **64-bit Windows too** — the name is
historical, not a bitness claim. Use `os.arch()` for that.

## The container problem

**`os.cpus().length` and `os.totalmem()` read the host, not your cgroup.** On a
Kubernetes node with 64 cores, a pod limited to 500 millicores still sees 64.

The consequences are direct:

```js
// ❌ 64 workers on a 0.5-CPU pod: constant context switching, OOM from 64 heaps
const pool = new WorkerPool(os.cpus().length);

// ❌ "we have 200 GB free" — that is the host's memory, not your pod's limit
if (os.freemem() > needed) { … }
```

**`os.availableParallelism()`** (Node 19.4+) is the right call for pool sizing.
It uses `uv_available_parallelism`, which respects CPU affinity masks — so it is
correct for `taskset` and for CPU-set-based limits. It still does **not** see a
CFS quota (`--cpus=0.5`), so on quota-limited containers it also over-reports.

The reliable answer is to **read the limit from configuration**:

```js
// pool-size.mjs
import os from 'node:os';

const configured = Number(process.env.WORKER_CONCURRENCY);
const poolSize = Number.isInteger(configured) && configured > 0
  ? configured
  : Math.max(1, Math.min(os.availableParallelism(), 4));
```

Set `WORKER_CONCURRENCY` from the same place you set the CPU limit, and the two
cannot drift. The same reasoning applies to memory: use `--max-old-space-size`
and your own budget, not `os.totalmem()`.

Reading the cgroup directly is possible
(`/sys/fs/cgroup/cpu.max`, `/sys/fs/cgroup/memory.max` on cgroup v2) and is what
libraries do, but it is version- and runtime-specific — configuration is simpler
and honest.

## `process` vs `os`

They answer different questions, and the boundary is worth knowing:

| Question | Use |
|---|---|
| How much memory is **this process** using? | `process.memoryUsage()` |
| How much does the **host** have? | `os.totalmem()` |
| What CPU time has **this process** used? | `process.cpuUsage()` |
| What is the host's load? | `os.loadavg()` |
| What platform? | `process.platform` — identical to `os.platform()` |
| Where is the temp dir? | `os.tmpdir()` |
| Where am I running? | `process.cwd()` |

`process.memoryUsage()` is the one that matters for an alert. `os.freemem()` in
a container tells you about a machine you do not control.

## Platform branching, sparingly

```js
const isWindows = os.platform() === 'win32';
const shell = isWindows ? 'powershell.exe' : '/bin/sh';
```

Most platform differences are better handled by the API that abstracts them —
`path` for separators, `os.tmpdir()` for temp locations, `os.EOL` for line
endings — than by branching. Branch when invoking external programs or touching
platform-specific paths, and keep the branch in one place.

`os.EOL` deserves a caveat: use it for text files a human will open in a native
editor. **Do not** use it for network protocols, JSON, or anything crossing
machines — those specify their own line endings (HTTP is `\r\n` always), and
`os.EOL` would make the output depend on the host.

## Gotchas

**Symptom:** A worker pool spawns dozens of workers in a small container
**Cause:** `os.cpus().length` reports host cores.
**Fix:** Configure the number explicitly; `availableParallelism()` as a fallback,
clamped.

**Symptom:** Memory-based logic never triggers, or triggers constantly
**Cause:** `os.freemem()`/`os.totalmem()` are host-wide.
**Fix:** `process.memoryUsage()` and a configured budget.

**Symptom:** `os.platform()` returns `win32` on 64-bit Windows
**Cause:** It is the platform name, not the architecture.
**Fix:** `os.arch()` for bitness.

**Symptom:** Files written with `os.EOL` break a parser on another machine
**Cause:** Line endings became host-dependent.
**Fix:** Pick the format's line ending explicitly; reserve `os.EOL` for local
text files.

**Symptom:** `os.loadavg()` is always `[0, 0, 0]`
**Cause:** Not implemented on Windows.
**Fix:** Use `process.cpuUsage()` deltas for a portable measure.

**Symptom:** `os.tmpdir()` is not writable
**Cause:** A read-only root filesystem, a hardened container, or a `TMPDIR`
pointing somewhere absent.
**Fix:** Make the temp location configurable and check it at boot with `access`.

**Symptom:** `os.hostname()` is a random string in Kubernetes
**Cause:** It is the pod name.
**Fix:** That is usually what you want in logs — but read the node name from the
downward API if you need the physical host.

## Interview questions

**★ Why is `os.cpus().length` wrong for sizing a worker pool in production?**
It reports the host's cores, not the container's CPU limit. A pod restricted to
half a core on a 64-core node still sees 64, so you spawn 64 workers that
context-switch and each carry their own heap.

**★ What is the right way to size a pool?**
Take it from configuration set alongside the CPU limit, falling back to
`os.availableParallelism()` clamped to something sane.
`availableParallelism()` respects CPU affinity but still does not see a CFS
quota.

**★ When would you use `os.totalmem()`?**
Diagnostics and logging. For anything the application decides —
alerts, cache sizing, back-pressure — use `process.memoryUsage()` and a
configured budget, because `os` describes a machine you may be sharing.

**★ What does `os.platform()` return on 64-bit Windows?**
`'win32'`. It is the platform identifier, not the architecture; `os.arch()`
gives `'x64'`.

**When should you not use `os.EOL`?**
For anything leaving the machine — protocols, JSON, CSV consumed elsewhere. HTTP
specifies `\r\n` regardless of host. `os.EOL` is for local text files.
