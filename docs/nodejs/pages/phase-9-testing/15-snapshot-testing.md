<span className="db-tier t-know">Know</span>

> Verified: 2026-08 on **Node 24.19.0** — `t.assert.snapshot()` needs **no flag** on
> this version.

**A snapshot test records the output of something and fails when it changes.** It is
excellent for large structured output nobody wants to hand-write, and it is the
easiest kind of test to render worthless.

## How it works

```js
import {test} from 'node:test';
import {invoiceLines} from '../src/render.mjs';

test('invoice rendering', (t) => {
  t.assert.snapshot(invoiceLines(items));
});
```

The first run has nothing to compare against:

```console
✖ invoice rendering (3.3ms)
  Error [ERR_INVALID_STATE]: Invalid state: Cannot read snapshot file
  '…/render.test.mjs.snapshot.' Missing snapshots can be generated by rerunning
  the command with the --test-update-snapshots flag.
```

```bash
node --test --test-update-snapshots
```

```js
// render.test.mjs.snapshot
exports[`invoice rendering 1`] = `
"2 x Widget       19.98\n1 x Gizmo        24.50"
`;
```

The file is **committed**. It is the expected value; a snapshot outside version control
tests nothing.

Later, a change to the renderer produces a diff:

```console
AssertionError [ERR_ASSERTION]: Expected values to be strictly equal:
+ actual - expected

+ '\n"2 x Widget   19.98\\n1 x Gizmo    24.50"\n'
- '\n"2 x Widget       19.98\\n1 x Gizmo        24.50"\n'
```

## The trap

```bash
node --test --test-update-snapshots      # after changing the code
```

```console
✔ invoice rendering (2.6ms)
ℹ fail 0
```

**The snapshot was silently rewritten to match the new behaviour and the test went
green.** Measured. The change might have been the point — or it might be the bug the
test existed to catch, now recorded as the expectation.

Two rules follow:

1. **Run without the flag first.** Read the diff. Decide whether it is intended.
2. **A snapshot change is a code review event.** The `.snapshot` diff must be in the
   pull request and read like any other change. A reviewer approving a 400-line
   snapshot diff without reading it is the normal failure mode, which is an argument
   for keeping snapshots small.

## Where snapshots are right

- **Rendered text** — an invoice, a receipt, a generated email, a CLI help screen.
- **Serialised structures** — an OpenAPI document, a generated migration, a normalised
  AST.
- **Error formatting** — the shape of your error responses across many cases.
- **Pinning legacy behaviour before a refactor**, then deleting the snapshot afterwards.
  This is the best use: it is a temporary net, and it is honest about being one.

## Where they are wrong

- **Business rules.** `assert.equal(total, 4200)` states the expectation. A snapshot
  states "whatever it did the day I ran it", and a reviewer cannot tell 4200 from 4300
  in a blob.
- **Anything with a timestamp, uuid or ordering that varies.** It fails randomly, gets
  updated blindly, and the habit spreads.
- **Whole API responses.** They contain generated ids and dates. Assert on the fields
  that matter, or use `assert.partialDeepStrictEqual`
  ([page 02](./02-node-assert.md)).
- **Anything you would not read in review.** If it is too big to read, it is too big to
  be evidence.

## Making them stable

Normalise before snapshotting:

```js
const stable = (order) => ({
  ...order,
  id: '<id>',
  createdAt: '<date>',
  items: [...order.items].sort((a, b) => a.sku.localeCompare(b.sku)),
});

test('order payload', (t) => {
  t.assert.snapshot(stable(buildPayload(order)));
});
```

Or remove the variance at the source — an injected clock and id generator
([page 04](./04-testable-code.md)) make snapshots deterministic without a scrubbing
layer, and improve the rest of the suite at the same time.

## Multiple snapshots in one test

Each call increments a counter, which is why the key ends `1`:

```js
test('renders both formats', (t) => {
  t.assert.snapshot(renderText(invoice));    // … 1
  t.assert.snapshot(renderHtml(invoice));    // … 2
});
```

Reordering the calls reassigns the keys and produces a confusing double diff. Prefer one
snapshot per test.

## Serialisers

```js
test('order payload', (t) => {
  t.assert.snapshot(order, {
    serializers: [(v) => JSON.stringify(v, null, 2)],
  });
});
```

The default serialiser handles most values; a custom one gives a readable, diffable
format — worth it, because a snapshot that is hard to read will not be reviewed.

## Gotchas

**Symptom:** `ERR_INVALID_STATE: Cannot read snapshot file`
**Cause:** No snapshot recorded yet.
**Fix:** `--test-update-snapshots` once, and commit the file.

**Symptom:** A behaviour change went in unnoticed
**Cause:** `--test-update-snapshots` run reflexively after every change.
**Fix:** Run without the flag first and read the diff.

**Symptom:** Snapshots fail on other machines or in CI
**Cause:** Timestamps, uuids, locale-dependent formatting, unordered collections.
**Fix:** Normalise before snapshotting, or inject a clock and id generator.

**Symptom:** Snapshot diffs are approved without being read
**Cause:** They are too large.
**Fix:** Smaller snapshots, one per test, and a readable serialiser.

**Symptom:** Unrelated snapshots change when a test is reordered
**Cause:** Multiple `snapshot()` calls in one test, keyed by call order.
**Fix:** One snapshot per test.

**Symptom:** The suite passes locally and fails in CI on a fresh clone
**Cause:** The `.snapshot` file was not committed.
**Fix:** Commit it — it is the expected value.

## Interview questions

**★ What is the main risk of snapshot testing?**
Blind updates. Measured: after changing the renderer, `--test-update-snapshots`
rewrote the file and reported `✔` with zero failures. The regression the test existed
to catch became the new expectation. Run without the flag first; review the snapshot
diff.

**★ When is a snapshot the right tool?**
Large structured output nobody wants to hand-write — rendered documents, generated
schemas, error formats — and pinning legacy behaviour before a refactor. For business
rules, an explicit assertion states the expectation; a snapshot only states what
happened.

**★ Do you commit snapshot files?**
Yes. The file is the expected value. Uncommitted, the first CI run regenerates it and
the test asserts nothing.

**★ How do you keep snapshots from being flaky?**
Remove non-determinism before the snapshot: scrub ids and timestamps, sort
collections, or inject a clock and id generator so the output is deterministic at
source.

**Why one snapshot per test?**
Keys are assigned by call order within the test, so reordering calls reshuffles them
and produces a misleading diff.

**Does `node:test` need a flag for snapshots?**
Not on 24.19.0 — `t.assert.snapshot()` works out of the box. Only
`--test-update-snapshots` is needed, and only when writing them.
