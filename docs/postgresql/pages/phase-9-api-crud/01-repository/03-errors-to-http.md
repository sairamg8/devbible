**A database error that reaches the client as a 500 is nearly always a 4xx that
nobody mapped.** "Email already taken" is a constraint violation with a specific
code, and turning it into a 409 is five lines — but only if you know which field
of the error object to trust.

## Every error, produced for real

Each of these was caused by actually running the statement, not looked up:

Read the fourth and fifth columns carefully — **`constraint` is populated only for
the `23xxx` integrity errors**, and **`column` only for `23502`**. That asymmetry
is what decides how you write the mapping.

## The mapping

| SQLSTATE | Name | HTTP | Why |
|---|---|---|---|
| `23505` | unique_violation | **409** | The resource already exists |
| `23503` | foreign_key_violation | **400** or **409** | 400 if the client named a bad parent; 409 if they are deleting something still referenced |
| `23514` | check_violation | **400** | Input violated a rule the database enforces |
| `23502` | not_null_violation | **400** | A required field was missing |
| `22P02` | invalid_text_representation | **400** | `?id=abc` — malformed input, not a missing resource |
| `22003` | numeric_value_out_of_range | **400** | The value does not fit the column |
| `40001` | serialization_failure | retry, then **503** | Not the client's fault |
| `40P01` | deadlock_detected | retry, then **503** | Not the client's fault |
| `42703`, `42601`, `42P01` | undefined_column, syntax_error, undefined_table | **500** | Your bug, not theirs |

```js
const STATUS = {
  '23505': 409, '23503': 409, '23514': 400,
  '23502': 400, '22P02': 400, '22003': 400,
};

export function toHttpError(err) {
  const status = STATUS[err.code];
  if (!status) throw err;                    // 42703 and friends stay 500s
  return {status, code: err.constraint ?? err.code};
}
```

**The `42xxx` codes must stay 500s.** `42703 column "nope" does not exist` means
the deployed SQL is wrong; mapping it to a 400 tells the client they made a
mistake and hides a broken build from your error rate.

## Switch on the constraint name, not the message

A table usually has several unique constraints, and they are not the same error to
a user. The `code` is `23505` for all of them; only `constraint` distinguishes:

```js
if (err.code === '23505') {
  switch (err.constraint) {
    case 'r_users_email_key':    return {status: 409, error: 'email_taken'};
    case 'r_users_username_key': return {status: 409, error: 'username_taken'};
    default:                     return {status: 409, error: 'conflict'};
  }
}
```

This is the reason to **name constraints explicitly in your DDL** rather than
accept `<table>_<column>_key`. The generated name is stable enough in practice,
but it is a schema detail your error handling now depends on — and it changes if
the column is renamed. `CONSTRAINT users_email_unique UNIQUE (email)` makes the
dependency deliberate.

Do not parse `err.message`. It is English prose that varies with server version
and `lc_messages`, and a server running in another locale returns a translated
string that no regex of yours will match.

## What `detail` leaks

```console
=== 5. what err.detail leaks ===
e.detail   : Key (email)=(ada@x.com) already exists.
↑ contains the submitted value; returning it verbatim echoes user data back
e.constraint: r_users_email_key ← this is the safe thing to switch on
```

`detail` is the most useful field for debugging and the one you must not forward.
Two reasons:

1. **It echoes the submitted value.** For a signup form that is the user's own
   email, which is harmless. For a `23505` on a password-reset token or an
   invite code, it is the secret.
2. **`23514`'s detail is the entire failing row** — `Failing row contains (4,
   n@x.com, N, -1, ...)`, every column including ones the client never sent and
   should never see.

It also turns a create endpoint into an existence oracle: POST an email, and a 409
tells you whether that address has an account. That may be acceptable — most
signup forms leak it anyway — but it should be a decision, not a side effect of
forwarding `detail`.

Log `detail` server-side with the request id. Return `constraint` mapped to a
stable machine-readable string.

## Where the mapping lives

Not in the repository. The repository lets the error propagate; a single
error-handling middleware calls `toHttpError`.

Putting it in the repository means every function needs a try/catch, and it forces
a database concept — "this is a 409" — into a layer whose job is to run
statements. It also breaks composition: the same `23505` is a 409 from a signup
endpoint and a *retry signal* inside an
[idempotent write](../11-idempotent-writes.md), and only the caller knows which.

The exception is when the repository can add information the middleware cannot
have. If two constraints on the same table mean two different domain errors, the
repository is the only place that knows the query's intent, and translating
there — to a domain error, not an HTTP status — is right.

## Trade-off

A thorough mapping is a coupling to your schema: rename a constraint and an API
response changes. The alternative — validating everything in the application
before it reaches the database — decouples them, but it cannot be complete. Uniqueness
cannot be checked in application code without a race: `SELECT` then `INSERT`
leaves a window in which another request inserts the same value, and the only
thing that closes it is the unique index raising `23505`.

So the honest position is both: validate in the application for good error
messages on the common path, and map the SQLSTATE for the cases only the database
can detect. The database constraint is the correctness boundary; the application
check is the user experience.

## Gotchas

**Symptom:** "Email already taken" arrives as a 500
**Cause:** `23505` propagating unmapped.
**Fix:** Map `23505` → 409 in the error middleware, keyed on `err.constraint`.

**Symptom:** A locale change breaks error handling
**Cause:** Matching on `err.message`, which is translated prose.
**Fix:** Switch on `err.code` and `err.constraint`, which are stable identifiers.

**Symptom:** The API tells clients their input was invalid, but the real problem is
a bad deploy
**Cause:** `42703`/`42P01` mapped into the 400 range with the rest.
**Fix:** Only allowlist the codes you mean. Anything unrecognised stays a 500 and
pages someone.

**Symptom:** An error response contains a column the client never sent
**Cause:** Forwarding `err.detail` for `23514`, whose detail is the whole failing row.
**Fix:** Log `detail`, return a mapped code.

**Symptom:** Two different unique constraints produce the same user-facing message
**Cause:** Switching on `err.code` alone — every unique violation is `23505`.
**Fix:** Switch on `err.constraint`, and name constraints explicitly in the DDL.

**Symptom:** `err.column` is `undefined` for a unique violation
**Cause:** It is populated only for `23502`. Measured: `23505`, `23503` and `23514`
all returned `-` for column.
**Fix:** Use `constraint` for integrity errors; do not expect `column`.

## Interview questions

**★ How do you turn a duplicate-key error into a useful API response?**
Catch it in error-handling middleware, switch on `err.code === '23505'`, then on
`err.constraint` to tell which unique index was violated, and return 409 with a
stable machine-readable string. Never parse the message, and never forward
`err.detail` — measured, it contains the submitted value.

**★ Which PostgreSQL errors should never become 4xx?**
The `42xxx` family — `42703 undefined_column`, `42601 syntax_error`,
`42P01 undefined_table`. They mean the SQL you deployed is wrong. Mapping them to
400 blames the client and hides a broken deploy behind a normal-looking error rate.

**★ Why switch on `err.constraint` rather than `err.code`?**
Because `err.code` is `23505` for every unique violation on the table, and a
duplicate email and a duplicate username are different errors to the user. The
constraint name is the only field that distinguishes them — which is why
constraints should be named explicitly in the DDL rather than left to the
generated `<table>_<column>_key`.

**★ Why not check uniqueness in application code and avoid the error entirely?**
Because `SELECT` then `INSERT` is a race: another request can insert the same
value in the gap. Only the unique index can close it, so `23505` has to be handled
regardless. The application check is for a better message on the common path, not
for correctness.

**Should the repository catch database errors?**
Generally no — it should let them propagate to one place that maps them.
The same `23505` means a 409 from a signup endpoint and a successful retry inside
an idempotent write, and only the caller knows which. Catching in the repository
also forces try/catch into every function.

**What is in `err.detail` and why is it dangerous?**
The specifics of the violation — for `23505` the key and its value, for `23514`
the entire failing row. It is the best thing to log and the worst thing to
return: it echoes user input back and can expose columns the client never sent.
