> **node-pg-migrate 9.0.0**, **graphile-migrate 1.4.1**, **prisma 7.9.1**,
> **drizzle-kit 0.31.10**, **@databases/pg-migrations 6.0.0**. Behaviour claims are
> from each tool's documented model, not measured here — the measured runner is
> [Writing a minimal migration runner](08-minimal-runner.md).

**Every tool here implements the same tracking table you would write yourself. What
differs is what they assume about your workflow — and that assumption is the thing
to choose on, not the feature list.**

## The four models

| Tool | You write | Assumes |
|---|---|---|
| **node-pg-migrate** 9.0.0 | SQL or JS migration files, forward and optional down | You own the schema; SQL is the source of truth |
| **graphile-migrate** 1.4.1 | One `current.sql`, re-run on every save, committed as a numbered file | Development is iterative; the *idempotent* current file is the workspace |
| **Prisma Migrate** 7.9.1 | A `schema.prisma`; migrations are **generated** by diffing it | The Prisma schema is the source of truth, and you use Prisma's client |
| **drizzle-kit** 0.31.10 | TypeScript schema objects; SQL generated by diffing | The TS schema is the source of truth, and you use Drizzle |

The split that matters: **do you write the schema, or does the tool derive it?**

- **You write it** (node-pg-migrate, graphile-migrate, your own runner): full access
  to every PostgreSQL feature — partial indexes, exclusion constraints, triggers,
  `CREATE INDEX CONCURRENTLY`, extensions — because you are writing SQL.
- **The tool derives it** (Prisma, Drizzle): less to write and types come free, but
  anything the tool's schema language cannot express has to go in a hand-edited
  escape-hatch migration, and the diff engine may not understand it afterwards.

Given this project's stated path — raw SQL and `pg` first, ORMs later —
**node-pg-migrate is the natural next step from the hand-written runner.** It is the
same model with the missing pieces filled in.

## What you get over sixty lines of your own

From [Writing a minimal migration runner](08-minimal-runner.md), the things that are
structural changes rather than additions:

- **Per-file transaction opt-out**, for `CREATE INDEX CONCURRENTLY` — the `25001`
  problem from [Wrapping a migration in `BEGIN`/`COMMIT`](06-tx-migration.md). This
  is usually the first thing that forces the switch.
- **A generator command** producing correctly timestamped filenames, which removes
  the lexical-ordering bug measured in [Migrations](02-migrations.md) (`1, 10, 11, 2`).
- **Status and dry-run output** — what is pending, what has run, what would run.
- **Baselining**, marking migrations as applied without executing them, needed to
  adopt migrations on a database that already exists.
- **JavaScript migrations**, for a data backfill that needs real logic in the same
  ordering as the schema changes.

## graphile-migrate's different bet

Worth understanding because the model is genuinely unusual. You edit one
`current.sql` which is re-run on every save; when the change is ready you "commit"
it and it becomes an immutable numbered file.

The requirement is that `current.sql` must be **idempotent** — it runs many times
during development — so it is written with `DROP … IF EXISTS` / `CREATE OR REPLACE`
throughout. That fits schema-as-code work (functions, triggers, views, row-level
security) extremely well and fits incremental `ALTER TABLE` work badly.

It pairs naturally with PostGraphile, where much of the "schema" is functions and
policies rather than tables. If your migrations are mostly `ALTER TABLE`, it is the
wrong shape.

## Choosing

- **Already committed to Prisma or Drizzle as the client** → use their migration
  tool. Splitting the schema's source of truth across two systems is worse than any
  limitation either has.
- **Raw SQL with `pg`, schema owned by you** → node-pg-migrate.
- **Schema is mostly functions, triggers, views, policies** → graphile-migrate.
- **A handful of tables and no `CONCURRENTLY` yet** → your own runner is genuinely
  fine, and you will understand what you switch to.

## Migrating between them

Cheaper than it looks, because they all record applied versions in a table:

1. Freeze the current schema as a single baseline migration (`pg_dump --schema-only`).
2. Mark it applied in the new tool's tracking table without running it — the
   baselining feature above.
3. Write every subsequent change in the new tool.

The old history stops being replayable, which is the real cost. If you rely on
rebuilding a database from migration zero — some teams do, for CI — squash to a
baseline deliberately rather than as a side effect.

## Trade-off

A tool removes the cases you have not thought of yet, which for infrastructure is
most of its value: the unhandled case in a migration runner is discovered during an
incident. It costs a dependency, a config file, and a model you must learn — and if
that model assumes an ORM you are not using, it costs far more than it gives.

The honest summary: your own runner to understand the mechanism, node-pg-migrate the
moment you need `CONCURRENTLY` or baselining, and a schema-derived tool only when
you have already adopted its client.

## Gotchas

**Symptom:** `25001 … cannot run inside a transaction block` after adding an index
migration
**Cause:** `CREATE INDEX CONCURRENTLY` inside a transaction-wrapped file.
**Fix:** A tool with a per-file opt-out — this is the usual reason to stop hand
rolling.

**Symptom:** Prisma or Drizzle wants to drop a column you added by hand
**Cause:** The tool diffs against its own schema file, which does not know about
out-of-band changes.
**Fix:** Represent every change in the tool's schema, or accept the escape hatch and
re-baseline.

**Symptom:** Two developers' migrations conflict on merge
**Cause:** Counter-based filenames.
**Fix:** Timestamped names, which every tool here generates.

**Symptom:** Adopting a tool tries to recreate tables that already exist
**Cause:** No baseline — the tool sees an empty tracking table and assumes an empty
database.
**Fix:** Baseline first: record the initial migration as applied without running it.

**Symptom:** `current.sql` fails on the second save under graphile-migrate
**Cause:** It is not idempotent; the model re-runs it continuously.
**Fix:** `DROP … IF EXISTS` / `CREATE OR REPLACE`, or a tool with a different model.

**Symptom:** A tool's generated migration is subtly wrong for a large table
**Cause:** Diff engines generate correct SQL, not *safe* SQL — a type change can
mean a full rewrite under `ACCESS EXCLUSIVE`.
**Fix:** Read generated migrations before applying them; see
[DDL locks and the blocking they cause](./01-ddl-from-node/02-locks-and-blocking.md).

## Interview questions

**★ What actually differs between migration tools?**
Not the tracking table — they all have one. What differs is whether *you* write the
schema (node-pg-migrate, graphile-migrate) or the tool *derives* migrations by
diffing a schema file (Prisma, Drizzle). The first gives full access to PostgreSQL
features; the second gives less typing and free types, at the cost of anything the
schema language cannot express.

**★ When do you stop using a hand-written runner?**
The first time you need `CREATE INDEX CONCURRENTLY` (requires per-file transaction
opt-out), baselining an existing database, dry-run/status output, or JavaScript data
migrations. Each is a structural change, not an addition.

**★ Why is graphile-migrate's model different, and who is it for?**
You edit one `current.sql` that re-runs on every save until you commit it as an
immutable numbered file, so it must be idempotent. That suits schemas made largely
of functions, triggers, views and policies, and suits incremental `ALTER TABLE` work
poorly.

**★ How do you adopt a migration tool on a database that already exists?**
Baseline: dump the current schema as one initial migration and record it as applied
without executing it, then write every subsequent change through the tool. The cost
is that history before the baseline is no longer replayable.

**★ Should you use Prisma Migrate without using Prisma Client?**
Generally no. Its value comes from `schema.prisma` being the single source of truth;
using it only for migrations means maintaining a schema definition in a language you
otherwise do not use, and accepting its expressiveness limits for no benefit.

**Why review a generated migration before applying it?**
Diff engines produce *correct* SQL, not necessarily *safe* SQL. A column type change
can trigger a full table rewrite under `ACCESS EXCLUSIVE`, which is fine on a
thousand rows and an outage on ten million.
