**Use `bigint GENERATED ALWAYS AS IDENTITY` unless you have a specific reason not
to.** It is the SQL-standard form, it refuses accidental manual inserts, and
`bigint` costs four extra bytes against an `int` you may one day run out of.

## `GENERATED ALWAYS AS IDENTITY` vs `serial`

```sql
CREATE TABLE id_a (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, t text);
CREATE TABLE id_b (id bigserial PRIMARY KEY, t text);
```

```console
$ node ex11-ddl-alter.mjs
=== 3. GENERATED ALWAYS AS IDENTITY vs serial ===
id_a   {"column_name":"id","column_default":null,"is_identity":"YES","identity_generation":"ALWAYS"}
id_b   {"column_name":"id","column_default":"nextval('id_b_id_seq'::regclass)","is_identity":"NO","identity_generation":null}
id_a: manual id → 428C9 cannot insert a non-DEFAULT value into column "id"
id_b: manual id accepted
sequence left after DROP TABLE id_b: 0
```

Three things worth keeping:

- **Identity refuses a manual value** (`428C9`); `serial` accepts one. That is the
  substantive difference. A manual insert into a `serial` column does not advance the
  sequence, so the sequence later hands out an id that is already taken and you get a
  `23505` on a table nobody touched. Identity makes that impossible.
- **Identity has no `column_default`.** It is a distinct catalog property
  (`is_identity`), which matters for drift checks — a comparison that only looks at
  defaults will not notice identity being dropped
  ([Schema drift](../phase-8-schema-from-node/13-schema-drift.md)).
- **`serial` is not a type.** It is shorthand that creates an `integer` plus a
  sequence plus a default. The sequence is owned by the column, so it is dropped with
  the table — measured, 0 sequences left.

Use `GENERATED BY DEFAULT AS IDENTITY` when you genuinely need to supply ids — data
imports, tests that pin ids. It behaves like `serial` for inserts while remaining a
proper identity column.

## `bigint`, not `int`

An `int` primary key stops at 2 147 483 647. That is reachable: the sequence
advances on *attempts*, not successes, so failed inserts and rolled-back
transactions consume the range.

```console
=== 4. where sequence gaps come from ===
┌─────────┬─────┬─────┐
│ (index) │ id  │ t   │
├─────────┼─────┼─────┤
│ 0       │ '1' │ 'a' │
│ 1       │ '4' │ 'b' │
└─────────┴─────┴─────┘
→ rollback and failed inserts both consume ids; sequences are non-transactional
```

Two rows, ids 1 and 4 — a rolled-back insert took 2 and a failed unique insert took
3. A table with a high failure rate burns its id space far faster than its row count
suggests. Migrating `int` → `bigint` later means a **full table rewrite** under
`ACCESS EXCLUSIVE` — measured at 431 ms per 200 000 rows in
[`ALTER TABLE`](05-alter-table.md), which is an outage at real scale. Four bytes now
is cheaper.

Gaps are not a bug and not worth avoiding. Anything that needs a gapless sequence —
invoice numbers, legal document numbering — needs a separate, deliberately
serialised counter, not a primary key.

## `bigint` ids arrive in JavaScript as strings

```console
$ node ex4-soft-delete.mjs
rowCount: 1 | returned: { id: '1', email: 'hard@x.com', name: 'Hard' }
```

`id` is `'1'`, not `1`. `pg` returns `bigint` as a string because 64-bit integers
exceed JavaScript's safe integer range. Consequences you must design for:

- `user.id + 1` produces `'11'`.
- `JSON.stringify` emits `"1"`, so API clients see a string. That is correct and
  worth documenting rather than "fixing".
- Comparisons with `===` against a number always fail.

Treat ids as opaque strings in application code. Do not install a global parser to
turn them into numbers — that reintroduces the precision loss the string exists to
avoid.

## Natural vs surrogate keys

A **natural key** is data that identifies the row: an ISO country code, an email
address. A **surrogate key** is a meaningless generated id.

Surrogate keys win in almost every application table, for one reason: **natural keys
change.** Emails change, product SKUs get restructured, country codes get
reassigned. A changing primary key means updating every referencing row, which is
what `ON UPDATE CASCADE` exists for — and needing it is the signal you chose wrong.

Natural keys are right for genuinely immutable reference data — a `currencies` table
keyed by ISO 4217 code — where the key is stable by definition and the join reads
better (`WHERE currency = 'EUR'` needs no join at all).

**Having a surrogate key does not excuse you from the unique constraint on the
natural one.** A `users` table with `id` and no `UNIQUE (email)` will accumulate
duplicate accounts; the surrogate key makes the rows distinct without making them
correct.

## UUIDs

Legitimate when ids must be generated client-side, must not leak volume, or must be
merged across systems. The costs are real:

- **16 bytes against 8**, in the table and in every index and foreign key.
- **Random UUIDs (v4) destroy index locality.** Inserts land in random pages of the
  btree, so the working set is the whole index rather than its right-hand edge.
- They are unreadable in logs and support conversations.

If you need them, prefer **UUIDv7** (time-ordered), which restores insert locality.
And note from [`ALTER TABLE`](05-alter-table.md): adding a
`uuid DEFAULT gen_random_uuid()` column to an existing table **rewrites it** —
measured 902 ms per 200k rows — because the default is volatile.

## Composite primary keys

The natural fit for a join table:

```sql
CREATE TABLE post_tags (
  post_id bigint NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  tag_id  bigint NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)
);
```

The composite key *is* the uniqueness rule — a post cannot have the same tag twice —
so a surrogate `id` here adds a column, an index, and no guarantee. Column order
matters: the primary key's index serves `WHERE post_id = $1` but not
`WHERE tag_id = $1`, so the reverse direction needs its own index. See
[Modeling relationships](06-relationships.md).

## Trade-off

A surrogate `bigint` identity key is stable, small, fast to index, and meaningless —
which means every lookup by something a user actually knows requires a join or a
second unique index. That is the cost, and it is almost always worth paying.

The mistake is treating "surrogate key" as the whole answer. It settles *identity*;
it says nothing about *uniqueness*, which still has to be declared on the natural
key.

## Gotchas

**Symptom:** `23505` on a `serial` primary key nobody touched
**Cause:** A manual insert supplied an id without advancing the sequence; the
sequence later reached it.
**Fix:** `GENERATED ALWAYS AS IDENTITY`, which rejects manual values with `428C9`.
Repair with `setval`.

**Symptom:** `user.id + 1` gives `'11'`
**Cause:** `pg` returns `bigint` as a string — measured, `{ id: '1' }`.
**Fix:** Treat ids as opaque strings. Do not add a global int8 parser.

**Symptom:** Ids have gaps
**Cause:** Sequences are non-transactional; rollbacks and failed inserts consume
values. Measured: ids 1 and 4 after four attempts.
**Fix:** Nothing — gaps are correct. A gapless sequence needs a separate serialised
counter.

**Symptom:** An `int` key is approaching exhaustion
**Cause:** The sequence advances on attempts, not rows.
**Fix:** `bigint` from the start; migrating later is a full rewrite under
`ACCESS EXCLUSIVE`.

**Symptom:** Insert performance degrades as a UUID-keyed table grows
**Cause:** Random v4 UUIDs scatter inserts across the whole index.
**Fix:** UUIDv7, or a `bigint` key with the UUID as a separate unique column.

**Symptom:** Duplicate user accounts despite a primary key
**Cause:** The surrogate key makes rows distinct, not correct.
**Fix:** A unique constraint on the natural key as well.

**Symptom:** A drift check misses an identity column being dropped
**Cause:** Identity is `is_identity`, not `column_default`.
**Fix:** Compare `is_identity` too.

## Interview questions

**★ `GENERATED ALWAYS AS IDENTITY` or `serial`?**
Identity. It is the SQL standard, and it refuses a manually supplied value with
`428C9` — measured, while `serial` accepts one. That matters because a manual insert
into a `serial` column does not advance the sequence, so the sequence later collides
with an existing row. Identity is also a catalog property rather than a default,
which drift checks must account for.

**★ Why `bigint` rather than `int`?**
Because sequences advance on *attempts*: rolled-back and failed inserts consume ids,
so the range is used faster than the row count implies — measured, ids 1 and 4 after
four attempts. Migrating `int`→`bigint` later rewrites the whole table under
`ACCESS EXCLUSIVE`, measured at 431 ms per 200k rows.

**★ Why does `pg` return ids as strings?**
`bigint` is 64-bit and exceeds JavaScript's safe integer range, so parsing it as a
`number` would silently lose precision. Measured: `{ id: '1' }`. Treat ids as opaque
strings rather than installing a parser.

**★ Are sequence gaps a bug?**
No. Sequences are deliberately non-transactional so concurrent inserters never block
on each other — which means rollbacks and failures leave holes. Anything needing
gapless numbering requires a separately serialised counter, at the cost of that
concurrency.

**★ When is a natural key the right choice?**
For genuinely immutable reference data — currencies by ISO code, countries by ISO
code — where the key cannot change and joins read better. For anything a user can
edit, use a surrogate key: needing `ON UPDATE CASCADE` is the sign you chose wrong.

**★ What do UUID primary keys cost?**
16 bytes against 8 in the table and every index, and random v4 UUIDs destroy insert
locality so the whole index becomes the working set. Use UUIDv7 if you need
client-generated ids. Also: adding a `uuid DEFAULT gen_random_uuid()` column to an
existing table rewrites it, because the default is volatile.

**Does a surrogate key remove the need for a unique constraint?**
No — it settles identity, not uniqueness. Without `UNIQUE (email)` you get duplicate
accounts that are distinct rows and wrong data.
