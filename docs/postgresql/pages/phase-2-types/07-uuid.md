<span className="db-tier t-understand">Understand</span>

> Verified: 2026-08 on **PostgreSQL 18.4** (`postgres:18-alpine`, `127.0.0.1:55432`),
> **Node 24.19.0**, `pg` 8.23.0. Script: `sandbox/pg-api/ex33-types-core.mjs`.

**A random UUID primary key costs 82% more insert time and a 94% larger index than a
`bigint` — not because it is 16 bytes instead of 8, but because random values scatter writes
across the whole B-tree. PostgreSQL 18's `uuidv7()` recovers most of that by making the
values time-ordered.**

## The three key types, measured

200 000 inserts into an otherwise identical table:

```console
$ node ex33-types-core.mjs
=== 7. uuid — v4 vs PostgreSQL 18 uuidv7, and the index cost ===
bigint identity: 200k inserts    947.4 ms | table   16 MB | pk index 4408 kB
uuid v4       : 200k inserts   1726.8 ms | table   18 MB | pk index 8552 kB
uuid v7       : 200k inserts   1356.4 ms | table   18 MB | pk index 6184 kB
column sizes: {"uuid_b":16,"bigint_b":8,"uuid_as_text_b":40}
```

| Key | Insert time | Index size | vs bigint |
|---|---|---|---|
| `bigint` identity | 947 ms | 4408 kB | baseline |
| `uuid` v4 (random) | 1727 ms | 8552 kB | **1.8× slower, 1.94× the index** |
| `uuid` v7 (time-ordered) | 1356 ms | 6184 kB | 1.4× slower, 1.40× the index |

The index is 8 bytes wider per entry, which explains roughly half the size difference. The
rest — and all of the insert-time difference — is **B-tree locality**. Sequential keys always
append to the rightmost leaf page, which stays in cache and fills completely. Random keys hit
a different page every time, so pages split half-empty and the working set is the entire
index rather than its right edge.

**`uuidv7` closes most of the gap** because the first 48 bits are a millisecond timestamp,
making consecutive values nearly sequential.

## Generating them

```console
{"v4":"b19b1ef9-96f3-4b01-9597-e1184dd65f15","v7":"019ff600-e83b-765d-9b2f-59d8689f7ba0",
 "v7_version":7,"v7_time":"2026-08-12 12:44:42.427+00"}
```

```sql
-- PostgreSQL 13+ : random
gen_random_uuid()

-- PostgreSQL 18  : new built-ins, no extension required
uuidv7()                      -- time-ordered
uuidv4()                      -- same as gen_random_uuid()
uuid_extract_version(u)       -- 7
uuid_extract_timestamp(u)     -- 2026-08-12 12:44:42.427+00
```

**`uuid_extract_timestamp()` recovers the creation time from a v7 value**, which is a real
feature — you get a free `created_at` — and a real caveat: **a v7 id leaks when the row was
created**, and roughly how many were created nearby. For a public identifier on sensitive
data, that may matter.

```sql
CREATE TABLE events (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- internal key
  public_id uuid NOT NULL UNIQUE DEFAULT uuidv7(),     -- what the API exposes
  ...
);
```

Before PostgreSQL 18, `uuidv7` means generating in the application (`uuidv7` on npm) and
passing it in.

## When a UUID earns its cost

- **Ids generated by the client, or before the database sees the row.** Offline-first apps,
  and any flow where you need the id before insert.
- **Ids merged from several databases or shards** without coordination.
- **Ids exposed publicly** where a sequential integer would leak volume (`/orders/1042` tells
  a competitor how many orders you have). Note this is the argument a v7 UUID partly
  undermines — it leaks timing instead.

When none of those apply, `bigint` identity is smaller, faster, and easier to read in a log.

**The common middle path is both**: `bigint` for the primary key and joins, a `uuid` unique
column for external exposure. You pay for one extra index and keep the fast key everywhere it
matters.

## Never store a UUID as text

```console
column sizes: {"uuid_b":16,"bigint_b":8,"uuid_as_text_b":40}
```

**16 bytes as `uuid`, 40 as `text`** — 2.5× the storage in the table *and* in every index,
plus string comparison instead of a 16-byte integer comparison, plus no validation of the
format. There is no upside. If a UUID arrives as a string, cast it at the boundary and store
the real type.

## From Node

```js
// pg sends and receives uuid as a plain string — no conversion needed
const {rows} = await pool.query(
  'SELECT * FROM events WHERE public_id = $1', ['b19b1ef9-96f3-4b01-9597-e1184dd65f15']);

// generating in the application when you need the id first
import {v7 as uuidv7} from 'uuid';
const id = uuidv7();
await pool.query('INSERT INTO events (public_id, kind) VALUES ($1, $2)', [id, 'signup']);
```

`pg` does not validate — an invalid string reaches the server and comes back as
`22P02 invalid input syntax for type uuid`. The server normalises case and accepts the
braced and unbraced forms, so `'{B19B1EF9-...}'` and the lower-case unbraced form are the
same value.

## Trade-off

**A UUID buys client-side generation and non-enumerable ids, and costs insert throughput,
index size and readability.** The measured numbers are the honest ones: v4 is 1.8× the
insert time and 1.94× the index of a `bigint`; v7 reduces that to 1.4× and 1.40× while
leaking creation time. On a small table none of this is visible. On a large, write-heavy
table the index is the thing that hurts — it is the structure that must stay in memory, and
doubling it doubles the memory needed to keep inserts fast. Choose `uuid` for a reason you
can name, not as a default.

## Gotchas

**Symptom:** Insert throughput degrades as a UUID-keyed table grows
**Cause:** Random v4 keys scatter B-tree writes; pages split half-empty
**Fix:** `uuidv7()` (PostgreSQL 18) or an application v7 generator — measured 1727 ms → 1356 ms

**Symptom:** The primary key index is far larger than expected
**Cause:** 16-byte keys plus poor page fill from random insertion
**Fix:** v7 for locality (measured 8552 kB → 6184 kB), or `bigint` with a separate uuid column

**Symptom:** UUID columns are huge and joins are slow
**Cause:** Stored as `text` — 40 bytes instead of 16, with string comparison
**Fix:** Use the `uuid` type; cast at the boundary

**Symptom:** `22P02 invalid input syntax for type uuid`
**Cause:** A malformed string reached the server; `pg` does not validate
**Fix:** Validate in the application before the query

**Symptom:** Public ids reveal when records were created
**Cause:** v7 encodes a millisecond timestamp, recoverable with `uuid_extract_timestamp()`
**Fix:** Use v4 for public identifiers where creation time is sensitive

**Symptom:** Ordering by a UUID primary key gives meaningless order
**Cause:** v4 is random
**Fix:** Order by a timestamp column; v7 does sort chronologically, v4 never will

## Interview questions

**★ Why is a random UUID primary key slower than `bigint`?**
Random values scatter inserts across the whole B-tree, so pages split half-empty and the
working set is the entire index rather than its right edge. Measured: 1727 ms vs 947 ms for
200 000 inserts, and a 8552 kB index vs 4408 kB.

**★ What does `uuidv7` change?**
The first 48 bits are a millisecond timestamp, so consecutive values are nearly sequential
and locality returns. Measured 1356 ms and 6184 kB — most of the gap closed.

**★ What is the downside of v7?**
It leaks creation time — `uuid_extract_timestamp()` recovers it exactly — and roughly how
many ids were created around it.

**★ When would you choose a UUID over `bigint`?**
Client-side generation, merging data from independent databases, or avoiding enumerable
public ids. Otherwise `bigint` is smaller and faster.

**★ Why not store a UUID as text?**
40 bytes instead of 16, in the table and every index, with slower string comparison and no
format validation. Measured.

**Can you have both?**
Yes, and it is the common answer: `bigint` primary key for joins, a `uuid` unique column for
external exposure.

**Does `pg` need special handling for uuid?**
No — it is a plain string in both directions. It does not validate, so a malformed value
fails server-side with `22P02`.
