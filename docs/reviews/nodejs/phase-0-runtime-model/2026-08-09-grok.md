## 9.3 Findings

### Major

```
[MAJOR] 08-running-node.md:31-41 — positive demo + claim about process.execArgv

Quoted:

$ node --watch-path=. args.js --port 3000
[ '--port', '3000' ] []

… process.execArgv holds the flags Node itself received, which is how you check.
```

**What is wrong:** Under `--watch` / `--watch-path`, Node runs the user script in a child that does **not** put the watch flags in `process.execArgv`. The transcript shows `[]` even though a Node flag was used. The next sentence teaches that `execArgv` is how you verify flags — using an example where that check fails. The process also waits for file changes; the transcript omits that.

**Evidence:** On Node 24.19.0:

```
$ node --trace-warnings args.js --port 3000
argv [ '--port', '3000' ]
execArgv [ '--trace-warnings' ]

$ timeout 1.2 node --watch-path=. args.js --port 3000
argv [ '--port', '3000' ]
execArgv []
Completed running 'args.js --port 3000'. Waiting for file changes before restarting...
```

**Impact:** A reader places flags correctly, inspects `execArgv`, sees `[]`, and concludes Node ignored them — the opposite of the lesson. The second command (misplaced `--watch` in app args) remains a good *negative* example.

**Fix:** Use a non-watch Node flag for the positive case; keep watch restart output in the `--watch` section:

```console
$ node --trace-warnings args.js --port 3000
[ '--port', '3000' ] [ '--trace-warnings' ]

$ node args.js --port 3000 --watch
[ '--port', '3000', '--watch' ] []      # ⚠ --watch is NOT active
```

### Minor

```
[MINOR] 04-libuv-thread-pool.md:20-23 — "There is no such API for reading a file. Portable filesystem calls block, full stop."
```

**What is wrong:** The *teaching* model (libuv fakes non-blocking fs via the pool) is still what you size and debug against, and it is what libuv documents. Absolute “no such API / full stop” is stronger than the real OS landscape and than Node’s own fs notes.

**Evidence:** https://docs.libuv.org/en/v1.x/threadpool.html — default size 4, max 1024 since 1.30.0. Node 24 fs docs: callback/promise fs APIs use the pool **except** `fs.FSWatcher()`. Re-run: five concurrent `pbkdf2` on 24.19.0 → four finish ~552–612ms, fifth ~1105ms (same four-then-fifth pattern as the page).

**Impact:** A pedantic or io_uring-aware reader discounts an otherwise excellent page.

**Fix:** “Portable filesystem work is still treated as blocking at the libuv boundary: the pool runs it so the main thread does not wait. Size and debug as if the pool owns async `fs` (with `fs.watch` / FSWatcher as the usual exception).”

---

```
[MINOR] 04-libuv-thread-pool.md:29 — "Everything in node:fs (async form)"
```

**What is wrong:** Node’s own docs carve out `fs.FSWatcher()` from threadpool usage. “Everything” is one word too strong for a table people will memorise.

**Evidence:** https://nodejs.org/docs/latest-v24.x/api/fs.html#threadpool-usage — “All callback and promise-based file system APIs (with the exception of `fs.FSWatcher()`) use libuv's threadpool.”

**Impact:** Someone wondering why a heavy `fs.watch` setup does not show pool saturation may get confused later.

**Fix:** “Most of async `node:fs` (not `fs.watch` / `FSWatcher`)”.

- **04 is one of the best handbook pages on the pool:** default 4, max 1024, lazy fixed size, DNS-lookup vs resolve, and the “outbound HTTP starves `fs`” failure mode — with a demo that still shows the fifth `pbkdf2` finishing a full generation later.
- **06 path lesson** (`__dirname` / `import.meta.dirname` vs `cwd`) is the Docker/cron bug people actually hit; version notes for `import.meta.dirname` match the docs (added v21.2.0/v20.11.0; non-experimental v24.0.0/v22.16.0).
- **07 + release schedule** track nodejs.org: 24 LTS for production, 26 Current, odd/even ends after 26, annual majors from 27. Pin quartet (`.nvmrc`, `engines`, full image tag, CI `node-version-file`) is complete.
- **08 (aside from the execArgv demo)** is excellent operational truth: flag-order silence, env precedence, no `$VAR` expansion, `--env-file-if-exists`, NODE_OPTIONS bans for `--eval` / `--print` / `--env-file` / `--test` — all re-verified. Stability callout for `--env-file` at v24.10.0 matches v24 CLI history.
- **09 refuses benchmark theatre** and still gives real jobs for Deno (permissions) and Bun (install/test tool while deploying Node).
- **10’s priority stack** (DB → network → loop block → JSON → algorithms → V8 micro-opts) is the correct When Needed posture; keep that ranking when fixing shapes.
