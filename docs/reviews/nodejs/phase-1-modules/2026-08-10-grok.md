## 11.1 Verdict

Phase 1 is ready to trust as a modules-and-packages reference on Node 24 LTS. Pages 01–13 are accurate against Node 24.19.0 and npm 12.0.2: exports, live bindings, `require(esm)`, prefix-only builtins, type stripping, lockfiles, and workspaces all reproduce as written. Syllabus coverage is complete (16 rows → 14 pages with documented merges).

The single most important fix is page 14: it teaches `module.register()` as the customization-hooks API and says hooks are “still experimental,” while on the target docs **`module.register` is Stability 0 / deprecated since v24.15.0** and the successor is **`module.registerHooks()`** (sync, in-thread, Stability 1.2 RC). That is a When Needed page, but it is the wrong API for anyone who lands there on 24.19.0. Fix that, clean two cross-reference nits, and the phase sits in the high 4s.

## 11.3 Findings

### Major

```
[MAJOR] 14-node-module-api.md:9-10, 57-93, 128-146, 149-153
— teaches module.register() as current hooks API; banner says hooks are
  "still experimental"

Quoted (banner):
> Customization hooks are still experimental; `enableCompileCache()` is not.

Quoted (body):
import { register } from 'node:module';
register('./hooks.js', import.meta.url);
…
Hooks run on a **separate thread** from application code.
…
**Symptom:** An `ExperimentalWarning` about customization hooks in production logs
**Cause:** The hooks API is still experimental in Node 24.
```

**What is wrong:** On the target docs for Node 24.x, `module.register()` is **Stability 0 — Deprecated since v24.15.0**. The documented replacement is `module.registerHooks()` (synchronous, in-thread, Stability 1.2 — Release candidate as of v24.13.1). The page’s “separate thread” story and “ExperimentalWarning in production” gotcha describe the **async loader** path, not the API Node now tells you to use. The example still *runs* on 24.19.0 (no deprecation warning emitted in this environment even with `--trace-deprecation`), which makes the outdated teaching harder to notice.

**Evidence:**
- https://nodejs.org/docs/latest-v24.x/api/module.html#moduleregisterspecifier-parenturl-options — “Stability: 0 - Deprecated: Use `module.registerHooks()` instead.” History: “Deprecated since: v24.15.0”.
- Same page: `module.registerHooks(options)` — Stability 1.2 RC; “Synchronous and in-thread hooks”.
- Local re-run: `validation/14-module-api/register.js` → `custom specifier resolved → production` with **no** ExperimentalWarning; `register-hooks-sync.js` using `registerHooks` also resolves `config:prod` correctly.

**Impact:** A reader who only opens this When Needed page ships the deprecated API, mis-models threading (separate worker thread vs same-thread sync hooks), and looks for an ExperimentalWarning that may never appear. Interview follow-up “how do you register a resolve hook on Node 24 LTS?” is answered with the wrong name.

**Fix:** Rewrite the hooks section around `registerHooks` first; keep `register` only as a short “deprecated async form, do not start new work here” note. Example:

```js
// register-hooks.js — preferred on Node 24.15+
import { registerHooks } from 'node:module';

registerHooks({
  resolve(specifier, context, nextResolve) {
    if (specifier.startsWith('config:')) {
      return {
        url: new URL('./config-' + specifier.slice(7) + '.js', import.meta.url).href,
        shortCircuit: true,
      };
    }
    return nextResolve(specifier, context);
  },
});

const { env } = await import('config:prod');
console.log('custom specifier resolved →', env);
```

Banner: “`enableCompileCache()` is stable; prefer `module.registerHooks()` for customization (RC). `module.register()` is deprecated since v24.15.0.”

Gotcha: replace ExperimentalWarning with “you used `register` after v24.15 — migrate to `registerHooks`.”

Interview answer for `module.register()`: rename to `registerHooks`, note deprecation of `register`.

```
[MINOR] 05-module-resolution.md:117 — table cell for typeless `.js`
"| `.js` with no `type` field | **Detected from the source** — on by default since v22.7.0 / v20.19.0 |"
```

**What is wrong:** Detection is a *fallback after CJS parse fails*, not the default parse mode. The interview answer on the same page is more precise (try CommonJS, reparse as ESM with `MODULE_TYPELESS_PACKAGE_JSON`). The table cell oversells “detected from the source” as the primary rule.

**Evidence:** Runtime on 24.19.0 (`validation/07-package-json/OUT.txt`): typeless file with `export` emits `[MODULE_TYPELESS_PACKAGE_JSON]` and reparses — consistent with “fallback,” not “always detect first.”

**Impact:** Interview half-answer if someone only memorizes the table.

**Fix:** `| \`.js\` with no \`type\` field | Treated as CommonJS first; if the source has module syntax, reparsed as ESM with a warning (v22.7.0 / v20.19.0+) |`
