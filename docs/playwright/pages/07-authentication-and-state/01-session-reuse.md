# 🎭 Authentication & State: `storageState` & Global Setup Projects

## 1. Under-The-Hood Mechanics

Logging in via the UI at the start of every single test is slow and repetitive — Playwright's `storageState` mechanism lets a login happen **once**, serializing the resulting cookies/localStorage to a file, which every subsequent test then loads directly, skipping the UI login flow entirely.

```
Global setup PROJECT (runs ONCE, before the main test suite):
  1. Launch a page, navigate to /login, perform the ACTUAL login flow
  2. context.storageState({ path: 'auth.json' })  ──► serializes cookies + localStorage to a file
        │
        ▼
Main test projects (each test): configured with `storageState: 'auth.json'`
  ──► every test's browser context STARTS ALREADY LOGGED IN — no repeated login UI flow needed
```

### Why a Dedicated Setup Project, Not a `beforeEach` Login
Repeating a full UI-based login in every single test's `beforeEach` multiplies the login flow's cost (however fast) by the total number of tests — for a large suite, this adds up to genuinely significant total run time. A dedicated global setup project runs the login flow **exactly once**, and every other test project simply loads the resulting `storageState`, making authentication effectively free for the rest of the suite.

### Per-Role Authentication Files
For apps needing to test multiple distinct user roles (admin, regular member, guest), separate `storageState` files (`admin-auth.json`, `member-auth.json`) — each generated by its own setup step — let different test files/projects each start pre-authenticated as the specific role that test actually needs, without re-running any login flow inline.

---

## 2. Real-World Engineering Scenario

**Scenario**: A 500-Test Suite Where Repeated UI Logins Consumed a Third of Total CI Run Time.
A large E2E suite's `beforeEach` hook performed a full UI login (navigate, fill credentials, submit, wait for redirect) for every single test — multiplied across 500 tests, this login flow alone consumed roughly a third of the suite's total CI run time, despite each individual login taking only ~2 seconds. Introducing a dedicated global setup project that logged in **once**, saving the resulting `storageState`, and configuring every other project to load that file directly cut total CI run time significantly — the login flow itself was now exercised exactly once (still verified, still tested), while every other test simply started from an already-authenticated state.

## 3. Production-Grade Code Example

```typescript
// tests/auth.setup.ts — the dedicated global setup project
import { test as setup } from '@playwright/test';

const authFile = 'playwright/.auth/user.json';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Username').fill('testuser');
  await page.getByLabel('Password').fill('testpass');
  await page.getByRole('button', { name: 'Log in' }).click();
  await page.waitForURL('/dashboard');

  await page.context().storageState({ path: authFile }); // serialize cookies/localStorage to disk
});
```

```typescript
// playwright.config.ts — wiring the setup project as a dependency of the main test project
import { defineConfig } from '@playwright/test';

export default defineConfig({
  projects: [
    { name: 'setup', testMatch: /.*\.setup\.ts/ }, // runs the auth.setup.ts file above, ONCE

    {
      name: 'chromium',
      use: { storageState: 'playwright/.auth/user.json' }, // every test in THIS project starts pre-authenticated
      dependencies: ['setup'], // ensures setup runs FIRST, before any of these tests
    },
  ],
});
```

```typescript
// dashboard.spec.ts — tests just work, already authenticated, NO login flow repeated here at all
test('shows the user dashboard', async ({ page }) => {
  await page.goto('/dashboard'); // already logged in — storageState was loaded automatically
  await expect(page.getByRole('heading', { name: 'Welcome back' })).toBeVisible();
});
```

```typescript
// Per-role authentication — separate storageState files for different user types
// tests/admin.setup.ts logs in as an admin, saves to 'playwright/.auth/admin.json'
// playwright.config.ts:
{
  name: 'admin-tests',
  use: { storageState: 'playwright/.auth/admin.json' },
  testMatch: /admin\/.*\.spec\.ts/,
  dependencies: ['admin-setup'],
}
```

## 4. Senior Engineer Edge Cases & Pitfalls

### ⚠️ Pitfall 1: A Stale `storageState` File Persisting Across CI Runs
```
❌ RISKY: if the saved auth.json file is cached/persisted across CI runs (rather than being
regenerated by the setup project EVERY run) and the session token it contains expires,
every test loading it fails with authentication errors that have NOTHING to do with the
actual feature being tested — confusing, misleading test failures

✅ CORRECT: ensure the setup project genuinely RUNS (and regenerates storageState) on every
CI invocation, rather than reusing a cached artifact from a previous run
```

### ⚠️ Pitfall 2: Committing `storageState` Files (Containing Real Session Tokens) to Version Control
```
❌ DANGEROUS: a checked-in auth.json contains ACTUAL cookies/tokens — committing it to a
git repository leaks real (even if test-environment-only) session credentials into
repository history, visible to anyone with repo access, indefinitely

✅ CORRECT: .gitignore the storageState output path, generating it fresh via the setup
project in CI (and locally) rather than ever committing the file itself
```

### ⚠️ Pitfall 3: Sharing One `storageState` Across Tests That Need to Verify Different Auth States
```typescript
// ❌ WRONG: a test specifically verifying UNAUTHENTICATED behavior (e.g. redirect-to-login)
// run under a project configured with a pre-authenticated storageState will never actually
// see the logged-out state it's trying to test
test('redirects to login when unauthenticated', async ({ page }) => {
  await page.goto('/dashboard'); // ALREADY logged in via storageState — never reaches the unauthenticated case!
  await expect(page).toHaveURL('/login'); // ❌ fails — page is actually on /dashboard, fully authenticated
});

// ✅ CORRECT: tests needing to verify unauthenticated behavior should use a project/context
// WITHOUT storageState configured, or explicitly clear cookies first
test.use({ storageState: { cookies: [], origins: [] } }); // explicitly empty state for this specific test file
```
