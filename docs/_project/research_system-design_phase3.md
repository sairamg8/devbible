## RFC 9111 — HTTP Caching
URL: https://www.rfc-editor.org/rfc/rfc9111.html

**What a cache is, and the two kinds** (§1.2, §1.3)
- *"An HTTP 'cache' is a local store of response messages and the subsystem that controls storage, retrieval, and deletion of messages in it."* — §1.2
- *"A 'shared cache' is a cache that stores responses for reuse by more than one user; shared caches are usually (but not always) deployed as a part of an intermediary. A 'private cache', in contrast, is dedicated to a single user; often, they are deployed as a component of a user agent."* — §1.3

**Freshness** (§4.2)
- *"A 'fresh' response is one whose age has not yet exceeded its freshness lifetime."* — §4.2.1
- *"Conversely, a 'stale' response is one where it has."* — §4.2.1
- *"A response's 'freshness lifetime' is the length of time between its generation by the origin server and its expiration time."* — §4.2.2
- *"A response's 'age' is the time that has passed since it was generated by, or successfully validated with, the origin server."* — §4.2.3

🔴 **These four sentences are the spine of the HTTP-caching page.** Freshness is a *computation over
two clocks*, not a flag, and age survives revalidation — that is what makes `Age` from an
intermediary meaningful and what makes a long chain of caches able to serve something older than
its own `max-age` suggests.

**Response directives — one defining sentence each** (§5.2.2)
- `max-age`: *"The max-age response directive indicates that the response is to be considered stale after its age is greater than the specified number of seconds."* — §5.2.2.1
- `s-maxage`: *"The s-maxage response directive indicates that, for a shared cache, the maximum age specified by this directive overrides the maximum age specified by either the max-age directive or the Expires header field."* — §5.2.2.10
- `no-cache`: *"The no-cache response directive, in its unqualified form (without an argument), indicates that the response MUST NOT be used to satisfy any other request without forwarding it for validation and receiving a successful response."* — §5.2.2.4
- `no-store`: *"The no-store response directive indicates that a cache MUST NOT store any part of either the immediate request or the response and MUST NOT use the response to satisfy any other request."* — §5.2.2.5
- `private`: *"The unqualified private response directive indicates that a shared cache MUST NOT store the response (i.e., the response is intended for a single user)."* — §5.2.2.7
- `public`: *"The public response directive indicates that a cache MAY store the response even if it would otherwise be prohibited, subject to the constraints defined in Section 3."* — §5.2.2.9
- `must-revalidate`: *"The must-revalidate response directive indicates that once the response has become stale, a cache MUST NOT reuse that response to satisfy another request until it has been successfully validated by the origin."* — §5.2.2.2

🔴 **`immutable` is NOT in RFC 9111** — it is RFC 8246, quoted below. Do not attribute it to 9111.

**Vary — the secondary cache key** (§4.1)
- *"When a cache receives a request that can be satisfied by a stored response and that stored response contains a Vary header field, the cache MUST NOT use that stored response without revalidation unless all the presented request header fields nominated by that Vary field value match those fields in the original request."* — §4.1

⚠️ **This is the quote behind the CDN cache-fragmentation gotcha.** `Vary` on a header with many
distinct values (`User-Agent`, an unbounded `Accept-Encoding`, a cookie) multiplies the stored
entries for one URL. The RFC states the matching rule; the *fragmentation consequence* is
mechanism — state it as such, and never attach a hit-rate number to it.

**Serving stale** (§4.2.4)
- *"A cache MUST NOT generate a stale response unless it is disconnected or doing so is explicitly permitted by the client or origin server."* — §4.2.4.3
- *"A cache MUST NOT generate a stale response if it is prohibited by an explicit in-protocol directive (e.g., by a no-cache response directive, a must-revalidate response directive, or an applicable s-maxage or proxy-revalidate response directive)."* — §4.2.4.2

**Invalidation by unsafe methods** (§4.4)
- *"A cache MUST invalidate the target URI when it receives a non-error status code in response to an unsafe request method (including methods whose safety is unknown)."* — §4.4.2

🔴 **The invalidation topic's one genuinely specified guarantee.** Everything else about
invalidation — TTL vs event-driven, versioned keys, tag purge — is design practice, not protocol.

## RFC 9110 — HTTP Semantics (validators, safe, idempotent)
URL: https://www.rfc-editor.org/rfc/rfc9110.html

- Entity tag: *"An entity tag is an opaque validator for representing a selected representation of the target resource."* — §8.8.3
- Strong validator: *"A strong validator is representation metadata that changes value whenever the associated representation's observable state changes."* — §8.8.1
- Weak validator: *"A weak validator is representation metadata that might not change for every alteration to the associated representation."* — §8.8.1
- 304: *"The 304 response indicates that a conditional GET or HEAD request has been received and would have resulted in a 200 OK response if it were not for the evaluated precondition being false."* — §15.4.5
- `Last-Modified`: *"The Last-Modified header field in a response provides a timestamp indicating the date and time at which the origin server believes the selected representation was last modified."* — §8.8.2
- `If-Modified-Since`: *"The If-Modified-Since header field makes a GET or HEAD request conditional on the selected representation's modification date being more recent than the date provided in the field-value."* — §13.1.3
- Safe: *"Request methods are considered 'safe' if their defined semantics are essentially read-only; they do not commit to any action on the origin server."* — §9.2.1
- Idempotent: *"A request method is considered 'idempotent' if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request."* — §9.2.2

⚠️ The `If-None-Match` sentence returned by the fetch (*"A recipient MUST use the If-None-Match
header field when making a conditional request."*) is a **garbled extraction** — it inverts the
actual requirement, which is about precedence between conditional header fields. **Do not quote
it.** Describe `If-None-Match` as mechanism: the client echoes the stored `ETag`, the origin
compares and answers 304 or 200. The 304 sentence above is safe to quote.

🔴 Safe and idempotent are already quoted in
[research_system-design_phase1.md](research_system-design_phase1.md) from the same RFC — the two
banks agree; do not re-fetch to check.

## RFC 5861 — stale-while-revalidate and stale-if-error
URL: https://www.rfc-editor.org/rfc/rfc5861.html

- `stale-while-revalidate` (§3): grammar *"stale-while-revalidate = \"stale-while-revalidate\" \"=\" delta-seconds"*; permission — *"caches MAY serve the response in which it appears after it becomes stale, up to the indicated number of seconds."*; constraint — *"If delta-seconds passes without the cached entity being revalidated, it SHOULD NOT continue to be served stale, absent other information."*
- `stale-if-error` (§4): grammar *"stale-if-error = \"stale-if-error\" \"=\" delta-seconds"*; permission — *"when an error is encountered, a cached stale response MAY be used to satisfy the request, regardless of other freshness information."*; constraint — *"when the cached response is more stale than the indicated amount, the cached response SHOULD NOT be used to satisfy the request, absent other information."*

🔴 **`stale-while-revalidate` is the protocol-level answer to the stampede topic** — the cache
serves the stale copy *and* refreshes behind it, so no user waits on the origin and only one
request goes back. Say that; it is mechanism straight from the permission sentence. **`MAY` and
`SHOULD NOT` are the words the RFC used — do not upgrade either to `MUST`.**

## RFC 8246 — the `immutable` Cache-Control extension
URL: https://www.rfc-editor.org/rfc/rfc8246.html

- *"When present in an HTTP response, the immutable Cache-Control extension indicates that the origin server will not update the representation of that resource during the freshness lifetime of the response."* — §2
- *"Clients SHOULD NOT issue a conditional request during the response's freshness lifetime (e.g., upon a reload) unless explicitly overridden by the user (e.g., a force reload)."* — §2
- *"The immutable extension only applies during the freshness lifetime of the stored response. Stale responses SHOULD be revalidated as they normally would be in the absence of the immutable extension."* — §2

⚠️ **This is the citation for content-hashed asset URLs** (`app.4f3a9c.js` served
`max-age=31536000, immutable`). The *pattern* is common practice; the *directive's meaning* is
quoted. Keep the two apart.

## MDN — `Cache-Control`
URL: https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control

- 🔴 *"Note that `no-cache` does not mean \"don't cache\". `no-cache` allows caches to store a response but requires them to revalidate it before reuse. If the sense of \"don't cache\" that you want is actually \"don't store\", then `no-store` is the directive to use."*
- *"The `no-store` response directive indicates that any caches of any kind (private or shared) should not store this response."*
- *"The `must-revalidate` response directive indicates that the response can be stored in caches and can be reused while fresh. If the response becomes stale, it must be validated with the origin server before reuse."*
- *"HTTP allows caches to reuse stale responses when they are disconnected from the origin server. `must-revalidate` is a way to prevent this from happening - either the stored response is revalidated with the origin server or a 504 (Gateway Timeout) response is generated."*
- *"In theory, if directives are conflicted, the most restrictive directive should be honored. So the example below is basically meaningless because `private`, `no-cache`, `max-age=0` and `must-revalidate` conflict with `no-store`."*
- *"The `stale-while-revalidate` response directive indicates that the cache could reuse a stale response while it revalidates it to a cache."*
- *"Revalidation will make the cache be fresh again, so it appears to clients that it was always fresh during that period — effectively hiding the latency penalty of revalidation from them."*
- 🔴 *"You should add the `private` directive for user-personalized content, especially for responses received after login and for sessions managed via cookies. If you forget to add `private` to a response with personalized content, then that response can be stored in a shared cache and end up being reused for multiple users, which can cause personal information to leak."*

🔴 **The `no-cache` ≠ "don't cache" quote and the `private` leak quote are the two most useful
sentences in this whole bank** — the first is the single most common misunderstanding in the
topic, the second is the failure that turns a caching bug into a security incident. Use them
verbatim on the HTTP-caching page and again in "what not to cache".

## Redis — Key eviction
URL: https://redis.io/docs/latest/develop/reference/eviction/

**The policies, verbatim**
- `noeviction`: *"Keys are not evicted but the server will return an error when you try to execute commands that cache new data. If your database uses replication then this condition only applies to the primary database. Note that commands that only read existing data still work as normal."*
- `allkeys-lru`: *"Evict the least recently used (LRU) keys."*
- `allkeys-lrm`: *"Evict the least recently modified (LRM) keys."*
- `allkeys-lfu`: *"Evict the least frequently used (LFU) keys."*
- `allkeys-random`: *"Evict keys at random."*
- `volatile-lru` / `volatile-lrm` / `volatile-lfu`: the same, restricted to *"keys that have an associated expiration (TTL)"*.
- `volatile-random`: *"Evicts random keys that have an associated expiration (TTL)."*
- `volatile-ttl`: *"Evict keys with an associated expiration (TTL) that have the shortest remaining TTL value."*
- 🔴 *"The `volatile-xxx` policies behave like `noeviction` if no keys have an associated expiration."*

**maxmemory**
- *"Redis lets you specify an eviction policy to evict keys automatically when the size of the cache exceeds a set memory limit. Whenever a client runs a new command that adds more data to the cache, Redis checks the memory usage. If it is greater than the limit, Redis evicts keys according to the chosen eviction policy until the total memory used is back below the limit."*
- ⚠️ *"Note that when a command adds a lot of data to the cache (for example, a big set intersection stored into a new key), this might temporarily exceed the limit by a large amount."*
- *"Set `maxmemory` to zero to specify that you don't want to limit the memory for the dataset. This is the default behavior for 64-bit systems, while 32-bit systems use an implicit memory limit of 3GB."*
- Replication/persistence: *"Redis will use some RAM as a buffer to store the set of updates waiting to be written to the replicas or AOF files. The memory used by this buffer is not included in the total that is compared to `maxmemory`"* — and the reason: *"the key evictions themselves generate updates that must be added to the buffer."*

**Approximated LRU — the load-bearing quote of the eviction topic**
- 🔴 *"The Redis LRU algorithm uses an approximation of the least recently used keys rather than calculating them exactly. It samples a small number of keys at random and then evicts the ones with the longest time since last access."*
- *"From Redis 3.0 onwards, the algorithm also tracks a pool of good candidates for eviction. This improves the performance of the algorithm, making it a close approximation to a true LRU algorithm."*
- *"The reason Redis does not use a true LRU implementation is because it costs more memory. However, the approximation is virtually equivalent for an application using Redis."*
- *"The Redis LRU algorithm will instead only probabilistically expire the older keys."*
- Tunable: `maxmemory-samples` — *"You can tune the performance of the algorithm by changing the number of samples to check before every eviction"*; *"you can raise the sample size to 10 at the cost of some additional CPU usage to closely approximate true LRU"*.

**LFU**
- *"LFU is approximated like LRU: it uses a probabilistic counter, called a Morris counter to estimate the object access frequency using just a few bits per object, combined with a decay period so that the counter is reduced over time. At some point we no longer want to consider keys as frequently accessed, even if they were in the past, so that the algorithm can adapt to a shift in the access pattern."*
- Defaults, quoted: *"Saturate the counter at, around, one million requests."* / *"Decay the counter every one minute."* Knobs: `lfu-log-factor 10`, `lfu-decay-time 1`.
- *"The counter logarithm factor changes how many hits are needed to saturate the frequency counter, which is just in the range 0-255."*

**LRM (Redis 8.6+)**
- *"Starting with Redis 8.6, the Least Recently Modified (LRM) eviction policy is available. LRM is similar to LRU but only updates the timestamp on write operations, not read operations."*
- *"LRU (Least Recently Used): Updates the access timestamp on both read and write operations"* / *"LRM (Least Recently Modified): Updates the access timestamp only on write operations"*

**Measuring — the only hit-ratio formula anyone should write**
- `INFO stats` gives `keyspace_hits` and `keyspace_misses`; the documented formula is
  `keyspace_hits / (keyspace_hits + keyspace_misses) * 100`.
- Also documented: `evicted_keys`, `expired_keys`, `used_memory_dataset`,
  `current_eviction_exceeded_time`, `mem_not_counted_for_evict`.
- ⚠️ *"When the `EXISTS` command reports that a key is absent then this is counted as a keyspace miss."*

🔴 **The "as a rule of thumb" guidance is Redis's own and may be quoted**, e.g. *"Use `allkeys-lru`
when you expect that a subset of elements will be accessed far more often than the rest… a good
default option if you have no reason to prefer any others."* ⛔ **The Pareto/power-law simulation
claim (*"the difference between true LRU and Redis approximation were minimal or non-existent"*)
is Redis's own simulation, not ours — attribute it explicitly, and never restate it as our
measurement.**

## Caffeine — Efficiency (the JVM in-process cache)
URL: https://github.com/ben-manes/caffeine/wiki/Efficiency

- *"Caffeine uses the `Window TinyLfu` policy due to its high hit rate and low memory footprint."*
- *"W-TinyLfu uses a small admission `LRU` that evicts to a large `Segmented LRU` if accepted by the `TinyLfu` admission policy."*
- 🔴 *"However, in typical workloads LRU is not optimal and may have a poor hit rate in cases like full scans."*
- *"This implementation uses a 4-bit CountMinSketch, growing at 8 bytes per cache entry to be accurate."*
- *"The policy provides a substantial improvement to `LRU` across a variety of workloads, making it a good choice for a general purpose cache."*

⚠️ **"Substantial improvement" is the strongest phrasing available — no percentage is documented
here. Do not attach one.** The full-scan sentence is the citation for why a nightly report job
can destroy a hot cache, which is the in-process-cache topic's best worked example.

## Cassandra — the Dynamo-style ring (consistent hashing and vnodes)
URL: https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html

**Consistent hashing using a token ring**
- *"Cassandra partitions data over storage nodes using a special form of hashing called consistent hashing."*
- *"Cassandra instead maps every node to one or more tokens on a continuous hash ring, and defines ownership by hashing a key onto the ring and then 'walking' the ring in one direction."*
- *"if we have an eight node cluster with evenly spaced tokens, and a replication factor (RF) of 3, then to find the owning nodes for a key we first hash that key to generate a token (which is just the hash of the key), and then we 'walk' the ring in a clockwise fashion until we encounter three distinct nodes."*

**Why not modulo — the sentence the whole topic turns on**
- 🔴 *"In naive data hashing, you typically allocate keys to buckets by taking a hash of the key modulo the number of buckets... adding a single node might invalidate almost all of the mappings."*
- 🔴 *"The main difference of consistent hashing to naive data hashing is that when the number of nodes (buckets) to hash into changes, consistent hashing only has to move a small fraction of the keys."*

**Virtual nodes**
- *"Virtual nodes solve the problem by assigning multiple tokens in the token ring to each physical node."*
- *"When a new node is added it accepts approximately equal amounts of data from other nodes in the ring, resulting in equal distribution."*
- *"When a node is decommissioned, it loses data roughly equally to other members of the ring."*
- *"If a node becomes unavailable, query load is evenly distributed across many other nodes."*
- *"Cassandra seeks to avoid token imbalance because uneven token ranges lead to uneven request load."*

⚠️ **Cassandra is a data store, not a cache** — quote it for the ring mechanics and say so. The
Memcached-client and Redis-Cluster applications of the same idea are common practice; the Dynamo
quote in the phase-0 bank (*"walking the consistent hashing ring"*) ties the lineage together.
🔴 **Do not state a number of vnodes per node, a key-movement fraction, or a variance bound** —
none of those is quoted here. *"only has to move a small fraction of the keys"* is the strongest
claim available, and `K/N` may be **derived on the page** as mathematics.
