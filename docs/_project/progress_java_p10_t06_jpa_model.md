## Load-bearing claims verified (with source)
- **Entity class rules** — JPA 3.2 §2.1, verbatim: "An enum, record, or interface may
  not be designated as an entity"; public/protected no-arg ctor; non-final class and
  non-final persistent members; top-level or static inner.
- **Hibernate is looser** — UG §3.4.1: no-arg ctor may be public/protected/package;
  need not be top-level; final classes persist but lose proxy lazy loading.
- **No identifier is deprecated** — UG §3.4.5: "should be considered a deprecated
  feature that will be removed in an upcoming release." Recommends wrapper `Long`.
- **Identity guarantee** — UG §3.4.7: "Hibernate guarantees equivalence of persistent
  identity (database row) and Java identity inside a particular session scope."
- **Access type from `@Id` placement** — Intro §3.2. `@Access` "strongly discouraged".
- **`@Basic(optional=false)` vs `@Column(nullable=false)`** — Intro §3.10: logical vs
  mapping layer; "optional=false implies nullable=false, but not vice versa."
- **Record as `@Embeddable` IS allowed** — Intro §3.15, with the no-arg ctor
  requirement relaxed.
- **JEP 395** — "transparent carriers for immutable data" (curl -A Mozilla works;
  WebFetch 403s on openjdk.org).
- **IDENTITY disables INSERT batching** — UG §3.7.10 verbatim: "Hibernate will not be
  able to batch INSERT statements for the entities using the IDENTITY generation."
- **Default allocationSize = 50** — `OptimizableGenerator.DEFAULT_INCREMENT_SIZE = 50`
  (hibernate-orm 7.4 source).
- **Implicit optimizer** — `OptimizerFactory.determineImplicitOptimizerName`: `none`
  when increment ≤ 1, else `pooled` (or `hibernate.id.optimizer.pooled.preferred`).
- **Sequence increment mismatch default = EXCEPTION** —
  `SequenceMismatchStrategy.interpret(null)` returns `EXCEPTION`; `SequenceStyleGenerator`
  passes `SequenceMismatchStrategy.EXCEPTION` as the default. Throws MappingException.
- **PostgreSQL identity DDL** — `PostgreSQLIdentityColumnSupport.getIdentityColumnString`
  returns `"generated by default as identity"` (hibernate-orm 7.4 source).
- **AUTO interpretation** — UG §3.7.8: UUID type → UUID generator; numeric →
  SequenceStyleGenerator (sequence if supported, else table).
- **Implicit sequence name** — UG §3.7.9: `<table>_seq`.
- **Flush order** — UG §7.5, the ActionQueue order: OrphanRemovalAction,
  EntityInsertAction/EntityIdentityInsertAction, EntityUpdateAction,
  QueuedOperationCollectionAction, CollectionRemoveAction, CollectionUpdateAction,
  CollectionRecreateAction, EntityDeleteAction.
- **AUTO flush triggers** — UG §7.1: before commit; before a JPQL/HQL query that
  overlaps queued actions; before a native query with no registered synchronization.
- **merge returns a different instance** — Intro §5.9: "merge() returns a distinct
  instance f representing the same row"; JPA 3.2 §3.3.7.1.
- **`spring.jpa.open-in-view` default is `true`** — Boot 4 properties appendix; warning
  string verbatim from `JpaBaseConfiguration.JpaWebConfiguration#openEntityManagerInViewInterceptor`
  (github.com/spring-projects/spring-boot, `module/spring-boot-jpa/...`).
- **`spring.jpa.hibernate.ddl-auto` default** — Boot appendix: "create-drop" for an
  embedded database with no schema manager detected, otherwise "none".
- **Statistics** — UG §28: `hibernate.generate_statistics=true`, off by default,
  `SessionFactory.getStatistics()`. `getOptimisticFailureCount`, `getEntityUpdateCount`,
  `getPrepareStatementCount`, `getFlushCount` all confirmed in §28.1.
- **Enum default is ORDINAL** — Intro §3.11. Since Hibernate 6, `@Enumerated(STRING)`
  maps to VARCHAR (ENUM on MySQL); any other enum → TINYINT with a CHECK constraint.

## 🔴 CORRECTION the web has not caught up with — Boot 4 naming strategy
Boot 4's `HibernateProperties.Naming.applyNamingStrategies` sets:
- implicit → `org.springframework.boot.hibernate.SpringImplicitNamingStrategy`
- physical → **`org.hibernate.boot.model.naming.PhysicalNamingStrategySnakeCaseImpl`**

That physical class is **Hibernate's own, new in ORM 7.0** — NOT Boot's old
`SpringPhysicalNamingStrategy`/`CamelCaseToUnderscoresNamingStrategy`. Its javadoc says
"Originally copied from Spring's SpringPhysicalNamingStrategy". Behaviour read from
source: applies to catalog/schema/table/**sequence**/column; lowercases via
`toLowerCase(Locale.ROOT)`; inserts `_` only between (lower|digit)(UPPER)(lower|digit)
so consecutive capitals are not split; and **leaves quoted identifiers alone** —
`@Column(name="\"createdAt\"")` survives, unquoted does not.
Escape hatch: `PhysicalNamingStrategyStandardImpl` (exists in 7.4, verified 200).

## 🔴 SECOND CORRECTION — `@Lob` on PostgreSQL. The internet is wrong here.
Hibernate 7.4 *Introduction* §4.10, verbatim conclusion:
> - on PostgreSQL, `@Lob` always means the **OID** type,
> - `@Lob` should never be used to map columns of type BYTEA or TEXT, and
> - please don't believe everything you read on stackoverflow.

`@Lob` selects a **JDBC API**, not a column size: Hibernate writes with
`PreparedStatement.setClob()/setBlob()` and reads with `ResultSet.getClob()/getBlob()`.
pgJDBC "doesn't allow BYTEA or TEXT columns to be read via the JDBC LOB APIs" — which is
the origin of every dialect-hacking blog post. Removing `@Lob` "has exactly the same
effect".
**Correct mapping: `@Column(length = LONG32)`** using `org.hibernate.Length`:
DEFAULT=255, LONG=32600, LONG16=32767, LONG32=2147483647. Hibernate adapts the DDL type.
UG §3.2.47: `@Lob` is "a special-purpose tool that should only be used when a default
basic mapping to String would result in unacceptable performance characteristics"; and a
LOB **locator** is not portably usable after its transaction ends.
(My first draft of chunk 05 said `@Lob String` → `text` on PostgreSQL. That was WRONG
and is why chunk 05 was split into 05 + 05b.)

## PostgreSQL 18 facts verified (batch 4)
- CREATE SEQUENCE: "The default value is 1" for INCREMENT BY.
- CACHE: "The minimum value is 1 … and this is also the default"; unused cached values

- JPA 3.2 §3.3.8 `contains`: TRUE for retrieved/getReference-and-not-removed-or-detached,

  Cascade effects "immediately visible to the contains method" while DB changes deferred.
- JPA 3.2 §3.2: persist/merge/remove/refresh REQUIRE a transaction
  (TransactionRequiredException); find (no lock / NONE) and getReference do NOT — and
  "the resulting entities will be detached" with a transaction-scoped context.
- Intro §5.4: the two tables; "except for getReference(), the following operations all
  result in immediate access to the database"; "there's no update() operation for a
  stateful session"; "a session is considered to be unusable after any of its methods
  throws an exception"; "When you call detach(), clear(), flush(), or refresh(), you've
  already strayed from the narrow path."
- JPA 3.2 §3.3.7.1 merge: X vs X' — "copied onto a pre-existing managed entity instance
  X' … or a new managed copy X' of X is created"; new ⇒ new managed copy; removed ⇒
  IllegalArgumentException; managed ⇒ ignored. "The persistence provider must not merge
  fields marked LAZY that have not been fetched." Version columns checked during merge.
- Intro §5.9: "merge() returns a distinct instance f representing the same row";
  Hibernate "first selects the current persistent state … before applying the
  modification"; cascade merge uses ONE select, avoiding N+1; "this query does not occur

- UG §6.12.1: `hibernate.event.merge.entity_copy_observer` — default `disallow` throws

- JPA 3.2 §3.3.6 detach: changes "will not be synchronized"; portable apps "must use the
  flush method prior to the detach method"; must NOT assume changes are unwritten.
- UG §6.4: Hibernate's Session accepts a DETACHED entity for delete; EntityManager.remove

### Dirty checking
- UG §6.2.2 *In-line dirty tracking*, verbatim: "Historically Hibernate only supported
  diff-based dirty calculation … Hibernate would keep track of the last known state of an
  entity in regards to the database (typically the last read or write). Then, as part of
  flushing the persistence context, Hibernate would walk every entity associated with the
  persistence context and check its current state against that 'last known database
  state'. This is by far the most thorough approach to dirty checking because it accounts
  for data-types that can change their internal state (java.util.Date is the prime example
  of this). However, in a persistence context with a large number of associated entities,
  it can also be a performance-inhibiting approach."
- 🔴 **`hibernate.enhancer.enableDirtyTracking` is DEPRECATED FOR REMOVAL, no
  replacement** — UG Appendix A (bytecode enhancement settings): "Whether to enhance the
  model for dirty-tracking. **This setting is deprecated for removal without a
  replacement.**" Same wording on the Gradle/Maven plugin `enableDirtyTracking`
  parameters. Defaults to `true` in the plugins. **The web is full of Hibernate-5 advice
  to turn this on; on 7.4 it is on its way out.**
- 🔴 **Extended bytecode enhancement is deprecated too** — UG §6.2.2: "Hibernate's
  extended bytecode enhancement feature has been deprecated, primarily because it relies
  on assumptions and behaviors that often require a broader runtime scope than what
  Hibernate alone can reliably provide … Applications which make use of this feature
  should instead use proper object-oriented encapsulation, exposing managed state via
  getters and setters."
- UG §3.15 *Mutability*: mutability is "an overloaded term" — internal-state mutability
  vs database updateability. "Hibernate uses this distinction for numerous internal
  optimizations related to dirty checking and making copies."
- UG §3.15.2 `@Immutable` on an entity: "reducing memory footprint since there is no need
  to retain the loaded state for the dirty checking mechanism" and "speeding-up the
  Persistence Context flushing phase since immutable entities can skip the dirty checking
  process". Modifications are silently skipped — no UPDATE. `@Mutability` is **not**
  allowed on an entity.
- UG §3.15.3: `@Immutable` on a **plural** attribute — "While most immutable changes are
  simply discarded, modifying an immutable collection will cause an exception":
  `org.hibernate.HibernateException: changed an immutable collection instance: [...]`
- UG §3.15.6 `@Mutability`: mutating a `Date` in place (`entity.getActiveTimestamp()
  .setTime(...)`) "has the same effect as the setting example — they each will make the
  entity dirty."
- UG §6.10: "By default, when you modify an entity, all columns but the identifier are
  being set during update." Two named advantages: JDBC statement caching, and batching
  across entities that modified different properties. Downside: "If you have multiple
  indexes, the database might update those redundantly."
- UG §6.10.1 `@DynamicUpdate`: "allows you to set just the columns that were modified".
- UG §7.5: "The UPDATE statement is generated by `EntityUpdateAction` during flushing if
  the managed entity has been marked modified. The dirty checking mechanism is responsible
  for determining if a managed entity has been modified since it was first loaded."
- Intro §5.1: persistence contexts "enable automatic dirty checking: after modifying an
  entity, we don't need to perform any explicit operation".
- Intro §5.3: "there's no `update()` operation for a stateful session. Modifications are
  automatically detected when the session is flushed."
- Intro §5.10: "Since flushing is a somewhat expensive operation (**the session must
  dirty-check every entity in the persistence context**), setting the flush mode to COMMIT
  can occasionally be a useful optimization. But take care — in this mode, queries might
  return stale data."
- Intro §6.3 *Auto-flush*: "By default, Hibernate dirty checks entities in the persistence
  context **before executing a query** … But if there are many entities associated with
  the persistence context, then this can be an expensive operation."

### Flush
- UG §7 opening: "The persistence context acts as a **transactional write-behind cache**,
  queuing any entity state change … The flush operation takes every entity state change
  and translates it to an INSERT, UPDATE or DELETE statement. Because DML statements are
  grouped together, Hibernate can apply batching transparently."
- UG §7 flush types — Hibernate has **four**, JPA only two:
  ALWAYS (before every query) · AUTO (default, "only if necessary") · COMMIT ("tries to
  delay the flush until the current Transaction is committed, **although it might flush
  prematurely too**") · MANUAL.
- UG §7.1 AUTO triggers, verbatim three bullets: "prior to committing a Transaction";
  "prior to executing a JPQL/HQL query that **overlaps with the queued entity actions**";
  "before executing any native SQL query that **has no registered synchronization**".
- UG §7.1.2: the Advertisement/Person worked example — a query for `Advertisement` does
  not flush a pending `Person` insert "because there's no overlapping between the
  Advertisement and the Person tables".
- UG §7.1.3 + Example 7.7: the escape hatch is
  `session.createNativeQuery(...).addSynchronizedEntityClass(Person.class)`.
- 🔴 **A CONTRADICTION INSIDE THE 7.4 DOCS, §7.1.3.** The prose says "If you bootstrap
  Hibernate natively, and not through Jakarta Persistence, by default, the Session API
  will trigger a flush automatically when executing a native query." The immediately
  following Example 7.6 asserts the count is **0** both before and after the persist —
  i.e. NO flush happened. The §7.1 bullet ("no registered synchronization") agrees with
  the example, not the prose. **Written up as an unresolved doc inconsistency; the
  behaviour claimed on the page is the §7.1 bullet + Example 7.6.**
- UG §7.2 COMMIT: quotes the spec, "If FlushModeType.COMMIT is set, the effect of updates
  made to entities in the persistence context upon queries is unspecified." And: with
  COMMIT set, a **native** query still flushes ("Because Jakarta Persistence doesn't
  impose a strict rule on delaying flushing").
- UG §7.3: "The ALWAYS is only available with the native Session API."
- Intro §5.10 Table 5.7 *Flush modes*: MANUAL and ALWAYS have **no** JPA equivalent.
- Intro §6.3: `setQueryFlushMode(QueryFlushMode.NO_FLUSH)` is the per-query switch;
  "Setting the flush mode to NO_FLUSH, COMMIT, or MANUAL might cause the query to return
  stale results."
- UG §7.1.1: AUTO-on-commit "is valid for the SEQUENCE and TABLE identifier generators.
  The IDENTITY generator must execute the insert right after calling persist()."

### Flush operation order
- UG §7.5, the `ActionQueue` order, verbatim list, in order:
  `OrphanRemovalAction` → `EntityInsertAction`/`EntityIdentityInsertAction` →
  `EntityUpdateAction` → `QueuedOperationCollectionAction` → `CollectionRemoveAction` →
  `CollectionUpdateAction` → `CollectionRecreateAction` → `EntityDeleteAction`.
  "Hibernate does not execute the SQL statements in the order of their associated entity
  state operations." Worked example: remove(person id 1) then persist(new id 2) emits
  **INSERT before DELETE**.

### @Version and optimistic locking
- UG §11.1.1: JPA's permitted `@Version` types are **`int`/`Integer`, `short`/`Short`,
  `long`/`Long`, `java.sql.Timestamp`** — "However, Hibernate allows you to use even
  Java 8 Date/Time types, such as `Instant`."
- Intro §3.8: "A version attribute is usually of type `Integer`, `Short`, `Long`,
  `LocalDateTime`, `OffsetDateTime`, `ZonedDateTime`, or `Instant`." · "**Almost every
  entity which is frequently updated should have a version attribute.**" · numeric version
  starts at **0**; `@Version int version = 1;` makes it start at 1 · datetime versions are
  generated in the JVM by default, `@CurrentTimestamp @Version` moves that to the database.
- UG §11.1: "A version or timestamp property **can never be null for a detached
  instance**. Hibernate detects any instance with a null version or timestamp as
  transient, regardless of other unsaved-value strategies that you specify."
- UG §11.1.1: "Your application is **forbidden** from altering the version number set by
  Hibernate." To bump it artificially use `LockModeType.OPTIMISTIC_FORCE_INCREMENT` or
  `PESSIMISTIC_FORCE_INCREMENT`.
- UG §11.1.1 *Excluding attributes*: "By default, **every entity attribute modification**
  is going to trigger a version incrementation." `@OptimisticLock(excluded = true)` opts a
  field out — and the doc's own worked example shows the resulting **lost update**:
  "you should only use this feature if you can accommodate lost updates on the excluded
  entity properties."
- UG §11.1.1 *Versionless*: `@OptimisticLocking(type = …)` with four
  `OptimisticLockType`s — NONE ("optimistic locking is disabled **even if there is a
  @Version annotation present**"), VERSION (the default), ALL, DIRTY.
  ALL → every column in the WHERE clause; DIRTY → only changed columns.
  Both "should also use `@DynamicUpdate`". Failure throws "a `StaleStateException` or an
  `OptimisticEntityLockException`".
- Intro §5.3: "A version check is included in the where clause of every SQL update or
  delete statement for a versioned entity. If a version check fails — that is, if no rows
  are updated — Hibernate infers that the entity was updated in some other unit of work
  and throws an `OptimisticLockException` … As with other exceptions, this loss of
  synchronization … means that we must discard the current session."
- UG §11.3 LockMode/LockModeType table: NONE · READ+OPTIMISTIC ("version is checked
  towards the end of the currently running transaction") · WRITE+OPTIMISTIC_FORCE_INCREMENT

- UG §11.2: "Hibernate always uses the locking mechanism of the database, and **never

### 🔴 ORIGINAL FINDING — read from Spring Framework 7.0.x source, NOT in the reference docs
`@Transactional(readOnly = true)` has **two** distinct effects on Hibernate, and only one
of them always happens:
1. **Always** — `HibernateJpaDialect.prepareFlushMode(session, true)` sets
   `FlushMode.MANUAL`. Source comment: *"We should suppress flushing for a read-only
   transaction."* The snapshot is still taken; only the write is suppressed.
2. **Conditionally** — `beginTransaction` calls `session.setDefaultReadOnly(true)` **only**
   inside `if (definition instanceof ResourceTransactionDefinition rtd &&
   rtd.isLocalResource())`. `JpaTransactionManager` passes
   `txObject.isNewEntityManagerHolder()` as that flag, i.e. **true only when the
   transaction opened its own EntityManager**.
   ⇒ **`spring.jpa.open-in-view=true` binds an EntityManager to the request first, so
   `isNewEntityManagerHolder()` is false and `setDefaultReadOnly(true)` never runs.**
   Open-in-view therefore *weakens* `readOnly = true` to flush-suppression only.
   Written up in 14f and 18c as source-read, explicitly NOT claimed as documented.
   Files: `spring-orm/.../orm/jpa/vendor/HibernateJpaDialect.java` (7.0.x, lines 132–190)
   and `spring-orm/.../orm/jpa/JpaTransactionManager.java` (7.0.x, lines 398–413, 762–783).
- Non-read-only branch, for completeness: `if (flushMode.lessThan(FlushMode.COMMIT))
  session.setHibernateFlushMode(FlushMode.AUTO);`
- JDBC half: `prepareConnection` defaults **true** → `DataSourceUtils
  .prepareConnectionForTransaction` → `Connection.setReadOnly(true)`. The javadoc notes
  the behaviour changed in **Spring 4.1**: "propagating the read-only status to the JDBC
  Connection now … This may have the effect that you're running into read-only enforcement
  now where previously write access has accidentally been tolerated."

- **`create` is ambiguous, and the Hibernate source says so** — `@apiNote` on

  `\"create\"` here. The old-school Hibernate configuration interprets this as the action

  hbm2ddl → none, drop, create-only, create(=CREATE, drop+create), create-drop, validate,

  config string selects it.

- UG A.17.18 `hibernate.hbm2ddl.halt_on_error` **Default false** — "When enabled, specifies
