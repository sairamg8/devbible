# Link map · System design · Part 2 (phases 2–3)

Covers every topic row of phases 2 and 3 in `docs/system-design/syllabus/02-the-network-path-and-caching.md`: the request path from DNS to gateway (T02-01 to T02-18) and caching everywhere (T03-01 to T03-16). That is 34 rows. Phase 2 has a written page for every row under `docs/system-design/pages/phase-2-request-path`. Phase 3 has only its overview page so far (`docs/system-design/pages/phase-3-caching/README.md`, which names the sources but covers no single topic), so every phase 3 block is marked not written and its "Our delta" line records what the syllabus row promises.
*read* = I read the passage that supports the claim on the fetched page; *headings only* = fetched at HTTP 200 and not read for the claim. Every link was re-fetched and its claim re-checked on 2026-10-14. Third-party links carry a date only where the page shows one. No `#anchors` are given. Where no good non-official explanation turned up, the block has no "Beyond the docs" line. Official means RFCs, MDN, vendor and project documentation (Cloudflare, AWS, Istio, Kubernetes, Redis, PostgreSQL), the Google SRE book and the Twelve-Factor text. Cloudflare Learning, Toptal, the Dynamo and Facebook memcache PDFs were not usable (403 to the fetcher, or unreadable PDF text), so none is linked. GitHub pages return 403 to plain `curl` but serve normally in a browser; their text was read from the raw README and wiki sources.

## Phase 2 — The request path: DNS to gateway

### T02-01 · From the tap to the first byte — Master · ✅ written `docs/system-design/pages/phase-2-request-path/01-from-the-tap-to-the-first-byte.md`
- **Read this:** [Understanding latency](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Understanding_latency) · MDN · splits a request into DNS resolution, TCP connect, TLS handshake, sending, waiting and receiving, and says the first 14KB of a first request pays for DNS, TCP and TLS setup while later requests on an open connection do not (*read*) · covers our angle: **partial** — no CDN, balancer or gateway hops, and no order-of-magnitude costs per hop · fetched 2026-10-14
- **Also good:** [Timeouts, retries and backoff with jitter](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter) · Amazon Builders' Library · connection setup can count against a timeout, and a 20 ms timeout caused errors after each deploy until connections were opened at process start (*read*) · covers our angle: **partial** — one hop's cost, not the whole path · fetched 2026-10-14
- **Beyond the docs:** [Primer on latency and bandwidth](https://hpbn.co/primer-on-latency-and-bandwidth/) · Ilya Grigorik, High Performance Browser Networking · splits delay into propagation, transmission, processing and queuing, puts propagation within a small factor of the speed of light, and gives last-mile latencies of 10 to 65 ms by access technology (*read*) · why it explains differently: the physics under every hop, with the CDN framed as the way to shorten the distance (*read*) · fetched 2026-10-14
- **Our delta:** names every hop in latency order and the hops that can answer without the rest (edge cache, gateway), and ties the trace to the storefront and to the latency ladder in phase 0.

### T02-02 · Load balancing, layer 4 vs layer 7 — Master · ✅ written `docs/system-design/pages/phase-2-request-path/02-load-balancing-layer-4-vs-layer-7.md`
- **Read this:** [Layer 4 and layer 7 proxy mode](https://www.haproxy.com/blog/layer-4-and-layer-7-proxy-mode) · HAProxy · layer 4 forwards on IP and port without reading the message and suits databases; layer 7 (`mode http`) reads the request and routes on it; the mode is set per section, and a frontend and its backend must share it (*read*) · covers our angle: **partial** — no algorithms, no connection draining · fetched 2026-10-14
- **Also good:** [HTTP load balancing](https://nginx.org/en/docs/http/load_balancing.html) · nginx · round robin by default, `least_conn`, `least_time`, `ip_hash` for sticky sessions, weights, and passive health checks with `max_fails` and `fail_timeout`; active health checks are listed as paid NGINX Plus features (*read*) · covers our angle: **partial** — passive checks only, no draining · fetched 2026-10-14
- **Our delta:** says the algorithm matters less than the health check and the drain, and when a connection-level balancer is enough and when request routing is needed.

### T02-06 · Long-lived connections — Master · ✅ written `docs/system-design/pages/phase-2-request-path/06-long-lived-connections.md`
- **Read this:** [Using server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) · MDN · the browser reconnects by default with a server-set `retry` delay, and without HTTP/2 only about six connections per browser and domain are allowed, shared across tabs (*read*) · covers our angle: **partial** — one-way only, nothing on message routing to a node · fetched 2026-10-14
- **Also good:** [The WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API) · MDN · two-way sessions without polling, but no backpressure, so a fast sender can fill the client's memory (*read*) · covers our angle: **partial** · fetched 2026-10-14
- **Also good:** [RFC 6202](https://www.rfc-editor.org/rfc/rfc6202.html) · IETF · long polling holds a request open and streaming keeps a response open, with the costs of full headers per message and intermediaries that buffer partial responses (*read*) · covers our angle: **partial** — HTTP/1.x era, no fleet concerns · fetched 2026-10-14
- **Beyond the docs:** [Real-time messaging](https://slack.engineering/real-time-messaging/) · Slack engineering, 2023-04-11 · clients hold a websocket to stateful gateway servers in the nearest region, channels map to channel servers by consistent hashing, and a message goes to the channel server, which fans it out to every subscribed gateway (*read*) · why it explains differently: a production answer to "route the message to the node holding the socket" (*read*) · fetched 2026-10-14
- **Our delta:** the fleet problems nobody frames together: a connection lives on one node, a message must find that node, and a deploy disconnects everyone at once (reconnection storm).

### T02-07 · Rate limiting — Master · ✅ written `docs/system-design/pages/phase-2-request-path/07-rate-limiting.md`
- **Read this:** [Scaling your API with rate limiters](https://stripe.com/blog/rate-limiters) · Stripe · four limiters (request rate, concurrent requests, fleet load shedder, worker-utilisation shedder), a token bucket on Redis, and a rule that limiter bugs or Redis outages must fail open (*read*) · covers our angle: **partial** — no sliding window, no 429 contract · fetched 2026-10-14
- **Also good:** [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html) · IETF · section 4 defines 429 Too Many Requests, allows `Retry-After`, and says a 429 response must not be stored by a cache (*read*) · covers our angle: **full** for the 429 contract · fetched 2026-10-14
- **Also good:** [Redis rate limiter](https://redis.io/docs/latest/develop/use-cases/rate-limiter/) · Redis docs · local per-process counters break behind a balancer, so counters live in one shared store; `INCR` with `EXPIRE` for fixed windows and Lua scripts for atomic token buckets (*read*) · covers our angle: **partial** — no placement advice · fetched 2026-10-14
- **Beyond the docs:** [Counting things, a lot of different things](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/) · Cloudflare engineering blog · a sliding-window counter blends the previous and current window (the example gives 49.5), and on 400 million requests it was wrong for 0.003 percent, with two numbers per counter instead of a log (*read*) · why it explains differently: measured accuracy against the exact log (*read*) · fetched 2026-10-14
- **Our delta:** puts all five algorithms side by side with the 429 contract and argues for enforcing in more than one place (edge, gateway, service).

### T02-08 · Timeouts, retries and budgets along the path — Master · ✅ written `docs/system-design/pages/phase-2-request-path/08-timeouts-retries-and-budgets.md`
- **Read this:** [Timeouts, retries and backoff with jitter](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter) · Amazon Builders' Library · retries at every layer multiply (three per layer over five layers is about 243 times the load on the database), jitter spreads retries, and a local token bucket limits retries (*read*) · covers our angle: **full** — timeouts, amplification, jitter and budgets · fetched 2026-10-14
- **Also good:** [Addressing cascading failures](https://sre.google/sre-book/addressing-cascading-failures/) · Google SRE book · naive retries add load to a backend that is already rejecting, so use randomised backoff, a cap per request and a server-wide budget, and propagate deadlines (*read*) · covers our angle: **full** · fetched 2026-10-14
- **Also good:** [Deadlines](https://grpc.io/docs/guides/deadlines/) · gRPC docs · a deadline is a point in time and a timeout is a duration, gRPC sends the remaining duration downstream so clock skew does not matter (*read*) · covers our angle: **partial** — propagation only · fetched 2026-10-14
- **Beyond the docs:** [Designing robust and predictable APIs with idempotency](https://stripe.com/blog/idempotency) · Stripe · idempotency keys let a client retry an ambiguous failure safely, with exponential backoff and jitter (*read*) · why it explains differently: shows the write-side precondition for any retry (*read*) · fetched 2026-10-14
- **Our delta:** the arithmetic of per-hop timeouts that sum past the client's, and the 2 second client timeout that became a 14 second outage at the database.

### T02-09 · DNS as a component — Understand · ✅ written `docs/system-design/pages/phase-2-request-path/09-dns-as-a-component.md`

### T02-10 · TLS termination and where it lives — Understand · ✅ written `docs/system-design/pages/phase-2-request-path/10-tls-termination-and-where-it-lives.md`

- **Also good:** [Configuring HTTPS servers](https://nginx.org/en/docs/http/configuring_https_servers.html) · nginx · the handshake is the most CPU-intensive TLS operation, cut by keep-alive and a shared `ssl_session_cache` (about 4000 sessions per megabyte, 5 minute default timeout) (*read*) · covers our angle: **partial** — the cost and resumption at one terminator, not placement · fetched 2026-10-14

### T02-11 · HTTP/1.1, HTTP/2 and HTTP/3 — Understand · ✅ written `docs/system-design/pages/phase-2-request-path/11-http-1-1-http-2-and-http-3.md`
