**An HTTP cache does not decide anything on its own: the origin declares, per response, how
long the response may be reused, by whom, and what must happen when that time runs out — and the
single most useful thing a senior can say about HTTP caching is that `no-cache` does not mean
"do not cache".** The browser and the CDN are the two caches in the storefront that are
configured entirely by headers the application sends. There is no client library to write and no
cluster to size; there is a small, precisely-defined vocabulary, and the failures are almost
all a misreading of it: a private page stored in a shared cache, a "never cache this" that
caches it, a lifetime so long it cannot be undone, a lifetime so short the origin does all the
work. An interviewer asking about "caching headers" is checking whether you know the vocabulary
well enough to write the header for each class of response without looking it up.

The layers this configures are the browser and the CDN/gateway rows of
[01](01-where-a-cache-can-live.md); the hop mechanics are in
[CDNs](../phase-2-request-path/05-cdns.md). This page is the language.

## Freshness is a computation, not a flag

The protocol defines three terms, and everything else is arithmetic over them.

> *"A 'fresh' response is one whose age has not yet exceeded its freshness lifetime."* — RFC 9111 §4.2.1

> *"Conversely, a 'stale' response is one where it has."* — RFC 9111 §4.2.1

> *"A response's 'freshness lifetime' is the length of time between its generation by the origin server and its expiration time."* — RFC 9111 §4.2.2

> *"A response's 'age' is the time that has passed since it was generated by, or successfully validated with, the origin server."* — RFC 9111 §4.2.3

So a cache holding a response asks one question: **is `age` less than `freshness lifetime`?**
If so it may serve the response without contacting the origin. If not the response is *stale* —
and stale does not mean unusable. A stale response can be revalidated (asked of the origin with a
conditional request, [07c](07c-validators-etag-and-conditional-requests.md)), or served stale
where the origin or client permits it ([07d](07d-vary-stale-directives-and-configuring-the-edge.md)).
Three details hide in the definitions:

- **Age is measured from the origin, not from the cache.** It runs from when the response was
  generated *or successfully validated*, so a response sitting in a CDN for a while and then
  passed to a browser arrives with the time it has already spent. The browser's remaining
  freshness is the lifetime minus that age, not the full lifetime. This is why a chain of HTTP
  caches does not add lifetimes the way hand-built layers do ([01b](01b-stacking-layers-and-the-arithmetic-of-staleness.md)).
- **Validation resets age.** A response successfully revalidated is fresh again from that moment
  — the reason a `304` is useful and the reason a cache can keep serving a large object for a
  long time at the cost of a small request per lifetime.
- **The lifetime is the origin's to declare.** `max-age`, `s-maxage` and the legacy `Expires`
  header are the three ways. When none is present a cache may estimate a lifetime itself
  (heuristic freshness, commonly derived from how long ago `Last-Modified` was). That is a
  fallback, not a design: **a response with a validator and no lifetime is being cached for a
  period the cache chose, not you.** Always send an explicit lifetime or an explicit prohibition.

## Private and shared, again

[01](01-where-a-cache-can-live.md) quoted the two definitions (§1.3). In HTTP terms the browser
cache is the private one and everything between the browser and the origin that stores — CDN,
gateway, corporate proxy — is shared. The directives below split on that axis: some address every
cache, some only shared ones, and one exists to keep a response out of the shared ones while
leaving the browser free to keep it.

## The response directives that matter

Seven directives carry almost every real configuration. Each is quoted for its defining sentence;
below the quotes is what to take from them.

**`max-age`**
> *"The max-age response directive indicates that the response is to be considered stale after its age is greater than the specified number of seconds."* — RFC 9111 §5.2.2.1

**`s-maxage`**
> *"The s-maxage response directive indicates that, for a shared cache, the maximum age specified by this directive overrides the maximum age specified by either the max-age directive or the Expires header field."* — RFC 9111 §5.2.2.10

**`no-cache`**
> *"The no-cache response directive, in its unqualified form (without an argument), indicates that the response MUST NOT be used to satisfy any other request without forwarding it for validation and receiving a successful response."* — RFC 9111 §5.2.2.4

**`no-store`**
> *"The no-store response directive indicates that a cache MUST NOT store any part of either the immediate request or the response and MUST NOT use the response to satisfy any other request."* — RFC 9111 §5.2.2.5

**`private`**
> *"The unqualified private response directive indicates that a shared cache MUST NOT store the response (i.e., the response is intended for a single user)."* — RFC 9111 §5.2.2.7

**`public`**
> *"The public response directive indicates that a cache MAY store the response even if it would otherwise be prohibited, subject to the constraints defined in Section 3."* — RFC 9111 §5.2.2.9

**`must-revalidate`**
> *"The must-revalidate response directive indicates that once the response has become stale, a cache MUST NOT reuse that response to satisfy another request until it has been successfully validated by the origin."* — RFC 9111 §5.2.2.2

What to take from them:

- **`max-age` is for everyone; `s-maxage` is for shared caches only and overrides `max-age`
  there.** That is the pair that lets a response have *one* lifetime for the CDN and a different
  one for the browser: `max-age=0, s-maxage=<seconds>` means "the browser always asks, the CDN
  holds it". The reason to want this is the asymmetry of [01](01-where-a-cache-can-live.md): the
  CDN is a cache you can purge and the browser is one you cannot, so the long lifetime goes on
  the layer you can empty.
- **`no-cache` is "store, but revalidate every time". `no-store` is "do not keep it".** They are
  different instructions with different costs: `no-cache` still saves bandwidth, because the
  revalidation can return a body-less `304`; `no-store` saves nothing and is the only one that
  keeps bytes off disk.
- **`private` keeps a response out of shared caches and lets the browser keep it**; it combines
  with `max-age` (a user's own profile may be reused by their own browser for a minute).
- **`public` overrides a default prohibition.** Responses to requests carrying an `Authorization`
  header are not stored by a shared cache by default; `public` is how a response opts back in.
  That makes it a deliberate act, not a decoration — it belongs on responses you have checked
  contain nothing user-specific.
- **`must-revalidate` withdraws a permission the protocol otherwise gives.** Without it a cache
  may in some circumstances reuse a stale response (for example when it cannot reach the origin).
  With it, a stale entry must be validated or the cache must fail.

### The sentence that prevents the most mistakes

MDN states it directly:

> *"Note that `no-cache` does not mean "don't cache". `no-cache` allows caches to store a response but requires them to revalidate it before reuse. If the sense of "don't cache" that you want is actually "don't store", then `no-store` is the directive to use."* — MDN, `Cache-Control`

And the one that turns a caching bug into a security incident:

> *"You should add the `private` directive for user-personalized content, especially for responses received after login and for sessions managed via cookies. If you forget to add `private` to a response with personalized content, then that response can be stored in a shared cache and end up being reused for multiple users, which can cause personal information to leak."* — MDN, `Cache-Control`

The second sentence has a second half worth saying aloud: the default for a response that sets
no `Cache-Control` is *permission to cache*, with the cache choosing the lifetime. Forgetting is
not neutral. The failure is silent in testing, because a developer talks to the application
without a shared cache in the path.

### Conflicts resolve to the strictest

> *"In theory, if directives are conflicted, the most restrictive directive should be honored. So the example below is basically meaningless because `private`, `no-cache`, `max-age=0` and `must-revalidate` conflict with `no-store`."* — MDN, `Cache-Control`

Note "in theory". A pile of directives ("belt and braces") reads as caution and behaves as
whichever the oldest cache in the path implements first. State the one you mean.

## Legacy headers, estimated lifetimes, and what a response with no header gets

Three things sit around the directives, and an interview answer that names them separates
someone who has read the specification from someone who has copied a header.

- **`Expires`** is the older absolute-date way to give a lifetime. It still works, and the
  `s-maxage` quote above names it: `s-maxage` overrides *"either the max-age directive or the
  Expires header field"*. When both `max-age` and `Expires` are present `max-age` is the one to
  reason about; a fixed date also depends on the origin's and the cache's clocks agreeing, which
  is the reason a relative `max-age` replaced it. Send `max-age`; do not send both and hope.
- **`Pragma: no-cache`** is an HTTP/1.0-era header. I did not fetch its current status in
  the specification, so treat it as legacy that some old intermediaries read and rely on
  `Cache-Control` for everything you mean.
- **Heuristic freshness.** A response with a validator such as `Last-Modified` and no explicit
  lifetime may be given one by the cache, commonly a fraction of how long ago the resource last
  changed. That is mechanism from the specification's allowance for estimating, stated here
  without its exact rule or any figure because the rule was not quoted in the research for this
  page. The design consequence needs no number: **silence is not "do not cache" — it is "cache
  for a period the cache chooses"**, and two caches may choose differently.

The request side has `Cache-Control` too — a client can ask for a response no older than some
age or force revalidation, which is what a browser's "hard reload" does — but the origin's
directives are what the design controls and the part an interview probes. The one request-side
fact worth carrying: a reload button does not behave like a normal navigation, so test lifetime
behaviour with ordinary navigation, not with reload.

## Gotchas

**★ Symptom: a page marked `no-cache` is still being served from a cache.** Cause: `no-cache`
means "store, but revalidate before reuse" — it is permitted to be stored, and a `304` from the
origin lets the cache serve it. The author meant "do not store". Fix: `no-store` for "must not be
kept"; `no-cache` only when revalidation is what you want. The wrong direction is also a cost:
`no-store` on a static shell throws away every cheap `304`.

**★ Symptom: a `Cache-Control` header list with seven directives and unpredictable behaviour.**
Cause: contradictory directives; "the most restrictive directive should be honored" is a *should*
and implementations differ. Fix: send one coherent policy per response class (the table above)
and treat any conflict as a bug.

**Symptom: a response that must never be stored is stored.** Cause: `private` or `no-cache` used
where `no-store` was needed; neither prevents a private cache storing it, and `no-cache` allows
any cache to. Fix: `no-store` for data that must not rest in a browser's disk cache — account
pages, anything with tokens in the body.

**Symptom: a `public` annotation was added "to be safe" and an authenticated response got
shared.** Cause: `public` overrides a default prohibition on storing responses to authenticated
requests; it is permission, not caution. Fix: put `public` only on responses audited as
user-independent.

**Symptom: two caches disagree about how long the same response is fresh.** Cause: no explicit
lifetime was sent, so each estimated its own, or both `Expires` and `max-age` were sent and a
cache read the wrong one. Fix: send an explicit `max-age` (and `s-maxage` where the CDN should
differ) on every cacheable response and drop `Expires`.

**Symptom: a long lifetime was tested with the reload button and appeared not to work.** Cause:
reload sends request-side directives that ask for revalidation or a fresh copy, so it does not
exercise the stored lifetime. Fix: test with normal navigation and with the `Age` header, not
with reload.

## Interview questions

**★ What is the difference between `no-cache` and `no-store`?**
`no-cache` allows a cache to store the response but forbids reusing it without first
revalidating with the origin and getting a successful answer (RFC 9111 §5.2.2.4); the revalidation
can return a `304` with no body, so it still saves bandwidth. `no-store` forbids storing any part
of the request or response at all (§5.2.2.5). MDN's wording is the one to remember: `no-cache`
does not mean "don't cache". Use `no-store` for sensitive data, `no-cache` for content that must
be current but is expensive to resend.

**★ How does a cache decide whether it may serve a response without asking the origin?**
It compares the response's age with its freshness lifetime. Age is the time since the origin
generated or last validated the response, which is why it survives passing through other caches;
the lifetime comes from `max-age` (or `s-maxage` for a shared cache, or `Expires`). Fresh means
age has not exceeded lifetime. When stale the cache revalidates, or serves stale where permitted.
If the response carries no lifetime at all, a cache may estimate one, which is why an explicit
header is always better than silence.

**What does `public` do, and when is it a mistake?**
It lets a cache store a response it would otherwise not — notably responses to authenticated
requests. It is permission, not a safety label, so it belongs only on responses audited to
contain nothing user-specific. On a personalised response it is the quickest route to a shared
cache serving one user's data to another.

**Why not just set `no-store` on everything?**
It discards the cheapest savings: the browser's cache for hashed assets and the `304`
revalidation of a large HTML shell or JSON document. The origin would serve every byte on every
view, and the CDN would hold nothing. The headers should follow the class of response, not the
caution of the author.

**Is a response with no `Cache-Control` header uncached?**
No, and this is the common wrong assumption. The absence of a lifetime does not forbid storing;
a cache may estimate a lifetime itself, commonly from how long ago the resource last changed,
and a response to an ordinary anonymous `GET` is eligible. Two caches can estimate differently.
The rule for the storefront is that every response class gets an explicit header — a lifetime
or a prohibition — so the policy is written rather than inferred.
