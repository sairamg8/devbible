**Every cache holds a copy whose source can change, and invalidation is the set of decisions about how a change reaches the copy: the copy expires on its own (time-to-live), it is told (event-driven), or it is never edited at all because the name changes instead (versioned keys).** The famous quip that there are only two hard problems, one of them cache invalidation, is true for a precise reason: the cache is a second copy of the truth with no transaction shared with the first, so any scheme is a bet about which of the failure interleavings you can tolerate. The interviewer is not asking for the quip. They are asking whether you can state, for a given piece of data, the **maximum time a reader can see a wrong value**, name the mechanism that enforces that bound, and say what happens when that mechanism itself fails.

This chunk is the two basic mechanisms, the question of what an invalidation must reach, and the arithmetic of staleness. Versioned keys and tag-based purge are in [03b](03b-versioned-keys-and-tag-purge.md); the storefront's price (hard) versus description (easy), outbox-driven invalidation and version-checked writes are in [03c](03c-price-versus-description-the-hard-case.md). The population strategies whose write paths do the invalidating are in [02](02-the-four-strategies.md).

## Freshness is a bound, and the protocol already says so

HTTP caching has a vocabulary for this that applies to any cache. RFC 9111 defines it in four sentences:

> *"A 'fresh' response is one whose age has not yet exceeded its freshness lifetime."* — §4.2.1
>
> *"Conversely, a 'stale' response is one where it has."* — §4.2.1
>
> *"A response's 'freshness lifetime' is the length of time between its generation by the origin server and its expiration time."* — §4.2.2
>
> *"A response's 'age' is the time that has passed since it was generated by, or successfully validated with, the origin server."* — §4.2.3

A TTL is a freshness lifetime. The thing to carry over to application caches is that **age is measured from generation at the source, not from when this cache stored it.** When caches are stacked — browser, CDN, gateway, Redis, an in-process map — each layer's TTL starts counting at different moments, and the worst-case staleness a user can see is not the largest TTL but the sum of the ones that each can add: an object that the CDN fetched one second before its TTL ended from a Redis entry one second before *its* TTL ended is as old as the two TTLs together. The arithmetic of layered staleness belongs to **01 Where a cache can live** *(not written yet)*; here the point is that a TTL is a *bound*, and a bound only means something once you add the layers below it.

## Mechanism 1 — expire by time

Set a TTL on every cached value and do nothing else. The value is wrong for at most the TTL after the source changes. No writer needs to know the cache exists.

```js
await redis.set(`product:${id}`, JSON.stringify(row), 'EX', 300);   // wrong for at most 300 s
```

What this buys:

- **A guarantee that does not depend on any code path being correct.** A migration, an admin SQL console, a different service, a restored backup — all change the source, and the cache heals on its own. This is why a TTL belongs on every key, including the ones with event-driven invalidation: it is the repair mechanism for the invalidations that did not happen.
- **Simplicity and decoupling.** The write path does not import the cache client.
- **Bounded memory.** An expired key can be reclaimed, so a TTL is also a form of garbage collection for data that stopped being read.

What it costs:

- **Wrongness for the whole TTL is guaranteed after every change**, not merely possible. If a price changes at t = 1 s and the TTL is 300 s, every reader for 299 s sees the old price.
- **Synchronised expiry.** Keys written together expire together. A page of a hundred products populated by one request expires in one instant and sends a hundred misses at once. Jitter on the TTL (a random addition per key) spreads this; it is part of the stampede topic (**04 Stampede and thundering herd** *(not written yet)*).
- **Picking the number is a guess dressed as a decision.** A short TTL reduces staleness and raises miss rate and database load; a long TTL does the opposite. The right TTL is *derived from a requirement* — "a price may be wrong for at most N seconds" — and only then checked against the load it implies. No page can give you the number; what can be said is that the requirement exists per data type and that the TTL is its upper bound.

Redis note: a TTL is also the knob the `volatile-*` eviction policies key off. Redis documents that *"The `volatile-xxx` policies behave like `noeviction` if no keys have an associated expiration."* — a cache configured with a volatile policy whose writers forgot to set TTLs will stop accepting writes when full instead of evicting.

## Mechanism 2 — invalidate on change

The writer, or something observing the writer, removes or replaces the affected cache entries when the source changes. Wrongness lasts only for the propagation delay.

The HTTP specification contains exactly one guarantee of this kind and it is worth knowing because it shows both the power and the limit of the idea:

> *"A cache MUST invalidate the target URI when it receives a non-error status code in response to an unsafe request method (including methods whose safety is unknown)."* — RFC 9111 §4.4.2

A cache that sees a `POST`, `PUT` or `DELETE` to `/products/42` succeed must drop its stored response for `/products/42`. The limit is in the words *"the target URI"*: only the URI of the request, and only caches that actually saw the request. The CDN edge in Mumbai never saw the `PUT` that went through a different edge, and `/products` (the listing that contains product 42) is a different URI. The protocol's own rule invalidates the one entry that is obviously affected and leaves every derived entry to someone else. Application-level invalidation has exactly this shape, and the hard part is always the derived entries.

### What an invalidation must reach

Changing one product row can make wrong:

| Cached thing | Key | Reached by deleting `product:42`? |
|---|---|---|
| the product detail | `product:42` | yes |
| the category listing page that includes it | `list:shoes:page1` | no |
| the search index document | search engine | no |
| the "also bought" recommendation card for product 17 that shows its title | `reco:17` | no |
| the CDN copy of `/products/42` | edge cache | no |
| the browser's copy | each user's device | no, and cannot be reached |
| a materialised aggregate: category product count | `count:shoes` | no |

Each row is a different invalidation problem. The listing page depends on a *set* of products and the cache does not know the set. The browser's copy cannot be told anything and can only expire. This is the real content of the invalidation topic: **the dependency graph between the source and the cached derivations, and which edges of it you track**. The three honest strategies for a derived entry are (a) track the dependency explicitly (tags, [03b](03b-versioned-keys-and-tag-purge.md)), (b) make the derived entry short-lived enough that tracking is unnecessary (a TTL, accepting the bound), or (c) don't cache the derivation, only its parts, and assemble at read time.

### Event-driven invalidation, three ways to deliver the event

1. **The writer does it inline** after committing: `await pg.query(UPDATE…); await redis.del(key)`. Simple, correct in the common case, and wrong when the process dies between the two statements, when another service writes the table, or when the delete itself fails.
2. **A message on a bus** (Redis pub/sub, a queue, Kafka): the writer publishes "product 42 changed" and invalidators subscribe. This decouples writers from caches and allows many caches (each region, each service) to react, at the cost of a new component, delivery semantics, and an ordering story. Redis pub/sub is fire-and-forget: a subscriber that is disconnected misses the message permanently. If invalidation uses it, a TTL must be the safety net and reconnection must flush or revalidate.
3. **Derive the event from the database's own change log** (change data capture, or an outbox table written in the same transaction as the data). No writer can forget because the writer is not involved; every change to the table produces the event. This is the strongest option and has the most moving parts. It is worked in [03c](03c-price-versus-description-the-hard-case.md).

## Choosing: the decision is a requirement, not a preference

State the requirement as a sentence: *"A reader may see a value at most N seconds after it changed."* Then:

- N is a minute or more and writes are infrequent: **TTL only.** Simple, self-healing. The product description and the review list fall here.
- N is seconds, or a human waits to see their own change: **TTL plus event-driven delete** (the TTL is the backstop). The price falls here; so does a user's own profile after they edit it.
- N is zero — a reader must never see a wrong value: **do not cache it**, or cache a value that cannot be wrong (an immutable object under a versioned key) and fetch the *pointer* to the current version from the source of truth. Stock at checkout and payment status fall here.

The tell of a weak answer is "we invalidate on write" without a TTL (nothing repairs the missed invalidation), or "we use a 60-second TTL" without saying what requirement 60 seconds satisfies.

### Serve stale on purpose

Sometimes the right invalidation is to keep serving the old value while a new one is fetched. RFC 5861 gives the protocol form: *"caches MAY serve the response in which it appears after it becomes stale, up to the indicated number of seconds."* — and the constraint: *"If delta-seconds passes without the cached entity being revalidated, it SHOULD NOT continue to be served stale, absent other information."* The application-cache equivalent is a soft TTL (when to refresh) and a hard TTL (when to stop serving). Between them the entry is served and a single refresh runs in the background, so no reader waits and the source sees one request. The general RFC rule that bounds this: *"A cache MUST NOT generate a stale response unless it is disconnected or doing so is explicitly permitted by the client or origin server."* — §4.2.4.3. The explicit permission is the directive; in an application cache the permission is your own code, and the deliberate choice should be visible in it.

## A deletion is a write, and it can be lost

An invalidation message is itself a distributed operation that can fail. The delete may time out and be retried. The message may be dropped. The invalidator may be down. The Redis node may fail over to a replica that had not received the delete. Treat invalidation as a reliable-delivery problem — at-least-once with an idempotent handler — or accept the TTL as the bound on what a lost invalidation costs. Both are legitimate; the unforced error is a design that assumes the delete always lands.

Idempotence helps here: `DEL key` is idempotent, so retrying an invalidation until it is acknowledged is safe, and "at-least-once" is enough. What is not safe is invalidation that *recomputes and writes* with a stale input, because a retried or reordered recompute can write an older value after a newer one. Deletes commute; writes of derived values do not.

## Gotchas

**★ Symptom: a value stays wrong long after the TTL should have expired it.** Cause: the TTL is per layer, not per system — the CDN, a gateway cache and the browser each held the object for their own freshness lifetime starting at different moments, and RFC 9111 measures age from generation at the origin, so a copy can arrive already partly aged, or the intermediary refreshed it. Fix: compute the worst case as the sum across layers, set the browser layer short or `no-cache`/revalidate, and invalidate the layers you can reach.

**★ Symptom: "we invalidate on write" and a stale value appears anyway, weeks after launch.** Cause: some writer does not invalidate — a batch job, a second service, a hand-run SQL fix — and the key has no TTL, so nothing ever corrects it. Fix: a TTL on every cached key regardless of event-driven invalidation, and an invalidation path driven by the database's change log rather than by each writer's discipline.

**★ Symptom: the product detail updates immediately and the category page still shows the old price.** Cause: the delete targeted the entity's key; the listing is a derived entry with a different key that nobody invalidated. Fix: enumerate the derived entries per source entity, then invalidate by tag, bump a version, or give the derived entry a TTL and accept the bound ([03b](03b-versioned-keys-and-tag-purge.md)).

**★ Symptom: invalidations are lost during a Redis failover or subscriber restart.** Cause: pub/sub delivers only to currently connected subscribers, and a replica promoted during failover may not have applied the last deletes. Fix: do not rely on a fire-and-forget bus alone — use a durable queue or the change log, retry until acknowledged, flush or revalidate local caches on reconnect, and keep the TTL as the bound.

**★ Symptom: one TTL value is copied to every cache in the system.** Cause: the TTL was chosen as a number rather than derived from a requirement per data type. Fix: write the staleness requirement beside the TTL constant (`PRICE_MAX_STALE_S`) and review it with the owner of the data.

**Symptom: after a bulk import or deploy, a hundred keys expire in the same second and the database spikes.** Cause: keys populated together share a TTL and expire together. Fix: add random jitter to each TTL; see **04 Stampede and thundering herd** *(not written yet)*.

**Symptom: the browser shows the old version after a purge.** Cause: a purge reaches caches you operate; it cannot reach a private cache on the user's device, which only expires. Fix: do not give mutable responses a long browser lifetime; use revalidation (MDN: *"`no-cache` allows caches to store a response but requires them to revalidate it before reuse."*) or change the URL ([03b](03b-versioned-keys-and-tag-purge.md)).

**Symptom: invalidation by recompute writes an old value over a newer one.** Cause: the handler recomputed from a stale input or ran out of order and *wrote* the result. Fix: invalidate by deleting (commutative), or make the write carry a version and refuse to go backwards ([03c](03c-price-versus-description-the-hard-case.md)).

**Symptom: the cache is invalidated before the transaction commits and the stale value returns.** Cause: a concurrent reader repopulated from the pre-commit database state. Fix: invalidate after commit — see the ordering rule in [02](02-the-four-strategies.md).

## Interview questions

**★ How do you keep a cache consistent with its database?**
You do not make it consistent; you bound how inconsistent it can be and say what the bound is. Every cached value gets a TTL as the upper bound. Where the requirement is tighter than the TTL allows, the write path also invalidates after commit, preferably driven by the database's change log or an outbox so no writer can forget. Where the requirement is zero staleness, the value is not cached or is an immutable object found through a pointer read from the source. The answer should name the maximum staleness per data type.

**★ TTL or event-driven invalidation?**
It is not either-or. A TTL is the guarantee that survives bugs, missing writers and lost messages; events make staleness short in the common case. The deciding factor is the staleness requirement: if the business can tolerate minutes, a TTL alone is the cheapest correct design; if it cannot, add events and keep the TTL as the safety net. Events without a TTL is the combination to push back on.

**★ A product's price changed but the category page shows the old price. Why?**
The write invalidated the entity's key and not the entries derived from it. The listing page depends on a set of products and the cache has no record of which. Options are to tag the page with the products (or categories) it contains and purge by tag, to bump a version in the listing's key so old entries become unreachable, to give the listing a short TTL and accept its bound, or to avoid caching the assembled page and cache the parts.

**★ What does RFC 9111 guarantee about invalidation?**
One thing: a cache must invalidate the target URI when it receives a non-error response to an unsafe method. It does not reach other URIs that embed the data, other caches that did not see the request, or private caches in browsers. Everything else — tags, versions, purges, TTLs — is application design, which is why invalidation is a design problem rather than a protocol feature.

**★ How do you invalidate when many services or regions each have a cache?**
Publish a change event from a durable source — an outbox row written in the same transaction as the data, or the change log — and have each cache's subscriber delete the affected keys. Delivery is at-least-once, the handler is idempotent (deletes are), and each cache keeps a TTL to bound the cost of a lost event. Fire-and-forget pub/sub on its own loses messages to disconnected subscribers.

**Why delete rather than recompute in the invalidation handler?**
Deleting is idempotent and commutative: any order, any number of retries, same result. Recomputing and writing is neither, since a delayed or retried recompute can overwrite a newer value with an older one. Delete, let the next read load, and use versioned writes if you must write.

**What should the TTL be?**
Derived from a statement of how long a wrong value may be served, per data type, then checked against the load a short TTL puts on the source. A fixed number across a system is a sign the question was not asked. The answer is not a figure; it is the requirement, the derivation, and the load check.

**How is `stale-while-revalidate` related to application cache invalidation?**
It is the same technique at the protocol level: serve the entry past its freshness time for a bounded interval while one refresh runs. RFC 5861 words the permission as `MAY` and the bound as `SHOULD NOT` continue past it. An application cache does it with a soft TTL for refresh and a hard TTL for removal, so users never wait for the refresh and the source sees one request.
