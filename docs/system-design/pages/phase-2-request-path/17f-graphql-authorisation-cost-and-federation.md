**Once a graph is at the edge, three of the things [03](03-reverse-proxies-and-api-gateways.md)'s
gateway was doing for you stop being possible there, and one thing you thought you had solved
comes back generated by the client instead of by your code.** Authorisation was a property of a
route, and a graph has no routes: one query can reach a customer's email address through three
hops of an object graph, so the check moves into the resolvers, per field and per object instance,
and the gateway can authenticate but can no longer authorise. Rate limiting counted requests, and
a graph's requests are not comparable: a short query can request a deep traversal or a very large
list, so the limiter must price the query before executing it. And the resolver N+1 is
[17c](17c-the-fan-out-n-plus-1.md)'s fan-out amplification arriving from a direction you cannot
review, because the shape that causes it is written by a client. This page is those three, plus
the ownership question a shared schema raises and the federated answer to it.

## Authorisation moves per field, and the gateway cannot do it

With fixed endpoints, the route is the unit of authorisation: the gateway can say "this path
requires this role", and it is checked once, at the edge, before any service is called. A graph
has one path. The same query language that lets a client ask for a product's title lets it walk
from an order to its customer to that customer's email, and whether that is allowed depends on
*which* customer and *who is asking* — a decision about an object instance, not about a URL.

So the work splits, and saying the split is the answer in the round:

| Concern | Where it stays | Where it moves |
|---|---|---|
| **Authentication** — is this a valid identity? | the shared policy edge ([03](03-reverse-proxies-and-api-gateways.md)): token verified locally against a cached key, identity forwarded | unchanged |
| **Coarse admission** — may this client type reach the graph at all? | the edge | unchanged |
| **Authorisation** — may *this* identity see *this* field of *this* object? | — | the resolvers, or better, the domain layer they call |

Three practical rules follow. The identity travels in the execution context and every resolver
that returns something sensitive consults it — a field-level check, not a query-level one. The
check belongs in the *business layer* the resolver calls rather than in the resolver itself,
because the same rule must hold for every entry point into that data, including the REST routes
you kept ([17e](17e-graphql-at-the-edge.md)) and any internal caller. And the batch loader of
[17c](17c-the-fan-out-n-plus-1.md) becomes a security-relevant object: its memo is filled under
one identity's authorisation, so it must be constructed per request — a process-wide loader in a
graph server is the cross-user leak with a query language attached.

## The limiter has to count cost, not requests

[07](07-rate-limiting.md)'s counters assume requests are roughly comparable. In a graph they are
not: one small request can ask for a deeply nested traversal, or a list with a very large page
size, or the same expensive field a hundred times under different aliases. A request-count limit
therefore prices a cheap query and an expensive one identically, and the expensive one is the
denial of service.

The controls, and each is doing a different job:

- **Depth limit.** Reject queries nested beyond a fixed depth. Cheap, static, and it stops the
  obvious recursive traversal — a `user { friends { friends { … } } }` shape — before execution.
- **Complexity or node cost, computed before execution.** Give every field a cost, multiply
  list fields by their requested page size, sum, and reject above a threshold with the 429
  contract of [07](07-rate-limiting.md). This is the control that actually generalises, because it
  prices the query rather than pattern-matching it.
- **Caps on list arguments.** A maximum page size enforced by the schema and the resolver, so
  `first: 100000` is a validation error rather than a very long query.
- **Alias and field-count limits.** Aliases let one request repeat the same expensive field many
  times under different names; the cost calculation must count aliased selections, not distinct
  field names.
- **A cost budget per identity per window**, not a request budget — the same token-bucket idea as
  [07](07-rate-limiting.md), with cost as the unit being spent.
- **A hard execution timeout**, so that a query which passed the static checks and still runs long
  is cut off; this is [08](08-timeouts-retries-and-budgets.md)'s deadline, and it must be
  propagated to the upstream calls the resolvers make.
- **Introspection gated in production.** Publishing the full schema to anonymous callers hands an
  attacker the map; it is normal to require authentication for it or disable it outside
  development. Stated as common practice, not as a specification requirement.
- **A persisted-query allowlist**, which is the strongest control of all because it removes
  arbitrary queries entirely — the reason [17e](17e-graphql-at-the-edge.md) treats persisted
  queries as three mechanisms in one.

## The resolver N+1

A list resolver returns fifty products; the `price` field's resolver runs once per product; fifty
upstream calls. This is exactly [17c](17c-the-fan-out-n-plus-1.md)'s fan-out N+1, with one
difference that matters: **the shape that causes it was written by a client, not by you.** A field
that has always been cheap becomes expensive the day a client asks for it inside a list, and no
code review of yours sees that change.

The standard answer is the same per-request batch loader, applied at the resolver boundary:

```text
without batching                          with a per-request loader
  products(limit: 50)      1 call           products(limit: 50)              1 call
  └─ price   × 50         50 calls          └─ price   → keys collected      1 batched call
  └─ seller  × 50         50 calls          └─ seller  → deduped to 7 keys   1 batched call
  ─────────────────────────────────         ─────────────────────────────────
  101 upstream calls                        3 upstream calls
```

Three things go with it. The loader is **per request**, for the authorisation reason above as much
as the correctness one. The upstream services need the **batch endpoints** of
[17c](17c-the-fan-out-n-plus-1.md), or the loader has nowhere to send its collected keys. And the
metric is the same one: **upstream calls per client query**, on the dashboard, because this
regression arrives without an error and now arrives from outside your repository.

## Schema ownership, and federation as the direction

One schema across many teams becomes the file everybody edits and nobody owns — which is
[17](17-gateway-patterns.md)'s third pressure, the single gateway's ownership problem, restored
with a type system on top of it. The direction the industry takes is **federation**: each team
owns a *subgraph* — its own types, its own resolvers, its own deploy — and a composing router
plans an incoming query across subgraphs, calls each one, and stitches the result.

What that buys is the ownership: the catalogue team changes catalogue types without a shared file
and without another team's review. What it costs, and this is the part that gets skipped:

- **A router on every request**, which is one more hop on the failure walk and one more box that
  must be replicated, drained and kept fast ([03](03-reverse-proxies-and-api-gateways.md)).
- **Cross-subgraph joins are fan-outs by another name.** A query that walks from an order to a
  product to a seller is a multi-subgraph plan with all of
  [17b](17b-aggregation-and-partial-failure.md)'s properties — a shared deadline, a slowest leg
  and a partial-failure decision — now produced by a planner rather than by code you wrote.
- **Composition checks in CI**, so one team cannot merge a subgraph change that breaks the
  composed graph. Without them, federation converts a shared file into a shared runtime failure.
- **Deprecation instead of removal.** You cannot make every client upgrade, so fields are marked
  deprecated and retired on evidence that nobody requests them — the same discipline
  [17](17-gateway-patterns.md) gave the partner API, applied per field.

## The storefront

```text
authorisation in the graph
  edge (03): token verified, identity forwarded — authentication only
  resolver:  order.customer.email checked against the caller's identity PER OBJECT, in the
             domain layer, so the REST routes we kept enforce the same rule
  loaders:   built per request; a process-wide loader here would leak across customers

cost limiting on /graphql
  persisted queries only in production → the allowlist IS the primary control
  plus, as defence in depth: max depth 8 · cost budget per user per minute · first: capped at 100
       aliased selections counted · execution deadline 2 s, propagated to upstream calls
  over budget → 429 + Retry-After (07, RFC 6585 §4); over depth/cost statically → 4xx before execution
  introspection: authenticated only outside development

the resolver N+1 we expect
  the app adds sellerRating to the 50-item list row → 50 seller calls unless the loader dedupes
  metric: upstream calls per client query, alerting on change — the code change was in the APP

ownership
  today: one schema, owned by the platform team, small enough that this works
  the trigger to federate: two teams blocked on each other's schema reviews in the same month
  the price we would then accept: a router hop, composition checks in CI, deprecation-only removals
```

The ownership block is the honest version of the federation conversation: it is a
reorganisation with a runtime cost, adopted when the review queue proves it is needed, not
because the graph is large.

## Gotchas

**★ Symptom: authorisation checked at the gateway, and a nested field returned another customer's
email.** Cause: a route-based check applied to an API with no routes. Fix: authorise per field and
per object instance in the domain layer the resolvers call, carrying the identity in the execution
context; the edge keeps authentication and coarse admission, and gives up authorisation.

**★ Symptom: one crafted query pinned the graph server's CPU.** Cause: a request-count limiter
pricing every query the same. Fix: cost computed before execution — per-field costs multiplied by
requested page sizes, aliased selections counted — with a depth limit, capped list arguments, a
cost budget per identity per window, a hard execution deadline, and 429 with `Retry-After` when
the budget is spent ([07](07-rate-limiting.md)).

**★ Symptom: the app added one field to a list and the seller service fell over.** Cause: a
resolver running once per parent — the N+1, generated by a query written outside your repository.
Fix: per-request batch loaders at the resolver boundary, batch endpoints upstream
([17c](17c-the-fan-out-n-plus-1.md)), and *upstream calls per client query* on the dashboard with
an alert on change.

**★ Symptom: the batch loader in the graph server leaked one customer's data to another.** Cause:
a loader constructed once per process, memoising values fetched under a different identity's
authorisation. Fix: construct loaders inside the request and let them die with it; in a graph this
is a security control, not only a performance one.

**★ Symptom: a field was removed from the schema and an app version already in the store broke.**
Cause: schema changes treated like server-side refactors. Fix: deprecate rather than remove, retire
on telemetry showing nobody requests the field, and — with persisted queries — check the registry
for hashes that still reference it before deleting anything.

**Symptom: introspection enabled in production and anonymous.** Cause: a development default left
on. Fix: require authentication for introspection or disable it outside development; it is the
map, and there is no reason to publish it to anonymous callers.

**Symptom: federation adopted, and one team's subgraph change broke the composed graph at
runtime.** Cause: no composition check before merge. Fix: compose the whole graph in CI on every
subgraph change and fail the build; federation without composition checks converts a shared file
into a shared outage.

**Symptom: a federated query is slower than the same data fetched by four REST calls.** Cause: a
cross-subgraph plan is a fan-out with a router hop in front of it, and nobody applied
[17b](17b-aggregation-and-partial-failure.md)'s rules to it. Fix: treat the plan as a fan-out —
required versus degradable fields, per-leg timeouts inside one propagated deadline, and the
router's own latency measured separately from the subgraphs'.

**Symptom: every team edits one schema file and reviews queue behind the platform team.** Cause:
the single-gateway ownership problem, restored with types. Fix: subgraphs with clear type
ownership and composition checks — or, if that is too much machinery for the size of the estate,
one small schema genuinely owned by one team; the failure is a shared file with no owner.

## Interview questions

**★ Where does authorisation live in a GraphQL API, and why can't the gateway do it?**
It lives per field and per object instance, in the business layer the resolvers call, with the
identity carried through the execution context. The gateway cannot do it because its unit of
authorisation was the route, and a graph has one route: the same query language that fetches a
product title can walk from an order to a customer to that customer's email, and whether that is
permitted depends on which object and which caller rather than on the path. So the edge keeps
authentication — verifying the token against a cached key and forwarding the identity — and coarse
admission, and hands authorisation to the domain. Putting the check in the domain layer rather
than the resolver matters too, because the REST routes you kept and any internal caller must
enforce the same rule.

**★ How do you rate-limit a GraphQL endpoint?**
By cost rather than by request count, because requests are not comparable: one small query can
request a deep traversal, a huge page size, or the same expensive field a hundred times under
aliases. Compute a cost before execution — a per-field cost multiplied by requested list sizes,
counting aliased selections — and reject above a threshold; cap list arguments in the schema; keep
a static depth limit for the obvious recursive shapes; spend from a per-identity cost budget per
window and answer 429 with `Retry-After` when it is exhausted; enforce a hard execution deadline
propagated to upstream calls; and gate introspection outside development. The strongest control is
a persisted-query allowlist, because it removes arbitrary queries entirely — which is why persisted
queries are worth adopting for three reasons at once.

**★ What is the resolver N+1, and why is it harder to prevent than the one in your own code?**
A list resolver returns fifty objects and a field resolver runs once per object, so one query
becomes fifty-one upstream calls — the same amplification as an aggregating gateway. It is harder
because the shape that triggers it is written by a client: a field that has always been cheap
becomes expensive the day someone asks for it inside a list, and that change never appears in your
code review. The fixes are a per-request batch loader at the resolver boundary that collects keys
within a tick and deduplicates them, batch endpoints upstream so the loader has somewhere to send
them, and a metric — upstream calls per client query, alerting on change — because this regression
arrives silently and from outside your repository.

**★ When does federation earn its cost?**
When schema ownership is the binding constraint: several teams own different parts of the domain,
clients genuinely need one graph, and the evidence is that teams are blocked on each other's schema
reviews. Then each team owns a subgraph it deploys independently and a router plans queries across
them. The costs to name in the same breath are a router hop on every request that must be
replicated and kept fast, cross-subgraph joins that are fan-outs with a shared deadline and a
slowest leg, composition checks in CI so one team cannot break the composed graph at runtime, and
deprecation-only field removal because clients cannot be forced to upgrade. Federation is a
reorganisation with a runtime price, not a scaling technique.

**A graph is being proposed for your storefront. What do you insist on before agreeing?**
Five things, and each maps to a cost that is otherwise discovered in production. Persisted queries
in production, which restore edge cacheability and safe-method retry and act as the allowlist
against expensive queries. Cost-based limiting with a depth limit, capped list arguments and an
execution deadline. Per-field authorisation in the domain layer, with the loaders built per
request. Error-rate alerting computed from the response body, because the HTTP status will be
`200` and the existing dashboards will go quiet. And a named owner for the schema, with the
federation trigger written down — because "who may change this type" is the question that decides
whether the graph is an asset or the next shared file nobody owns.
