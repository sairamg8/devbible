**The data model is derived, not drawn. Before naming an entity, list how each journey from the
functional requirements touches data — reads or writes, which thing, by what key, how often, and
with what consistency — and the entities, their keys, the indexes and the choice of primary
store follow from that list.** A model drawn from habit — a normalised schema because that is
what a relational database wants, or a document per order because that is what a document store
wants — is the model that gets redrawn at scale, because it was never checked against the
queries. The access-pattern table takes three minutes and answers the store question the
interviewer will ask ("why PostgreSQL?") with a reason instead of a preference: the order
journey needs a multi-row transaction and a unique constraint on the idempotency key, and that
is what a relational store is for; the cart needs a fast read-modify-write by user with no joins,
and that is what a key-value store is for.

## The access-pattern table

One row per read or write each journey performs, in the order the journey performs them:

| Journey | Operation | Entity | Key | Frequency (from [03](03-back-of-the-envelope-estimation.md)) | Consistency ([02](02-non-functional-requirements.md)) |
|---|---|---|---|---|---|
| view cart | read | cart | userId | every page view · ~1,000/s peak | eventual is fine |
| place order | read | cart | userId | per checkout | — |
| place order | check | idempotency key | (userId, key) | per checkout | must be exact — unique |
| place order | write | inventory (decrement) | productId | per line item · hot on the sale item | never oversell — single writer, conditional |
| place order | write | order + order items | orderId | per checkout · ~50/s peak | durable, atomic with the decrement |
| place order | write | outbox event | orderId | per checkout | same transaction as the order |
| provider callback | write | order.status, payment | providerPaymentId → orderId | per checkout, later | idempotent on providerPaymentId |
| order status | read | order | orderId | a few per order | read-your-writes for the buyer |
| order history | read | orders by user, newest first | (userId, createdAt desc) | per visit · paginated | may lag slightly |
| admin stock | write | inventory (adjust) | productId, version | rare | conflicts with the sale's decrement — versioned |
| browse catalogue | read | product | productId; by category; by search | dominant read · cached | stale by minutes is fine |

Every later decision reads off this table. The keys column gives the primary keys and the
indexes. The frequency column says which rows need a cache and which a single-writer path. The
consistency column says which entities must live in the same transaction and which may live in
a different store entirely.

## Entities and keys, derived

From the table: **cart** (by user, mutable, disposable), **product** (by id, read-heavy),
**inventory** (by product, contended, must be exact), **order** and **order item** (by order,
durable, written once then transitioned), **idempotency record** (by principal and key),
**payment** (by provider id, arriving asynchronously), **outbox event** (by order, drained by a
worker). The keys:

- **Order id** — generated by the service, not the database, so it can be returned before the
  commit and used as the outbox event's key. A time-ordered identifier (a UUID variant with a
  time prefix, or a ticket-server integer) keeps the primary-key index writing sequentially,
  which matters at the write peak; a random UUID scatters inserts across the index. Say the
  choice; phase 7 covers the options.
- **Inventory** keyed by `productId` with a `version` column, because it has two writers (the
  sale and the admin) and the decrement must be conditional.
- **Idempotency** keyed by `(userId, key)` with a unique index — the constraint is the
  correctness guarantee, per [05](05-the-api-sketch.md).
- **Order history** indexed on `(userId, createdAt DESC, id DESC)` — the cursor's sort key,
  so page two is a range scan.

## The schema, for the relational part

```sql
CREATE TABLE inventory (
  product_id   UUID PRIMARY KEY,
  available    INTEGER NOT NULL CHECK (available >= 0),   -- the invariant, enforced by the store
  version      BIGINT  NOT NULL DEFAULT 0                  -- optimistic concurrency for the admin path
);

CREATE TABLE orders (
  id               UUID PRIMARY KEY,                       -- time-ordered, generated by the service
  user_id          UUID NOT NULL,
  status           TEXT NOT NULL CHECK (status IN ('PENDING_PAYMENT','PAID','PAYMENT_FAILED','CANCELLED')),
  total_cents      BIGINT NOT NULL,
  idempotency_key  TEXT NOT NULL,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, idempotency_key)                        -- the retry guard
);
CREATE INDEX orders_by_user ON orders (user_id, created_at DESC, id DESC);  -- the history cursor

CREATE TABLE order_items (
  order_id         UUID NOT NULL REFERENCES orders(id),
  product_id       UUID NOT NULL,
  qty              INTEGER NOT NULL CHECK (qty > 0),
  unit_price_cents BIGINT NOT NULL,
  PRIMARY KEY (order_id, product_id)
);

CREATE TABLE payments (
  provider_payment_id TEXT PRIMARY KEY,                    -- idempotency for the callback
  order_id            UUID NOT NULL REFERENCES orders(id),
  outcome             TEXT NOT NULL CHECK (outcome IN ('SUCCEEDED','FAILED')),
  amount_cents        BIGINT NOT NULL,
  received_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE outbox (
  id          BIGSERIAL PRIMARY KEY,
  aggregate   TEXT NOT NULL,       -- 'order'
  aggregate_id UUID NOT NULL,
  event_type  TEXT NOT NULL,       -- 'ORDER_PLACED'
  payload     JSONB NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  published_at TIMESTAMPTZ
);
```

Three things the schema says that a diagram cannot: the `CHECK (available >= 0)` puts the
never-oversell invariant in the store, so a bug in application code cannot violate it; the
unique `(user_id, idempotency_key)` is the retry guard; and the outbox row is a table in the
same database so it can be written in the same transaction as the order. The cart and the
product catalogue are deliberately *not* here — see the next section.

## Choosing the store from the patterns

The table sorts entities into stores by what they need, not by what the team already runs:

| Entities | What the patterns need | Store family | Why |
|---|---|---|---|
| order, order items, inventory, idempotency, payments, outbox | multi-row atomic writes; unique constraints; a check constraint; range scans by user | **relational** (PostgreSQL) | the transaction and the constraints *are* the correctness; nothing else gives them as cheaply |
| cart | read-modify-write by one key; no joins; disposable; high read rate | **key-value / cache** (Redis) | one round trip, no schema, eventual is fine, loss is survivable |
| product catalogue for browsing | read-heavy by id and by category; stale by minutes is fine | relational primary with a **cache** in front | the source of truth stays relational; the read path is served from memory |
| product search | text query, ranking, facets | **search index** fed from the primary | an inverted index is a different structure, kept in sync asynchronously |
| analytics, page views | append-only, aggregated later, best-effort | **append-only sink** | never on the write path; rolled up |

The senior sentence is "orders are relational because the checkout is a transaction with three
constraints in it; the cart is in Redis because it is a single-key read-modify-write that may
be lost." The junior sentence is "we'll use PostgreSQL" — or "we'll use MongoDB" — with no
pattern behind it. Phase 4 of this track is the full store-selection treatment; this step is
where the reason is first said.

## Normalised or wide?

The table also answers the shape question. An order is read back whole — status, items, total —
so `order_items` as separate rows is a join on every read; at the storefront's scale the join
is cheap and the rows are needed for reporting, so the normalised form wins. A feed entry or a
product page that is read thousands of times per write and never queried by its parts is a
candidate for a wide row or a document — the read pattern is "the whole thing, by id". Neither
is the default; the frequency column decides, and the decision is said.

## What changes at scale, and what does not

The access-pattern table is also the shard-key analysis, later. Every row's key column is a
candidate: orders by `user_id` keeps a customer's history on one shard and makes the history
query local; inventory by `product_id` isolates the sale item's contention to one shard. A
model derived from the patterns shards along keys it already uses; a model drawn from habit
discovers at scale that its queries cross every shard. Phase 5 covers sharding; the point here
is that the table written in minute ten is the one that will be reused at year two.

## Gotchas

**★ Symptom: "why PostgreSQL?" and the answer is "it's what we use."** Cause: the store chosen
before the patterns were listed. Fix: the access-pattern table, then the store per entity with
the pattern as the reason — transaction and constraints for orders; single-key
read-modify-write for the cart.

**★ Symptom: entities drawn first, and the order-history query has no index.** Cause: the
model drawn from nouns rather than from queries. Fix: the key column of the table gives every
index — `(user_id, created_at DESC, id DESC)` for the cursor — before the schema is written.

**Symptom: the never-oversell rule lives only in application code.** Cause: the invariant not
pushed into the store. Fix: `CHECK (available >= 0)` and a conditional `UPDATE`; the store
refuses the violation regardless of the code.

**Symptom: the outbox is a separate system, and an order was placed with no event.** Cause: the
event written outside the order's transaction. Fix: the outbox is a table in the same database,
written in the same transaction; a worker publishes it.

**Symptom: random UUID primary keys and a write path that slows at the peak.** Cause: inserts
scattered across the primary-key index. Fix: a time-ordered id generated by the service; say
the choice and its reason.

**Symptom: the cart in the relational database, joined on every page view.** Cause: one store
for everything. Fix: the cart's pattern — single key, high read rate, disposable — is a
key-value pattern; put it there and say why.

**Symptom: a document per order, and the reporting query cannot aggregate by product.** Cause:
the shape chosen from the write pattern only. Fix: the frequency column shows the reads;
reporting by product wants rows, and the join is cheap at this scale.

**Symptom: the admin stock adjustment and the sale decrement lost each other's updates.**
Cause: two writers, no version. Fix: the version column and a conditional write on it; the
table's consistency column flagged the two writers.

## Interview questions

**★ How do you derive a data model in a design round?**
From an access-pattern table: for each journey, every read and write, the entity, the key it
uses, its frequency from the estimate, and the consistency it needs. Entities and primary keys
come from the entity and key columns; indexes from the keys the reads use — the order-history
cursor's `(user_id, created_at, id)`; the transaction boundaries from the consistency column —
order, items, inventory decrement and outbox together; and the store per entity from what the
patterns need. The table is written before any entity is named, and it is reused later as the
shard-key analysis.

**★ Why are orders relational and the cart in a key-value store, in the same design?**
Because their patterns differ. Checkout is a multi-row atomic write with a unique constraint on
the idempotency key, a check constraint on inventory and a same-transaction outbox row — the
transaction and the constraints are the correctness, and a relational store provides them
cheapest. The cart is a single-key read-modify-write on every page view, needs no joins, may be
eventually consistent and may be lost; that is a key-value pattern, and putting it in the
relational store would add joins to the hottest read path for nothing.

**What does the schema express that the diagram cannot?**
The invariants: `CHECK (available >= 0)` makes overselling impossible regardless of application
bugs; the unique `(user_id, idempotency_key)` is the retry guard that serialises concurrent
duplicates; the outbox as a table in the same database is what makes the event atomic with the
order; the version column on inventory is the two-writer protection; integer minor units are the
money decision. A diagram shows that these tables exist; the schema shows what they guarantee.

**How do you choose the primary key for orders, and why does it matter?**
Generated by the service, not the database, so it can be returned to the client and used as the
outbox key before the commit; and time-ordered — a time-prefixed UUID variant or a ticket-server
integer — so inserts at the write peak append to the primary-key index instead of scattering
across it. A random UUID is the habit choice and the one that shows up as write-path slowness on
sale day. Phase 7 has the full comparison of id schemes.

**Normalised rows or a wide document — how do you decide?**
From the read pattern in the table. Something read back whole, by id, thousands of times per
write and never queried by its parts is a document or wide-row candidate; something whose parts
are queried separately or aggregated for reporting wants rows. An order is read whole but
reported by product, and at the storefront's scale the join is cheap, so it stays normalised.
Neither shape is the default; the frequency column decides and the decision is said.
